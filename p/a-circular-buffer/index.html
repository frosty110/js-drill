Circular Buffer

Fixed-capacity ring buffer — writes past capacity overwrite the oldest slot. Modular arithmetic on head/tail indices keeps it O(1) per op.

Problem

Implement CircularBuffer(capacity) with write(v), read(), and a size field. Writes past capacity overwrite the oldest. With cap=3: write 1,2,3,4 then log size, read, read, read, read.

Expected output: 3 2 3 4 undefined

Canonical solution

Ring buffer (head/tail mod cap) · O(1) / O(capacity) (time / space)

class CircularBuffer {
  constructor(capacity) {
    this.cap = capacity;
    this.buf = new Array(capacity);
    this.head = 0;        // next slot to write
    this.tail = 0;        // next slot to read
    // size disambiguates head === tail (could mean full OR empty).
    this.size = 0;
  }
  write(v) {
    this.buf[this.head] = v;
    // Modulo on indices is the whole trick — never reallocate.
    this.head = (this.head + 1) % this.cap;
    if (this.size === this.cap) {
      // Overwrite policy: drop oldest by advancing tail too.
      this.tail = (this.tail + 1) % this.cap;
    } else {
      this.size++;
    }
  }
  read() {
    if (this.size === 0) return undefined;
    const v = this.buf[this.tail];
    this.tail = (this.tail + 1) % this.cap;
    this.size--;
    return v;
  }
}
  • Two indices (head=write, tail=read) plus a size counter — size disambiguates the full-vs-empty case where head === tail.
  • Decision: when full, additional writes overwrite the oldest element rather than throwing. Document the policy — both choices are valid.
  • All ops are O(1). Modulo on indices is the only trick — never reallocate.
  • Time O(1) per read/write. Space O(capacity).

Alternate approaches

Reject-on-full (bounded queue) O(1) / O(capacity)

Reach for this when the producer needs to KNOW that a write failed — backpressure flows, durable inbound queues, rate-limited APIs — anywhere silently dropping the oldest entry would be a data-loss bug. Same ring-buffer skeleton; only the overflow branch differs: instead of advancing tail to drop the oldest, refuse the new write and signal that to the caller (return false / throw).

class CircularBuffer {
  constructor(capacity) {
    this.cap = capacity;
    this.buf = new Array(capacity);
    this.head = 0;
    this.tail = 0;
    this.size = 0;
  }
  write(v) {
    // Reject policy: full buffer means caller's write is refused.
    if (this.size === this.cap) return false;
    this.buf[this.head] = v;
    this.head = (this.head + 1) % this.cap;
    this.size++;
    return true;                                // caller checks for backpressure
  }
  read() {
    if (this.size === 0) return undefined;
    const v = this.buf[this.tail];
    this.tail = (this.tail + 1) % this.cap;
    this.size--;
    return v;
  }
}
const b = new CircularBuffer(3);
b.write(2); b.write(3); b.write(4);  // buf full at [2,3,4]
b.write(5);                          // rejected — buf still [2,3,4]
console.log(b.size);
console.log(b.read());

  • Same modulo/head/tail/size scaffolding — only the full-buffer branch flips. Tail NEVER advances on write; the oldest entries are preserved.
  • Boolean return value is the signal — if (!buf.write(v)) handleBackpressure(). Throw instead if the caller should treat full as exceptional rather than expected.
  • Contrast on cap=3 writes of 1,2,3,4: reject-on-full keeps [1,2,3] and the 4 is lost; the overwrite variant keeps [2,3,4] and the 1 is silently dropped. Which 'wins' depends on whether oldest data or newest data is more valuable to the caller.

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why track size separately instead of inferring it from head and tail?

  1. A (head - tail + cap) % cap would be O(cap), not O(1)
  2. B When head === tail, it could mean either full or empty — size resolves the ambiguity correct
  3. C Modulo arithmetic on signed integers can produce negative values in JS
  4. D head and tail get reset to 0 between writes, so their difference is meaningless

Why: After three writes into a cap-3 buffer head has wrapped back to 0 and equals tail — identical pointers to the empty state. The alternative discriminator is leaving one slot permanently unused so head !== tail always means non-empty; the size counter buys the same answer without wasting a slot.

Q2 On a write to a full buffer (overwrite policy), which pointer must advance besides head?

  1. A Neither — head wrapping back to tail already overwrites the oldest
  2. B tail must also advance so the oldest entry is dropped correct
  3. C size must increment past cap so the overflow is recorded
  4. D tail must reset to head, since the read position is now invalid

Why: this.buf[this.head] = v has already clobbered the oldest element, so tail still points at a slot whose value was overwritten — advancing it is what makes the next read return the true oldest survivor. size deliberately does NOT change: one element in, one element out.

Q3 Time complexity of read() and write() on a circular buffer?

  1. A O(n)
  2. B O(log n)
  3. C O(1) correct
  4. D O(n) amortized

Why: Both methods are straight-line — one array index, one modulo, one counter update, no loop and no reallocation. That worst-case (not amortized) O(1) is the whole reason to move pointers instead of shift()ing elements down.

Q4 After capacity=3 and writes [1,2,3,4,5], what does the next read() return?

  1. A 1
  2. B 3 correct
  3. C 4
  4. D 5

Why: Writes 4 and 5 each hit a full buffer, so tail advanced twice and dropped 1 and 2; the buffer holds 3, 4, 5 and reads come out oldest-first. Reading 5 would be LIFO — this is a FIFO ring.
