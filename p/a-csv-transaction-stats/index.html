CSV Transaction Stats

Parse → group → aggregate pipeline in TypeScript: `.map` the CSV lines into header-keyed records (collection-transform), then a `for...of` upsert loop that dispatches on a `'DEPOSIT' | 'WITHDRAWAL'` union into a per-company stats class — the loop carries create-if-absent state and mutates an instance, so it is algorithm shape, not a fold.

Problem

In TypeScript: parse a CSV of transactions (date,company,type,amount where type is DEPOSIT or WITHDRAWAL), roll them up per company into a stats class tracking deposited, withdrawn and transaction count, and print one line per company ordered by net descending. Model the transaction type as a string-literal union and validate it at the parse boundary.

Expected output: Acme: +2000 / -450 (3 txns) net 1550 Globex: +900 / -300 (2 txns) net 600

Canonical solution

Header-keyed parse → Map upsert → union-typed dispatch into a stats class · O(n + k log k) / O(n) (time / space)

// ── A TypeScript primer, inline ──────────────────────────────────────────
// TypeScript is JavaScript plus type annotations. The annotations are checked
// while you write, then ERASED before anything runs — the JavaScript that
// actually executes is the same code with the types deleted. Nothing below
// costs you a single runtime operation.

// `type X = ...` gives a name to a shape. This one is a UNION: a TxnType is
// the string 'DEPOSIT' or the string 'WITHDRAWAL' and nothing else. Assigning
// 'TRANSFER' is a compile error. This is why we don't reach for `enum` —
// a union of string literals does the same job with zero runtime output.
type TxnType = 'DEPOSIT' | 'WITHDRAWAL';

// An object type: every CsvRow has these four fields, all `string`. They are
// strings because a CSV cell is always text until we convert it — writing
// `amount: number` here would be a lie the compiler couldn't catch.
type CsvRow = {
  date: string;
  company: string;
  type: string;
  amount: string;
};

class CompanyStats {
  // Class fields are declared with their types up front. `readonly` means
  // "assignable in the constructor, never reassigned after" — again a
  // compile-time rule only; nothing freezes the object at runtime.
  readonly company: string;
  // No annotation needed here: TypeScript INFERS `number` from the `0`.
  deposited = 0;
  withdrawn = 0;
  txns = 0;

  // Parameters take their types the same way. (Note we assign `this.company`
  // by hand rather than writing `constructor(readonly company: string)` —
  // that shorthand generates real runtime code, so it isn't erasable.)
  constructor(company: string) {
    this.company = company;
  }

  // `type: TxnType` is the payoff: every caller is checked against the two
  // legal values. `: void` says this method returns nothing.
  apply(type: TxnType, amount: number): void {
    this.txns++;
    if (type === 'DEPOSIT') this.deposited += amount;
    else this.withdrawn += amount;
  }

  // A getter annotates its return type after the parens, like a method.
  get net(): number {
    return this.deposited - this.withdrawn;
  }
}

// A TYPE GUARD. The return type `value is TxnType` is a promise to the
// compiler: "if this returns true, you may treat `value` as a TxnType from
// here on." It matters because types are erased at runtime — the compiler
// can police our own code, but it cannot police a CSV file, so text arriving
// from outside still needs a real check.
function isTxnType(value: string): value is TxnType {
  return value === 'DEPOSIT' || value === 'WITHDRAWAL';
}

// `: CsvRow[]` is the return type — an array of CsvRow.
function parseCsv(text: string): CsvRow[] {
  // Split off the header so column POSITION never gets hard-coded downstream.
  const [header, ...rows] = text.trim().split('\n');
  const cols = header.split(',');
  return rows.map(line => {
    const cells = line.split(',');
    // `as CsvRow` is a CAST: fromEntries hands back a loose object, and we
    // assert it has our shape. A cast changes what the compiler BELIEVES,
    // never what exists — which is exactly why isTxnType still has to run.
    return Object.fromEntries(cols.map((col, i) => [col, cells[i]])) as CsvRow;
  });
}

function summarize(text: string): CompanyStats[] {
  // The angle brackets on `Map<string, CompanyStats>` say what the keys and
  // values are, so `.get()` is known to return `CompanyStats | undefined`.
  const byCompany = new Map<string, CompanyStats>();
  for (const row of parseCsv(text)) {
    // Validate the untrusted string BEFORE it's used as a TxnType.
    if (!isTxnType(row.type)) throw new Error(`unknown type: ${row.type}`);
    // Upsert: create-if-absent, then ALWAYS mutate the stored instance.
    if (!byCompany.has(row.company)) {
      byCompany.set(row.company, new CompanyStats(row.company));
    }
    // The `!` is a non-null assertion: `.get()` could be undefined in general,
    // but we just guaranteed the key exists, so we drop it from the type.
    byCompany.get(row.company)!.apply(row.type, Number(row.amount));
  }
  return [...byCompany.values()].sort((a, b) => b.net - a.net);
}
  • TypeScript types are ERASED before the code runs — they cost nothing at runtime and change no behavior. Everything below is still the same JavaScript algorithm.
  • type TxnType = 'DEPOSIT' | 'WITHDRAWAL' is a union of string literals. Prefer it to enum: it checks callers just as tightly but emits no runtime code, whereas an enum generates a real object.
  • Because types are erased, the union does NOT validate the CSV. isTxnType — a type guard, signalled by the value is TxnType return type — is what actually checks the untrusted text, and it also narrows the type for the compiler.
  • as CsvRow is an unchecked cast: it changes what the compiler believes, not what exists. That's the precise reason the runtime guard is still required after it.
  • Objects need a real upsert: if (!map.has(k)) map.set(k, new X(k)) then mutate. The numeric map.get(k) || 0 habit fails here — map.get(k) || new X(k) mutates an instance that was never stored, silently dropping every company's first transaction.
  • Number(row.amount) is still load-bearing: CsvRow.amount is typed string because CSV cells ARE strings, so TypeScript would reject += row.amount at compile time — but nothing coerces it for you at runtime.
  • net is a getter, not a stored field — derived values can't drift out of sync when a new enum arm forgets to update them.

Positions 1–6 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why is the upsert written as if (!byCompany.has(k)) byCompany.set(k, new CompanyStats(k)) rather than the shorter const s = byCompany.get(k) || new CompanyStats(k)?

  1. A Map.get throws on a missing key, so it must be guarded by has before any read
  2. B The || form builds an instance that is never stored in the Map, so every company's first transaction is applied to a throwaway object and lost correct
  3. C Map.set refuses to overwrite an existing key, so has must be checked to avoid a silent no-op
  4. D Class instances are always falsy until their constructor returns, which makes || pick the wrong branch

Why: With numbers, map.get(k) || 0 works because you write the result back with set. With an object you mutate in place — so if the new instance was never stored, the mutation lands on an orphan and the Map still has no entry for that company.

Q2 CsvRow.amount is typed string, and the code still calls Number(row.amount). Why is the conversion required even though the field is typed?

  1. A It isn't required — TypeScript coerces a string field to number automatically when it is used in arithmetic
  2. B Types are erased before the code runs, so nothing converts the value at runtime; the annotation only stops you writing += row.amount in the editor correct
  3. C Number() is required because Map keys must be primitives and the amount is part of the composite key
  4. D The cast to CsvRow re-tags the field as number, so Number() merely documents a conversion that already happened

Why: TypeScript's job ends at compile time. The annotation catches the mistake in your editor — this.deposited += row.amount is a type error — but at runtime the value is still the string '1200', and '0' + '1200' is '01200'. The compiler tells you to convert; it never converts for you.

Q3 Records are built with Object.fromEntries(cols.map((col, i) => [col, cells[i]])) instead of reading cells[1], cells[2] directly. What does that buy?

  1. A It removes the need to call Number() on the amount, because fromEntries infers cell types
  2. B It is measurably faster than index access because fromEntries builds a hash table in one pass
  3. C It guarantees the row has exactly as many cells as the header has columns, throwing otherwise
  4. D The aggregation reads columns by NAME, so the CSV can add a column or reorder them without breaking any downstream code correct

Why: Hard-coded indices couple every downstream line to the exact column layout. Keying off the header row means only the header parse knows about positions.

Q4 net is written as a getter (get net() { return this.deposited - this.withdrawn; }) rather than a field updated inside apply. Why prefer the getter?

  1. A Getters are evaluated once at construction, so the value is cached and cheaper to read repeatedly
  2. B A stored net would have to be updated in every enum arm, so a newly added transaction type that forgets to touch it leaves net silently wrong; a derived value cannot drift correct
  3. C Fields assigned in a constructor are not enumerable, so a stored net would be invisible to the final .map
  4. D Only getters can be used inside a sort comparator, since comparators receive frozen copies of their operands

Why: Deriving net from the two totals makes it impossible for it to disagree with them. A stored copy is a second source of truth that every future code path has to remember to maintain.

Q5 The code calls text.trim() before split('\n'). What does that prevent?

  1. A A leading byte-order mark that would otherwise corrupt the first column name
  2. B Amounts with surrounding spaces being rejected by Number, which does not tolerate whitespace
  3. C A trailing newline producing one extra empty line, which parses into a record of undefined fields and creates a bogus company keyed undefined correct
  4. D The header row being included in the data rows, since split keeps the separator on the first element

Why: 'a\nb\n'.split('\n') yields ['a','b','']. That empty final line becomes a record whose every field is undefined, and the upsert then happily creates a company named undefined.

Q6 apply takes type: TxnType, a union of the only two legal strings. Why does the code STILL call isTxnType(row.type) before passing it?

  1. A Because a union type only constrains variables, not function parameters, so apply would accept any string regardless
  2. B Because isTxnType also converts the string to the union's underlying numeric representation
  3. C Because the union is erased at runtime, so it constrains code the compiler can see — not a CSV file; the guard is the only thing that actually rejects a bad value correct
  4. D Because TypeScript requires an explicit guard before any value may be passed to a parameter with a union type

Why: The compiler can police your own call sites, but the CSV arrives at runtime, long after every type has been deleted. Object.fromEntries(...) as CsvRow asserts a shape without verifying it, so row.type could be any string at all. The value is TxnType guard does two jobs: it performs the real runtime check, and it narrows the type so the compiler accepts the call afterwards.
