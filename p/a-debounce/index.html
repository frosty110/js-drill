Debounce

Debounce delays a function call until `ms` of quiet — every new call resets the timer. Built with an injectable fake clock so the verifier can advance time deterministically.

Problem

Implement debounce(fn, ms) with an injectable clock (_now + tick). Demonstrate: three rapid calls, advance just under ms (no fire), advance past ms (one fire with last args), then a fourth call + advance past ms (another fire).

Expected output: calls=0 calls=1 last=c calls=2 last=d

Canonical solution

Trailing-edge debounce (closure + due-time) · O(1) / O(1) (time / space)

function debounce(fn, ms) {
  let scheduled = null;       // due-at on fake clock, or null when idle
  let lastArgs = null;
  const api = function (...args) {
    lastArgs = args;
    scheduled = api._now + ms;     // (re)set the due time on every call
  };
  api._now = 0;
  api.tick = (delta) => {          // advance fake clock; fire if due
    api._now += delta;
    if (scheduled !== null && api._now >= scheduled) {
      scheduled = null;
      fn(...lastArgs);
    }
  };
  return api;
}
  • Each call resets scheduled to now+ms — the timer restarts, not accumulates. That's the debounce contract.
  • Only the most recent args are captured. The trailing call wins; intermediate args are dropped.
  • Injecting a clock (tick/_now) instead of using setTimeout makes the implementation testable without real timers.
  • Time O(1) per call and per tick. Space O(1) — two closure variables.

Alternate approaches

Leading-edge debounce (fire first, then ignore burst) O(1) / O(1)

Reach for this when the interviewer asks 'can you make it fire on the LEADING edge instead?' — the canonical follow-up. Different semantics: the first call of a burst fires immediately, then the wrapper goes silent until one full quiet period of ms elapses; subsequent burst calls are dropped (not deferred). Useful for 'fire once on click, ignore rapid repeats' UI patterns where a delayed firing would feel sluggish.

function debounce(fn, ms) {
  // lastFired tracks WHEN we last invoked fn; quietUntil is the next allowed fire time.
  // Initialize to -Infinity so the very first call always passes the gate.
  let quietUntil = -Infinity;
  const api = function (...args) {
    if (api._now >= quietUntil) {
      // Leading-edge: fire IMMEDIATELY on entry to a quiet window.
      fn(...args);
      quietUntil = api._now + ms;          // cooldown — drop calls until this passes
    } else {
      // Inside the cooldown — extend the silence (debounce-style),
      // but the call itself fires nothing. Args are gone, unlike trailing edge.
      quietUntil = api._now + ms;
    }
  };
  api._now = 0;
  api.tick = (delta) => { api._now += delta; };  // no fire on tick — leading edge only fires on call
  return api;
}
let calls = 0, last = null;
const d = debounce((x) => { calls++; last = x; }, 100);
console.log('calls=' + calls);
d('c');                              // first call — fires immediately (leading edge)
d('b'); d('a');                      // inside cooldown — dropped, args gone
d.tick(50);
d('x');                              // still inside cooldown — extends quiet window, drops
console.log('calls=' + calls + ' last=' + last);
d.tick(500);                         // clock past the extended quietUntil
d('d');                              // fresh quiet window — fires immediately
console.log('calls=' + calls + ' last=' + last);
  • The quietUntil sentinel replaces scheduled + lastArgs — leading edge has no concept of 'pending args' because the firing happens at call time, not later.
  • Calls inside the cooldown still EXTEND the quiet window (true debounce behavior) — they just don't get to fire. Without that extension this would be plain leading-edge throttle.
  • -Infinity initialization is the same trick throttle uses: it guarantees the very first call satisfies _now >= quietUntil without a separate hasFired boolean.

Q1 Three rapid calls in quick succession to a debounced fn (ms=100) result in how many invocations of the underlying fn (assuming time advances past 100ms only after the third call)?

  1. A 3
  2. B 0
  3. C 1 — only the last correct
  4. D 2

Why: Each call overwrites scheduled = api._now + ms rather than queuing a new timer, so the burst leaves exactly one due-time behind. That is the difference from throttle, which would let the leading call through and rate-limit the rest.

Q2 Which args does the underlying fn receive when the debounced wrapper finally fires?

  1. A Args from the first call in the burst (leading-edge convention)
  2. B Args from the most recent call correct
  3. C All accumulated args concatenated into one array
  4. D Whatever args are passed to tick() — the wrapper's args are discarded

Why: lastArgs = args overwrites on every call, so d('a'); d('b'); d('c') fires with 'c' — this is a trailing-edge debounce. Keeping the FIRST call's args instead would be the leading-edge variant.

Q3 Why expose a tick(delta) method instead of using real setTimeout?

  1. A setTimeout's minimum delay differs across runtimes, so tests would flake
  2. B Deterministic, synchronous testing without waiting for real wall-clock time correct
  3. C tick can fire before the debounce window even starts
  4. D Real setTimeout would prevent the test from awaiting the callback's args

Why: tick(delta) advances api._now and checks the due-time in the same synchronous call, so the whole L3 script runs start to finish with no timers and no waiting. Injecting the clock is also how you'd test a real debounce — the production version takes setTimeout, the test passes a fake.

Q4 After a debounced call, what should happen if tick(ms-1) is called (less than the debounce window)?

  1. A fn fires immediately — any tick after a call triggers a fire
  2. B fn does not fire — the window hasn't elapsed correct
  3. C scheduled is set to null because the partial tick consumed the timer
  4. D fn fires with a partial-progress flag set

Why: api._now >= scheduled is false at ms - 1, so the guard falls through and scheduled is left intact — a later tick(1) would still fire it. Only the branch that actually fires clears scheduled to null.
