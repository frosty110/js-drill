Date Normalizer & Extractor

Multi-format parse — scan text for ISO, US-slash, and long-month dates with `matchAll`, normalize each to `YYYY-MM-DD`, dedupe via a Set, and sort (ISO strings sort lexicographically = chronologically).

Problem

Extract every date from a medical note in three formats — 2024-01-05, 01/05/2024 (MM/DD/YYYY), and Jan 5, 2024 / January 5, 2024 — normalize each to ISO YYYY-MM-DD, dedupe, and return sorted ascending.

Expected output: 2024-01-05 2024-02-10 2024-03-03

Canonical solution

function extractDates(text) {
  const months = { january:1, february:2, march:3, april:4, may:5, june:6, july:7, august:8, september:9, october:10, november:11, december:12, jan:1, feb:2, mar:3, apr:4, jun:6, jul:7, aug:8, sep:9, sept:9, oct:10, nov:11, dec:12 };
  const pad = n => String(n).padStart(2, '0');
  // Set of normalized ISO strings — same date in two formats dedupes to one.
  const found = new Set();
  for (const m of text.matchAll(/\b(\d{4})-(\d{2})-(\d{2})\b/g)) {
    found.add(`${m[1]}-${m[2]}-${m[3]}`);
  }
  for (const m of text.matchAll(/\b(\d{1,2})\/(\d{1,2})\/(\d{4})\b/g)) {
    found.add(`${m[3]}-${pad(+m[1])}-${pad(+m[2])}`);
  }
  for (const m of text.matchAll(/\b([A-Za-z]+)\.?\s+(\d{1,2}),\s+(\d{4})\b/g)) {
    const mo = months[m[1].toLowerCase()];
    if (mo) found.add(`${m[3]}-${pad(mo)}-${pad(+m[2])}`);
  }
  // ISO YYYY-MM-DD sorts chronologically with a plain string sort.
  return [...found].sort();
}
const note = 'Initial visit Jan 5, 2024. Follow-up 02/10/2024. MRI on 2024-01-05 confirmed. Discharged March 3, 2024.';
console.log(extractDates(note).join('\n'));
  • Normalizing every format to ISO YYYY-MM-DD and storing in a Set makes 'Jan 5, 2024' and '2024-01-05' dedupe automatically — they collapse to the same canonical string.
  • ISO YYYY-MM-DD is designed so lexicographic (plain string) sort equals chronological order; no Date parsing or custom comparator needed.
  • matchAll with the /g flag returns every match as an iterable of arrays where m[1], m[2], m[3] are the capture groups — unlike match with /g, which drops the groups.
  • Time O(n + k log k), Space O(k) — three linear passes over text length n; k unique dates collected into a Set, then sorted (k ≤ total matches ≤ n).

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why store normalized ISO strings in a Set rather than pushing to an array?

  1. A A Set returns its elements in sorted order, so .sort() becomes a no-op
  2. B The same calendar date written in two formats ('Jan 5, 2024' and '2024-01-05') normalizes to the same string, and the Set dedupes them automatically correct
  3. C Arrays would push the regex Match objects whole; Set unwraps them to strings
  4. D Set guarantees O(1) .has() while array .includes() is O(n), so the regex passes run faster

Why: Both formats map to the canonical '2024-01-05'. Adding both to a Set keeps just one copy, so the multi-format extraction doesn't report the same date twice.

Q2 Why does [...found].sort() (a plain string sort) produce chronological order?

  1. A Array.prototype.sort checks for Date.parse-able strings and routes through numeric comparison
  2. B ISO YYYY-MM-DD is fixed-width with the most-significant field (year) first, so lexicographic string order equals chronological order correct
  3. C The hyphen is treated as a digit-zero in lexicographic comparison, so year and month align
  4. D Spread iteration over a Set yields entries in insertion order, which here matches chronological order

Why: Year-month-day ordering with zero-padding means comparing the strings character-by-character compares year, then month, then day — exactly chronological. No Date objects or comparators required.

Q3 Why use text.matchAll(/.../g) instead of text.match(/.../g) here?

  1. A match advances lastIndex between calls, so re-running it on the same text would skip matches
  2. B matchAll yields each match WITH its capture groups (m[1], m[2], m[3]); match with /g returns just the full matched strings and discards the groups correct
  3. C match requires the regex to be wrapped in new RegExp(...); matchAll accepts the literal directly
  4. D matchAll returns a lazy iterator so we can break after the first match if needed

Why: The code needs the year/month/day capture groups to reassemble each date. String.match with /g throws the groups away and returns only full-match strings, so matchAll is required to get the parts.

Q4 For the US-slash format, why is the group order ${m[3]}-${pad(+m[1])}-${pad(+m[2])}?

  1. A The matchAll iterator emits groups in regex-right-to-left order, so m[3] is the leftmost capture
  2. B The input is MM/DD/YYYY, so group 1 is month, group 2 is day, group 3 is year — reordered and zero-padded to YYYY-MM-DD correct
  3. C Capture group 3 is always the year by convention in JS regex literals
  4. D The + coercion swaps m[1] and m[3] so the year ends up first

Why: 02/10/2024 is MM/DD/YYYY: m[1]='02' (month), m[2]='10' (day), m[3]='2024' (year). Emitting year-month-day with pad produces the ISO '2024-02-10'. The + coerces to number so pad re-pads consistently.
