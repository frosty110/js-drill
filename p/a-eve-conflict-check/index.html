Conflict-of-Interest Check

Hash-map-of-sets adjacency lookup — build a Map of adverse-party -> matter-ids and a Set of our own clients from existing matters in one pass, then check a prospective client against both indexes in O(1).

Problem

We represent plaintiffs against defendants. Given existing matters ({id, plaintiff, defendants[]}) and a prospective client name, flag a conflict if the prospect is an adverse party (a defendant) in any matter — list those matter ids — or is already a current client. Otherwise CLEAR. Print the result for an adverse party, a clear name, and an existing client.

Expected output: Globex: CONFLICT — adverse party in M-1; adverse party in M-2 Stark Inc: CLEAR Acme Corp: CONFLICT — already a current client

Canonical solution

Map-of-lists + Set indexes, then O(1) membership · O(m·d + k) / O(m·d) (time / space)

// We represent plaintiffs against defendants. A prospect conflicts if they are
// an adverse party (a defendant) in any matter, or are already our client.
function checkConflict(matters, prospect) {
  // adverse: defendant name -> list of matter ids where they're opposed.
  const adverse = new Map();
  const ourClients = new Set();
  for (const m of matters) {
    ourClients.add(m.plaintiff);
    for (const def of m.defendants) {
      if (!adverse.has(def)) adverse.set(def, []);
      adverse.get(def).push(m.id);   // one party can be adverse across many matters
    }
  }
  const conflicts = [];
  if (adverse.has(prospect)) {
    for (const id of adverse.get(prospect)) conflicts.push(`adverse party in ${id}`);
  }
  if (ourClients.has(prospect)) conflicts.push('already a current client');
  if (conflicts.length === 0) return `${prospect}: CLEAR`;
  // Note the em-dash character — joins the conflict reasons.
  return `${prospect}: CONFLICT — ${conflicts.join('; ')}`;
}
  • Index defendant -> [matter ids] in a Map, because one party can be a defendant across multiple matters. A plain Set of defendant names would lose which matters they appear in.
  • Track our own plaintiffs in a separate Set too: we cannot represent someone we are already adverse to, AND we should not double-represent an existing client, so both indexes are checked.
  • The output uses a literal em-dash character (—, U+2014), not a hyphen-minus. The expected output will not match if you type a regular '-'.
  • Time O(m·d̄ + k) PER CALL — the indexes are built inside checkConflict, so every prospect re-scans m matters × d̄ avg defendants before its O(1) membership checks and the O(k) walk of its k adverse matter ids. Hoist the build out of the function and each query drops to O(k). Space O(m·d̄).

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why index defendants as a Map of name -> array-of-matter-ids rather than a plain Set of defendant names?

  1. A A Set's has() is O(n); a Map's has() is O(1), so the conflict check must use Map
  2. B One party can be a defendant across multiple matters, and we need to report which matter ids they appear in correct
  3. C Set deduplicates entries silently, so two matters with the same defendant would be collapsed into one
  4. D Iterating a Set is non-deterministic, so the matter-id list would come out in a different order each call

Why: A Set would tell you only that someone is adverse, not in which matters. The Map preserves the matter ids so the conflict report can name them.

Q2 Why does the function also track our own plaintiffs in a separate Set?

  1. A To filter the prospect out of the adverse index before reporting
  2. B We cannot represent both sides, so a prospect who is already our client is also a conflict — a different reason than being adverse correct
  3. C Plaintiffs are stored in adverse too, so the Set deduplicates them on output
  4. D So the rebuild logic can re-derive plaintiffs without re-scanning every matter's defendant list

Why: Two distinct conflict reasons: the prospect is on the other side of a matter (adverse), or we already represent them (current client). Both must be checked.

Q3 The CONFLICT output joins reasons with a special character. Which is it?

  1. A A regular hyphen-minus '-'
  2. B An en-dash '–'
  3. C An em-dash '—' (U+2014) correct
  4. D An underscore '_'

Why: The format string uses a literal em-dash (—). Typing a plain hyphen would make the output fail an exact-match comparison.

Q4 What is the lookup cost of checking a single prospect after the indexes are built?

  1. A O(n) — must rescan all matters
  2. B O(1) for the membership checks, plus O(k) to list the k matters they're adverse in correct
  3. C O(n^2) for the nested defendant loop
  4. D O(log n) via binary search

Why: Map/Set membership is constant time; the only extra work is iterating the (usually small) list of matter ids the prospect appears in.
