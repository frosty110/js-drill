Intake Completeness Validator

Recursive tree walk — a nested required-field schema (true = required leaf, object = required subtree); recurse to collect every missing required leaf as a dotted path, recursing into {} when a whole parent subtree is missing so its leaves still surface.

Problem

Given a nested required-field schema (true = required leaf, nested object = required subtree) and a submitted intake object, return the dotted paths of every missing required field. A field is missing if it's undefined, null, or ''. If a whole subtree's parent is missing, report each of its leaves. Print a header then each missing path as '- path'.

Expected output: Missing fields: - dob - incident.location - insurance.carrier - insurance.policyNumber

Canonical solution

Recursive schema walk collecting dotted paths · O(n) / O(d + m) (time / space)

// required: true = a required leaf; object = a required subtree.
// Return dotted paths of every missing required field.
// Missing = undefined, null, or '' (a blank form field is not filled).
function findMissing(required, data, prefix = '') {
  const missing = [];
  for (const key of Object.keys(required)) {
    const path = prefix ? `${prefix}.${key}` : key;
    const spec = required[key];
    const val = data == null ? undefined : data[key];
    if (spec === true) {
      // Leaf: required and empty -> report this path.
      if (val === undefined || val === null || val === '') missing.push(path);
    } else if (typeof spec === 'object') {
      // Subtree: if the whole parent is missing, recurse into {} so every
      // required leaf underneath still gets reported (not just the parent).
      if (val === undefined || val === null) {
        missing.push(...findMissing(spec, {}, path));
      } else {
        missing.push(...findMissing(spec, val, path));
      }
    }
  }
  return missing;
}
  • Recursion is what handles arbitrary nesting depth: the schema can nest subtrees inside subtrees, and the same function walks any depth without hardcoding levels.
  • When a parent subtree is missing entirely (insurance: null), recurse into {} rather than skipping — so every required leaf beneath it (carrier, policyNumber) is reported individually, not just the parent.
  • Empty string counts as missing alongside null/undefined — a blank text field on the form is not a filled field. Use === '' explicitly; a truthiness check would also reject 0 or false, which are valid values for other field types.
  • Time O(n), Space O(d + m) — n = total schema nodes visited once; d = recursion depth (stack); m = missing fields returned.

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why is recursion the right tool for validating this schema?

  1. A An iterative loop can't preserve the dotted prefix across nested levels
  2. B The schema nests subtrees to arbitrary depth, and one recursive function walks any depth without hardcoding the levels correct
  3. C Object.keys returns values in random order, so a recursive call is the only way to enforce a deterministic walk
  4. D A loop would have to mutate required in place to descend, which would corrupt the schema for the next call

Why: A subtree can contain subtrees; recursion descends each level uniformly instead of writing a fixed number of nested loops.

Q2 When insurance: null (a whole required subtree is missing), why recurse into {} instead of just reporting insurance?

  1. A Because the spec object isn't true, the leaf branch can't fire — pushing insurance directly would mis-tag a subtree as a leaf
  2. B So every required leaf under it (carrier, policyNumber) is reported individually, telling the user exactly which fields to fill correct
  3. C Recursing into null would corrupt the path prefix with a literal 'null' segment
  4. D {} resets data == null to false so the guard stops firing on subsequent siblings

Why: Recursing into {} makes each child read as missing, so the report names every concrete field the user must supply, not just the group.

Q3 Why does the validator treat an empty string '' as missing?

  1. A '' is coerced to null by JSON.stringify, so it would round-trip as missing anyway
  2. B A blank form field is not a filled field, so a required field left empty must be flagged correct
  3. C All falsy values must be rejected — '', 0, false, and NaN all signal an unfilled field
  4. D Object.keys would skip a property whose value is '', so the schema would never reach it

Why: The user typed nothing into a required box. Note it checks === '' explicitly rather than truthiness, so valid 0/false values on other field types are not wrongly flagged.

Q4 Why does the code read data == null ? undefined : data[key] instead of just data[key]?

  1. A data[key] returns the prototype value on missing own-keys; the guard suppresses inherited properties
  2. B When recursing into a missing subtree, data is {} (safe) — but the guard also prevents a TypeError if a null/undefined ever reaches the read correct
  3. C data == null only fires for undefined, so the branch lets null pass through as a falsy leaf value
  4. D Optional chaining data?.[key] was added in ES2020 and isn't backward compatible

Why: Reading a property off null/undefined throws. Here the missing-subtree branch already recurses into {}, so data is never null in practice — the guard is defensive, keeping the read total if one ever does reach it.
