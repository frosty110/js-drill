K Largest Files

Top-K shape on object input — return the k largest documents in a production by byte size. Sort-and-slice is the brute-force-OK answer; a size-k min-heap is the O(n log k) optimization to name.

Problem

Given an array of {name, bytes} files and a number k, return the names of the k largest files, ordered largest first.

Expected output: ["mri-scan.dcm","deposition.pdf","photo.jpg"]

Canonical solution

Sort by size descending, take the first k · O(n log n) / O(n) (time / space)

const files = [
  { name: 'deposition.pdf', bytes: 2400000 },
  { name: 'intake.docx', bytes: 38000 },
  { name: 'mri-scan.dcm', bytes: 9100000 },
  { name: 'photo.jpg', bytes: 512000 },
  { name: 'notes.txt', bytes: 4096 }
];

function largestFiles(files, k) {
  return [...files]
    .sort((a, b) => b.bytes - a.bytes)
    .slice(0, k)
    .map(f => f.name);
}

console.log(JSON.stringify(largestFiles(files, 3)));
  • The comparator b.bytes - a.bytes sorts descending, so the k largest land at the front.
  • Spread [...files] before sorting — .sort() mutates in place and you don't want to reorder the caller's array.
  • Sort-and-slice is O(n log n). When n is huge and k is small, a size-k min-heap is faster — see the alternate.

Alternate approaches

Min-heap of size k O(n log k) / O(k)

When n is huge but k is small — e.g. the 10 largest files out of a million-document production. A size-k min-heap avoids sorting everything: O(n log k) vs O(n log n).

class MinHeap {
  constructor() { this.h = []; }
  size() { return this.h.length; }
  push(v) {
    const h = this.h; h.push(v);
    let i = h.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (h[p].bytes <= h[i].bytes) break;
      [h[p], h[i]] = [h[i], h[p]];
      i = p;
    }
  }
  pop() {
    const h = this.h; const top = h[0]; const last = h.pop();
    if (h.length) { h[0] = last; let i = 0;
      while (true) {
        let s = i; const l = 2*i+1, r = 2*i+2;
        if (l < h.length && h[l].bytes < h[s].bytes) s = l;
        if (r < h.length && h[r].bytes < h[s].bytes) s = r;
        if (s === i) break;
        [h[s], h[i]] = [h[i], h[s]]; i = s;
      }
    }
    return top;
  }
}

const files = [
  { name: 'deposition.pdf', bytes: 2400000 },
  { name: 'intake.docx', bytes: 38000 },
  { name: 'mri-scan.dcm', bytes: 9100000 },
  { name: 'photo.jpg', bytes: 512000 },
  { name: 'notes.txt', bytes: 4096 }
];
const k = 3;
const heap = new MinHeap();
for (const f of files) {
  heap.push(f);
  if (heap.size() > k) heap.pop();
}
const top = [];
while (heap.size()) top.push(heap.pop());
top.reverse();
console.log(JSON.stringify(top.map(f => f.name)));
  • Keep a MIN-heap of size k: the smallest of the current top-k sits at the root, so a bigger incoming file evicts it in one pop.
  • Compare on .bytes, not the object — the heap orders files by size.
  • Drain and reverse at the end: a min-heap pops smallest-first, so reverse to get descending size.

Q1 To return the k LARGEST files with a heap, what kind of heap do you keep, and of what size?

  1. A A max-heap of size n
  2. B A min-heap of size k — the smallest of the current top-k sits at the root for cheap eviction correct
  3. C A min-heap of size n
  4. D A max-heap of size k

Why: Counterintuitively, you keep a MIN-heap of size k. The root is the smallest of your current top-k, so when a bigger file arrives you pop the root and push the newcomer — O(log k) per element.

Q2 What order does the comparator (a, b) => b.bytes - a.bytes produce?

  1. A Ascending by bytes
  2. B Descending by bytes — largest first correct
  3. C Alphabetical by file name
  4. D The original insertion order

Why: Subtracting in the order b - a flips the sort to descending, so the largest files come first and .slice(0, k) grabs the top k.

Q3 Why spread [...files] before calling .sort()?

  1. A It converts the array into a heap
  2. B .sort() mutates in place, so spreading first avoids reordering the caller's original array correct
  3. C Spreading makes the sort run faster
  4. D JavaScript requires it before calling .slice()

Why: Array.prototype.sort sorts in place and returns the same array. Spreading into a fresh array first keeps the caller's data untouched — important when other code still relies on the original order.

Q4 When does the size-k min-heap (O(n log k)) clearly beat sort-and-slice (O(n log n))?

  1. A When k is close to n
  2. B When n is very large and k is small — e.g. the 10 largest out of a million files correct
  3. C When the array is already sorted
  4. D Never — a full sort is always faster

Why: If k is tiny relative to n, log k is far smaller than log n, so the heap does much less work. When k approaches n the two converge and a plain sort is simpler.
