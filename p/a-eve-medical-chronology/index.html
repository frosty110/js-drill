Medical Chronology Builder

Hash-group then sort — group medical records by date into a Map, then emit dates in sorted order with same-date events kept in input order.

Problem

Turn a list of medical records ({date, provider, note}) into a chronological timeline. Sort by date; records on the same date collapse into one line, joined by ; .

Expected output: 2024-01-15 — PCP: Initial visit 2024-02-01 — ER: Admitted; Radiology: CT scan

Canonical solution

Hash-group by date, then sort keys · O(n + k log k) / O(n) (time / space)

function buildChronology(records) {
  // Group records by their date key. A Map preserves first-seen key order,
  // but we sort the keys explicitly so output is chronological regardless of input.
  const byDate = new Map();
  for (const r of records) {
    if (!byDate.has(r.date)) byDate.set(r.date, []);
    // push keeps same-date events in the order they appeared in the input.
    byDate.get(r.date).push(`${r.provider}: ${r.note}`);
  }
  // ISO dates (YYYY-MM-DD) sort chronologically as plain strings — no Date needed.
  return [...byDate.keys()].sort().map(date => `${date} — ${byDate.get(date).join('; ')}`);
}
  • ISO 8601 dates (YYYY-MM-DD) are lexicographically sortable: a plain string .sort() gives chronological order, so you never need to parse them into Date objects here.
  • if (!byDate.has(r.date)) byDate.set(r.date, []) lazily initializes the bucket; without it the first .get(...).push on a new date would throw on undefined.
  • Same-date records collapse in INPUT order because .push appends — sorting only reorders the date keys, never the events within a date.
  • Time O(n + k log k), Space O(n) — n = number of records (Phase 1 group); k = distinct dates (Phase 2 sort, k ≤ n).

Q1 Why are the records grouped into a Map keyed by date before emitting?

  1. A Sorting records directly would shuffle same-date entries because .sort() isn't stable on equal keys
  2. B So that all events sharing a date land in one bucket, ready to collapse into a single output line correct
  3. C An Object keyed by date would coerce ISO dates to milliseconds, breaking the prefix sort
  4. D Map iteration runs in parallel via web workers, which speeds up the emit phase

Why: The group-then-emit shape collects same-date events into one bucket so each date produces exactly one collapsed line.

Q2 Why does [...byDate.keys()].sort() produce chronological order without parsing dates?

  1. A Map.prototype.keys() returns keys in sorted order; the explicit .sort() is a defensive no-op
  2. B ISO 8601 dates (YYYY-MM-DD) sort the same lexicographically as chronologically correct
  3. C The hyphen character has a numeric collation weight that aligns string and date order
  4. D .sort() falls back to Date.parse when every element passes a date-shape heuristic

Why: Fixed-width YYYY-MM-DD strings compare character-by-character in the same order as the calendar, so a plain string sort is chronological.

Q3 Two records share the date 2024-02-01. What determines their order on the output line?

  1. A Alphabetical by provider name
  2. B The order they appeared in the input (the .push order) correct
  3. C Whichever record's .join('; ') call fired first during the emit pass
  4. D The order matching the buckets' sort by event count, ascending

Why: Sorting only reorders the date keys. Within a date, .push keeps events in the order they were read from the input.

Q4 What is the purpose of if (!byDate.has(r.date)) byDate.set(r.date, [])?

  1. A It overwrites any existing bucket so repeated dates don't accumulate stale events from a prior call
  2. B It lazily creates an empty array bucket the first time a date is seen, so the later .get().push won't throw correct
  3. C It registers the date with the Map's internal sort index so the later [...keys()].sort() is O(1)
  4. D It prevents byDate.get from returning the Map's default value of null instead of undefined

Why: Without initializing the bucket, byDate.get(r.date) would be undefined on a first-seen date and .push would throw.
