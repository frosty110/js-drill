Statute-of-Limitations Deadline

Date arithmetic + classify — compute each claim's filing deadline (incident date + statutory years, rebuilt by string) and days remaining vs a reference date, then bucket as EXPIRED / URGENT / OK.

Problem

For each claim, compute the filing deadline (incident date + statutory years for its type) and days remaining as of a reference date. Classify EXPIRED (past), URGENT (≤30 days left), or OK. Limits: personal injury 2yr, medical malpractice 3yr, property 4yr.

Expected output: C-1 (personal injury): deadline 2026-06-01, 5 days — URGENT C-2 (medical malpractice): deadline 2026-05-15, -12 days — EXPIRED C-3 (property): deadline 2024-01-01, -877 days — EXPIRED

Canonical solution

function checkDeadlines(claims, today) {
  const limits = { 'personal injury': 2, 'medical malpractice': 3, 'property': 4 };
  const nowMs = Date.parse(today);
  return claims.map(c => {
    const years = limits[c.type];
    // Rebuild the deadline by adding to the YEAR component as a string —
    // avoids Date-object month/leap-day drift from setFullYear etc.
    const [y, m, d] = c.incident.split('-').map(Number);
    const deadline = `${y + years}-${String(m).padStart(2, '0')}-${String(d).padStart(2, '0')}`;
    const daysLeft = Math.round((Date.parse(deadline) - nowMs) / 86400000);
    let status;
    if (daysLeft < 0) status = 'EXPIRED';
    else if (daysLeft <= 30) status = 'URGENT';
    else status = 'OK';
    return `${c.id} (${c.type}): deadline ${deadline}, ${daysLeft} days — ${status}`;
  });
}
  • The deadline is rebuilt by adding statutory years to the YEAR string component and re-padding month/day, NOT by mutating a Date object — setFullYear-style math can drift across leap days and month lengths.
  • Both sides of the day-diff use Date.parse on ISO strings, which parse as UTC midnight, so the subtraction is timezone-consistent and /86400000 gives whole days.
  • Classification order matters: test daysLeft < 0 (EXPIRED) first, then <= 30 (URGENT); a deadline exactly 0 days out is URGENT, not EXPIRED.
  • Time O(n), Space O(n) — one .map pass over n claims; each claim is O(1) constant work (lookup, string split, string rebuild, two Date.parse calls, divide + classify).

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why is the deadline rebuilt by adding years to the year string instead of mutating a Date object?

  1. A setFullYear returns the new timestamp but does not mutate the original Date, so the new year is silently discarded
  2. B Adding to the year component as a string avoids the month/leap-day drift that Date mutation (e.g. setFullYear) can introduce correct
  3. C Date constructors interpret a four-digit year as a Unix epoch offset, shifting deadlines into 1970
  4. D Date arithmetic on years that span a daylight-saving boundary returns a fractional result that cannot be re-stringified

Why: Keeping the month and day fixed by reconstructing the string sidesteps the subtle drift Date arithmetic can cause across leap years and month boundaries.

Q2 Why does the function call Date.parse on both the deadline and today rather than mixing parsing styles?

  1. A Date.parse strips the timezone offset before returning a millisecond value, so any input format produces a consistent UTC result
  2. B ISO date strings parse as UTC midnight, so both sides are on the same timezone basis and the day diff is consistent correct
  3. C Subtracting two Date objects requires both sides to come from Date.parse rather than new Date()
  4. D Mixing new Date(str) with Date.parse(str) returns objects with different epoch origins and silently corrupts the diff

Why: Date-only ISO strings are interpreted as UTC; parsing both sides the same way keeps the millisecond subtraction timezone-consistent.

Q3 A claim's deadline is exactly 30 days out. How is it classified, and why does branch order matter?

  1. A EXPIRED — the <= 30 branch is inclusive of the threshold, which the spec treats as already lapsed
  2. B URGENT — the check is daysLeft < 0 first (not <0), then daysLeft <= 30 catches 0..30 inclusive correct
  3. C OK — <= 30 is checked with < semantics in JavaScript when one operand is a string-cast comparison, so exactly 30 falls through
  4. D URGENT, but only because the branches are reordered at runtime by V8's predicate optimizer

Why: EXPIRED is tested first (daysLeft < 0); anything from 0 to 30 inclusive falls into the URGENT branch.

Q4 Why is String(m).padStart(2, '0') applied to the month and day when rebuilding the deadline?

  1. A String(m) returns the numeric Unicode code point unless padded, so single-digit months render as control characters
  2. B To keep the YYYY-MM-DD width fixed (e.g. month 6 becomes '06') so the result is a valid ISO string and sorts correctly correct
  3. C Without padStart, the + operator in the template literal would treat month as a numeric add and produce ${y+years+m} style collisions
  4. D Date.parse rejects any month value below 10 unless it is explicitly cast to a two-character string

Why: ISO dates need zero-padded two-digit month and day; padStart restores the fixed width after .map(Number) stripped leading zeros.
