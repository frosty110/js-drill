Fetch & Reshape an API Response

Call an endpoint, guard the status, then reshape the payload into the shape your app actually wants — the two awaits and the `res.ok` check are sequential algorithm steps, while the reshape itself is collection-transform, so it's a `.filter().map().sort()` chain. Typed so the wire shape and the app shape can never be confused.

Problem

In TypeScript: write loadActiveUsers(fetchImpl, url) that fetches a payload, throws HTTP <status> on a non-ok response, and reshapes results into {id, fullName, city, tagCount} — active users only, missing location/tags defaulted to 'unknown'/0, sorted by tagCount descending. Declare the wire shape and the app shape as separate interfaces, and type the transport as a parameter.

Expected output: 3 Grace Hopper - New York (3 tags) 1 Ada Lovelace - London (2 tags) 4 Linus Torvalds - unknown (0 tags) caught: HTTP 503

Canonical solution

await fetch → res.ok guard → await res.json() → typed filter/map/sort reshape · O(n log n) / O(n) (time / space)

// ── A TypeScript primer, inline ──────────────────────────────────────────
// TypeScript is JavaScript plus type annotations. They're checked while you
// write and ERASED before anything runs. Below, they do one specific job:
// keep the API's shape and OUR shape from being confused for each other.

// The shape that comes off the wire.
interface ApiUser {
  id: number;
  active: boolean;
  name: { first: string; last: string };
  // The `?` marks the field OPTIONAL — it may be absent entirely, so its type
  // is really `{ city: string } | undefined` and TypeScript will refuse to let
  // you write `u.location.city` without handling the missing case.
  location?: { city: string };
  tags?: string[];
}

interface ApiPayload {
  results: ApiUser[];
}

// The shape WE want. Keeping this separate from ApiUser is the entire point:
// nothing downstream should ever see the wire format.
interface UserRow {
  id: number;
  fullName: string;
  city: string;
  tagCount: number;
}

// A function type: `FetchLike` is anything callable with a url that resolves
// to a response we can read. Typing the transport as a PARAMETER — rather
// than calling the global `fetch` — is what lets a test inject a fake one,
// and the type is what stops that fake drifting from the real signature.
type FetchLike = (url: string) => Promise<{
  ok: boolean;
  status: number;
  json: () => Promise<ApiPayload>;
}>;

// An async function's return type is ALWAYS a Promise, so it's written
// `Promise<UserRow[]>` — a promise of an array of UserRow.
async function loadActiveUsers(fetchImpl: FetchLike, url: string): Promise<UserRow[]> {
  const res = await fetchImpl(url);
  // fetch does NOT reject on 404/500 — only on network failure. Guard it.
  // No type can catch this one: a failed response is a perfectly well-typed
  // response. It's a runtime fact about the protocol, not a shape.
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  // Reading the body is a SECOND await: the first resolved on headers alone.
  const body = await res.json();
  return body.results
    .filter(u => u.active)
    // `(u): UserRow => ({ ... })` annotates the ARROW's return type. That's
    // what makes the mapper checked against UserRow — forget a field, or
    // misspell one, and the error lands here instead of at some call site
    // three files away.
    .map((u): UserRow => ({
      id: u.id,
      fullName: `${u.name.first} ${u.name.last}`,
      // `?.` short-circuits to undefined when `location` is missing; `??`
      // then supplies the default. The `?` in the interface above is what
      // forces you to write both.
      city: u.location?.city ?? 'unknown',
      tagCount: u.tags?.length ?? 0,
    }))
    .sort((a, b) => b.tagCount - a.tagCount);
}
  • TypeScript types are ERASED before the code runs — they cost nothing at runtime and change no behavior.
  • fetch rejects ONLY on network-level failure (DNS, refused, CORS). A 404 or 500 resolves normally with ok: false, so without the explicit res.ok check you parse the error page and crash later somewhere unrelated. NO type catches this — a failed response is a perfectly well-typed response.
  • Two awaits, two moments: await fetch(...) resolves on the response HEADERS; await res.json() resolves once the body has streamed and parsed. Putting the guard between them means a bad status bails before downloading a body it would discard.
  • Two interfaces, on purpose: ApiUser is the wire shape and UserRow is ours. This function is the only code that knows both, so an API rename touches exactly one file — that separation is the whole reason to write the second interface down.
  • location?: { city: string } — the ? makes the field optional, which is what forces u.location?.city ?? 'unknown' at the use site. Declaring the API's optional fields honestly is what makes the compiler demand the defensive code.
  • .map((u): UserRow => ({ ... })) annotates the arrow's return type, so a missing or misspelled field fails right there instead of at a distant call site.
  • ?. prevents the TypeError when location is absent; ?? supplies the default for null/undefined only. || would also clobber a legitimately falsy value like an empty-string city.
  • The transport is a PARAMETER typed FetchLike, not a global fetch call — the same injectable-dependency trick the debounce lesson uses for its clock, and the type is what keeps a test fake honest.

L1 — Concept questions 5

Positions 1–5 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 The response type says ok: boolean; status: number. Why does TypeScript not save you from forgetting the if (!res.ok) throw guard?

  1. A It would, if ok were typed as a literal true instead of boolean — the widened type is what loses the guarantee
  2. B Because await erases the response's type, leaving any for everything downstream
  3. C A failed response is a perfectly well-typed response: ok: false satisfies boolean, so the shape is valid and only a runtime check can distinguish success from failure correct
  4. D Because res.ok is optional in the DOM lib's Response type, so the compiler treats reading it as unsafe either way

Why: Types describe shape, not protocol outcome. A 500 comes back with every field present and correctly typed — it simply has ok: false. fetch rejects only on network-level failure, so the status check is a runtime obligation the type system has no way to express or enforce.

Q2 Why are there two separate awaits (await fetchImpl(url) then await res.json()) rather than one?

  1. A res.json() is synchronous; the second await is a defensive habit that has no runtime effect
  2. B The first await resolves once the response HEADERS arrive, so the status is known before any body bytes are read; parsing the streamed body is a second asynchronous step correct
  3. C The first await resolves the DNS lookup and the second performs the actual request
  4. D Combining them would lose the response status, since res.json() discards everything but the parsed body

Why: Headers first, body second. That split is exactly why the res.ok guard can sit between them and bail before downloading a body it would throw away.

Q3 The map writes city: u.location?.city ?? 'unknown'. What would break if it were u.location.city || 'unknown'?

  1. A Nothing at runtime — || and ?? behave identically once optional chaining has already returned undefined
  2. B || cannot appear inside an object literal without parentheses, so it would be a syntax error
  3. C Two things: u.location.city throws a TypeError when location is absent, and || would additionally replace a legitimately falsy city (an empty string) with 'unknown' correct
  4. D || evaluates its right side eagerly, so 'unknown' would overwrite every city regardless of the left side

Why: ?. is what prevents the crash on a missing location; ?? narrows the default to null/undefined so real-but-falsy values survive. They solve two different problems and both are needed.

Q4 After this call you must fetch a detail page for each of the N returned users. Why prefer Promise.all(ids.map(fetchDetail)) over awaiting inside a for...of loop?

  1. A Promise.all retries failed requests automatically, while a sequential loop aborts on the first rejection
  2. B A for...of loop cannot contain await, so the requests would fire without being awaited at all
  3. C Promise.all guarantees results come back in completion order, which a sequential loop cannot provide
  4. D Awaiting in a loop serializes the round trips, so total latency is the SUM of N requests; Promise.all starts them concurrently so it finishes in roughly the slowest single request correct

Why: Sequential awaits are the classic accidental-serialization bug. Promise.all overlaps independent requests — and it preserves input order in its result array, unlike the completion-order claim.

Q5 Why declare a separate UserRow interface instead of letting TypeScript infer the mapped object's type?

  1. A Inference fails on object literals inside .map, so the annotation is required for the code to compile
  2. B It names the app's shape as a contract independent of the wire format, so an API change breaks in this one function rather than silently propagating a new shape to every consumer correct
  3. C Declared interfaces are erased while inferred types are emitted as runtime metadata, so declaring it is measurably lighter
  4. D .sort requires an explicitly declared element type to compare its operands

Why: With inference, the mapper's output type is derived FROM the API shape — so if the API renames a field and you update the mapper, the inferred type quietly changes and every consumer silently adopts it. Declaring UserRow (and annotating the arrow (u): UserRow =>) pins the contract, so the mismatch surfaces here, at the boundary, which is the only place that knows both shapes.
