Memoize

Cache a pure function's results by argument key — repeated calls with the same input return the stored value without re-running the body. The optional keyFn lets callers serialize complex args.

Problem

Implement memoize(fn, keyFn?). Call a counter-tracking slow fn with two repeated and one unique arg; show results and that the underlying fn ran only twice.

Expected output: 9 9 16 calls=2

Canonical solution

Map cache keyed by serialized args · O(1) hit / O(n) cached (time / space)

function memoize(fn, keyFn) {
  // Map (not plain object) — avoids __proto__ collisions and handles any string key.
  const cache = new Map();
  // Default key stringifies all args; callers can inject a custom keyFn.
  const toKey = keyFn || ((...args) => JSON.stringify(args));
  return function (...args) {
    const k = toKey(...args);
    // Hit: skip the body entirely — the whole point of memoization.
    if (cache.has(k)) return cache.get(k);
    const v = fn(...args);
    cache.set(k, v);
    return v;
  };
}
  • Default key is JSON.stringify(args) — fast and good enough for primitives + plain objects, but won't distinguish two objects with identical content from one passed twice.
  • Memoization only works for pure fns. A fn that reads Date.now() or mutates globals will return stale results on cache hits.
  • Use Map (not a plain object) for keys — Map handles any string cleanly and avoids prototype-pollution edge cases like __proto__.
  • Time O(k) per call where k = key serialization cost (negligible for primitives). Space O(unique args seen).

Alternate approaches

Object cache with null prototype O(k) / O(unique args)

Reach for this when you want the simplest possible implementation and args are always primitives or JSON-safe values. Object.create(null) avoids prototype-pollution without needing Map, and k in cache is the correct hit-test. Skip this for production code that might cache undefined returns or non-serializable args — Map is safer.

function memoize(fn, keyFn) {
  // Null-prototype object — no __proto__ or toString collisions, simpler syntax than Map.
  const cache = Object.create(null);
  const toKey = keyFn || ((...args) => JSON.stringify(args));
  return function (...args) {
    const k = toKey(...args);
    // `k in cache` correctly handles cached `undefined` — unlike `cache[k] !== undefined`.
    if (k in cache) return cache[k];
    const v = fn(...args);
    cache[k] = v;
    return v;
  };
}
let calls = 0;
const square = (n) => { calls++; return n * n; };
const m = memoize(square);
console.log(m(3));
console.log(m(3));
console.log(m(4));
console.log('calls=' + calls);
  • k in cache is the correct hit-test — checks key presence regardless of value; cache[k] !== undefined would re-run fn for any call that legitimately returns undefined.
  • Object.create(null) removes the prototype chain so keys like '__proto__' or 'constructor' can't shadow built-in properties.
  • Object key iteration order and Map iteration order are both insertion-order for string keys in modern JS, so neither has an ordering advantage.

Q1 Calling a memoized fn with the same args three times calls the underlying fn how many times?

  1. A 3 — memoize records calls but still invokes the body each time
  2. B 0 — the wrapper short-circuits before reaching the underlying fn even on the first call
  3. C 1 correct
  4. D 2 — the cache stores at most one value, so every other call has to recompute

Why: The first call misses cache.has(k), runs fn, and stores the result; calls 2 and 3 return from cache.get(k) without entering the body at all. That's why the L3 script's calls counter reads 2 after three invocations of m — m(3) twice plus m(4).

Q2 Why is the default key JSON.stringify(args) insufficient for some inputs?

  1. A JSON.stringify on an args array always returns '[]' because rest-parameter arrays aren't iterable in serialization
  2. B Functions, undefined, Symbols, and circular refs don't serialize cleanly — also two distinct objects with the same shape collide correct
  3. C Each call to JSON.stringify allocates a new string identity, so cache keys never compare equal across calls
  4. D JSON.stringify strips numeric precision past 6 digits, so two close-but-distinct numeric args collapse to one cache entry

Why: Functions, undefined and Symbols all serialize to null inside an array, so f(undefined) and f(someFn) share a cache slot, and a circular arg throws outright. The subtler failure is identity: {a:1} and a different {a:1} stringify identically, so two distinct objects are treated as the same call.

Q3 When is memoization unsafe?

  1. A Whenever the function takes more than one argument — the default key only captures the first
  2. B When the function isn't pure — same args may legitimately need different outputs correct
  3. C When the function returns an object — Map values must be primitives to be cached
  4. D When the wrapped function is recursive — the cache breaks the base-case detection

Why: The key is built from the args alone, so anything the result also depends on — Date.now(), a mutable global, a network read — is invisible to the cache and the first answer is served forever. Side effects are the mirror image: they run once and then silently stop happening on every hit.

Q4 What benefit does an explicit keyFn provide over the default?

  1. A Avoids the cost of JSON.stringify and lets you collapse equivalent-but-not-identical inputs to one key correct
  2. B It tracks the key insertion order so the cache can be replayed in call order during hot-reload
  3. C It lets the cache hold non-string keys directly (Map can otherwise only store stringified keys)
  4. D It enables async support — the default keyFn does not await Promise-typed arguments

Why: toKey = keyFn || (...) lets the caller key on just the field that matters — user => user.id skips walking the whole object AND makes two different objects with the same id share a cache entry. It also handles the args the default can't serialize at all, like a circular reference.
