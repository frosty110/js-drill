Implement Promise.all

Reimplement Promise.all from scratch — wait for every input to resolve, preserve order, reject fast on the first error. Classic async interview question.

Problem

Implement promiseAll(arr) that resolves to an in-order array of resolved values, or rejects with the first error. Test with a mix of promises and bare values; also test the rejection path.

Expected output: [1,2,3] boom

Canonical solution

Preallocated result array + completion counter · O(n) / O(n) (time / space)

function promiseAll(arr) {
  return new Promise((resolve, reject) => {
    // Preallocate so out-of-order resolves still land at the right index.
    const out = new Array(arr.length);
    let done = 0;
    // Empty input must resolve to [] — forgetting this leaves a forever-pending promise.
    if (arr.length === 0) return resolve(out);
    arr.forEach((item, i) => {
      // Lift bare values into promises so plain entries still go through .then.
      Promise.resolve(item)
        .then(v => {
          out[i] = v;
          // Count completions; resolved `undefined` is still a real result.
          if (++done === arr.length) resolve(out);
        })
        // First rejection wins — later errors are ignored.
        .catch(reject);
    });
  });
}
  • Wrap each entry with Promise.resolve() — values may be raw, not promises, but you still want a microtask boundary.
  • Track completion with a counter, not by checking out for empty slots. A resolved undefined is still a real result.
  • Empty input must resolve to [] synchronously (well, in a microtask). Forgetting this gives a forever-pending promise.
  • Time O(n) setup + wall-clock max(durations). Space O(n) for the preallocated out array.

Alternate approaches

Sequential async/await (for-of loop) O(n) / O(n)

Use only when you explicitly want serial execution — each item must finish before the next begins. Produces correct output but loses all concurrency: n promises each taking 100ms take 100n ms total instead of ~100ms. Show this to an interviewer as the naive version, then explain why the counter-based approach is what Promise.all is actually for.

async function promiseAll(arr) {
  // Sequential: awaits each item in turn — simple but not parallel.
  const out = [];
  for (const item of arr) out.push(await Promise.resolve(item));
  return out;
}
(async () => {
  const ok = await promiseAll([Promise.resolve(1), 2, Promise.resolve(3)]);
  console.log(ok);
  try {
    await promiseAll([Promise.resolve(1), Promise.reject(new Error('boom')), 3]);
  } catch (e) {
    console.log(e.message);
  }
})();
  • Each await blocks the next iteration — the loop serializes what should be parallel work.
  • Wall-clock latency is sum(durations), not max(durations); the parallel counter-based version brings it down to max.
  • Rejection propagates correctly (await re-throws) but not fail-fast: items before the rejection still run to completion.

Q1 Why preallocate out = new Array(arr.length) instead of pushing as each resolves?

  1. A new Array(n) allocates a contiguous buffer that the engine fills atomically — .push would tear under concurrent then-handlers
  2. B Promises may resolve out of order — assigning by index preserves input order correct
  3. C .push inside a .then callback executes on a different microtask queue than the constructor, so it skips the outer Promise's resolve
  4. D Preallocating sets out.length upfront, which is what makes the done === out.length completion check valid

Why: The handler writes out[i] = v with i captured from forEach, so a promise that settles third still lands in its input slot; .push would order the output by completion time. Note the completion check is ++done === arr.length, not out.length — preallocation isn't what makes it valid.

Q2 What happens when one input rejects?

  1. A Other inputs are cancelled via AbortSignal and the outer promise rejects with an AggregateError
  2. B Other inputs keep running, but the outer promise rejects with the first error and ignores later results correct
  3. C It waits for all to settle, then collects errors into a .errors array on the rejection reason
  4. D It silently resolves with undefined at the rejected index and keeps the other resolutions

Why: .catch(reject) is attached to every entry and a Promise settles once, so the first rejection wins and later reject calls are no-ops. Nothing is cancelled — the other promises keep running and their handlers still write out[i]; that array is simply unreachable once the outer promise has rejected. AggregateError belongs to Promise.any; collect-all-errors is Promise.allSettled.

Q3 Why wrap each item in Promise.resolve(item)?

  1. A .then directly on a non-thenable returns undefined, silently dropping the value from the output
  2. B Items may be plain values; Promise.resolve normalizes them to thenables correct
  3. C It defers the value to a different microtask queue so the outer Promise constructor's resolve can complete first
  4. D Promise.resolve triggers internal reference-counting so the runtime can GC each input once it settles

Why: arr may hold bare values — the driver passes [Promise.resolve(1), 2, Promise.resolve(3)]. Calling .then on 2 throws TypeError: 2.then is not a function; Promise.resolve returns a promise untouched and wraps anything else, so one code path handles both.

Q4 What must promiseAll([]) resolve to?

  1. A undefined — there are no results to package into an array
  2. B A forever-pending Promise — done === length is 0 === 0 which never re-fires
  3. C [] — an empty array correct
  4. D It should reject with a TypeError — an empty iterable is invalid input by the spec

Why: The explicit if (arr.length === 0) return resolve(out) exists for exactly this case: forEach over an empty array never runs, so without the guard nothing ever calls resolve and the returned promise hangs forever.
