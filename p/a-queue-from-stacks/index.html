Queue Using Two Stacks

FIFO queue built from two LIFO stacks (just JS arrays). push goes to `in`. pop/peek read from `out`; when `out` is empty, drain ALL of `in` into `out` by popping — which reverses the order, putting the oldest element on top. Each element migrates at most once, so the work is amortized O(1) per op.

Problem

Build Queue with push, pop, peek, size. push 1,2,3; log peek, pop; push 4; log pop, peek, pop, pop, size.

Expected output: 1 1 2 3 3 4 0

Canonical solution

Two stacks, drain only when out is empty · O(1) amortized / O(n) (time / space)

class Queue {
  constructor() { this.in = []; this.out = []; }
  // Pushes always go to `in` — cheap, no reorder.
  push(v) { this.in.push(v); }
  _shift() {
    // Drain ONLY when out is empty — that's what amortizes pop to O(1).
    if (!this.out.length) {
      // Pop from in + push to out flips LIFO to FIFO; oldest ends up on top.
      while (this.in.length) this.out.push(this.in.pop());
    }
  }
  pop() { this._shift(); return this.out.pop(); }
  peek() { this._shift(); return this.out[this.out.length - 1]; }
  // size sums both halves — forgetting one makes the queue look smaller than it is.
  get size() { return this.in.length + this.out.length; }
}
// Amortized O(1) push/pop/peek, Space O(n)
  • Only drain when out is empty. Draining on every pop ruins the amortization and produces wrong order.
  • Pop from in and push to out — this reversal turns LIFO order into FIFO order.
  • size combines both stacks. Forgetting one half makes the queue look smaller than it is.

Alternate approaches

Single-stack with full reversal on every pop (O(n) per dequeue) O(n) pop / O(1) push

Mention this when the interviewer asks for the naive approach before you optimize, or when they explicitly say 'use only one stack'. Useful to name so you can pivot to explaining why the two-stack version is better.

class Queue {
  constructor() { this.inStk = []; }
  push(v) { this.inStk.push(v); }
  pop() {
    // Reverse entire stack into temp, pop oldest, restore everything back.
    const temp = [];
    while (this.inStk.length) temp.push(this.inStk.pop());
    const oldest = temp.pop();
    while (temp.length) this.inStk.push(temp.pop());
    return oldest;
  }
  peek() {
    const temp = [];
    while (this.inStk.length) temp.push(this.inStk.pop());
    const oldest = temp[temp.length - 1];
    while (temp.length) this.inStk.push(temp.pop());
    return oldest;
  }
  get size() { return this.inStk.length; }
}
const q = new Queue();
q.push(1); q.push(2); q.push(3);
console.log(q.peek());
console.log(q.pop());
q.push(4);
console.log(q.pop());
console.log(q.peek());
console.log(q.pop());
console.log(q.pop());
console.log(q.size);
  • Every pop/peek reverses the entire stack into temp, takes the oldest element off the bottom, then restores — O(n) each time.
  • No amortization possible with one stack: every pop is worst-case O(n) because the restore pour undoes all the reversal work.
  • The two-stack variant wins by caching the reversed view in out and only rebuilding when out is empty.

Q1 Why two stacks instead of one?

  1. A One stack for values, one for sizes — the size stack mirrors the value stack to make size an O(1) read
  2. B A single stack cannot give FIFO order; reversing one stack into another flips LIFO to FIFO correct
  3. C Each stack is bounded to half the queue capacity, so two stacks double the available headroom before resizing
  4. D Stacks must alternate writers and readers; one stack at a time would block pop while push is in progress

Why: while (this.in.length) this.out.push(this.in.pop()) takes the newest first and buries it, leaving the oldest element on top of out where pop() can reach it. A single stack only ever exposes the element you pushed last.

Q2 When should the in-stack be drained into the out-stack?

  1. A On every push — newer values must immediately propagate to out so peek can read them
  2. B On every pop, regardless of whether out has elements waiting
  3. C Only when out is empty and a pop/peek is requested correct
  4. D When in.length exceeds out.length — keeping the two stacks balanced minimizes peak memory

Why: _shift is guarded by if (!this.out.length). Draining while out still holds elements re-buries them under the newer arrivals: after push(1,2,3), pop(), push(4), an unconditional drain makes out end [3,2,4] and the next pop() returns 4 instead of 2.

Q3 What is the amortized cost of pop?

  1. A O(n) worst case applies to every pop because each pop may force a fresh drain of the in-stack
  2. B O(log n) — the drain halves the work each pop via repeated bisection of the in-stack
  3. C O(1) — each element moves between stacks at most once correct
  4. D O(n) amortized — the drain cost spreads evenly across pops, leaving each one O(n)

Why: Each element is pushed to in once, popped once, pushed to out once and popped once — four constant-time steps over its entire lifetime, no matter how many drains happen. A single drain is O(n), but it pays for the n pops that follow it.

Q4 After push(1), push(2), push(3), what does pop return?

  1. A 3 — pop reads from the top of the in-stack directly without draining
  2. B 1 — FIFO correct
  3. C 2 — the middle element of the in-stack is taken first, then the ends alternate
  4. D undefined — pop only works after an explicit _shift() call by the caller

Why: The first pop() finds out empty, drains in = [1,2,3] into out = [3,2,1], and out.pop() takes the top — which is now the 1 that was pushed first. That reversal is the whole reason for the second stack.
