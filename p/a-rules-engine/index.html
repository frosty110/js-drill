Keyword Rules Engine

Route free text to a team by matching keywords against a declarative, typed rule table — a `for...of` scan with an early return, because array order IS the priority and the first rule that hits wins, which a `.find`-style fold would hide.

Problem

In TypeScript: build a keyword rules engine. Given a declarative table of { team, keywords } rules, route each ticket to the FIRST team whose keywords appear as whole words in the text, reporting which keywords matched, and falling back to Triage when nothing hits. Type the rule table so a mistyped field is a compile error.

Expected output: Billing <- invoice, refund Security <- phishing, password Platform <- outage, latency, deploy Billing <- refund Triage <- no keyword hit

Canonical solution

Typed rule table + first-match-wins scan over a whole-word token Set · O(n + r*k) / O(n) (time / space)

// ── A TypeScript primer, inline ──────────────────────────────────────────
// TypeScript is JavaScript plus type annotations. They're checked while you
// write and ERASED before anything runs, so none of them costs a runtime
// operation — the shipped JavaScript is this code with the types deleted.

// `interface` names an object shape. (`type Rule = { ... }` would work the
// same here; interfaces are the conventional choice for a contract like this.)
interface Rule {
  team: string;
  // `readonly string[]` = an array of strings this code promises not to
  // mutate. Compile-time only — the array isn't frozen at runtime.
  keywords: readonly string[];
}

// The annotation `: readonly Rule[]` makes the table's shape explicit, so a
// typo like `{ team: 'X', keyword: [...] }` is caught here rather than
// silently producing a rule that can never match.
//
// Rules are DATA, not control flow. Array order IS the priority, and adding
// a team means appending an entry — route() never changes.
const RULES: readonly Rule[] = [
  { team: 'Security', keywords: ['breach', 'phishing', 'password'] },
  { team: 'Billing', keywords: ['invoice', 'refund', 'charge'] },
  { team: 'Platform', keywords: ['outage', 'latency', 'deploy'] },
];
const FALLBACK = 'Triage';

// `Set<string>` — the angle brackets say what the Set holds, so `.has()` is
// known to take a string. Whole-word tokens: 'recharge' must NOT match the
// keyword 'charge'.
function tokenize(text: string): Set<string> {
  return new Set(text.toLowerCase().match(/[a-z0-9']+/g) ?? []);
}

// The return type is written inline: this hands back a team plus the keywords
// that matched it. Naming the shape in the signature is what stops a caller
// from quietly depending on a field we never meant to expose.
//
// `rules: readonly Rule[] = RULES` is a typed parameter WITH a default —
// callers can inject their own table, which is how you'd test this.
function route(text: string, rules: readonly Rule[] = RULES): { team: string; matched: string[] } {
  const words = tokenize(text);
  for (const rule of rules) {
    // filter, not some — keeping the hits makes the decision explainable.
    const matched = rule.keywords.filter(k => words.has(k));
    if (matched.length > 0) return { team: rule.team, matched };
  }
  return { team: FALLBACK, matched: [] };
}
  • TypeScript types are ERASED before the code runs — they cost nothing at runtime and change no behavior. The algorithm below is the same JavaScript either way.
  • Rules are an ARRAY OF DATA typed readonly Rule[], so adding a team is appending an entry and reprioritizing is reordering — route() itself never changes, and the table can move to JSON or a DB untouched. The annotation catches a mistyped field (keyword vs keywords) that would otherwise produce a rule which silently never matches.
  • Array order IS the priority: the first rule with any hit returns immediately, so a later rule that would also match is never consulted. That early exit is the semantics, which is why this is a for...of and not a chained fold.
  • Tokenize into a Set<string> and test with has — text.includes('charge') would misroute 'Recharge the battery' to Billing. Whole-word matching kills that class of false positive, and the Set makes each keyword test O(1).
  • filter rather than some: returning WHICH keywords matched makes the routing decision explainable after the fact, which is what you need the first time someone disputes it. The inline return type { team: string; matched: string[] } is what pins that contract.
  • readonly string[] documents that the engine never mutates a rule's keyword list. It's a compile-time promise only — nothing is frozen at runtime.
  • String.match returns null (not []) when nothing matches, so ?? [] normalizes before the Set is built. TypeScript surfaces this: the match result is typed RegExpMatchArray | null, so it won't let you skip the check.
  • Keyword matching cannot handle negation — 'this is NOT a refund request' still routes to Billing. That's a limit of the technique, not a bug to patch, and no amount of typing fixes it.

Q1 Why tokenize into a Set and test words.has('charge') instead of the simpler text.includes('charge')?

  1. A String.includes is case-sensitive and cannot be made case-insensitive without a regex
  2. B includes matches substrings, so 'Recharge the battery' would falsely fire the 'charge' keyword; Set membership tests whole words correct
  3. C includes performs a full scan per call, and Set lookup is the only way to avoid re-reading the string
  4. D A Set automatically strips punctuation from the keywords, which includes cannot do

Why: The substring false positive is the real bug: 'recharge', 'discharge' and 'surcharge' all contain 'charge'. Tokenizing makes them distinct words. The O(1) lookup is a bonus, not the reason.

Q2 The rules live in an array of { team, keywords } objects rather than a chain of if/else statements. What is the primary benefit?

  1. A Array iteration is faster than sequential conditionals because the engine can vectorize the comparisons
  2. B Objects in an array are garbage-collected together, reducing memory churn on repeated routing calls
  3. C It avoids the banned labeled-break needed to exit an if/else chain early
  4. D Rules become data: adding a team is appending an entry and reprioritizing is reordering, so the table can be edited, tested, or loaded from config without touching the routing code correct

Why: The if/else version buries the priority order in the physical layout of the code and turns every rule change into a code change. A table makes both the rules and their order explicit, testable, and externally editable.

Q3 Each rule collects hits with rule.keywords.filter(k => words.has(k)) rather than rule.keywords.some(k => words.has(k)). Why keep the full list?

  1. A some stops at the first match, so it would miss rules whose later keywords are the higher-priority ones
  2. B filter returns the matched keywords as evidence, so the engine can explain WHY a text routed where it did — some returns only a boolean and throws that away correct
  3. C some returns undefined rather than false when the keywords array is empty, breaking the length check
  4. D filter is required because the result is later spread into the fallback rule's keyword list

Why: Both work for the routing decision itself. filter additionally answers 'why did this ticket go to Billing?' — which is the first question anyone asks of a routing system in production.

Q4 A ticket reading 'Refund the customer after the outage' contains keywords from both the Billing rule and the Platform rule. What decides the outcome, and what would change if the requirement became best-match-wins (most keyword hits)?

  1. A The rule with more total keywords defined wins; best-match-wins would instead require sorting the rules by keyword count up front
  2. B Both rules fire and the result is an array of teams; best-match-wins would just take the first element of that array
  3. C Position in the rules array decides — the earlier rule returns immediately. Best-match-wins would remove the early return, since no rule can be declared the winner until every rule has been scored correct
  4. D The rule whose keyword appears earliest in the text wins; best-match-wins would compare hit counts at that same point in the scan

Why: First-match-wins means array order IS the priority and the loop can exit as soon as anything hits. Best-match-wins forces a full pass to score every rule, with rule order surviving only as a tie-break.

Q5 tokenize is written text.toLowerCase().match(/[a-z0-9']+/g) ?? []. What does TypeScript add here that plain JavaScript doesn't?

  1. A It converts the regex match into a typed tuple, so the ?? [] fallback becomes unnecessary
  2. B It types the match result as RegExpMatchArray | null, so omitting the null check is a compile error rather than a crash the first time nothing matches correct
  3. C It makes .match() return an empty array instead of null, which is why the ?? is only defensive style
  4. D It narrows the regex literal to the exact set of strings it can match, letting the Set be typed more precisely

Why: String.prototype.match is typed to return RegExpMatchArray | null. Feeding that straight into new Set(...) — or into any array method — is rejected until you handle the null, so the bug 'text with no word characters at all' gets caught in the editor instead of in production. The runtime behavior is identical to the JavaScript version; the difference is when you find out.
