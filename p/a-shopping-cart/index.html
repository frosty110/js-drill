Problem

Build a Cart with add/remove/setQty/total. Sequence: add 2 apple ($1), add 1 bread ($3) → 5. add 1 more apple → 6. setQty(apple, 5) → 8. remove(bread) → 5. setQty(apple, 0) → 0.

Expected output: 5 6 8 5 0

Canonical solution

class Cart {
  constructor() {
    // Map keyed by item.name — O(1) add/remove/setQty vs O(n) array.find.
    this.lines = new Map();
  }
  add(item, qty = 1) {
    const line = this.lines.get(item.name);
    // Existing item: bump qty rather than duplicate the line (easy bug to ship).
    if (line) line.qty += qty;
    else this.lines.set(item.name, { item, qty });
  }
  remove(item) { this.lines.delete(item.name); }
  setQty(item, qty) {
    // qty <= 0 == remove. No phantom zero-qty rows.
    if (qty <= 0) return this.remove(item);
    const line = this.lines.get(item.name);
    if (line) line.qty = qty;
  }
  total() {
    let sum = 0;
    // values() yields {item, qty} records; keys() would only give names.
    for (const { item, qty } of this.lines.values()) sum += item.price * qty;
    return sum;
  }
  items() { return [...this.lines.values()]; }
}
  • Use a Map keyed by item.name (or a SKU id) — array.find is O(n) per add, Map is O(1).
  • add of an existing item must bump qty, not duplicate the line. Easy bug to ship.
  • setQty to 0 should remove the line. Otherwise the cart shows phantom 0-qty rows.
  • Time O(1) add/remove/setQty, O(n) total(); Space O(n) unique line items.

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why key the lines Map by item.name instead of pushing items into an array?

  1. A Maps coerce numeric strings to numbers, so SKU-shaped names stay sortable for the line-order view
  2. B O(1) lookup on add/remove/setQty instead of O(n) array.find correct
  3. C An array of objects doesn't survive JSON.stringify when objects share property names with array methods
  4. D Map.size invalidates on every mutation, forcing recomputation that an array's cached length avoids

Q2 What should add(apple) do when apple is already in the cart?

  1. A Throw a DuplicateItemError — apples are already in the cart and re-adding is a UX mistake
  2. B Replace the existing line — the most recent add overrides the prior quantity (last-write-wins)
  3. C Increment the existing line's qty by the new qty (default 1) correct
  4. D Add a second line for the same item, deduping at checkout instead of at add-time

Q3 What should setQty(item, 0) do?

  1. A Throw a RangeError — qty must be a positive integer per the cart contract
  2. B Leave a zero-qty line in the cart so the user can still see the item was once chosen
  3. C Remove the line entirely correct
  4. D Clamp the value to 1 — carts treat 0 as an underflow and round up to the minimum positive qty

Q4 Why does total() iterate lines.values() instead of lines.keys()?

  1. A lines.keys() returns the Map's internal hash buckets, not the item-name keys you'd expect
  2. B values() yields the {item, qty} records you need to compute price × qty correct
  3. C keys() iterates in hash-bucket order rather than insertion order, breaking the per-line price math
  4. D Both work; values() is just a stylistic preference because it reads as 'sum the values'
