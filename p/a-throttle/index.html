Throttle

Throttle caps invocations to one per `ms` window — extra calls during the cool-down are dropped (leading-edge variant). Built with an injectable clock so tests advance time deterministically.

Problem

Implement throttle(fn, ms) leading-edge with injectable clock. Show: first call fires, two more within window drop, advance past window, next call fires.

Expected output: calls=1 last=a calls=1 last=a calls=2 last=d

Canonical solution

Leading-edge throttle (gate on call) · O(1) / O(1) (time / space)

function throttle(fn, ms) {
  // -Infinity so the very first call always satisfies _now - lastFired >= ms.
  let lastFired = -Infinity;
  const api = function (...args) {
    // Leading edge: fire on the first call of each window, drop the rest silently.
    if (api._now - lastFired >= ms) {
      lastFired = api._now;
      fn(...args);
    }
    // No queueing — throttle does NOT keep latest args like debounce does.
  };
  api._now = 0;
  // Injected clock — tests advance time deterministically without setTimeout.
  api.tick = (delta) => { api._now += delta; };
  return api;
}
  • Leading-edge throttle fires on the first call of each window; trailing-edge would defer to the window end. Both are valid — pick one and document it.
  • Initialize lastFired = -Infinity (or any sentinel < -ms) so the very first call always fires.
  • Dropped calls are lost — no queueing. Debounce keeps the latest args; throttle does not.
  • Time O(1) per call and per tick; Space O(1) — one closure variable lastFired.

Alternate approaches

Trailing-edge throttle (defer + latest args win) O(1) / O(1)

Reach for this when the spec asks 'fire with the LATEST args, but no more than once per window' — the canonical follow-up to leading-edge throttle. This variant looks more like debounce: it keeps lastArgs AND a scheduled due-time, fires at the END of the window with whatever args arrived most recently. Common for 'autosave every N seconds' or 'send the last cursor position per frame' patterns where leading-edge would fire on a stale state.

function throttle(fn, ms) {
  let scheduled = null;       // due-at on fake clock, or null when idle
  let lastArgs = null;
  const api = function (...args) {
    // Always capture latest args — trailing-edge fires with the freshest snapshot.
    lastArgs = args;
    // Only ARM the timer if none is pending; subsequent calls just refresh lastArgs.
    if (scheduled === null) {
      scheduled = api._now + ms;
    }
  };
  api._now = 0;
  api.tick = (delta) => {
    api._now += delta;
    if (scheduled !== null && api._now >= scheduled) {
      scheduled = null;
      fn(...lastArgs);
    }
  };
  return api;
}
let calls = 0, last = null;
const t = throttle((x) => { calls++; last = x; }, 100);
t('a');                             // schedules fire at _now+100
t.tick(110);                        // window elapsed — fires with 'a'
console.log('calls=' + calls + ' last=' + last);
console.log('calls=' + calls + ' last=' + last);
t('d');                             // schedules fire at _now+100
t.tick(110);                        // fires with 'd'
console.log('calls=' + calls + ' last=' + last);
  • The if (scheduled === null) guard is what makes this throttle (one fire per window) rather than debounce (timer resets on every call). Calls inside the pending window refresh lastArgs but do NOT extend the deadline.
  • Trailing-edge fires with the FRESHEST args, not the first ones — opposite of leading-edge's 'first call wins' policy. The two variants pick different winners from the same burst.
  • If you wanted BOTH edges (lodash's default), combine the leading gate with this trailing scheduler — fire immediately on first call, then schedule a trailing fire if more calls arrived during the window.

Q1 Three calls within one ms window to a leading-edge throttled fn invoke the underlying fn how many times?

  1. A 3 — throttle records the calls but defers their firing to a single batched flush
  2. B 0 — the gate is closed on the first call until one full window has elapsed
  3. C 1 — the first one correct
  4. D 1 — the last one (trailing-edge default)

Why: t('a') clears the gate because _now - (-Infinity) is Infinity, and it sets lastFired = 0; t('b') and t('c') at the same _now compute 0 - 0 >= 100 → false and are dropped with no queue. Firing the last one instead would be trailing-edge throttle.

Q2 What is the key difference between debounce and throttle?

  1. A Throttle resolves a Promise per window; debounce returns the underlying fn's value synchronously
  2. B Debounce delays until quiet; throttle caps the rate (at most one per window) correct
  3. C Throttle queues calls in a buffer and replays them after the window; debounce discards everything but the first
  4. D Throttle requires a real timer; debounce works purely off comparisons of call timestamps

Why: Throttle's gate is _now - lastFired >= ms — a rate limit measured from the last FIRE. Debounce restarts its timer from the last CALL, so a caller who never pauses gets zero invocations out of a debounce and a steady one-per-window out of this.

Q3 Why initialize lastFired to -Infinity?

  1. A To make _now - lastFired >= ms true on the very first call correct
  2. B -Infinity is the only numeric value JavaScript treats as 'unset' in arithmetic comparisons against integers
  3. C Initializing to 0 would cause the first call at _now=0 to silently coerce ms to a negative value via the subtraction
  4. D It prevents the closure variable from being collapsed by V8's constant-folding optimization

Why: 0 - (-Infinity) is Infinity, which clears any ms. Initialize to 0 instead and the first call at _now = 0 computes 0 - 0 >= 100 → false, so the very first call is silently swallowed.

Q4 If the underlying fn is called inside the cool-down window, what happens to its args?

  1. A Queued and applied in order once the window elapses, the same behavior as Promise.allSettled with a delay
  2. B Stored as lastArgs and fired automatically when the next call passes the gate
  3. C Dropped — leading-edge throttle does not buffer correct
  4. D Merged into the previous fire's args via Object.assign so the most recent args win

Why: The gate is a bare if with no else — a call that fails it falls off the end of the function and its args are never stored anywhere. That is the deliberate split from debounce, which keeps lastArgs so the deferred fire uses the most recent ones.
