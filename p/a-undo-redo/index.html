Undo/Redo Stack

Command-pattern undo/redo — each action is an object with apply/revert. Two stacks: done and undone. Doing a fresh command clears the redo stack.

Problem

Build a History class with do/undo/redo over a number variable. Sequence: do(+1), do(+2), undo (now 1), do(+10) — clears redo. Then undo, undo. Log value after each step.

Expected output: 1 3 1 11 1 0

Canonical solution

Command pattern over two stacks · O(1) per op / O(n) (time / space)

class History {
  // done = applied stack; undone = redo stack. Two stacks model a linear timeline.
  constructor() {
    this.done = [];
    this.undone = [];
  }
  do(cmd) {
    cmd.apply();
    this.done.push(cmd);
    // A fresh action invalidates redo — branching destroys the old future.
    this.undone = [];
  }
  undo() {
    const cmd = this.done.pop();
    // No-op on empty stack — don't throw; UI buttons just stay disabled.
    if (!cmd) return;
    cmd.revert();
    this.undone.push(cmd);
  }
  redo() {
    const cmd = this.undone.pop();
    if (!cmd) return;
    cmd.apply();
    this.done.push(cmd);
  }
}
// Time O(1) per do/undo/redo, Space O(n) commands
  • Each command must be self-contained: apply() and revert() are inverses. The history doesn't know what the command does.
  • Doing a new action after an undo clears the undone stack — branching destroys the redo path. Standard editor behavior.
  • Undo and redo are no-ops on empty stacks. Don't throw — UI buttons just stay disabled.
  • Time O(1) per operation; Space O(n) where n is history depth.

Alternate approaches

Cursor-index into a single command array O(n) do (slice) / O(1) undo/redo

Reach for this when you want to avoid two separate stacks and don't mind a slice on every do(). The cursor approach keeps all commands in one array and uses an index to mark the boundary between past and future. The two-stacks version is cleaner: 'clear undone' is one assignment vs 'slice to cursor'.

class History {
  constructor() {
    this.cmds = [];
    this.cursor = 0;  // index of the next slot to fill — cmds[0..cursor-1] are applied
  }
  do(cmd) {
    // Truncate stale future — same as clearing the undone stack in the two-stack version.
    this.cmds = this.cmds.slice(0, this.cursor);
    cmd.apply();
    this.cmds.push(cmd);
    this.cursor++;
  }
  undo() {
    if (this.cursor === 0) return;  // nothing to undo
    this.cursor--;
    this.cmds[this.cursor].revert();
  }
  redo() {
    if (this.cursor === this.cmds.length) return;  // nothing to redo
    this.cmds[this.cursor].apply();
    this.cursor++;
  }
}
let x = 0;
const h = new History();
const add = n => ({ apply: () => x += n, revert: () => x -= n });
h.do(add(1));
console.log(x);
h.do(add(2));
console.log(x);
h.undo();
console.log(x);
h.do(add(10));
console.log(x);
h.undo();
console.log(x);
h.undo();
console.log(x);
  • cursor is the pivot: cmds[0..cursor-1] are applied (the 'done' stack); cmds[cursor..] are future (the 'undone' stack).
  • do slices off the future (O(n) allocation) — equivalent to this.undone = [] in the two-stack version, just more expensive.
  • Two-stacks wins on do() cost (O(1) assignment vs O(n) slice) and is easier to reason about without index arithmetic.

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why does do(cmd) clear this.undone?

  1. A Otherwise the next redo would re-apply both the new command and the stale undone commands as a batch
  2. B A fresh action creates a new branch; the previously-undone commands are no longer reachable correct
  3. C Without it, cmd.apply() would compose with the undone stack's pending reverts and cancel itself out
  4. D Clearing undone is what triggers the done.push(cmd) to fire — otherwise do is a no-op

Why: After an undo the timeline forks, and the undone command belongs to the future you just abandoned. this.undone = [] discards it — which is why an editor greys out Redo the moment you type something new.

Q2 What pair of operations must each command expose?

  1. A execute / cancel — cancel aborts an in-flight command but cannot reverse a completed one
  2. B apply / revert (inverses of each other) correct
  3. C forward / backward — both run the same logic but with a direction flag passed in
  4. D commit / rollback — borrowed from transaction APIs, mapping commit to do and rollback to undo

Why: do and redo both call cmd.apply(); undo calls cmd.revert(). History never inspects the command — add(n) supplies () => x += n and () => x -= n, and that inverse pair is the entire contract.

Q3 Where do commands sit after undo()?

  1. A Garbage-collected — once reverted, the command object has no remaining references
  2. B Moved from done to undone so redo can replay them correct
  3. C Stay in done but flagged with an inverted: true property; redo unsets the flag
  4. D Pushed to a third redoQueue that decouples reapplication from the original do/undo stacks

Why: undo is const c = this.done.pop(); … this.undone.push(c) — the command object survives, it just changes stacks. redo pops it straight back the other way, which is only possible because nothing discarded it.

Q4 What does redo() do when undone is empty?

  1. A Throws an EmptyHistoryError — the caller must check canRedo() before calling
  2. B Replays the last done command as a fallback, treating redo as a repeat-last-action shortcut
  3. C Returns early — it's a no-op correct
  4. D Returns undefined and silently re-applies the most recently undone command from a prior session

Why: const c = this.undone.pop(); if (!c) return; — popping an empty array yields undefined and the guard bails before c.apply() could throw. undo carries the same guard; the UI just leaves the button disabled instead of handling an exception.
