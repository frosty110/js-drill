Buy/Sell Stock

Track the minimum price seen so far; compute profit at each step. Single pass, O(1) space.

patterns Sliding Window 8 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write maxProfit(prices) — max profit from one buy then one sell. Log maxProfit([7, 1, 5, 3, 6, 4]).

Expected output: 5

Canonical solution

One-pass greedy with a running minimum · O(n) / O(1) (time / space)

function maxProfit(prices) {
  // best starts at 0: if prices only decline, you simply don't buy (profit 0).
  let minSoFar = Infinity, best = 0;
  for (const p of prices) {
    // Update min OR sell — can't do both same day, and you must buy before selling.
    if (p < minSoFar) minSoFar = p;
    else best = Math.max(best, p - minSoFar);
  }
  return best;
}
// Time O(n), Space O(1)
  • best starts at 0 — if prices only decline, you simply hold (profit 0, not negative).
  • You can’t sell before you buy, so minSoFar must come from earlier iterations.
  • Initialize minSoFar to Infinity (or use prices[0] and start at index 1).

Alternate approaches

Brute force (nested loops) O(n²) / O(1)

Name this before the optimal answer to show you understand the buy-before-sell constraint — every candidate pair (i, j) with j > i. Discard it quickly; it only appears in the interview as the starting point you reason away from.

function maxProfit(prices) {
  let best = 0;
  for (let i = 0; i < prices.length; i++) {
    for (let j = i + 1; j < prices.length; j++) {
      best = Math.max(best, prices[j] - prices[i]);
    }
  }
  return best;
}
console.log(maxProfit([7, 1, 5, 3, 6, 4]));
  • Correct but O(n²) — for every buy day i, re-scans all later sell days j.
  • The redundancy: for each new j we recompute the same prefix min of prices[0..j-1] instead of caching it.
  • Seeing this redundancy directly motivates the running-min: collapse the inner loop to a single scalar updated in O(1).

Q1 Why initialize best to 0 instead of -Infinity?

  1. A -Infinity would propagate into Math.max and force every subtraction to produce -Infinity
  2. B Otherwise the first iteration's best would be undefined and the comparison would NaN out
  3. C You can hold without selling for 0 profit correct
  4. D Math.max returns the first argument when both are negative, so best would never increase

Why: Not trading is a legal outcome worth 0. On a decline-only input like [7,6,4,3,1] every price takes the if branch and the else never runs, so whatever best was initialized to IS the returned answer — -Infinity would ship as the result.

Q2 Time complexity?

  1. A O(n²)
  2. B O(n log n)
  3. C O(n) correct
  4. D O(1)

Why: One for...of pass with a comparison and at most one subtraction per price — minSoFar caches the only thing the brute force's inner rescan of earlier days was recomputing.

Q3 Space complexity?

  1. A O(1) correct
  2. B O(log n)
  3. C O(n)
  4. D O(n²)

Why: Two scalars, minSoFar and best — the entire prefix collapses to one number, so nothing allocated grows with the input.

Q4 Invariant on each iteration:

  1. A minSoFar is the global minimum of all prices (including future ones)
  2. B minSoFar is the minimum of all PRIOR prices correct
  3. C minSoFar is the minimum of prices[0..i-1] AND best is the optimal profit considering future prices
  4. D minSoFar is the previous day's price (a size-2 sliding window)

Why: At the moment p - minSoFar is computed, minSoFar was built only from days already iterated — that's what enforces buy-before-sell. It can't see future prices, and best is only the best profit found so far, not yet the final answer.

Q5 Is this a fixed-size sliding window of size 2 (compare each price to the one before it)?

  1. A Yes — it compares prices[i] to prices[i-1] like a 2-wide window
  2. B No — it's a single pass tracking the running minimum so far, then profit = price - minSoFar at each step correct
  3. C Yes, but the window can grow to size 3
  4. D No — it sorts the prices first

Why: A size-2 window only sees adjacent days, but the best buy day can be far in the past; you must track the minimum over ALL prior days, not just the previous one.

Q6 Why does tracking minSoFar over all prior days beat only comparing adjacent prices?

  1. A Adjacent comparison is slower
  2. B The cheapest buy day may be many days before the best sell day, so you must remember the global-so-far min, not just yesterday correct
  3. C Adjacent comparison uses more memory
  4. D There is no difference — both give the same answer

Why: In [7,1,5,3,6,4] the best trade is buy at 1 (day 1) and sell at 6 (day 4); a size-2 window comparing neighbors never connects those non-adjacent days.

Q7 Why must minSoFar come from EARLIER iterations only (never the current or a future price)?

  1. A For performance
  2. B You can't sell before you buy — the buy day must be strictly before the sell day correct
  3. C Infinity requires it
  4. D To avoid integer overflow

Why: Profit = sellPrice - buyPrice requires the buy to precede the sell in time, so minSoFar is built only from prices seen on prior days.

Q8 Why is the answer NOT simply max(prices) - min(prices)?

  1. A Those functions are too slow
  2. B If the minimum price occurs AFTER the maximum, that subtraction would require selling before buying correct
  3. C max and min ignore duplicates
  4. D It actually is correct in all cases

Why: In [7,6,4,3,1] the min (1) comes after the max (7), so max-min=6 implies an impossible buy-after-sell; the real answer is 0.
