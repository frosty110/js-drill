Binary Search

Halve the search range on a sorted array. Closed interval [l, r] with `l <= r`.

patterns Binary Search 9 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write binarySearch(nums, target) returning the index of target, or -1. Log binarySearch([-1, 0, 3, 5, 9, 12], 9).

Expected output: 4

Canonical solution

Closed-interval binary search [l, r] · O(log n) / O(1) (time / space)

function binarySearch(nums, target) {
  let l = 0, r = nums.length - 1;
  // Closed interval [l, r] — `<=` is required to hit single-element ranges.
  while (l <= r) {
    const m = Math.floor((l + r) / 2);
    if (nums[m] === target) return m;
    // Move PAST m (+1/-1) to guarantee progress — `l = m` risks an infinite loop.
    if (nums[m] < target) l = m + 1;
    else r = m - 1;
  }
  return -1;
}
// Time O(log n), Space O(1)
  • Array MUST be sorted — that’s the whole prerequisite.
  • Loop condition is l <= r because [l, r] is a CLOSED interval; missing = skips single-element ranges.
  • Move past m by +1/-1 to guarantee progress and avoid infinite loops.
  • Why O(log n)? Each iteration halves the search range. After k halvings, size = n / 2^k; loop ends when 2^k ≥ n, so k ≈ log₂(n). For the full derivation + contrast with O(1)/O(n)/O(n²), drill the s-bigo-intuition lesson.

Alternate approaches

Recursive O(log n) / O(log n)

Reach for this when the interviewer specifically asks for the recursive formulation, or when you want to show you can express the same idea both ways. Prefer iterative in production — JS has no tail-call optimization, so every call adds an O(log n) stack frame.

function binarySearch(nums, target, l = 0, r = nums.length - 1) {
  if (l > r) return -1;
  const m = Math.floor((l + r) / 2);
  if (nums[m] === target) return m;
  if (nums[m] < target) return binarySearch(nums, target, m + 1, r);
  return binarySearch(nums, target, l, m - 1);
}
console.log(binarySearch([-1, 0, 3, 5, 9, 12], 9));
  • Same three-branch logic as iterative — base case, hit, recurse into the live half.
  • Default parameters l = 0, r = nums.length - 1 make the public call site clean.
  • Space is O(log n) from the call stack — the iterative version's key advantage over this one.

Q1 Why l <= r instead of l < r?

  1. A < would let m go negative on the last iteration when the range shrinks
  2. B [l, r] is closed; without the equal you miss single-element ranges correct
  3. C < would terminate one step too late and re-check an already-discarded half
  4. D <= is required to correctly compute Math.floor((l+r)/2) when l === r

Why: r is a real candidate index, so when l === r one element is still unchecked. Swap in < and binarySearch([5], 5) exits the loop immediately and returns -1.

Q2 If you write l = m instead of l = m + 1:

  1. A Returns the first occurrence of target instead of an arbitrary occurrence
  2. B Risk of infinite loop correct
  3. C Off-by-one — the returned index is one less than the true index of target
  4. D Loses the lower_bound property — l no longer points to the insertion point on a miss

Why: When r === l + 1, Math.floor((l + r) / 2) is l itself, so l = m leaves the interval unchanged and the loop spins forever. Moving past m is what guarantees the range shrinks every iteration.

Q3 Time complexity?

  1. A O(n)
  2. B O(log n) correct
  3. C O(n log n)
  4. D O(sqrt(n))

Why: Each iteration throws away half of [l, r], so the range goes n → n/2 → n/4 … and can only be halved about log₂(n) times before it is empty.

Q4 Prerequisite on the input?

  1. A Values must be distinct (no duplicates)
  2. B Must be sorted correct
  3. C Length must be a power of 2 so the halving is exact
  4. D Values must be non-negative

Why: The single test nums[m] < target is only entitled to discard an entire half because order guarantees everything left of m is <= nums[m]. Duplicates and negatives are both fine; unsortedness is not.

Q5 With the closed interval [l, r], what is the loop invariant — what stays true at the start of every iteration?

  1. A l and r are always different
  2. B If target is present, its index is within [l, r] correct
  3. C nums[l] is always less than target
  4. D m is always the answer

Why: The interval [l, r] always still contains target if it exists; each step discards a half that provably cannot contain it.

Q6 Why is m = l + ((r - l) >> 1) preferred over m = (l + r) / 2 in fixed-width-integer languages like C++/Java?

  1. A >> is a single CPU instruction whereas / is multi-cycle, so the loop iterations are tighter
  2. B l + r can overflow INT_MAX even when both indices are valid; l + (r-l)/2 cannot correct
  3. C It rounds toward zero on negative ranges, which matters when binary-searching answer-space below zero
  4. D It avoids the implicit float→int truncation that JIT compilers handle inconsistently across versions

Why: For large l and r, l + r can exceed the int max and wrap negative; l + (r - l)/2 stays within range. (In JS, Numbers are 64-bit floats so it is only a portability concern.)

Q7 Why is the algorithm guaranteed to terminate?

  1. A Because the array is finite
  2. B Because moving past m (l = m+1 / r = m-1) strictly shrinks [l, r] every iteration until l > r correct
  3. C Because target is always found
  4. D Because m eventually equals 0

Why: Each non-returning step removes at least the element at m plus one half, so the interval strictly shrinks and the loop must end.

Q8 After a FAILED search (target absent), what does l point to when the loop exits?

  1. A The last index checked
  2. B The insertion point — the index where target would be inserted to keep the array sorted correct
  3. C Always 0
  4. D Always nums.length

Why: On exit l is the lower_bound: the leftmost index whose value is >= target, i.e. where target would go to keep order.

Q9 Binary search is applicable whenever the input is exactly which of the following?

  1. A A sorted array only
  2. B Any data with a monotonic predicate — sortedness is one instance, but answer-space searches qualify too correct
  3. C Any array of numbers
  4. D Only arrays with unique values

Why: The real requirement is a monotone yes/no boundary; a sorted array gives one, but so does any monotone feasibility predicate (e.g. binary search on the answer).
