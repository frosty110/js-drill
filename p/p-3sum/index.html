3Sum

Sort, then for each anchor i, two pointers converge on the remaining pair. Skip duplicates at every level to keep results unique.

Problem

Write threeSum(nums) returning every unique triplet summing to 0. Log JSON.stringify(threeSum([-1, 0, 1, 2, -1, -4])).

Expected output: [[-1,-1,2],[-1,0,1]]

Canonical solution

Sort, then fixed anchor + converging two pointers · O(n²) / O(1) (time / space)

function threeSum(nums) {
  const res = [];
  // Sort unlocks two-pointer convergence — and groups duplicates for skipping.
  nums.sort((a, b) => a - b);
  // length - 2 leaves room for l = i+1 and r.
  for (let i = 0; i < nums.length - 2; i++) {
    // Skip duplicate anchors so we don't re-emit the same triplet.
    if (i > 0 && nums[i] === nums[i - 1]) continue;
    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (sum === 0) {
        res.push([nums[i], nums[l], nums[r]]);
        // After a hit, skip duplicate l and r values before advancing.
        while (l < r && nums[l] === nums[l + 1]) l++;
        while (l < r && nums[r] === nums[r - 1]) r--;
        l++; r--;
      } else if (sum < 0) l++;  // need bigger — left side has smaller values
      else r--;                 // need smaller — right side has bigger values
    }
  }
  return res;
}
// Time O(n^2), Space O(1) extra (ignoring sort + output)
  • Sorting is what unlocks the two-pointer step — without it you cannot decide which pointer to move.
  • Three layers of dedup: skip equal i, skip equal l after a hit, skip equal r after a hit.
  • Outer loop stops at length - 2 so l = i + 1 and r still leave room for a pair.

Alternate approaches

Sort + hash-set inner scan O(n²) / O(n)

A natural first step when you think 'fix anchor, Two-Sum the rest with a hash set.' Still O(n²) time but requires an extra O(n) set per anchor and an output-sort pass to guarantee deterministic order. Use when you'd rather not derive the two-pointer direction rule in an interview.

function threeSum(nums) {
  nums.sort((a, b) => a - b);
  const res = [];
  for (let i = 0; i < nums.length - 2; i++) {
    if (i > 0 && nums[i] === nums[i - 1]) continue;
    const seen = new Set();
    let j = i + 1;
    while (j < nums.length) {
      const complement = -nums[i] - nums[j];
      if (seen.has(complement)) {
        res.push([nums[i], complement, nums[j]]);
        while (j + 1 < nums.length && nums[j] === nums[j + 1]) j++;
      }
      seen.add(nums[j]);
      j++;
    }
  }
  res.sort((a, b) => a[0] - b[0] || a[1] - b[1] || a[2] - b[2]);
  return res;
}
console.log(JSON.stringify(threeSum([-1, 0, 1, 2, -1, -4])));
  • The hash set finds the complement that was seen earlier in the scan — because the array is sorted, complement ≤ nums[j], so each pushed triplet is already internally sorted.
  • An output sort is needed because hits for different anchors can arrive out of order; the two-pointer approach avoids this cost.
  • Same O(n²) time as the two-pointer variant but O(n) extra space per anchor for the set vs. O(1) with two pointers.

Brute force O(n³) O(n³) / O(n)

Only when you need to confirm understanding before deriving the faster solution. Three nested loops are correct but O(n³) — too slow for n > ~300. Name it out loud, then discard it.

function threeSum(nums) {
  nums.sort((a, b) => a - b);
  const resSet = new Set();
  const res = [];
  for (let i = 0; i < nums.length - 2; i++) {
    for (let j = i + 1; j < nums.length - 1; j++) {
      for (let k = j + 1; k < nums.length; k++) {
        if (nums[i] + nums[j] + nums[k] === 0) {
          const key = nums[i] + ',' + nums[j] + ',' + nums[k];
          if (!resSet.has(key)) {
            resSet.add(key);
            res.push([nums[i], nums[j], nums[k]]);
          }
        }
      }
    }
  }
  return res;
}
console.log(JSON.stringify(threeSum([-1, 0, 1, 2, -1, -4])));
  • Sorting first means each triplet is already in ascending order, so the string key i+','+j+','+k is unique per distinct value-triple — a cheap dedup without sorting each candidate.
  • O(n³) time: each of the three loops visits up to n positions; even with early exits on anchors > 0 the worst case is cubic.
  • The Set grows up to O(n³) entries in the worst case (all unique pairs), though in practice it's bounded by the output size.

Q1 Why sort the array first?

  1. A To collapse equal values into a single representative — the two-pointer scan then runs over uniques only
  2. B So two-pointer convergence can decide which side to move correct
  3. C So the inner loop can binary-search for the complement in O(log n)
  4. D To shift all negative numbers to the front, allowing a single-direction scan

Why: Ascending order is what makes sum < 0 → l++ / sum > 0 → r-- valid — on an unsorted array a pointer move tells you nothing about how the sum changes. Sorting also clusters equal values, which is what the three dedup skips rely on.

Q2 Time complexity?

  1. A O(n)
  2. B O(n log n)
  3. C O(n^2) correct
  4. D O(n^3)

Why: Sort is O(n log n); the nested two-pointer loop dominates at O(n^2).

Q3 When sum < 0, which pointer moves?

  1. A l moves right (bigger value) correct
  2. B r moves left (smaller value)
  3. C Both move
  4. D i moves forward

Why: The sum is too small so you need a bigger value, and in ascending order the bigger values sit to the right of l. Moving r left would swap in a smaller value and push the sum further below zero.

Q4 Purpose of if (i > 0 && nums[i] === nums[i - 1]) continue;?

  1. A Skip anchors whose value cannot reach zero with any later pair (already known to be too large after sorting)
  2. B Skip duplicate triplets at the anchor correct
  3. C Reset the inner pointers l and r when the anchor's value didn't change
  4. D Avoid re-processing the anchor's mirror position from the previous iteration

Why: An anchor equal to its predecessor would run the identical two-pointer scan over the same suffix and re-emit triplets already recorded — the second -1 in [-4,-1,-1,0,1,2]. The i > 0 guard keeps nums[-1] out of the comparison.

Q5 There are THREE dedup checks in the canonical solution. Where do they sit?

  1. A All three are at the anchor i, run before the inner loop
  2. B Skip duplicate anchors (i), then after a hit skip duplicate l values and duplicate r values correct
  3. C One at i, one at sum < 0, one at sum > 0
  4. D All three are inside the while-loop condition

Why: Anchor dedup (nums[i] === nums[i-1]) runs in the outer loop; the l and r dedup-skip loops run only after recording a hit, before advancing the pointers.

Q6 Besides enabling two-pointer convergence, what second benefit does sorting provide for 3Sum?

  1. A It removes all duplicate elements automatically as a side effect of the in-place sort
  2. B It clusters equal values adjacently, so duplicates can be skipped by comparing neighbors correct
  3. C It guarantees the resulting triplets emerge in lexicographic order, which the problem statement requires
  4. D It guarantees the inner two-pointer loop converges in O(log n) by enabling binary halving

Why: Sorting groups identical values next to each other, which is exactly what lets the dedup checks work by comparing nums[i] to nums[i-1] (or nums[l] to nums[l+1]).

Q7 Why is a hash-set approach messier for 3Sum than for Two Sum?

  1. A The inner Two-Sum's hash map must be rebuilt for every anchor, blowing the time bound to O(n³)
  2. B You still fix one element and Two-Sum the rest, but deduplicating the resulting triplets requires sorting/stringifying each one — work the sorted two-pointer avoids in place correct
  3. C Hash collisions are more frequent with three numbers because the implicit sum-key clashes with the pair-key
  4. D Hashing requires the input to be non-negative, so an extra pass to shift the range is needed

Why: A hash approach finds the pairs but produces duplicate triplets, forcing you to canonicalize (sort + stringify) each triplet into a set; the sorted two-pointer dedups in place with simple neighbor skips.

Q8 After recording a hit, why do the dedup-skip loops include the l < r guard (e.g. while (l < r && nums[l] === nums[l + 1]))?

  1. A To stop advancing once the remaining window is too small to form a valid pair complement to the anchor
  2. B Without it, on input like [0,0,0,0] the skip could advance l past r and read out of bounds correct
  3. C Because nums[l + 1] would coerce to NaN at the array boundary, breaking the equality check
  4. D To prevent the inner loop from recording the same triplet from the right pointer's perspective

Why: On all-equal inputs the skip loop would keep advancing; the l < r guard stops it before the pointers cross and prevents reading nums[l+1] out of range.

Q9 Why does the outer loop stop at i < nums.length - 2 rather than i < nums.length?

  1. A The last two anchors can never sum to zero with any pair to their right, so they are safe to skip
  2. B Because l = i + 1 and r need to point at two more distinct positions, so i must leave room for a pair after it correct
  3. C The dedup check nums[i] === nums[i - 1] would index past the end at the last two positions
  4. D Sorted arrays in V8 are stored with two trailing sentinel slots that should not be read as data

Why: A triplet needs i plus two later indices (l = i+1 and r); once fewer than two elements remain after i, no triplet can form, so the loop ends at length - 2.
