Group Anagrams

Group strings that are anagrams. Use a sorted-character key in a Map to bucket them. O(n·k log k) where k is max word length.

patterns Arrays & Hashing 8 concept · 1 fill-in · 1 drill

Results carried by this link

Problem

Write groupAnagrams(strs) returning groups of anagrams (each group preserving first-seen order). Log JSON.stringify(groupAnagrams(["eat","tea","tan","ate","nat","bat"])).

Expected output: [["eat","tea","ate"],["tan","nat"],["bat"]]

Canonical solution

function groupAnagrams(strs) {
  // Map preserves insertion order so groups stay in first-seen order.
  const map = new Map();
  for (const s of strs) {
    // Sorted chars are the canonical anagram fingerprint — same multiset → same key.
    const key = s.split("").sort().join("");
    // Lazy-init the bucket on first sighting of this key.
    if (!map.has(key)) map.set(key, []);
    map.get(key).push(s);
  }
  return Array.from(map.values());
}
// Time O(n * k log k), Space O(n * k)
  • The sorted-char string is the canonical anagram fingerprint.
  • A Map preserves insertion order; an Object loses some guarantees.
  • Alternative key: a 26-length count array joined into a string — O(k) keying beats O(k log k) sorting for long words.

Alternate approaches

Count-array key (O(n·k)) O(n·k) / O(n·k)

Reach for this when the interviewer asks you to beat the O(k log k) sort cost, or when the problem guarantees lowercase ASCII only. Builds a 26-slot count array per string instead of sorting its chars.

function groupAnagrams(strs) {
  const map = new Map();
  for (const s of strs) {
    // Build a 26-slot frequency array (a→0, b→1, … z→25).
    const counts = new Array(26).fill(0);
    for (const c of s) counts[c.charCodeAt(0) - 97]++;
    // Join with '#' so counts [1,0,...] and [10,...] don't collide.
    const key = counts.join("#");
    if (!map.has(key)) map.set(key, []);
    map.get(key).push(s);
  }
  return Array.from(map.values());
}
console.log(JSON.stringify(groupAnagrams(["eat","tea","tan","ate","nat","bat"])));
  • Count array is O(k) per string vs O(k log k) for sorting — asymptotically faster for long words.
  • Separator '#' in the joined key prevents count-vector collisions (e.g. counts [1,10] vs [11,0]).
  • Only correct for a fixed, known alphabet (e.g. lowercase ASCII); sorted-string key handles arbitrary Unicode.

Q1 Why does sorting each string produce a valid anagram key?

  1. A Sorting normalizes case and whitespace, which is what defines anagrams
  2. B Two strings are anagrams iff they share the same multiset of chars, which sorting canonicalizes correct
  3. C Sorting collapses duplicate chars so the key is the unique-letter set
  4. D JavaScript's Map only accepts strings, so the key must be a sorted string

Q2 Time complexity where n is the number of words and k is max word length?

  1. A O(n)
  2. B O(n * k)
  3. C O(n * k log k) correct
  4. D O(n^2)

Q3 Why prefer a Map over a plain object?

  1. A Maps deduplicate identical values automatically, which an Object would not
  2. B Maps preserve insertion order and accept any key type without prototype collisions correct
  3. C Maps support O(1) .has() while Object key lookup is O(log n)
  4. D Object property access is asynchronous in strict mode

Q4 A faster keying strategy than sorting is:

  1. A Reverse the string — same multiset, but built in linear time
  2. B A length-26 count array joined to a string — O(k) per word correct
  3. C Sum the char codes — equal sums imply equal multisets
  4. D XOR the char codes together for a constant-size key

Q5 Two strings are guaranteed to land in the same bucket exactly when:

  1. A They have the same length
  2. B They produce the same canonical key (same sorted chars / same char-count signature) correct
  3. C They start with the same letter
  4. D They were adjacent in the input

Why: The Map buckets by key; anagrams share an identical multiset of characters, so their canonical keys collide and only then are they grouped.

Q6 Why is if (!map.has(key)) map.set(key, []) needed before pushing?

  1. A To clear any stale bucket left from a previous call to groupAnagrams
  2. B To lazily create the bucket array on first sighting — otherwise map.get(key) is undefined and .push throws correct
  3. C Map.prototype.set silently overwrites existing entries, so the guard prevents wiping the bucket
  4. D It is optional — without the guard, Map auto-initializes missing keys to []

Why: A brand-new key has no array yet, so map.get(key) returns undefined; the guard initializes an empty array so the subsequent .push has something to push into.

Q7 For a single word of length k, why is the count-signature key O(k) while the sorted-string key is O(k log k)?

  1. A Both are O(k); the log k factor only appears across all n words
  2. B Counting chars is a single linear pass; sorting k chars costs O(k log k) correct
  3. C Counting requires k passes (one per bucket of the count array), making it O(k²)
  4. D Array.prototype.sort uses radix sort for chars, which is O(k log k) only on Unicode strings

Why: Tallying each character is one O(k) sweep, whereas comparison-sorting the k characters incurs the O(k log k) sort factor.

Q8 Why does the canonical use a Map rather than a plain object for the buckets here?

  1. A Object keys must be valid identifiers, so a sorted string with non-letters would throw
  2. B A Map preserves first-seen insertion order for the output groups and avoids string-key/prototype edge cases correct
  3. C Object key lookup is O(log n) while Map lookup is O(1)
  4. D Plain objects use reference equality on string keys, so two equal sorted strings would land in different buckets

Why: Map iteration follows insertion order, so Array.from(map.values()) emits groups in first-seen order, and Map sidesteps prototype-key collisions a plain object can hit.
