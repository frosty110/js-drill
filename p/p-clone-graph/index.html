Clone Graph

DFS with a visited Map from original-node to clone-node. The Map handles cycles AND avoids exponential reclones of shared neighbors.

patterns Graphs 8 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write cloneGraph(node) using DFS + a visited Map. Build the 4-cycle graph with edges 1-2, 2-3, 3-4, 4-1, clone it, then log (1) cloned !== original (deep-copy proof), (2) a DFS-order serialization as val:[n1,n2,...] entries space-separated.

Expected output: true 1:[2,4] 2:[1,3] 3:[2,4] 4:[1,3]

Canonical solution

DFS memoized on an original-node -> clone Map · O(V+E) / O(V) (time / space)

function cloneGraph(node) {
  if (!node) return null;
  // Map original-node OBJECT → clone — identity keys, vals can repeat.
  const map = new Map();
  function dfs(orig) {
    // Already cloned (or mid-clone) — return the recorded copy to break cycles.
    if (map.has(orig)) return map.get(orig);
    const copy = { val: orig.val, neighbors: [] };
    // CRITICAL: record BEFORE recursing — otherwise a cycle infinite-loops.
    map.set(orig, copy);
    for (const nb of orig.neighbors) copy.neighbors.push(dfs(nb));
    return copy;
  }
  return dfs(node);
}
// Time O(V + E), Space O(V) for the map + recursion stack
  • CRITICAL: set map.set(orig, copy) BEFORE recursing into neighbors. Otherwise a cycle re-enters dfs and infinite-loops.
  • The Map keys are the original node OBJECTS (identity), not their .val — vals can repeat.
  • For each original node you create exactly one clone, then wire its neighbors by recursing or fetching from the map.

Alternate approaches

BFS (iterative queue) O(V+E) / O(V)

Use BFS when you want to avoid recursion-stack overflow on large graphs (V can be up to ~100 on LeetCode but arbitrary in production). The same visited Map discipline applies — set-before-enqueue instead of set-before-recurse.

function cloneGraph(node) {
  if (!node) return null;
  const map = new Map();
  // Create the root clone and seed the queue with the original root.
  map.set(node, { val: node.val, neighbors: [] });
  const queue = [node];
  while (queue.length) {
    const orig = queue.shift();
    for (const nb of orig.neighbors) {
      if (!map.has(nb)) {
        // Create the clone and enqueue BEFORE wiring — same discipline as DFS set-before-recurse.
        map.set(nb, { val: nb.val, neighbors: [] });
        queue.push(nb);
      }
      // Wire this edge on every visit (both directions of an undirected edge).
      map.get(orig).neighbors.push(map.get(nb));
    }
  }
  return map.get(node);
}
function serialize(start) {
  const seen = new Set();
  const order = [];
  function walk(n) {
    if (seen.has(n)) return;
    seen.add(n);
    order.push(n);
    for (const nb of n.neighbors) walk(nb);
  }
  walk(start);
  return order.map(n => n.val + ":[" + n.neighbors.map(x => x.val).join(",") + "]").join(" ");
}
const a = { val: 1, neighbors: [] };
const b = { val: 2, neighbors: [] };
const c = { val: 3, neighbors: [] };
const d = { val: 4, neighbors: [] };
a.neighbors = [b, d];
b.neighbors = [a, c];
c.neighbors = [b, d];
d.neighbors = [a, c];
const cloned = cloneGraph(a);
console.log(cloned !== a);
console.log(serialize(cloned));
  • Create the root's clone and add it to the map BEFORE entering the loop — the root has no 'parent' to trigger the if (!map.has) branch for it.
  • Wire each neighbor edge inside the loop for every dequeued node — this correctly handles undirected edges appearing from both endpoints.
  • BFS traverses level-by-level vs DFS depth-first, but the result is identical: every node cloned exactly once, all edges wired.

Q1 Why must you put the clone in the map BEFORE recursing into neighbors?

  1. A So the neighbor recursion can mutate the parent's copy via the shared Map reference
  2. B Otherwise a cycle re-enters dfs on a node that is not yet recorded and recurses forever correct
  3. C Map.set assigns a stable identity hash that neighbor recursions rely on for ordering
  4. D The Map's insertion order determines the clone's neighbor order in the result

Why: In a cycle the neighbor loop re-enters dfs on a node whose clone is still being wired; the earlier map.set(orig, copy) makes map.has(orig) true so that call returns the in-progress copy instead of building a second one and recursing again.

Q2 What are the keys of the visited Map?

  1. A Node values (.val)
  2. B Original node object references correct
  3. C Clone references
  4. D A tuple of (original, clone) pairs, with the original side compared by identity

Why: map.set(orig, copy) keys on the original node object, and Map compares object keys by identity — so two distinct originals that happen to share a val still get distinct clones.

Q3 Time complexity?

  1. A O(V)
  2. B O(V + E) correct
  3. C O(V * E)
  4. D O(V^2)

Why: The map.has guard limits object creation to one clone per original (V), and the for (const nb of orig.neighbors) loop walks each stored adjacency entry exactly once (2E for an undirected graph), with O(1) Map operations throughout.

Q4 For a null input, the function returns:

  1. A An empty node { val: null, neighbors: [] } to preserve the deep-copy contract
  2. B null correct
  3. C undefined
  4. D throws

Why: The guard if (!node) return null handles the empty-graph case before any cloning begins.

Q5 Why is a plain visited SET insufficient here, requiring a MAP instead?

  1. A Set.has takes O(n) on objects while Map.has is O(1), so cycles would be too slow with a Set
  2. B You need the original->clone mapping to wire each clone's neighbors to the right clone objects correct
  3. C Set iteration order isn't insertion-preserving, which would scramble the neighbor order in the clones
  4. D A Set can only break cycles for directed graphs; undirected graphs need a Map's bidirectional lookup

Why: A Set only answers 'seen this?'; cloning needs to fetch the EXISTING clone for an already-seen original so neighbors point at shared clones, which requires the value side of a Map.

Q6 Besides breaking cycles, what second problem does the visited Map solve?

  1. A It guarantees the clone's neighbor lists are in the same insertion order as the original
  2. B It ensures a neighbor shared by multiple nodes (e.g. a diamond) is cloned exactly once correct
  3. C It records the depth of each node so the recursion knows when to terminate
  4. D It distinguishes nodes with equal .val by appending a unique tag to each clone

Why: Without the Map, a node reachable via two paths (diamond A->B->D, A->C->D) would be cloned twice, producing two distinct D-copies and a wrong structure.

Q7 Could you solve Clone Graph with BFS instead of DFS?

  1. A No — BFS would clone nodes level-by-level, but cycles span levels and would be cloned twice
  2. B Yes — use a queue plus the same original->clone Map; both traverse every node once correct
  3. C Yes, but the clones must be wired up in a second pass after BFS finishes enumerating all originals
  4. D No — BFS visits each node before its neighbors are cloned, so neighbor pointers would be null

Why: BFS with an explicit queue and the identical visited Map clones correctly and avoids deep recursion; the Map (set-before-enqueue) is what handles cycles in either traversal.

Q8 Why MUST the Map key be the original node OBJECT, not node.val?

  1. A Map.get(val) does linear scan on numeric keys; object keys hash in O(1)
  2. B If two distinct nodes share a val, keying on val would alias them into one clone — wrong graph correct
  3. C Map keys must be reference types — primitives are silently converted to Object wrappers that lose equality
  4. D node.val could be mutated during traversal, invalidating prior Map entries

Why: Map uses identity for object keys, so distinct originals stay distinct even with equal vals; keying on val collapses different nodes when values repeat.
