Coin Change

Fewest coins to make `amount`. Bottom-up dp[a] = min over coins of dp[a - c] + 1. Returns -1 if no combination reaches the amount.

patterns Dynamic Programming 8 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write coinChange(coins, amount) returning the fewest coins that sum to amount, or -1 if impossible. Log coinChange([1, 2, 5], 11).

Expected output: 3

Canonical solution

Bottom-up DP over amounts — try every coin as the last one · O(amount·k) / O(amount) (time / space)

function coinChange(coins, amount) {
  // Infinity = unreachable; any subproblem still Infinity at the end becomes -1.
  const dp = new Array(amount + 1).fill(Infinity);
  // Base case: 0 coins make amount 0 — anchors the recurrence.
  dp[0] = 0;
  // Bottom-up: solve every amount from 1..target, reusing smaller solutions.
  for (let a = 1; a <= amount; a++) {
    for (const c of coins) {
      // Skip coins bigger than current amount; otherwise try using one of c + best for the remainder.
      if (c <= a) dp[a] = Math.min(dp[a], dp[a - c] + 1);
    }
  }
  return dp[amount] === Infinity ? -1 : dp[amount];
}
// Time O(amount * coins.length), Space O(amount)
  • Fill dp with Infinity so any unreachable subproblem stays Infinity and bubbles up to -1.
  • dp[0] = 0 anchors the recurrence — zero coins to make amount 0.
  • Unbounded coin supply means the inner loop reuses dp[a - c] from the SAME iteration (forward fill).

Alternate approaches

BFS layer-by-layer (shortest path) O(amount * coins.length) / O(amount)

Reach for this when the interviewer frames the problem as 'fewest steps' and you want to make the shortest-path lens explicit — treat each remaining sum as a node, coins as edges, and BFS depth IS the coin count. Often beats DP in practice because BFS short-circuits the moment it reaches amount, while bottom-up DP always fills the whole table.

function coinChange(coins, amount) {
  // Zero-amount base case — no coins needed, no BFS layer to run.
  if (amount === 0) return 0;
  // Visited set prevents re-expanding sums; without it BFS would revisit nodes exponentially.
  const visited = new Set([0]);
  let frontier = [0];
  let depth = 0;
  while (frontier.length) {
    depth++;
    const next = [];
    for (const sum of frontier) {
      for (const c of coins) {
        const ns = sum + c;
        // First time we reach `amount` IS the shortest path — BFS guarantees minimum depth.
        if (ns === amount) return depth;
        if (ns < amount && !visited.has(ns)) {
          visited.add(ns);
          next.push(ns);
        }
      }
    }
    frontier = next;
  }
  // Frontier exhausted without hitting amount — unreachable.
  return -1;
}
console.log(coinChange([1, 2, 5], 11));
  • BFS guarantees the first time sum === amount we return is the minimum coin count — that's the shortest-path invariant in disguise.
  • The visited Set is load-bearing: without it the same partial sum gets re-expanded from every path that reaches it, blowing up to exponential work.
  • Often faster than bottom-up DP in practice — BFS exits as soon as it touches amount, while DP fills dp[1..amount] regardless of when the answer is found.

Q1 The bottom-up recurrence for Coin Change is:

  1. A dp[a] = dp[a-1] + 1
  2. B dp[a] = min over coins c of dp[a-c] + 1 correct
  3. C dp[a] = sum over coins of dp[a-c]
  4. D dp[a] = dp[a / 2] + 1

Why: Fixing coin c as the LAST one used leaves the smaller subproblem a-c, so that plan costs dp[a - c] + 1; the min over all coins tries every possible last coin. Summing instead counts the number of ways (that is Coin Change II), it does not minimise.

Q2 Why fill the dp array with Infinity?

  1. A So Math.min(dp[a], cand) returns cand on the first valid coin instead of needing a special initial check
  2. B So unreachable amounts stay Infinity and convert to -1 at the end correct
  3. C So the dp array allocates as a packed Float64Array, which is faster than a sparse holey array
  4. D So dp[a - c] returns Infinity instead of undefined when a - c is out of bounds

Why: Infinity means "no known way yet", so it never wins a Math.min and any amount still Infinity at the end maps to -1. The out-of-bounds worry is moot — the c <= a guard keeps a - c at 0 or above.

Q3 What does dp[0] represent and why is it 0?

  1. A It's a sentinel slot to detect off-by-one errors when the inner loop wraps around
  2. B Zero coins needed to make amount 0 — anchors the recurrence correct
  3. C It holds the smallest coin denomination, used as a tie-breaker in the inner min
  4. D It marks the array's lower bound so dp[a - c] returns 0 when c === a

Why: It is the base case: no coins are needed to make 0. It is the only cell not derived from the recurrence, and every other cell bottoms out here — a coin with c === a reads dp[0] + 1 = 1, which is what makes a single-coin amount come out right.

Q4 Time complexity?

  1. A O(amount)
  2. B O(coins.length)
  3. C O(amount * coins.length) correct
  4. D O(amount^2)

Why: Outer loop runs amount times, inner loop tries every coin — O(amount * coins.length).

Q5 Why does a greedy 'always take the largest coin' strategy fail? Take coins=[1,3,4], amount=6.

  1. A Greedy is too slow
  2. B Greedy picks 4 then 1+1 = 3 coins, but the optimum is 3+3 = 2 coins correct
  3. C Greedy returns -1 incorrectly
  4. D Greedy works fine here; it only fails on large inputs

Why: Committing to the biggest coin first (4) strands you needing 2, costing three coins; DP explores all last-coin choices and finds the 3+3 two-coin optimum.

Q6 What does dp[a] represent in this solution?

  1. A The number of distinct ways to make amount a
  2. B The fewest coins that sum exactly to amount a correct
  3. C Whether amount a is reachable (boolean)
  4. D The largest coin usable for amount a

Why: dp[a] is the minimum coin count for amount a; the answer is dp[amount], or -1 if it stayed Infinity.

Q7 The 'try each coin as the LAST coin used' framing makes each subproblem:

  1. A dp[a + c] — moving forward by one coin, which forces top-down recursion
  2. B dp[a - c], a strictly smaller amount — which is why bottom-up works correct
  3. C dp[c], the cost of making just the last coin's denomination (independent of a)
  4. D dp[a / c], dividing the remaining amount by the coin to skip already-counted multiples

Why: Fixing coin c as the last one leaves the smaller amount a-c, so solving amounts in increasing order guarantees dp[a-c] is already final.

Q8 Coin Change II asks for the NUMBER OF WAYS to make the amount. How does the recurrence change?

  1. A Nothing changes
  2. B You SUM dp[a-c] over coins instead of taking the min, and loop coins on the outside to avoid double-counting correct
  3. C You take the max instead of the min
  4. D You switch from DP to greedy

Why: Counting ways accumulates (sum) rather than optimizing (min); iterating coins outermost counts combinations, not permutations.
