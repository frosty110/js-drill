Construct Tree from Preorder + Inorder

Preorder gives roots in order; inorder splits left/right around each root. Recurse on the two halves, indexing inorder with a Map for O(n).

patterns Trees 9 concept · 1 fill-in · 1 drill

Results carried by this link

Problem

Write buildTree(preorder, inorder) returning the reconstructed binary tree. Log the post-order traversal as a JSON array for preorder=[3,9,20,15,7], inorder=[9,3,15,20,7].

Expected output: [9,15,7,20,3]

Canonical solution

function buildTree(preorder, inorder) {
  // value → inorder index, so each root's split is O(1) instead of O(n).
  const idx = new Map();
  inorder.forEach((v, i) => idx.set(v, i));
  // Single moving pointer — the next preorder element is always the next root.
  let p = 0;
  function build(lo, hi) {
    if (lo > hi) return null;          // empty inorder window
    const val = preorder[p++];
    const node = { val, left: null, right: null };
    const mid = idx.get(val);
    // Left FIRST — preorder consumes the whole left subtree before the right root.
    node.left = build(lo, mid - 1);
    node.right = build(mid + 1, hi);
    return node;
  }
  return build(0, inorder.length - 1);
}
// Time O(n), Space O(n) for the index map + recursion
  • The next unused preorder element is ALWAYS the root of the current inorder window — that is why a single moving pointer p suffices.
  • Build the left subtree before the right: preorder consumes left subtree entirely before the right root appears.
  • Without the inorder→index Map, finding mid costs O(n) per call → O(n^2) overall.

Q5 How do you split inorder into the left and right subtrees once you know the root?

  1. A Split inorder in half by length

  3. C Take the first half of preorder
  4. D Sort inorder and split at the median

Why: Inorder is left-root-right, so the root's position partitions it: inorder[lo..mid-1] is the left subtree and inorder[mid+1..hi] is the right.

Q6 From the inorder index mid and window start lo, the left subtree's size is:

  1. A mid
  2. B mid - lo correct
  3. C hi - mid
  4. D mid + 1

Why: The left subtree spans inorder[lo..mid-1], which is mid - lo elements — this size is what lets a sliced version know where to cut preorder.

Q7 Without the value→index Map, what is the time complexity and why?

  1. A Still O(n), the map only saves memory
  2. B O(n^2), because finding the root's index in inorder is an O(n) linear scan repeated for each of n nodes correct
  3. C O(n log n), from binary searching inorder
  4. D O(log n), the scan is bounded by height

Why: Re-scanning inorder for mid on every recursive call costs O(n) each, and there are n calls, giving O(n^2); the map makes each lookup O(1).

Q8 Why can't preorder alone reconstruct a unique binary tree?

  1. A Preorder records each node twice (once on entry, once on exit) and the duplicates are ambiguous
  2. B Preorder gives the root-first order but not where each subtree ends; inorder supplies the split that resolves the ambiguity correct
  3. C Preorder skips leaf nodes, so a second traversal is needed to recover them
  4. D Preorder works only for BSTs; arbitrary binary trees need a second traversal

Why: Many distinct trees share the same preorder; you need inorder (or another order) to know how the elements partition into left vs right subtrees.

Q9 Why does a single moving pointer p over preorder suffice across all recursive calls?

  1. A The inorder Map records the next-root index, so p is recomputed from idx on entry to each call
  2. B Preorder visits a node then its ENTIRE left subtree before any of the right subtree, so consuming p front-to-back, building left before right, lines up exactly correct
  3. C The recursion uses mid - lo to derive p from the inorder window size at each level
  4. D Preorder and inorder share the same index space, so the inorder window's lo doubles as the preorder pointer

Why: Preorder order is root, all-of-left, all-of-right; building the left subtree fully before the right means p advances through preorder in the exact order the roots appear.
