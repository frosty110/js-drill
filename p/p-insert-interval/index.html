Insert Interval

Insert a new interval into a sorted, non-overlapping list and re-merge. Single pass in three phases: before, overlapping, after. O(n).

Problem

Implement insert(intervals, newInterval) returning the merged list after insertion. Log JSON.stringify(insert([[1,2],[3,5],[6,7],[8,10],[12,16]], [4,8])).

Expected output: [[1,2],[3,10],[12,16]]

Canonical solution

Three-phase linear scan (before / merge / after) · O(n) / O(n) (time / space)

function insert(intervals, newInterval) {
  const res = [];
  let i = 0, n = intervals.length;
  // 1) append intervals strictly BEFORE newInterval
  while (i < n && intervals[i][1] < newInterval[0]) {
    res.push(intervals[i++]);
  }
  // 2) merge any that overlap by expanding newInterval bounds
  while (i < n && intervals[i][0] <= newInterval[1]) {
    newInterval[0] = Math.min(newInterval[0], intervals[i][0]);
    newInterval[1] = Math.max(newInterval[1], intervals[i][1]);
    i++;
  }
  res.push(newInterval);
  // 3) append the rest, all strictly after
  while (i < n) res.push(intervals[i++]);
  return res;
}
// Time O(n), Space O(n) for the output
  • Three-phase walk: BEFORE (end < newStart), OVERLAP (start <= newEnd), AFTER. Each interval is visited once.
  • During overlap, take Math.min of starts and Math.max of ends — newInterval may be entirely contained.
  • Sortedness of the input is the whole reason this runs in O(n). Don't sort again.

Q1 What invariant lets this run in O(n) without sorting?

  1. A newInterval is guaranteed to come last in sort order, so it can be appended in O(1)
  2. B The input list is already sorted and non-overlapping correct
  3. C All interval endpoints are integers, allowing a counting-sort-style bucket pass
  4. D The number of overlaps with newInterval is bounded by O(log n) on average

Why: The input arrives already sorted and non-overlapping, so 'before', 'overlapping' and 'after' are three contiguous runs that one forward-only i can walk — no sort needed.

Q2 How do you decide an interval comes BEFORE newInterval?

  1. A Its start is less than newInterval's start
  2. B Its end is strictly less than newInterval's start correct
  3. C Both its endpoints are less than newInterval's start (otherwise it might overlap)
  4. D Its end is less than or equal to newInterval's start

Why: Strict < because touching at the endpoint should still merge.

Q3 During the overlap phase you update newInterval by:

  1. A Replacing it with the current overlapping interval and continuing
  2. B Taking Math.min of starts and Math.max of ends correct
  3. C Pushing the overlapping interval into res and leaving newInterval unchanged
  4. D Taking the average of starts and ends to produce a centered merged range

Why: newInterval[0] = Math.min(...) and newInterval[1] = Math.max(...) grow the merged range to swallow each overlapper; the absorbed intervals are never pushed themselves — only the expanded newInterval, once, after the loop.

Q4 Why Math.min for the start and Math.max for the end?

  1. A Because the overlapping interval is guaranteed to be entirely INSIDE newInterval, so min/max are identity ops that just defend against bad input
  2. B The overlapping interval may extend newInterval on either side; you must expand, never shrink correct
  3. C Because intervals are sorted by start, so newInterval's start is always the min — Math.min is a no-op but Math.max is needed for the end
  4. D To clamp the merged interval into the convex hull of the two endpoint pairs, which is what min,max computes

Why: An overlapping interval may extend past newInterval on either side, or sit entirely inside it, so the merged range is their union — assigning either endpoint outright could shrink it.

Q5 newInterval partitions the sorted list into how many regions the algorithm handles as separate phases?

  1. A Two — overlapping and non-overlapping (the non-overlapping ones handled together)
  2. B Three — intervals fully before, intervals overlapping, intervals fully after correct
  3. C One — a single merge sweep treating newInterval as just another input
  4. D Four — fully-before, touching-left, engulfed, fully-after

Why: The three phases are: pass through everything ending before newInterval, merge everything overlapping it, then drain everything starting after it.

Q6 Why is this O(n) while Merge Intervals is O(n log n)?

  1. A It uses a faster sort
  2. B The input is already sorted and non-overlapping, so there is no sort — each interval is visited once and the pointer never resets correct
  3. C It skips some intervals entirely
  4. D It uses a heap

Why: The pre-sorted invariant removes the sort; the three while-loops share one monotonically advancing pointer i, so total work is a single O(n) pass.

Q7 Phase 1 uses intervals[i][1] < newInterval[0] (strict <) but phase 2 uses intervals[i][0] <= newInterval[1] (<=). Why the different operators?

  1. A They are interchangeable
  2. B Strict < in phase 1 keeps a touching interval out of 'before' so phase 2 can merge it; <= in phase 2 makes touching count as overlap correct
  3. C Phase 1 should also be <=
  4. D It is a bug

Why: Both operators encode 'touching = overlap': an interval that merely touches newInterval fails the strict phase-1 test and is caught by the inclusive phase-2 test.

Q8 Where is res.push(newInterval) placed, and why does that matter?

  1. A Inside phase 2, once per overlap
  2. B Between phase 2 and phase 3, unconditionally — so the no-overlap case (phase 2 runs zero times) still inserts it correct
  3. C At the very end after phase 3
  4. D Inside phase 1

Why: The push must be unconditional between phases 2 and 3; putting it inside the overlap loop would silently drop newInterval whenever it overlaps nothing.

Q9 Inserting [1,10] into [[2,3],[4,5],[6,7]] returns:

  1. A [[1,10],[2,3],[4,5],[6,7]]
  2. B [[1,10]] — newInterval engulfs all of them, phase 2 absorbs each via min/max correct
  3. C [[2,3],[4,5],[6,7],[1,10]]
  4. D [[1,3],[4,10]]

Why: Each existing interval starts <= 10 so all merge into newInterval; Math.min/Math.max grow it to [1,10], swallowing the whole list into one interval.
