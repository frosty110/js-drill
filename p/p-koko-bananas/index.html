Koko Eating Bananas

Binary search the ANSWER on [1, max(piles)]: find the minimum k such that `canFinish(k)` is true.

patterns Binary Search 9 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write minEatingSpeed(piles, h) returning the minimum k bananas/hour Koko needs to finish all piles in h hours. Log minEatingSpeed([30, 11, 23, 4, 20], 6).

Expected output: 23

Canonical solution

Binary search on the answer (monotone predicate) · O(n log maxPile) / O(1) (time / space)

function minEatingSpeed(piles, h) {
  // Binary-search the ANSWER (speed), not an array index — answer space is [1, max(piles)].
  let l = 1, r = Math.max(...piles);
  const canFinish = (k) => {
    let hours = 0;
    // Ceiling because Koko can't split a pile across hours.
    for (const p of piles) hours += Math.ceil(p / k);
    return hours <= h;
  };
  while (l < r) {
    const m = Math.floor((l + r) / 2);
    if (canFinish(m)) r = m;     // m works — try smaller
    else l = m + 1;              // too slow — must go faster
  }
  return l;
}
// Time O(n log(max(piles))), Space O(1)
  • You're binary-searching the answer space, not an index in piles. The predicate canFinish(k) is monotonic: false for small k, true for large k.
  • Use the half-open pattern while (l < r) with r = m on success and l = m + 1 on failure — converges on the leftmost true.
  • Math.ceil(p / k) is correct: any leftover banana in a pile costs a whole hour.

Alternate approaches

Linear scan (brute force) O(n·max(piles)) / O(1)

The brute force to name before you discard it. Try every speed from 1 up to max(piles) and return the first that finishes in time. Correct but O(n·max(piles)) — untenable when piles can reach 10⁹. Only use this as the stepping-stone that motivates BS-on-the-answer.

function minEatingSpeed(piles, h) {
  const maxP = Math.max(...piles);
  for (let k = 1; k <= maxP; k++) {
    let hours = 0;
    for (const p of piles) hours += Math.ceil(p / k);
    if (hours <= h) return k;
  }
  return maxP;
}
console.log(minEatingSpeed([30, 11, 23, 4, 20], 6));
  • Scanning k from 1 upward hits the minimum feasible speed first because canFinish is monotone — same monotonicity the BS version exploits.
  • The outer loop runs up to max(piles) times; binary search collapses that to log(max(piles)) iterations.
  • State this out loud, then say 'the answer space is monotone — I can binary-search it' to motivate the optimal solution.

Q1 What is being binary-searched here?

  1. A An index into the piles array
  2. B The answer space: candidate eating speeds k from 1..max(piles) correct
  3. C The hours h, looking for the smallest h that admits a feasible k
  4. D The pile sizes after sorting, looking for the median pile

Why: l and r are speeds, not positions — they start at 1 and Math.max(...piles). piles is only ever read inside canFinish, and it never has to be sorted.

Q2 Why does this work — what property must the predicate have?

  1. A It must be O(1) so the inner loop doesn't dominate
  2. B It must be monotonic: once k is fast enough, every larger k also works correct
  3. C It must be symmetric — canFinish(k) === canFinish(max-k+1) — so midpoint reflection is valid
  4. D The piles must be sorted so canFinish can short-circuit on the largest pile first

Why: Eating faster never costs more hours, so canFinish is false for every speed below the answer and true for every speed at or above it. That false-then-true boundary is the same shape sortedness gives plain binary search — canFinish being O(n) costs time but doesn't affect correctness.

Q3 Why Math.ceil(p / k) instead of Math.floor?

  1. A floor would round 1.0 down to 0 due to JS float drift, undercounting hours on exactly-divisible piles
  2. B A partial pile still takes a full hour to finish correct
  3. C ceil matches the C++/Java integer division semantics the problem assumes
  4. D floor would count the FIRST hour of each pile as 0, off-by-one across all piles

Why: Koko can't move to another pile inside the same hour, so the leftovers cost a whole hour: 7 bananas at speed 3 is 3 hours, while Math.floor(7 / 3) would claim 2. Undercounting hours lets a too-slow speed pass — the floor variant returns 3 instead of 4 on [3,6,7,11], h=8.

Q4 Overall time complexity?

  1. A O(n)
  2. B O(n log n)
  3. C O(n * max(piles))
  4. D O(n * log(max(piles))) correct

Why: The loop halves the speed range [1, max(piles)], so it runs about log₂(max(piles)) times — not max(piles) times — and each iteration's canFinish walks all n piles once.

Q5 Why is the search range upper bound max(piles) and not sum(piles)?

  1. A To save memory
  2. B At speed max(piles), even the biggest pile takes exactly 1 hour — no larger speed ever finishes faster, so it is the slowest speed worth considering correct
  3. C Because sum(piles) overflows
  4. D Because the array is sorted

Why: Eating speed is capped meaningfully at the largest pile: any faster still clears that pile in one hour, so max(piles) is the true upper bound.

Q6 The loop uses the half-open form while (l < r) with r = m on success and l = m + 1 on failure. Why not r = m - 1 on success?

  1. A r = m - 1 would make the range [l, m-1) half-open the wrong way — it must be closed on the right
  2. B Because m itself might be the minimum feasible speed; r = m keeps m as a candidate, while r = m - 1 could skip the answer correct
  3. C r = m - 1 paired with while (l < r) can cause r to go below l on small ranges, terminating before convergence
  4. D Because m is computed via floor and is always one less than the true midpoint, so m - 1 double-decrements

Why: We're finding the leftmost true; a feasible m must stay in the range, so we shrink to [l, m], not [l, m-1].

Q7 What does it mean to 'binary search the answer' here, as opposed to ordinary binary search?

  1. A You sort the piles first, then binary search them as the input array
  2. B You search over candidate ANSWERS (eating speeds) using a monotone feasibility predicate, instead of searching for a value inside the input array correct
  3. C You binary search the hours array — bisect on h until the predicate flips
  4. D You binary-search a precomputed hours-per-speed lookup table built in one pass

Why: The 'array' is the implicit conceptual range of speeds 1..max(piles); the predicate canFinish(k) supplies the monotone ordering BS needs.

Q8 If you replaced canFinish to return whether hours < h instead of <= h, what breaks?

  1. A Nothing — the loop converges to the same answer because r = m on success absorbs the off-by-one
  2. B Speeds that finish in exactly h hours would be rejected, so the returned minimum speed would be too large (or no answer found when h is tight) correct
  3. C The returned speed would be too SMALL by exactly 1 — you'd need to add 1 at the end
  4. D The loop would no longer terminate when l + 1 === r

Why: Finishing in exactly h hours is allowed, so the predicate must use <=; using < discards valid speeds and inflates the answer.

Q9 Which OTHER problem uses this identical 'binary search on the answer' template?

  1. A Two Sum — binary search for target - nums[i] in the sorted-array variant
  2. B Capacity To Ship Packages Within D Days — search the answer space of ship capacities with a 'finishes in <= D days' predicate correct
  3. C Merge Intervals — binary search for the insertion point of each new interval
  4. D Search in Rotated Sorted Array — binary search the answer space of pivot positions

Why: Capacity To Ship, Split Array Largest Sum, and Aggressive Cows all share the monotone-predicate-on-the-answer skeleton.
