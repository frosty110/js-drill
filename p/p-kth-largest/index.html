Kth Largest

Easy: sort descending and index k-1. Optimal interview answer: size-K min-heap → O(n log k). See the Implement Min-Heap lesson for the heap primitive.

Problem

Write findKthLargest(nums, k) using the sort approach. Log findKthLargest([3,2,3,1,2,4,5,5,6], 4).

Expected output: 4

Canonical solution

Sort descending, index k-1 · O(n log n) / O(1) (time / space)

// Easy version — sort descending, pick index k - 1.
function findKthLargest(nums, k) {
  // Numeric comparator required — bare .sort() coerces to strings.
  nums.sort((a, b) => b - a);
  // After descending sort, the kth largest sits at index k - 1.
  return nums[k - 1];
}
// Time O(n log n), Space O(1) extra.

Alternate approaches

Min-heap of size k O(N log k) / O(k)

Streaming input, or k << N and you want bounded memory. Pushes/pops cost O(log k) instead of O(log N), and you never have to hold the whole input in memory at once.

class MinHeap {
  constructor() { this.a = []; }
  size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(n) {
    this.a.push(n);
    let i = this.a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.a[p] <= this.a[i]) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0];
    const last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      const n = this.a.length;
      while (true) {
        const l = 2 * i + 1;
        const r = 2 * i + 2;
        let s = i;
        if (l < n && this.a[l] < this.a[s]) s = l;
        if (r < n && this.a[r] < this.a[s]) s = r;
        if (s === i) break;
        [this.a[s], this.a[i]] = [this.a[i], this.a[s]];
        i = s;
      }
    }
    return top;
  }
}
function findKthLargest(nums, k) {
  // Min-heap of size k: root is the smallest of the k largest seen → kth largest.
  const heap = new MinHeap();
  for (const n of nums) {
    if (heap.size() < k) heap.push(n);
    // Beat the worst keeper? Evict it and admit the newcomer.
    else if (n > heap.peek()) { heap.pop(); heap.push(n); }
  }
  return heap.peek();
}
console.log(findKthLargest([3, 2, 3, 1, 2, 4, 5, 5, 6], 4));
  • Heap holds at most k entries — the k LARGEST seen so far; root (peek) is the smallest of those, i.e. the kth largest.
  • Skip the push entirely when n <= heap.peek() once the heap is full — saves a push+pop pair for values that can't make the cut.
  • Generalizes to a streaming KthLargest class: maintain the heap across calls, each add is O(log k).

Quickselect (Lomuto partition) O(N) avg, O(N²) worst / O(1)

When you want sub-log k average time and don't mind the unstable worst case (or are using median-of-medians, which we won't here). The 'staff-level' answer when interviewers push past the heap.

function findKthLargest(nums, k) {
  // (N-k)-th smallest == k-th largest — partition around a pivot and recurse into the side holding the target index.
  const target = nums.length - k;
  const a = nums.slice();
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    // Deterministic mid-pivot — swap to end so Lomuto partition can use the last slot.
    const mid = Math.floor((lo + hi) / 2);
    [a[mid], a[hi]] = [a[hi], a[mid]];
    const pivot = a[hi];
    let store = lo;
    for (let i = lo; i < hi; i++) {
      if (a[i] < pivot) {
        [a[store], a[i]] = [a[i], a[store]];
        store++;
      }
    }
    // Drop the pivot into its final sorted position.
    [a[store], a[hi]] = [a[hi], a[store]];
    if (store === target) return a[store];
    if (store < target) lo = store + 1;
    else hi = store - 1;
  }
  return a[lo];
}
console.log(findKthLargest([3, 2, 3, 1, 2, 4, 5, 5, 6], 4));
  • Reframe: kth largest = (N-k)th smallest. Partition around a pivot; recurse into ONLY the side holding target = N-k, not both.
  • Mid-pivot keeps the snippet deterministic for testing; in interview you'd note Math.random() or median-of-medians to dodge the O(N²) adversarial worst case.
  • After partition, store is the pivot's final sorted index — compare to target and shrink the active window from one side only.

Q1 After nums.sort((a, b) => b - a), where is the kth largest?

  1. A Index k
  2. B Index k - 1 correct
  3. C Index nums.length - k
  4. D Index 0

Why: Descending sort puts the largest at index 0, so rank k lands at index k - 1. Index nums.length - k is the kth largest only after an ASCENDING sort.

Q2 Why pass a comparator instead of bare .sort()?

  1. A Bare .sort() skips negative numbers because - is treated as a sign character
  2. B Default sort coerces to strings — [10, 2].sort() gives [10, 2] not [2, 10] correct
  3. C Without a comparator, V8's Timsort falls back to O(n^2) bubble sort
  4. D Bare .sort() is stable only when a comparator is provided

Why: With no comparator .sort() compares the string forms, so "10" < "2" and [10, 2].sort() stays [10, 2]; (a, b) => b - a is what makes the ordering numeric.

Q3 Time complexity of the sort-based solution?

  1. A O(n)
  2. B O(n log n) correct
  3. C O(n log k)
  4. D O(n^2)

Why: The only real work is nums.sort(...) — a comparison sort is O(n log n) — and the nums[k - 1] read after it is O(1). O(n log k) belongs to the size-k heap variant.

Q4 For very large n where k is small, the best asymptotic approach is:

  1. A Sort the whole array — O(n log n)
  2. B Size-k min-heap — O(n log k) correct
  3. C Bubble sort — O(n^2)
  4. D Linear scan — O(n)

Why: Capping the heap at k makes each of the n elements cost O(log k) instead of O(log n); a plain linear scan is O(n) but with O(1) state it can only find the max, not an arbitrary kth rank.

Q5 To find the kth LARGEST with a size-k heap, which heap type and why?

  1. A A max-heap, so the root is the largest element
  2. B A min-heap, so the root is the smallest of the k kept — anything smaller gets evicted, leaving the k largest correct
  3. C Either works identically
  4. D A max-heap, because eviction from a min-heap is O(n) instead of O(log k)

Why: A min-heap of size k keeps the root as the smallest survivor; pushing then popping evicts the smallest, so the k LARGEST stay and the root is exactly the kth largest.

Q6 In the size-k min-heap, what does the root (peek) equal after processing all of nums?

  1. A The largest element
  2. B The smallest element overall
  3. C The kth largest element correct
  4. D The median

Why: The heap holds the k largest values; its minimum (the root) is the smallest of those k, which is the kth largest overall.

Q7 Why keep the heap capped at size k (pop when size exceeds k) instead of pushing everything?

  1. A To save a few bytes only
  2. B So each push/pop is O(log k) and space stays O(k) — that is what turns O(n log n) into O(n log k) correct
  3. C Because heaps cannot hold more than k items
  4. D It changes the answer

Why: Capping at k bounds every heap operation to O(log k) and space to O(k); the size-k invariant is exactly what beats a full sort when k is small.

Q8 Which alternative achieves O(n) average time for kth largest?

  1. A Quickselect (partition around a pivot, recurse on the side holding index k-1) correct
  2. B Merge sort
  3. C A balanced BST
  4. D Two nested loops

Why: Quickselect partitions like quicksort but recurses into only the side containing the target rank — O(n) average, though O(n^2) worst case.

Q9 For a streaming KthLargest class where numbers arrive one at a time and add must return the current kth largest, the natural structure is:

  1. A Re-sort the whole stream on every add
  2. B A persistent size-k min-heap — each add pushes, pops if over k, then returns the root in O(log k) correct
  3. C Quickselect on every add
  4. D A plain array with linear scan each add

Why: A maintained size-k min-heap makes each add O(log k) and the kth largest is always the root — sorting or quickselect would redo O(n) work per add.
