Longest Consecutive Sequence

Find the length of the longest run of consecutive integers in an unsorted array, in O(n). Trick: dump into a Set and only start counting from values whose predecessor is missing.

Problem

Write longestConsecutive(nums) returning the length of the longest run of consecutive integers, in O(n). Log longestConsecutive([100, 4, 200, 1, 3, 2]).

Expected output: 4

Canonical solution

function longestConsecutive(nums) {
  // Dedup via Set so each value is walked at most once.
  const set = new Set(nums);
  let best = 0;
  for (const x of set) {
    if (set.has(x - 1)) continue;        // only start runs from a sequence head
    let len = 1;
    // Walk forward as far as the consecutive chain extends.
    while (set.has(x + len)) len++;
    best = Math.max(best, len);
  }
  return best;
}
// Time O(n) amortized — each value enters the inner while loop at most once.
// Space O(n) for the set.
  • The if (set.has(x - 1)) continue guard is what makes this O(n) — without it you'd re-walk runs.
  • Iterating the Set (not the array) avoids redundant work on duplicates.
  • Empty input is a base case — best starts at 0 and the loop is a no-op.

Alternate approaches

Sort + linear scan O(n log n) / O(n)

Reach for this when you want the simplest code and O(n log n) is acceptable, or when the interviewer asks for a solution that avoids the Set's O(n) extra space (a sort-in-place variant would use O(log n) stack space). After deduplication and sorting, consecutive values are adjacent.

function longestConsecutive(nums) {
  if (nums.length === 0) return 0;
  // Dedup via Set, then sort numerically — duplicates would cause false run-breaks otherwise.
  const sorted = [...new Set(nums)].sort((a, b) => a - b);
  let best = 1;
  let len = 1;
  for (let i = 1; i < sorted.length; i++) {
    if (sorted[i] === sorted[i - 1] + 1) {
      len++;
      best = Math.max(best, len);
    } else {
      len = 1;
    }
  }
  return best;
}
console.log(longestConsecutive([100, 4, 200, 1, 3, 2]));
  • Sort requires a numeric comparator (a,b)=>a-b; default lexicographic sort mis-orders [1,10,2].
  • Dedup before sorting to prevent a duplicate from looking like a gap-reset mid-run.
  • O(n log n) vs O(n) amortized — correct but slower; worth knowing as the 'obvious' solution to name first.

Q1 Why skip values where x - 1 is also in the set?

  1. A Those values were already counted backward when the run's tail was processed
  2. B Those are mid-run; counting only from sequence heads bounds total work to O(n) correct
  3. C x - 1 indicates a duplicate of an earlier element with a stale insertion order
  4. D Set iteration visits ascending values, so x - 1 having been seen means we already covered x

Q2 Overall time complexity?

  1. A O(n log n)
  2. B O(n) amortized correct
  3. C O(n^2)
  4. D O(n sqrt n)

Why: Each value is touched at most twice — once as a head, once by the inner while loop.

Q3 Why iterate the Set instead of the original array?

  1. A Set iteration triggers a fresh hash on each entry, refreshing the O(1) lookup constant
  2. B Skip duplicates so the head-check guard does its job correct
  3. C Array iteration in V8 holds a copy-on-write reference that breaks once the Set is also referencing the same backing store
  4. D Sets iterate in ascending value order, so we hit run heads before mid-run values

Q4 For [100, 4, 200, 1, 3, 2] the answer is:

  1. A 3
  2. B 4 correct
  3. C 5
  4. D 6

Why: The run 1,2,3,4 has length 4. 100 and 200 are isolated runs of length 1.

Q5 Without the if (set.has(x - 1)) continue head-guard, what is the worst-case time complexity?

  1. A Still O(n)
  2. B O(n²) — every element starts its own forward walk, re-counting the same run repeatedly correct
  3. C O(n log n)
  4. D O(1)

Why: Without the guard each member of a length-k run triggers a walk of up to k steps, so a single long run alone costs O(k²), degrading the whole algorithm to O(n²).

Q6 What is the FIRST step of the algorithm and why?

  1. A Sort the array so consecutive values are adjacent before counting runs
  2. B Dump nums into a Set — deduplicates AND gives O(1) predecessor/successor membership checks correct
  3. C Find the minimum value so the forward walk knows where to start
  4. D Build a Map of value → original index so we can reconstruct the longest run's positions

Why: The Set both collapses duplicates (so they don't waste iterations) and provides the O(1) has lookups the head-check and forward-walk both depend on.

Q7 Why does the inner while loop NOT make the algorithm O(n²) overall?

  1. A The while loop runs at most O(log n) times per outer step, giving O(n log n) overall
  2. B Each value is entered by an inner while at most once across the whole run, so total inner work is bounded by n correct
  3. C V8 inlines tight while loops so they execute in constant time regardless of iteration count
  4. D The while loop is bounded by the largest gap in the array, which is a constant for typical inputs

Why: Only run-heads trigger the inner walk, and that walk visits each successor exactly once over the entire algorithm — total work is amortized O(n), not O(n) per element.

Q8 Compared to this O(n) Set solution, the sort-then-scan approach is:

  1. A Faster, at O(log n)
  2. B O(n log n) — correct but slower, dominated by the sort correct
  3. C O(n²)
  4. D Also O(n)

Why: Sorting brings consecutive values adjacent so a linear scan can count runs, but the sort itself costs O(n log n), making it slower than the Set approach.
