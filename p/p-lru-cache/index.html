LRU Cache

Least Recently Used cache with O(1) get and put. JS Map preserves INSERTION order — delete+re-set on every hit promotes to most-recent end; the first key is the LRU evict target.

Problem

Implement LRUCache(capacity) with O(1) get (returns value or -1) and put. Run capacity-2: put(1,1), put(2,2), get(1), put(3,3), get(2), put(4,4), get(1), get(3), get(4). Logs: 1, -1, -1, 3, 4.

Expected output: 1 -1 -1 3 4

Canonical solution

Insertion-ordered Map as hash + recency list · O(1) / O(capacity) (time / space)

class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    // JS Map preserves INSERTION order — leverage that to skip a doubly-linked list.
    this.map = new Map();
  }
  get(key) {
    if (!this.map.has(key)) return -1;
    const v = this.map.get(key);
    // Delete + re-set bumps key to the back (most-recent end). Skip this and it becomes FIFO.
    this.map.delete(key);
    this.map.set(key, v);
    return v;
  }
  put(key, value) {
    if (this.map.has(key)) {
      this.map.delete(key);
    } else if (this.map.size >= this.capacity) {
      // First key in iteration order = LRU. Evict the front.
      const oldest = this.map.keys().next().value;
      this.map.delete(oldest);
    }
    this.map.set(key, value);
  }
}
// Time O(1) per op, Space O(capacity)
  • Map preserves insertion order — leverage that to skip a doubly-linked list.
  • On HIT, delete + set to move the key to the end. Forgetting this turns the cache into FIFO.
  • Evict from the FRONT via this.map.keys().next().value — that key is the oldest.
  • Time O(1) amortized per op, Space O(capacity).

Alternate approaches

Doubly-linked list + HashMap (language-agnostic classic) O(1) / O(capacity)

This is the canonical interview answer in Java, C++, or Python — languages without an ordered map. Also reach for it if the interviewer explicitly asks for the 'classic' implementation or asks you to avoid relying on Map insertion order. Sentinel head/tail nodes eliminate all null-pointer edge cases in the link/unlink helpers.

class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map(); // key -> DLL node
    // Sentinel dummy nodes — head.next = LRU, tail.prev = MRU
    this.head = { key: null, val: null, prev: null, next: null };
    this.tail = { key: null, val: null, prev: null, next: null };
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }
  _remove(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }
  _insertBack(node) {
    node.prev = this.tail.prev;
    node.next = this.tail;
    this.tail.prev.next = node;
    this.tail.prev = node;
  }
  get(key) {
    if (!this.map.has(key)) return -1;
    const node = this.map.get(key);
    this._remove(node);
    this._insertBack(node);
    return node.val;
  }
  put(key, value) {
    if (this.map.has(key)) {
      const node = this.map.get(key);
      node.val = value;
      this._remove(node);
      this._insertBack(node);
    } else {
      if (this.map.size >= this.capacity) {
        const lru = this.head.next; // oldest
        this._remove(lru);
        this.map.delete(lru.key);
      }
      const node = { key, val: value, prev: null, next: null };
      this._insertBack(node);
      this.map.set(key, node);
    }
  }
}

  • Sentinel dummy head/tail nodes mean _remove and _insertBack never handle null neighbors — no edge-case checks needed inside those helpers.
  • HashMap stores key → DLL node so O(1) lookup → O(1) move-to-back on both get and put, without scanning the list.
  • Eviction is O(1): head.next is always the LRU node; unlink it and delete its key from the map.

Q1 Why use a Map instead of a plain object for the LRU store?

  1. A Maps allow non-string keys, which the LRU spec requires
  2. B Maps preserve insertion order — recency tracking for free correct
  3. C Object key order is undefined, so eviction would be non-deterministic
  4. D Map.delete is O(1) but object property deletion is O(n) due to deoptimization

Why: Eviction reads this.map.keys().next().value, which only means 'least recently used' because delete + set re-inserts a touched key at the end. An object's key order isn't undefined — it's worse for this: integer-like keys iterate in ascending numeric order regardless of insertion, so numeric cache keys would evict by value.

Q2 On a cache HIT, what must get do?

  1. A Return the value — recency is only updated by put
  2. B Return the value AND delete+re-set the key to mark it most recent correct
  3. C Increment a per-key access counter and compare on eviction
  4. D Swap the hit key with the back key, an O(1) reorder

Why: this.map.delete(key) then this.map.set(key, v) is what moves the key to the back of the iteration order. Drop those two lines and reads stop counting as uses — the cache silently becomes FIFO and evicts a key you just read.

Q3 When the cache is at capacity, which key do we evict?

  1. A A random key
  2. B The most recently used (back of the map)
  3. C The least recently used (front of the map) correct
  4. D The smallest key

Why: Every hit and every write re-inserts its key at the back, so whatever is still at the front was touched longest ago — this.map.keys().next().value reads it without iterating the rest.

Q4 Time complexity of get and put?

  1. A O(log n) — eviction needs a balanced tree by access time
  2. B O(n) — finding the LRU requires scanning all entries
  3. C O(1) amortized correct
  4. D O(1) for get, O(n) for put because eviction must scan for the oldest

Why: Each op is a fixed number of has / get / delete / set calls plus at most one keys().next() — nothing walks the cache, so eviction never costs O(n). 'Amortized' is the honest qualifier because hash tables occasionally rehash on growth.
