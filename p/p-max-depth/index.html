Max Depth of Tree

Depth of a node = 1 + the deeper of its two children. Null subtree contributes 0.

patterns Trees 8 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write maxDepth(root) returning the height of a binary tree. Log maxDepth(root) for the tree [3, 9, 20, null, null, 15, 7].

Expected output: 3

Canonical solution

Post-order DFS (1 + the deeper subtree) · O(n) / O(h) (time / space)

function maxDepth(root) {
  // Null contributes 0 depth — the +1 comes from the parent above.
  if (!root) return 0;
  // Deeper of the two subtrees, plus 1 for the current node.
  return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
}
// Time O(n), Space O(h) for recursion stack
  • Base case must return 0 for null — otherwise you would over-count by 1 at every leaf.
  • Use Math.max of the two recursive calls, then add 1 for the current node.
  • Space is O(h) where h is the tree height — O(n) worst case for a skewed tree, O(log n) for balanced.

Alternate approaches

Iterative BFS (level count) O(n) / O(w)

Switch to this when the tree could be adversarially skewed and big enough to blow the recursion stack (~10k+ deep in V8). Also the right move if the interviewer asks for an explicit iterative solution or you're already standing up a queue for related level-order work.

function maxDepth(root) {
  // Empty tree → 0; nothing to traverse.
  if (!root) return 0;
  // Queue holds the current level; depth ticks once per level drained.
  let queue = [root];
  let depth = 0;
  while (queue.length) {
    // Snapshot this level's nodes; the next level builds into `next`.
    const next = [];
    for (const node of queue) {
      if (node.left)  next.push(node.left);
      if (node.right) next.push(node.right);
    }
    queue = next;
    depth++;
  }
  return depth;
}
const root = { val: 3, left: { val: 9, left: null, right: null }, right: { val: 20, left: { val: 15, left: null, right: null }, right: { val: 7, left: null, right: null } } };
console.log(maxDepth(root));
  • One outer iteration per level → depth = number of times the queue drains. No per-node depth bookkeeping needed.
  • Build the next level into a fresh array instead of shift()-ing the queue — shift() is O(n) on a JS array, so the array-swap pattern keeps the loop O(n) total.
  • Space is O(w) where w is the max level width. For a balanced tree that's O(n/2) at the bottom level — heavier than recursion's O(log n) average, but bounded by tree shape, not call-stack ceiling.

Q1 Base case return value for a null node?

  1. A 0 correct
  2. B 1
  3. C -1
  4. D null

Why: A missing child contributes zero depth; the +1 comes from the current node above it.

Q2 Time complexity?

  1. A O(log n)
  2. B O(n) correct
  3. C O(n log n)
  4. D O(n^2)

Why: Every node is visited exactly once.

Q3 Space complexity (recursion stack)?

  1. A O(1)
  2. B O(h) where h is tree height correct
  3. C Always O(log n)
  4. D O(n^2)

Why: The only extra memory is the call stack, which holds one frame per level of the current root-to-node path. Always O(log n) is true for a balanced tree only — a skewed chain has h = n.

Q4 Why 1 + Math.max(...) rather than Math.max(1 + ..., 1 + ...)?

  1. A Distributing the +1 inside changes the precedence so the result is off by one
  2. B They produce different answers because Math.max short-circuits on the smaller branch
  3. C Both work, the first is cleaner correct
  4. D The inner form forces eager evaluation of both branches, doubling the recursion cost

Why: Adding 1 shifts both arguments equally, so Math.max(1 + a, 1 + b) is exactly 1 + Math.max(a, b). Both recursive calls run either way — Math.max takes evaluated arguments, it can't short-circuit — so this is purely readability.

Q5 Max-depth is naturally a DFS (post-order) computation. Why post-order specifically?

  1. A Post-order is the only DFS order that visits each node exactly once on a binary tree
  2. B A node's depth needs BOTH children's depths computed first, then combines them — that bottom-up order IS post-order correct
  3. C Pre-order would over-count by 1 at every leaf because it adds before recursing
  4. D Post-order keeps the recursion-stack frames in left-then-right order, matching Math.max's argument evaluation

Why: You can't compute 1 + max(left, right) until you have the subtree results, so the work happens on the way back up — the defining trait of post-order DFS.

Q6 You could also solve max-depth with BFS. How does the BFS version compute the answer?

  1. A It returns the queue's maximum size during traversal, which equals the deepest level's width
  2. B It counts how many levels the queue-based level-order loop processes correct
  3. C It tracks the last node enqueued and returns its index in the level-order array
  4. D It runs until the queue is empty and returns the total number of enqueue operations

Why: BFS processes the tree level by level; the number of levels it drains equals the max depth.

Q7 For a left-skewed tree of n nodes (a straight chain), the DFS recursion stack space is:

  1. A O(1)
  2. B O(log n)
  3. C O(n) — the chain forces recursion depth equal to node count correct
  4. D O(n^2)

Why: Space is O(h); a skewed tree has h = n, so the worst-case stack depth is O(n), not O(log n).

Q8 Why Math.max of the two subtrees rather than Math.min?

  1. A Math.min would return 0 whenever one child is null, collapsing the depth to 1 for every internal node
  2. B Depth is the length of the LONGEST root-to-leaf path, so we keep the deeper subtree correct
  3. C Math.min ignores null subtrees by default, which would skip whole branches of the tree
  4. D min is used for the related minDepth problem with no extra care needed

Why: Maximum depth follows the longest path; min would compute a different (and trickier — null children must be excluded) quantity.
