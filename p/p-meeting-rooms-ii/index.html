Meeting Rooms II

Minimum rooms = max simultaneous meetings. Sort starts and ends separately, then sweep with two pointers — a meeting reuses a room iff its start is at or after the next ending. O(n log n).

Problem

Implement minMeetingRooms(intervals) returning the minimum number of rooms. Log it for [[0,30],[5,10],[15,20]] then [[7,10],[2,4]].

Expected output: 2 1

Canonical solution

Sorted start/end sweep (peak concurrency) · O(n log n) / O(n) (time / space)

function minMeetingRooms(intervals) {
  const n = intervals.length;
  if (n === 0) return 0;
  // Decouple starts and ends — only the event timeline matters, not which start pairs with which end.
  const starts = intervals.map(x => x[0]).sort((a, b) => a - b);
  const ends   = intervals.map(x => x[1]).sort((a, b) => a - b);
  let rooms = 0, used = 0, e = 0;
  for (let s = 0; s < n; s++) {
    // Strict < — a start equal to an end can reuse the freed room.
    if (starts[s] < ends[e]) {
      used++;
      rooms = Math.max(rooms, used);
    } else {
      e++;
    }
  }
  return rooms;
}
// Time O(n log n), Space O(n)
  • The starts/ends arrays are decoupled — pairing is irrelevant; only the timeline of events matters.
  • Strict <: a meeting starting exactly when another ends can reuse the room.
  • Equivalent min-heap solution: push end times, pop when the next start is ≥ heap top — same O(n log n).

Alternate approaches

Min-heap of end times O(n log n) / O(n)

Reach for this when the interviewer asks which room each meeting goes in, or when the greedy decoupled-sort feels unintuitive. Each heap entry represents one occupied room; the heap root is the soonest-to-free room. Generalizes cleanly to 'assign meeting → room ID' variants.

function minMeetingRooms(intervals) {
  if (intervals.length === 0) return 0;
  // Sort by start time so we process meetings in chronological order.
  const sorted = intervals.slice().sort((a, b) => a[0] - b[0]);
  // Min-heap of end times (smallest end = soonest freed room at the top).
  // JS has no built-in heap; simulate with a sorted array for correctness.
  const heap = [];
  const heapPush = (v) => { heap.push(v); heap.sort((a, b) => a - b); };
  const heapPop  = ()  => heap.shift();
  for (const [start, end] of sorted) {
    if (heap.length > 0 && start >= heap[0]) {
      // Earliest-ending meeting has freed its room — reuse it.
      heapPop();
    }
    heapPush(end);
  }
  return heap.length;
}
console.log(minMeetingRooms([[0,30],[5,10],[15,20]]));
console.log(minMeetingRooms([[7,10],[2,4]]));
  • Heap size at any point = rooms currently occupied; final size = peak rooms needed.
  • Pop before push when reusing: if the new start is >= the earliest end, one room has freed up.
  • In production JS use a proper MinHeap class — the sorted-array simulation is O(n log n) amortized but with high constants.

Q1 Why can starts and ends be sorted independently?

  1. A Sorting each separately is twice as fast as one combined sort by pair (since each sub-array is half the comparison work)
  2. B We only need the timeline of events, not which start pairs with which end correct
  3. C Independent sorts allow the two pointers to advance simultaneously instead of sequentially, halving wall-clock time
  4. D Because pairing intervals at sort time would require an O(n log n) stable sort, but two unstable sorts suffice

Why: Rooms in use is a property of the event timeline — how many starts precede the next end — so which start belongs to which end never enters the count.

Q2 When starts[s] < ends[e], what happens?

  1. A A meeting ends and we decrement used — a freed room becomes available
  2. B A new meeting begins before any current one ends — we need an additional room correct
  3. C We skip the current start because no end has yet been reached on the timeline
  4. D We pair starts[s] with ends[e] and remove both pointers' entries from consideration

Why: ends[e] is the earliest end not yet used to free a room, so a start before it means nothing has come free — used++ and rooms takes the new max; a room is freed in the else branch, where e++ consumes an end event.

Q3 Why is the comparison < and not <=?

  1. A <= would skip starts that exactly match an end, missing them from the sweep entirely
  2. B If a meeting starts exactly when one ends, the room can be reused — no new room needed correct
  3. C <= would make e advance past s and cause ends[e] to read out of bounds
  4. D Because integer endpoints in floating-point JS Numbers can compare unreliably at ===, < is the safer test

Why: Endpoints are half-open here: a meeting starting exactly when another ends can reuse that room, so that case must fall through to the else and advance e instead of allocating.

Q4 Overall time complexity?

  1. A O(n)
  2. B O(n log n) correct
  3. C O(n^2)
  4. D O(n + max-endpoint-value)

Why: Sorting dominates; the sweep is linear.

Q5 The minimum number of rooms equals:

  1. A The total number of meetings
  2. B The maximum number of meetings overlapping at any single moment (peak concurrency) correct
  3. C The number of distinct start times
  4. D The longest meeting's duration

Why: You only need as many rooms as the busiest instant requires; reframing 'min rooms' as 'peak concurrency' is the core unlock.

Q6 In the min-heap approach, what do you store in the heap and what does its size represent?

  1. A Start times; size = number of meetings seen
  2. B End times of in-progress meetings; the heap size at any point = rooms currently in use correct
  3. C Meeting durations; size = total rooms ever opened
  4. D Room IDs; size = number of distinct starts

Why: Each live meeting contributes its end time to the heap; the heap's size is exactly the count of rooms occupied right now, and its peak is the answer.

Q7 For the min-heap approach, why sort the meetings by start first?

  1. A To make the heap smaller
  2. B So you process meetings in time order — when a new one starts you can compare its start to the earliest end (heap root) to decide reuse vs new room correct
  3. C Sorting by start is optional
  4. D To break ties by duration

Why: Processing in start order lets each new meeting check the smallest end time (heap root): if start >= that end, pop and reuse; otherwise push a new room.

Q8 In the heap approach, when a new meeting's start is >= the smallest end on the heap, you:

  1. A Push the new end and open another room
  2. B Pop the finished meeting's end and push the new one — the room is reused, heap size unchanged correct
  3. C Do nothing
  4. D Clear the whole heap

Why: The earliest-ending meeting has freed its room, so you pop it and push the new end — reuse keeps the room count flat instead of growing it.

Q9 In the two-pointer version, why can starts and ends be sorted as separate arrays (pairing discarded)?

  1. A It is a coincidence that works only on the examples
  2. B Concurrency only depends on how many starts precede the next end on the timeline, not on which start pairs with which end correct
  3. C JavaScript requires decoupled arrays
  4. D To save memory

Why: Peak concurrency is a property of the event timeline; we only need to know that *some* meeting ended to free a room, never which specific one — so pairing is irrelevant.
