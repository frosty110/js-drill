Merge Intervals

Sort by start, then sweep once: extend the last merged interval if the next overlaps; otherwise start a new one. O(n log n) sort + O(n) sweep.

Problem

Implement merge(intervals) that returns merged intervals (touching = overlap). Log JSON.stringify(merge([[1,4],[4,5]])).

Expected output: [[1,5]]

Canonical solution

Sort by start, then linear sweep · O(n log n) / O(n) (time / space)

function merge(intervals) {
  if (intervals.length === 0) return [];
  // Sort by start — after this, each interval only needs to compare to the LAST merged one.
  intervals.sort((a, b) => a[0] - b[0]);
  const res = [intervals[0]];
  for (let i = 1; i < intervals.length; i++) {
    const last = res[res.length - 1];
    const cur = intervals[i];
    // Touching counts as overlap (<= not <); use Math.max in case cur is fully inside last.
    if (cur[0] <= last[1]) {
      last[1] = Math.max(last[1], cur[1]);
    } else {
      res.push(cur);
    }
  }
  return res;
}
// merge([[1,3],[2,6],[8,10],[15,18]]) -> [[1,6],[8,10],[15,18]]
// Time O(n log n), Space O(n)
  • Sort by START. After sorting, compare a candidate only against the LAST merged interval.
  • Touching intervals overlap with <=; use < if the problem says strictly disjoint.
  • Take Math.max of ends — the next interval may be fully contained; you must not shrink the run.

Alternate approaches

Union-Find (DSU) on overlapping intervals O(n² α(n)) / O(n)

Reach for this when the problem morphs into 'add an interval and re-merge' (Insert Interval, dynamic calendar) or when intervals arrive as a stream and you need to keep merging incrementally without re-sorting. Sort+sweep is one-shot — DSU gives you a structure that absorbs new overlaps in near-constant amortized time per union.

function merge(intervals) {
  const n = intervals.length;
  if (n === 0) return [];
  // DSU: parent[i] is the root of interval i's merged component.
  const parent = Array.from({length: n}, (_, i) => i);
  function find(x) {
    while (parent[x] !== x) { parent[x] = parent[parent[x]]; x = parent[x]; }
    return x;
  }
  function union(x, y) { parent[find(x)] = find(y); }
  // Pairwise overlap check — union every overlapping pair into one component.
  for (let i = 0; i < n; i++) {
    for (let j = i + 1; j < n; j++) {
      const a = intervals[i], b = intervals[j];
      if (a[0] <= b[1] && b[0] <= a[1]) union(i, j);
    }
  }
  // Collapse each component to one [min-start, max-end] interval.
  const groups = new Map();
  for (let i = 0; i < n; i++) {
    const r = find(i);
    const iv = intervals[i];
    if (!groups.has(r)) groups.set(r, [iv[0], iv[1]]);
    else {
      const g = groups.get(r);
      g[0] = Math.min(g[0], iv[0]);
      g[1] = Math.max(g[1], iv[1]);
    }
  }
  return [...groups.values()].sort((a, b) => a[0] - b[0]);
}
console.log(JSON.stringify(merge([[1,4],[4,5]])));
  • Two intervals [a0,a1] and [b0,b1] overlap iff a0 <= b1 AND b0 <= a1 — the classic 'one starts before the other ends, both ways' test.
  • Path compression in find keeps the amortized cost per union near-constant; the O(n²) bound is from the pairwise overlap scan, not the DSU itself.
  • DSU shines on the Insert Interval / dynamic-calendar followup: incoming intervals just union with whatever they overlap, no re-sort needed.

Q1 Why sort by start before merging?

  1. A So the output is automatically returned in sorted order, satisfying the spec without a final sort pass
  2. B Lets us compare each interval to only the last merged one — one pass suffices correct
  3. C Sorting compacts the array in memory, eliminating cache misses on the sweep
  4. D So binary search can locate the merge target in O(log n) instead of O(n)

Q2 Overall time complexity?

  1. A O(n)
  2. B O(n log n) correct
  3. C O(n^2)
  4. D O(n + k log k) where k = number of merged runs

Q3 When merging, why use Math.max(last[1], cur[1])?

  1. A Because last[1] is read from a shared reference and could mutate during the iteration; Math.max snapshots it
  2. B cur may end before last — taking the max prevents shrinking the run correct
  3. C Math.max is required to extend the array correctly because JS array indexing rounds towards zero
  4. D Because sorting only orders starts, not ends, so cur[1] might be larger and Math.max picks it

Q4 Should touching intervals like [1,4] and [4,5] merge?

  1. A Always — they share an endpoint
  2. B Never — disjoint endpoints means disjoint intervals
  3. C Only when the problem says so; check <= vs < correct
  4. D Only when sorting by end (not start) — because end-sort places them adjacent

Q5 Which key do you sort by, and why that one?

  1. A By end — so the longest intervals come first
  2. B By start — once starts are ascending, any overlap must touch the most recently merged interval, so one pass suffices correct
  3. C By interval width
  4. D Either start or end works the same

Why: Sorting by start guarantees later intervals can only overlap the last merged run (their start is >= everything before), which is what collapses the problem to a single sweep.

Q6 After sorting by start, the overlap test for the current interval vs the last merged one is:

  1. A cur.start <= last.end correct
  2. B cur.end <= last.start
  3. C cur.start >= last.end
  4. D cur.end >= last.end

Why: Since starts are sorted, cur.start is already >= last.start; they overlap exactly when cur begins at or before last ends, i.e. cur.start <= last.end.

Q7 Why is one forward pass enough — never looking back at earlier merged intervals?

  1. A Because the array is short
  2. B Sorted starts mean every future interval starts at or after the current one, so it can never reach back across a gap into an older run correct
  3. C Because intervals never overlap
  4. D Because Math.max handles it

Why: Ascending starts give a no-look-back invariant: once a gap closes a run, no later interval can start before that gap, so earlier runs are final — that is why the sweep is O(n).

Q8 What guards against crashing on an empty input []?

  1. A The sort call
  2. B An up-front if (intervals.length === 0) return [] — otherwise res = [intervals[0]] seeds with undefined correct
  3. C Math.max
  4. D Nothing is needed

Why: Without the guard, seeding res = [intervals[0]] on an empty array yields [undefined] and silently returns garbage; the length check is the cheap fix.
