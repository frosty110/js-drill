Merge K Sorted Lists

Pairwise divide-and-conquer: merge lists in pairs, then pairs of pairs, until one remains. Each level merges N total nodes; log k levels gives O(N log k).

Problem

Write mergeKLists(lists) using pairwise divide-and-conquer with a mergeTwo helper. Use the toList/toArr helpers. Log JSON.stringify(toArr(mergeKLists([toList([1,4,5]), toList([1,3,4]), toList([2,6])]))).

Expected output: [1,1,2,3,4,4,5,6]

Canonical solution

Pairwise divide-and-conquer over mergeTwo (dummy head) · O(N log k) / O(1) (time / space)

function mergeTwo(a, b) {
  // Dummy sentinel — first append doesn't need a special case.
  const dummy = { next: null };
  let tail = dummy;
  while (a && b) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else { tail.next = b; b = b.next; }
    tail = tail.next;
  }
  // Attach whichever list still has nodes — it's already sorted.
  tail.next = a || b;
  return dummy.next;
}
function mergeKLists(lists) {
  if (lists.length === 0) return null;
  // Pair-merge each round → log k rounds, N work per round = O(N log k).
  while (lists.length > 1) {
    const merged = [];
    for (let i = 0; i < lists.length; i += 2) {
      // Odd-length round: last list pairs with null — mergeTwo handles it.
      merged.push(mergeTwo(lists[i], lists[i + 1] || null));
    }
    lists = merged;
  }
  return lists[0];
}
// Time O(N log k), Space O(1) extra
  • Pairwise merge beats naive merge-into-accumulator: that approach is O(N*k), this one is O(N log k).
  • Use a dummy head in mergeTwo so you never special-case the first append.
  • Attach the trailing tail with tail.next = a || b — the surviving list is already sorted.
  • A min-heap of (val, listIndex) also achieves O(N log k); pairwise merge avoids importing a heap.

Alternate approaches

Min-heap (k-way merge) O(N log k) / O(k)

If your language ships a heap (Python heapq, Java PriorityQueue), prefer this — each node moves exactly once and the constant factor is lower than pairwise. In JS the heap is a ~25-line detour, so pairwise usually wins for the interview.

class MinHeap {
  constructor() { this.a = []; }
  size() { return this.a.length; }
  push(n) {
    this.a.push(n);
    let i = this.a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.a[p].val <= this.a[i].val) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0];
    const last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      const n = this.a.length;
      while (true) {
        const l = 2 * i + 1;
        const r = 2 * i + 2;
        let s = i;
        if (l < n && this.a[l].val < this.a[s].val) s = l;
        if (r < n && this.a[r].val < this.a[s].val) s = r;
        if (s === i) break;
        [this.a[s], this.a[i]] = [this.a[i], this.a[s]];
        i = s;
      }
    }
    return top;
  }
}
function mergeKLists(lists) {
  // Seed: push each non-null head — heap holds ≤ k entries.
  const heap = new MinHeap();
  for (const h of lists) if (h) heap.push(h);
  const dummy = { next: null };
  let tail = dummy;
  while (heap.size()) {
    // Pop smallest head → splice onto output → push its successor (if any).
    const node = heap.pop();
    tail.next = node;
    tail = node;
    if (node.next) heap.push(node.next);
  }
  return dummy.next;
}
function toList(arr) { let d = { next: null }, c = d; for (const v of arr) { c.next = { val: v, next: null }; c = c.next; } return d.next; }
function toArr(h) { const o = []; while (h) { o.push(h.val); h = h.next; } return o; }
console.log(JSON.stringify(toArr(mergeKLists([toList([1, 4, 5]), toList([1, 3, 4]), toList([2, 6])]))));
  • Each node is pushed and popped exactly once → 2N heap operations × O(log k) each.
  • Heap holds at most k entries: every pop is replaced by the popped node's successor (or nothing if the list is exhausted).
  • Equal-val heads from different lists pop in unspecified order — fine for merge correctness; we're not stable-sorting.

Q1 Why is pairwise merge O(N log k) but merging one-list-at-a-time is O(N*k)?

  1. A Pairwise skips the comparison when one list is empty — sequential always compares
  2. B Each node is rewritten O(log k) times instead of O(k) times correct
  3. C Pairwise allocates merged nodes lazily; sequential allocates all up front
  4. D The two are equivalent — O(N log k) is just an overly tight bound on O(N*k)

Why: Halving the list count each round means every node is re-walked once per round, and there are log k rounds; folding into one accumulator re-walks everything already merged on each of the k-1 merges.

Q2 What does the dummy head in mergeTwo buy you?

  1. A Lets mergeTwo run in O(1) auxiliary space — without it you'd allocate a fresh node per merge
  2. B Avoids a special case for the first node — tail.next always means the same thing correct
  3. C Acts as a sentinel that ends the merge loop when both lists hit it
  4. D Lets mergeTwo work on circular lists by closing the loop at dummy

Why: With the sentinel in front, every splice is the same tail.next = node; tail = tail.next; without it the first one would have to assign the head instead. return dummy.next skips the sentinel at the end.

Q3 After the inner while exits with one list null, what do you do with the survivor?

  1. A Walk the survivor and append each node individually to preserve the dummy/tail invariant
  2. B Attach via tail.next = a || b — it is already sorted correct
  3. C Reverse the survivor first so its smallest value is closest to the tail
  4. D Merge it again with the merged-so-far prefix to re-balance the result

Why: The while (a && b) loop exits the moment one side is null, and the survivor is still a sorted, null-terminated list — so one assignment splices all its remaining nodes at once.

Q4 Time complexity for k sorted lists with N nodes total?

  1. A O(N)
  2. B O(N log k) correct
  3. C O(N*k)
  4. D O(N^2)

Why: Each round pair-merges every node exactly once (N work) and halves the list count, so there are log k rounds. O(N*k) is what the naive fold-left merge order costs.
