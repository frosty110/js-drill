Merge Two Sorted Lists

Splice two sorted lists into one sorted list using a dummy head and a tail pointer. Iterative, O(1) extra space beyond the dummy.

Problem

Write mergeTwoLists(a, b) merging two sorted singly linked lists. Use toList/toArr helpers and log JSON.stringify(toArr(mergeTwoLists(toList([1, 2, 4]), toList([1, 3, 4])))).

Expected output: [1,1,2,3,4,4]

Canonical solution

Dummy head + tail pointer, splice the smaller head (merge step) · O(n + m) / O(1) (time / space)

function mergeTwoLists(a, b) {
  const dummy = { val: 0, next: null };          // sentinel — simplifies edge cases
  let tail = dummy;
  while (a && b) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else                { tail.next = b; b = b.next; }
    tail = tail.next;
  }
  tail.next = a || b;                            // attach whichever isn't exhausted
  return dummy.next;
}
// Time O(n + m), Space O(1)
  • A dummy head removes the special case 'which list becomes the new head?'.
  • Don't forget to attach the remaining tail — one list will still have nodes.
  • Use <= (not <) for stability across equal values.

Alternate approaches

Recursive (divide at the smaller head) O(n + m) / O(n + m)

Reach for this when the interviewer wants the recursive formulation, or when the merge is a sub-call in a recursive algorithm (e.g. merge sort) and the call-stack depth is bounded. In JS the recursion depth is n+m, so for large lists prefer the iterative version.

function mergeTwoLists(a, b) {
  // Base cases: if either list is empty, the other is the merged result.
  if (!a) return b;
  if (!b) return a;
  // Splice whichever head is smaller; recurse for its successor.
  if (a.val <= b.val) {
    a.next = mergeTwoLists(a.next, b);
    return a;
  } else {
    b.next = mergeTwoLists(a, b.next);
    return b;
  }
}
function toList(arr) { let d = { next: null }, c = d; for (const v of arr) { c.next = { val: v, next: null }; c = c.next; } return d.next; }
function toArr(h) { const o = []; while (h) { o.push(h.val); h = h.next; } return o; }
console.log(JSON.stringify(toArr(mergeTwoLists(toList([1, 2, 4]), toList([1, 3, 4])))));
  • Each call either consumes one node from a or one from b, so there are at most n+m frames on the call stack.
  • No dummy head needed — the return value of each recursive call wires the next pointer naturally.
  • O(n+m) stack space; for long lists this risks a stack overflow, which is why the iterative version is generally preferred in production.

Q1 Why use a dummy head node?

  1. A Lets the merge run in O(1) space by reusing the dummy as the output head pointer
  2. B Removes the special case of picking the new head correct
  3. C Anchors the merge so cyclic inputs cannot loop the tail back to the start
  4. D Forces both lists to start at the same address so <= comparisons are stable

Why: Without the sentinel each iteration would first have to ask "is this the first node?"; with it, tail.next = node; tail = tail.next is uniform and the real head is just dummy.next.

Q2 After the while loop, why do we set tail.next = a || b?

  1. A To null-terminate the merged list — without it, tail.next still points at the last spliced node
  2. B One list may still have remaining sorted nodes to attach correct
  3. C To swap the two lists and rerun the merge in reverse order
  4. D It guards against a being null — a || b falls back to b when a was empty from the start

Why: while (a && b) exits the instant one side is null, leaving the other's nodes unspliced; the survivor is already sorted and null-terminated, so one assignment attaches all of them.

Q3 Time complexity for lists of length n and m?

  1. A O(n * m)
  2. B O((n + m) log (n + m))
  3. C O(n + m) correct
  4. D O(max(n, m)^2)

Why: Each node is compared and spliced exactly once. The inputs arrive sorted, so there is no sort step and none of the log factor that copy-and-sort would cost.

Q4 What does the function return?

  1. A dummy
  2. B dummy.next correct
  3. C tail
  4. D a

Why: dummy is the sentinel; the real merged head is dummy.next.

Q5 Concretely, what asymmetry does the dummy head eliminate?

  1. A Whether to compare with < or <=
  2. B The first append being special: without a dummy you'd need 'if head is null set head, else tail.next = node' every iteration correct
  3. C The need to track list lengths
  4. D Recursion versus iteration

Why: With a dummy, every append is the uniform tail.next = node; tail = tail.next — the dummy absorbs the empty-head special case.

Q6 Why does tail.next = a || b correctly finish the merge in one move?

  1. A It frees the unused list
  2. B The loop exits when one list is empty, and the other is already a fully sorted, terminated list correct
  3. C It reverses the leftover list first
  4. D It only works when both lists are empty

Why: The survivor is itself sorted and null-terminated, so attaching its head splices all remaining nodes at once — no extra loop needed.

Q7 Why does using <= (instead of <) preserve stability when values tie?

  1. A It avoids an infinite loop
  2. B On equal values it splices a's node first, keeping a's tied elements ahead of b's correct
  3. C <= is required for correct sorting
  4. D It makes the merge O(1) space

Why: With <=, a tie sends a's node in first; < would still sort correctly but flip the order of equal elements, breaking stability.

Q8 Why is this merge O(n + m) rather than O((n + m) log(n + m)) like copy-and-sort?

  1. A It uses a faster sort internally
  2. B The inputs are already sorted, so each node is examined and spliced exactly once with no sort step correct
  3. C Linked lists are inherently faster
  4. D The dummy head caches comparisons

Why: The merge exploits the sorted precondition: a single linear pass splices every node once, avoiding the log factor a general sort needs.

Q9 The canonical solution splices existing nodes in place. What does that buy over building a brand-new list?

  1. A It is stable while a new list is not
  2. B O(1) extra space — it rewires existing next pointers instead of allocating n + m new nodes correct
  3. C It runs in O(log n) time
  4. D It avoids the dummy head

Why: In-place splicing reuses the input nodes, so extra space is just the dummy and tail pointer; allocating new nodes would be O(n + m) space.
