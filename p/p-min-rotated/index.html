Find Minimum in Rotated Sorted Array

Binary search anchored to the right boundary. If `nums[mid] > nums[right]`, the rotation point — and the minimum — lies strictly right of mid. Otherwise it is at mid or left. O(log n).

Problem

Write findMin(nums) returning the minimum of a rotated sorted array with unique values. Log it for [4,5,6,7,0,1,2] then [11,13,15,17] (no rotation).

Expected output: 0 11

Canonical solution

function findMin(nums) {
  let l = 0, r = nums.length - 1;
  // Loop is `l < r` (not <=) — converge until pointers meet at the min.
  while (l < r) {
    const m = Math.floor((l + r) / 2);
    // Anchor to nums[r] — comparing to nums[l] is ambiguous in the unrotated case.
    if (nums[m] > nums[r]) {
      l = m + 1;            // min is strictly right of mid
    } else {
      // r = m (not m-1) — mid itself could BE the min, can't exclude it.
      r = m;                // min is at mid or to its left
    }
  }
  return nums[l];           // l === r points at the minimum
}
// Time O(log n), Space O(1)
  • Compare against nums[r], not nums[l] — comparing to left is ambiguous when the array isn't rotated.
  • Loop condition is l < r (not <=) and the answer is nums[l] when they converge.
  • When nums[m] <= nums[r], the right half (including m) is sorted — set r = m, NOT m - 1, because m itself could be the min.

Alternate approaches

Linear scan O(n) / O(1)

Name this before discarding it. A single pass tracking the running minimum is O(n) / O(1) and trivially correct. Use only as the brute force that motivates the O(log n) BS approach — the sortedness-after-rotation is information the linear scan ignores entirely.

function findMin(nums) {
  let min = nums[0];
  for (const n of nums) {
    if (n < min) min = n;
  }
  return min;
}
console.log(findMin([4,5,6,7,0,1,2]));
console.log(findMin([11,13,15,17]));
  • Correct for all inputs including duplicates — the only approach that doesn't break on Find-Min II inputs.
  • Ignores the rotated-sortedness invariant entirely; that wasted structure is the justification for upgrading to O(log n).
  • In an interview, state this first: 'O(n) linear scan works but doesn't use the sorted structure — I can do O(log n) by anchoring to nums[r].'

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why compare nums[mid] with nums[right] instead of nums[left]?

  1. A nums[l] <= nums[m] requires l < m, which fails in the 2-element case where m === l
  2. B Comparing against right disambiguates rotated vs. non-rotated halves; comparing against left does not correct
  3. C Anchoring left forces an extra nums[r] read at the end to verify, doubling memory accesses per iteration
  4. D Right-anchor lets the loop terminate with r = m whereas left-anchor would require l = m, creating the classic infinite-loop trap

Q2 If nums[mid] > nums[right], where is the minimum?

  1. A At mid itself, since mid is the largest element seen so far on the left side
  2. B In the left half [l..mid]
  3. C Strictly to the right of mid: (mid..r] correct
  4. D At index r — nums[r] is smaller than nums[mid], so it must already be the min

Q3 When nums[mid] <= nums[right], why do we set r = m and not r = m - 1?

  1. A r = m - 1 would skip past the pivot when the right half is exactly 2 elements long
  2. B mid itself could be the minimum — excluding it would lose the answer correct
  3. C r = m - 1 paired with l < r makes the loop terminate one iteration early on odd-length ranges
  4. D Setting r = m - 1 would discard the only sorted half, leaving the unsorted half to search — the opposite of the intent

Q4 Time complexity?

  1. A O(1)
  2. B O(log n) correct
  3. C O(n)
  4. D O(sqrt(n))
