Reverse Bits

Walk all 32 bits: shift result left, OR in the lowest bit of n, then shift n right. Coerce with `>>> 0` for unsigned result.

Results carried by this link

Problem

Write reverseBits(n) that reverses the 32 bits of an unsigned integer. Shift result left, OR in n & 1, then n >>>= 1. Return result >>> 0. Log it for 43261596 and 4294967293.

Expected output: 964176192 3221225471

Canonical solution

function reverseBits(n) {
  let result = 0;
  // Exactly 32 iterations — each moves n's current lowest bit into result's next slot.
  for (let i = 0; i < 32; i++) {
    result = (result << 1) | (n & 1);
    // Unsigned >>> — plain >> would sign-extend and leak 1s from the top.
    n >>>= 1;
  }
  // JS bitwise yields signed int32; >>> 0 reinterprets as unsigned.
  return result >>> 0;
}
// Time O(32) = O(1), Space O(1)
  • Use >>> (unsigned right shift) on n so the sign bit does not sticky-fill from the left.
  • JS bitwise ops yield signed 32-bit ints; finish with >>> 0 to interpret the result as unsigned.
  • Exactly 32 iterations regardless of n — every bit position is moved into its mirrored slot.

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why >>> 0 at the end?

  1. A It clears any high-bit garbage left over from intermediate shifts
  2. B JS bitwise ops return signed 32-bit; >>> 0 reinterprets as unsigned correct
  3. C It truncates the result to exactly 32 bits in case result << 1 overflowed into a 33rd bit
  4. D It coerces the result from a BigInt back to a regular Number

Q2 Why use >>> instead of >> on n during the loop?

  1. A >>> is one CPU cycle whereas >> is two, making the 32-iteration loop measurably faster
  2. B Unsigned shift avoids sign-bit extension so the high bit clears properly correct
  3. C >> returns a BigInt for large n; >>> keeps the result as a regular Number
  4. D >>> rounds toward zero while >> rounds toward negative infinity — only the former preserves the bit pattern

Q3 Order of the two operations inside the loop?

  1. A Shift n right first, then OR its (now-shifted) lowest bit into result
  2. B Shift result left and OR n's lowest bit, THEN shift n right correct
  3. C OR n's lowest bit into result FIRST, THEN shift result left so the bit moves to the next slot
  4. D Read n's HIGHEST bit (via n >>> 31), OR into result, then shift n left

Q4 Loop count?

  1. A log2(n) — one iteration per bit position of the input
  2. B popcount(n) — one iteration per set bit
  3. C 32 correct
  4. D Math.ceil(log2(n)) + 1 to cover the high bit
