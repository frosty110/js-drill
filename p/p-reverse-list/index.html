Reverse Linked List

Walk the list once; at each node rewrite next to point at the previous node. Three pointers: prev, curr, next.

patterns Linked List 9 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write reverseList(head) that reverses a singly linked list. Use toList/toArr helpers and log JSON.stringify(toArr(reverseList(toList([1, 2, 3, 4, 5])))).

Expected output: [5,4,3,2,1]

Canonical solution

Three-pointer in-place reversal (prev/curr/next) · O(n) / O(1) (time / space)

function reverseList(head) {
  // prev starts null so the original head becomes the new tail (next = null).
  let prev = null, curr = head;
  while (curr) {
    // Cache next BEFORE rewriting curr.next — otherwise the rest of the list is lost.
    const next = curr.next;
    curr.next = prev;
    prev = curr;
    curr = next;
  }
  // curr is null at the end; prev is the new head.
  return prev;
}
// Time O(n), Space O(1)
  • Cache curr.next BEFORE rewriting curr.next = prev, otherwise you lose the rest of the list.
  • Return prev, not curr — curr is null at the end; prev is the new head.
  • Start prev = null so the original head becomes the new tail with next = null.

Alternate approaches

Recursive (unwind from tail) O(n) / O(n)

Reach for this when the interviewer wants to see the recursive formulation or you're warming up for problems like Reverse Nodes in k-Group where a recursive subroutine slots in naturally. Skip it on production-sized inputs — JS has no TCO, so n deep recursion blows the stack around ~10k nodes.

function reverseList(head) {
  // Base case: empty list or last node — that node becomes the new head.
  if (!head || !head.next) return head;
  // Recurse first → newHead is the old tail, propagated unchanged up the stack.
  const newHead = reverseList(head.next);
  // On the way back up, flip the link: head.next.next = head; head.next = null.
  head.next.next = head;
  head.next = null;
  return newHead;
}
function toList(arr) { let d = { next: null }, c = d; for (const v of arr) { c.next = { val: v, next: null }; c = c.next; } return d.next; }
function toArr(h) { const o = []; while (h) { o.push(h.val); h = h.next; } return o; }
console.log(JSON.stringify(toArr(reverseList(toList([1, 2, 3, 4, 5])))));
  • Recurse all the way to the tail FIRST; the tail bubbles up as newHead unchanged through every return.
  • On unwind, head.next.next = head flips the link backward, then head.next = null severs the forward pointer so the new tail terminates cleanly.
  • Space is O(n) for the call stack — one frame per node. For long lists prefer the iterative version; JS doesn't optimize tail calls here anyway (the recursion isn't in tail position).

Q1 Why cache curr.next before reassigning curr.next?

  1. A JS evaluates right-to-left, so curr.next = prev reads curr.next first anyway — the cache is just defensive
  2. B Otherwise you lose the rest of the list correct
  3. C Without caching, prev would hold a stale pointer to the old head
  4. D Reassigning a .next property is illegal without first reading it on some JS engines

Why: curr.next = prev overwrites the only pointer to the remaining nodes, so const next = curr.next has to run first — the assignment doesn't hand back the old value.

Q2 What does the function return?

  1. A curr
  2. B prev correct
  3. C head
  4. D next

Why: When the loop exits, curr is null and prev points to the new head.

Q3 Why initialize prev to null?

  1. A So prev = curr on iter 1 makes the original head point at itself, terminating the list
  2. B So the original head ends up with next = null (new tail) correct
  3. C Because null is the only falsy value the while (curr) loop accepts as a starting state
  4. D It signals the GC that the original list can be freed once curr advances past it

Why: On iteration 1, curr.next = prev writes null into the original head's next — and the original head is the new tail, which has to terminate.

Q4 Space complexity of the iterative version?

  1. A O(1) correct
  2. B O(log n)
  3. C O(n)
  4. D O(n^2)

Why: The loop holds three pointers (prev, curr, next) no matter how long the list is — nothing is allocated per node, since the existing nodes are rewired in place.

Q5 Why is the recursive reversal O(n) space while the iterative version is O(1)?

  1. A Recursion copies the whole list at each call
  2. B Each recursive call holds a stack frame, so n nodes means n frames on the call stack correct
  3. C Recursion allocates a new node per call
  4. D There is no space difference — both are O(1)

Why: Recursion uses O(n) call-stack frames (one per node); the iterative loop reuses three local pointers regardless of length.

Q6 On a 1-million-node list, why might the recursive version crash while the iterative one is fine?

  1. A JS has no tail-call optimization, so n deep recursion overflows the call stack correct
  2. B The iterative version is faster so it finishes first
  3. C Recursion produces the wrong answer on long lists
  4. D Garbage collection halts recursion

Why: Engines don't apply TCO here, so ~1M nested frames blow the stack; the iterative loop has constant stack depth.

Q7 If you write prev = curr; curr.next = prev; (reorder the two assignments), what breaks?

  1. A Nothing — order doesn't matter
  2. B curr.next = prev now points the node at itself, creating a self-loop correct
  3. C It reverses twice and returns the original list
  4. D It throws a TypeError

Why: Setting prev = curr first makes prev === curr, so curr.next = prev points the node back to itself instead of the previous node.

Q8 What is the value of curr when the while loop exits?

  1. A The last node (old tail)
  2. B null correct
  3. C The new head
  4. D The old head

Why: The loop condition is while (curr), so it exits exactly when curr becomes null — which is why you return prev, not curr.

Q9 For a two-node list [1,2], what does node 1's next point to after reversal?

  1. A node 2
  2. B null correct
  3. C itself
  4. D the new head

Why: The original head (1) becomes the new tail, so its next is null — that comes from prev starting as null.
