Search Rotated Array

Binary search on a rotated sorted array. At each step one half is sorted — check if target lies inside. O(log n).

Problem

Write search(nums, target) for a rotated sorted array. Return the index of target, or -1. Log search([4,5,6,7,0,1,2], 0).

Expected output: 4

Canonical solution

Binary search with sorted-half detection · O(log n) / O(1) (time / space)

function search(nums, target) {
  let l = 0, r = nums.length - 1;
  while (l <= r) {
    const m = Math.floor((l + r) / 2);
    if (nums[m] === target) return m;
    // Invariant: after any rotation at least ONE half is still sorted. Identify it.
    if (nums[l] <= nums[m]) {
      // left half [l..m] is sorted
      // If target lies in the sorted-left range, discard the right; else discard the left.
      if (nums[l] <= target && target < nums[m]) r = m - 1;
      else l = m + 1;
    } else {
      // right half [m..r] is sorted
      if (nums[m] < target && target <= nums[r]) l = m + 1;
      else r = m - 1;
    }
  }
  return -1;
}
// Time O(log n), Space O(1)
  • Key: after any rotation, at least ONE of [l..m] or [m..r] is still sorted.
  • nums[l] <= nums[m] (inclusive) — equality handles single-element left half.
  • Boundary strictness matters: nums[l] <= target && target < nums[m] avoids re-testing nums[m].

Alternate approaches

Find-pivot-first, then plain BS (two-pass) O(log n) / O(1)

If you find the one-pass invariant hard to reason about under pressure, decompose into two explicit binary searches: first find the rotation pivot (index of the minimum), then pick the correct sorted half and run a standard binary search. Both passes are O(log n) so the total is still O(log n) / O(1) — same complexity, clearer structure.

function search(nums, target) {
  const n = nums.length;
  // Pass 1: find the pivot (index of minimum) using right-anchor find-min.
  let pl = 0, pr = n - 1;
  while (pl < pr) {
    const pm = Math.floor((pl + pr) / 2);
    if (nums[pm] > nums[pr]) pl = pm + 1;
    else pr = pm;
  }
  const pivot = pl;
  // Pass 2: binary-search the appropriate sorted half.
  let l, r;
  if (target >= nums[pivot] && target <= nums[n - 1]) {
    l = pivot; r = n - 1;
  } else {
    l = 0; r = pivot - 1;
  }
  while (l <= r) {
    const m = Math.floor((l + r) / 2);
    if (nums[m] === target) return m;
    if (nums[m] < target) l = m + 1;
    else r = m - 1;
  }
  return -1;
}
console.log(search([4,5,6,7,0,1,2], 0));
  • Pass 1 is exactly the Find-Minimum-in-Rotated-Array algorithm (right-anchor BS, r=m on <=).
  • After finding pivot, the problem reduces to two standard sorted sub-arrays — pick the one that can contain target by comparing to the array's endpoints.
  • Same O(log n) / O(1) complexity as the one-pass version; the constant factor is slightly higher (two loops), but correctness is easier to argue.

Q1 What invariant makes binary search still work after rotation?

  1. A The array remains globally sorted after rotation because rotation preserves relative order
  2. B At every step, at least one of [l..m] or [m..r] is sorted correct
  3. C The midpoint m always lands on or adjacent to the rotation pivot, so it can be detected and handled directly
  4. D nums[l] and nums[r] always bound target from both sides after the first iteration

Why: The code never needs the array globally sorted — only one half it can range-check by its endpoints. nums[l] <= nums[m] names that half, and whether target falls inside its value range decides which side survives.

Q2 Time complexity?

  1. A O(1)
  2. B O(log n) correct
  3. C O(n)
  4. D O(sqrt(n))

Why: Deciding which half is sorted and whether target sits in it is a fixed number of comparisons, and every branch still moves l or r past m — so the range halves exactly as in plain binary search.

Q3 How do you decide which half is sorted?

  1. A Compare nums[m] with target — equal means the sorted half is the one containing m
  2. B Compare nums[l] with nums[m]; if nums[l] <= nums[m] the left half is sorted correct
  3. C Compare nums[l] with nums[r] — if nums[l] <= nums[r] the whole array is sorted, otherwise the right half is
  4. D Compute the rotation index first via nums.indexOf(Math.min(nums[l], nums[r])) and split on it

Why: If nums[l] <= nums[m] there is no descent between them, so [l..m] is ascending; otherwise the single descent sits on the left and [m..r] is the clean half. Comparing nums[l] to nums[r] can't be used — it only tells you whether the array is rotated at all, not where m fell.

Q4 After identifying the sorted half, what do you check?

  1. A Whether nums[m] is closer to target than nums[l] is, and step toward the closer end
  2. B Whether target lies WITHIN the sorted half's value range — if yes, recurse there correct
  3. C Whether the unsorted half is longer than the sorted half; recurse into the longer one to make better progress
  4. D Whether nums[l] + nums[r] === 2 * target, the centerpoint test

Why: Only the sorted half can be range-checked by its two endpoints — nums[l] <= target && target < nums[m]. A yes keeps that half; a no is conclusive, so target can only be in the other one.

Q5 Why is it guaranteed that at least one of the two halves is always sorted?

  1. A Because the array is sorted globally
  2. B Because a single rotation creates exactly one 'break' point, which can fall in only one half — the other half is unbroken correct
  3. C Because m is always the pivot
  4. D It is not guaranteed; sometimes neither half is sorted

Why: One rotation produces a single descent point; it lands in one half, leaving the other half entirely ascending.

Q6 The check uses nums[l] <= nums[m] (with the =) rather than nums[l] < nums[m]. Why include equality?

  1. A Equality is needed so the half-check matches the loop's l <= r condition — both must use the same operator for the invariant to hold
  2. B When l == m (a single-element left side, e.g. 2-element subarray), < would wrongly flag the right half as sorted and mis-branch correct
  3. C Without =, the algorithm would silently drop the element at index l from consideration each iteration
  4. D < would skip the case where the rotation point lands exactly on m, since nums[l] === nums[m] signals m IS the pivot

Why: When the left half is a single element, nums[l] equals nums[m]; <= correctly treats it as sorted, while < would mis-route a 2-element subarray.

Q7 If the array contains DUPLICATES, what happens to the algorithm?

  1. A It still runs in O(log n) unchanged
  2. B The nums[l] <= nums[m] test can be ambiguous (e.g. [1,1,1,2,1]), forcing an l++ fallback that degrades to O(n) worst case correct
  3. C It returns the wrong index
  4. D It infinite-loops

Why: When nums[l] == nums[m] == nums[r] you can't tell which half is sorted, so you advance l by one and lose the log-n guarantee (Search Rotated II).

Q8 For an array rotated by 0 (still in original ascending order), how does the template behave?

  1. A It crashes
  2. B nums[l] <= nums[m] is always true, so it always takes the left-sorted branch — it degrades gracefully to plain binary search correct
  3. C It always returns -1
  4. D It enters the right-sorted branch

Why: With no rotation the whole array is the sorted-left half every step, reducing to standard binary search.

Q9 The Find-Minimum-in-Rotated-Array variant uses the same skeleton but differs how?

  1. A It searches for the maximum instead
  2. B It anchors comparisons to nums[r] and converges to the pivot itself rather than testing against a target value correct
  3. C It requires the array to be sorted first
  4. D It uses a hash map

Why: Find-Minimum compares nums[m] to nums[r] to decide which side the pivot is on, converging on the rotation point with no target.
