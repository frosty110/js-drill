Single Number (XOR)

XOR every value: pairs cancel to 0 and the loner survives. O(n) time, O(1) space.

patterns Bit Manipulation 4 concept · 2 fill-in · 1 drill

Problem

Write singleNumber(nums) where every value appears twice except one — return the loner using XOR. O(n) time, O(1) space. Log singleNumber([4, 1, 2, 1, 2]).

Expected output: 4

Canonical solution

XOR fold — pairs cancel, the loner survives · O(n) / O(1) (time / space)

function singleNumber(nums) {
  // 0 is the XOR identity (a ^ 0 = a); pairs self-cancel (a ^ a = 0), the loner survives.
  let result = 0;
  for (const n of nums) result ^= n;
  return result;
}
// Time O(n), Space O(1)
  • XOR is commutative and associative — order does not matter; all pairs cancel.
  • a ^ a === 0 and a ^ 0 === a are the two identities that make this work.
  • No hash set needed — the bit pattern itself stores the running parity.

Alternate approaches

Hash Set toggle O(n) / O(n)

Use this when you don't remember the XOR trick and need something correct and readable. Toggle each value into/out of a Set — if it's already present, remove it (pair cancelled); what remains is the loner. O(n) time but O(n) space.

function singleNumber(nums) {
  const seen = new Set();
  for (const n of nums) {
    if (seen.has(n)) seen.delete(n);
    else seen.add(n);
  }
  return [...seen][0];
}
console.log(singleNumber([4, 1, 2, 1, 2]));
  • Toggle into/out of a Set — presence means 'seen once', absence after removal means 'pair seen'.
  • O(n) extra space for the Set — the XOR approach avoids this entirely with a single integer accumulator.
  • Works even if the problem allowed more than two appearances (unlike XOR, which only handles pairs).

Q1 Why initialize the accumulator to 0?

  1. A Because nums could be empty — starting at 0 makes the result default to 0 instead of undefined
  2. B 0 is the identity for XOR (a ^ 0 === a) correct
  3. C Because XOR-ing into an uninitialized variable yields NaN in JS
  4. D Because the first element is treated as a pair-completion against the implicit seed

Why: a ^ 0 === a, so seeding with 0 lets the first element pass through untouched and keeps the fold correct for any length. Seeding with nums[0] also works, but then the loop has to skip index 0.

Q2 What is the value of 5 ^ 5?

  1. A 5
  2. B 10
  3. C 0 correct
  4. D 1 (one bit position differs from itself in two's-complement sign-extension)

Why: XOR sets a bit only where the two operands DIFFER, and no bit differs from itself, so a ^ a === 0 for every a. That self-cancellation is the entire algorithm — the pairs annihilate and only the loner is left.

Q3 Space complexity of this XOR approach?

  1. A O(n)
  2. B O(log n)
  3. C O(1) correct
  4. D O(32) for the bit-level parity counters

Why: A single accumulator, result, regardless of input size — no Set and no frequency Map. That is the reason to reach for XOR here instead of the obvious count-in-a-hash approach, which is O(n) memory.

Q4 Why does the order of the array not matter?

  1. A Because XOR internally sorts its operands before combining them
  2. B XOR is commutative and associative correct
  3. C Because each value is XOR'd against the running result, which absorbs order
  4. D Because the algorithm makes a second pass that re-XORs the loner into place

Why: XOR is commutative (a ^ b === b ^ a) and associative ((a ^ b) ^ c === a ^ (b ^ c)), so each duplicate cancels its partner no matter how far apart they sit in nums. Nothing in the loop depends on adjacency.
