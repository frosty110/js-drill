Sliding Window Maximum

Maintain a deque of indices whose values are strictly decreasing. The front is always the max of the current window. O(n) total because each index is pushed and popped at most once.

Problem

Write maxSlidingWindow(nums, k) returning the maximum of each window of size k. O(n). Log JSON.stringify(maxSlidingWindow([1, 3, -1, -3, 5, 3, 6, 7], 3)).

Expected output: [3,3,5,5,6,7]

Canonical solution

function maxSlidingWindow(nums, k) {
  const dq = [];                              // stores indices, values strictly decreasing
  const out = [];
  for (let i = 0; i < nums.length; i++) {
    // drop indices that fell out of the window
    if (dq.length && dq[0] <= i - k) dq.shift();
    // drop tail values smaller than nums[i] — they can never be the max again
    while (dq.length && nums[dq[dq.length - 1]] < nums[i]) dq.pop();
    dq.push(i);
    // Front of deque is the max; record only once the window is fully formed.
    if (i >= k - 1) out.push(nums[dq[0]]);
  }
  return out;
}
// Time O(n), Space O(k)
  • Deque stores INDICES, not values — you need the index to know when an item slides out of the window.
  • Pop from the back while the tail value is smaller than nums[i]; those tails can never be the window max once nums[i] enters.
  • Front of the deque is the answer for the current window — record it only once i >= k-1.
  • Each index enters and leaves the deque at most once → amortized O(n) despite the inner while.

Alternate approaches

Max-heap with lazy expiry O(n log k) / O(k)

Reach for this if the deque feels hard to derive under pressure. A max-heap with (value, index) pairs is easier to motivate — 'push everything, poll the top, skip stale entries' — and lands O(n log k), which is acceptable for most interviews. Many candidates write this first and then optimize to the deque only if pushed.

// Min-heap helper (JS has no built-in max-heap; simulate with negated values)
class MinHeap {
  constructor() { this.h = []; }
  push(val) {
    this.h.push(val);
    let i = this.h.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.h[p][0] <= this.h[i][0]) break;
      [this.h[p], this.h[i]] = [this.h[i], this.h[p]];
      i = p;
    }
  }
  pop() {
    const top = this.h[0];
    const last = this.h.pop();
    if (this.h.length) {
      this.h[0] = last;
      let i = 0;
      while (true) {
        let s = i, l = 2*i+1, r = 2*i+2;
        if (l < this.h.length && this.h[l][0] < this.h[s][0]) s = l;
        if (r < this.h.length && this.h[r][0] < this.h[s][0]) s = r;
        if (s === i) break;
        [this.h[i], this.h[s]] = [this.h[s], this.h[i]];
        i = s;
      }
    }
    return top;
  }
  peek() { return this.h[0]; }
  size() { return this.h.length; }
}
function maxSlidingWindow(nums, k) {
  // Store [-value, index] so the heap root is the maximum.
  const heap = new MinHeap();
  const out = [];
  for (let i = 0; i < nums.length; i++) {
    heap.push([-nums[i], i]);
    // Lazily expire entries whose index is outside the window.
    while (heap.peek()[1] <= i - k) heap.pop();
    if (i >= k - 1) out.push(-heap.peek()[0]);
  }
  return out;
}
console.log(JSON.stringify(maxSlidingWindow([1, 3, -1, -3, 5, 3, 6, 7], 3)));
  • Negate values so a min-heap acts as a max-heap; the root's negated value is the window max.
  • Lazy expiry: don't eagerly remove stale entries — just skip them when peeking. Worst-case heap size is O(n), but entries expire naturally.
  • O(n log k) vs deque's O(n) — the log k factor comes from each push/pop being O(log(heap size ≤ n)).

Brute force (Math.max per window) O(n·k) / O(1)

Name this first, then discard it. In an interview, saying 'O(n·k) naïve, then I'll optimize to O(n)' is the standard opening move. Some interviewers also accept O(n·k) if k is small.

function maxSlidingWindow(nums, k) {
  const out = [];
  for (let i = 0; i <= nums.length - k; i++) {
    let max = nums[i];
    for (let j = i + 1; j < i + k; j++) {
      if (nums[j] > max) max = nums[j];
    }
    out.push(max);
  }
  return out;
}
console.log(JSON.stringify(maxSlidingWindow([1, 3, -1, -3, 5, 3, 6, 7], 3)));
  • Each of the n-k+1 windows is scanned in O(k) — the k-1 elements that didn't change are rescanned from scratch on every slide.
  • The redundancy motivates the deque: instead of rescanning, maintain a data structure that updates in O(1) amortized as elements enter and leave.
  • Correct for any input; only impractical when n and k are both large (e.g. n=10^5, k=10^4 → 10^9 ops).

Why: Brute force redoes the max over k elements every slide; the deque amortizes the work because each index enters once and leaves once total.

  4. D O(k log n) — independent of array length

Why: Heap operations cost log k each, giving O(n log k); the monotonic deque avoids the log factor with constant-time amortized push/pop.

Q8 Why does the back-eviction use < (strictly less) rather than <=?

  1. A Performance — < is faster than <=
  2. B Using < keeps equal-valued indices in the deque so the max isn't lost prematurely when the front expires correct
  3. C It's an arbitrary choice with no effect
  4. D <= would cause an infinite loop

Why: On equal values, popping with <= would discard a still-valid future max; < retains duplicates so a later identical max survives after the front shifts out.

  3. C Use two heaps
  4. D Run the same code and negate the output indices

Why: The deque invariant just flips: pop tails while nums[tail] > nums[i], keeping values increasing so dq[0] is the window minimum.
