Trapping Rain Water

Total water trapped above a height array. Two pointers march inward; the shorter side fixes the water level on that column.

Problem

Write trap(height) returning total trapped water. Use two pointers and running max on each side. Log trap([0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]).

Expected output: 6

Canonical solution

function trap(height) {
  let l = 0, r = height.length - 1;
  // Running max on each side — the cap on water level at the inner pointer.
  let lMax = 0, rMax = 0, water = 0;
  while (l < r) {
    if (height[l] < height[r]) {                  // left side is the bottleneck
      // Update max BEFORE adding water — otherwise lMax - height[l] could go negative.
      lMax = Math.max(lMax, height[l]);
      water += lMax - height[l];
      l++;
    } else {
      rMax = Math.max(rMax, height[r]);
      water += rMax - height[r];
      r--;
    }
  }
  return water;
}
// Time O(n), Space O(1)
  • The shorter side bounds the water on its column — that's why we advance it.
  • Update the running max BEFORE adding water; otherwise you subtract too much.
  • No need to precompute left/right max arrays — the two-pointer walk is sufficient.

Alternate approaches

Prefix-max arrays (leftMax[] / rightMax[]) O(n) / O(n)

The most direct translation of the formula water[i] = min(leftMax[i], rightMax[i]) - height[i]. Reach for it when you want the clearest correctness story and O(n) extra space is acceptable — it's the natural stepping stone before the two-pointer optimization.

function trap(height) {
  const n = height.length;
  if (n === 0) return 0;
  // Pass 1: tallest bar at or left of i.
  const leftMax = new Array(n);
  leftMax[0] = height[0];
  for (let i = 1; i < n; i++) leftMax[i] = Math.max(leftMax[i - 1], height[i]);
  // Pass 2: tallest bar at or right of i.
  const rightMax = new Array(n);
  rightMax[n - 1] = height[n - 1];
  for (let i = n - 2; i >= 0; i--) rightMax[i] = Math.max(rightMax[i + 1], height[i]);
  // Pass 3: water above each column.
  let water = 0;
  for (let i = 0; i < n; i++) water += Math.min(leftMax[i], rightMax[i]) - height[i];
  return water;
}
console.log(trap([0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]));
  • Three linear passes: build leftMax[], build rightMax[], then sum the per-column water.
  • Materializes both maxes explicitly — easiest to verify, but pays O(n) space for the two arrays.
  • The two-pointer canonical is this exact idea with the two arrays collapsed into running scalars.

Monotonic stack (decreasing heights) O(n) / O(n)

Computes water in horizontal slabs rather than vertical columns. Worth knowing because the same decreasing-stack machinery solves Largest Rectangle in Histogram and Daily Temperatures — interviewers probing the stack family may steer you here.

function trap(height) {
  const stack = []; // indices of bars in decreasing height
  let water = 0;
  for (let i = 0; i < height.length; i++) {
    // Current bar is a right wall — drain every shorter bar it tops.
    while (stack.length && height[i] > height[stack[stack.length - 1]]) {
      const bottom = stack.pop();         // basin floor
      if (!stack.length) break;           // no left wall → nothing bounded
      const left = stack[stack.length - 1];
      const width = i - left - 1;          // span between the two walls
      const bounded = Math.min(height[i], height[left]) - height[bottom];
      water += width * bounded;            // one horizontal slab
    }
    stack.push(i);
  }
  return water;
}
console.log(trap([0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1]));
  • Keep a stack of indices with decreasing heights; a taller bar triggers draining.
  • Each pop fills one horizontal slab: width (i - left - 1) times bounded height min(height[i], height[left]) - height[bottom].
  • Each index is pushed and popped at most once → O(n) time; the stack is the O(n) space.

  3. C Maximum future height
  4. D Slope to the next bar

Q3 Space complexity of the two-pointer version?

  1. A O(n)
  2. B O(log n)
  3. C O(1) correct
  4. D O(n^2)

Q4 Why update lMax/rMax BEFORE adding to water?

  1. A Updating after would skip the current bar's contribution to lMax, leaving lMax one step stale for the rest of the run
  2. B Otherwise lMax - height[l] could be negative correct
  3. C Math.max coerces to NaN if called before its arguments are materialized in the loop
  4. D Updating after triggers a re-read of height[l] from the original array, which may have been mutated by another iteration

Why: If you add before updating, the current bar may exceed the old max and you subtract a stale value.

Q5 The exact water above column i is min(leftMax, rightMax) - height[i]. When height[l] < height[r], why can the algorithm safely use lMax alone instead of computing min(lMax, rMax)?

  1. A Because lMax is always larger than rMax
  2. B Because rMax is at least height[r], and height[r] > height[l], so rMax > lMax — making lMax the true minimum (the binding constraint) for column l correct
  3. C Because rMax has not been computed yet
  4. D Because the two maxes are always equal at that point

Why: rMax >= height[r] > height[l], and lMax already includes height[l], so lMax is provably the smaller of the two maxes; it IS the min, so column l can be settled with lMax - height[l].

Q6 Compared to the precompute-arrays approach (build leftMax[] and rightMax[] in two passes), what does the two-pointer version improve, and at what cost?

  1. A It is faster: O(log n) vs O(n) time
  2. B Same O(n) time, but O(1) space instead of O(n) — at the cost of a subtler correctness argument correct
  3. C It uses less time but more space
  4. D There is no difference

Why: Both run in O(n) time; the two-pointer walk maintains running maxes incrementally so it needs only O(1) extra space versus O(n) for the two precomputed arrays.

Q7 On a monotone increasing array like [1,2,3,4,5], the answer is 0. Why does the algorithm correctly add nothing?

  1. A It detects the array is sorted and returns 0 early
  2. B Each step settles the left side, and after lMax = max(lMax, height[l]) the current bar IS the new max, so lMax - height[l] is 0 every time correct
  3. C It skips every bar because heights increase
  4. D rMax stays 0 the whole time

Why: With strictly increasing heights, each new left bar becomes the running max, so lMax equals height[l] after the update and the contribution lMax - height[l] is 0; trapping needs a higher bar on BOTH sides.

Q8 Which alternative O(n) solution processes water 'horizontally' (level by level) rather than column by column?

  1. A A binary-search approach
  2. B A monotonic stack: push indices, and whenever the current bar exceeds the stack top, pop and compute the trapped rectangle at that level correct
  3. C A recursive divide-and-conquer
  4. D A prefix-sum array

Why: The stack-based variant keeps a decreasing stack of bar indices and, on each taller bar, pops to fill the bounded horizontal slab of water — same O(n) total, different mental model.

Q9 If you swapped the comparison to if (height[l] <= height[r]) (settle left on ties too) instead of <, would the total trapped water change?

  1. A Yes, it would overcount water
  2. B No — on a tie either side's running max equals the other's binding value, so settling either side adds the same correct amount; the total is unchanged correct
  3. C Yes, it would crash on equal heights
  4. D Yes, it would undercount by 1 each tie

Why: On equal heights the binding max is the same from either side, so choosing left or right on the tie settles the same column contribution and the running maxes stay consistent — the total is identical.
