Validate BST

Validate a BST by passing tightening (lo, hi) bounds down: every node must satisfy lo < node.val < hi. Recurse left with hi=node.val, right with lo=node.val. O(n).

Problem

Write isValidBST(root) using the (lo, hi) bounds approach. Build a valid BST [2,1,3] and an invalid BST [5,1,4,null,null,3,6]. Log both.

Expected output: true false

Canonical solution

Bounds-passing recursion — every node must fit (lo, hi) · O(n) / O(h) (time / space)

function isValidBST(root) {
  // Carry the open interval (lo, hi) each node must fall inside — strict inequalities.
  function check(node, lo, hi) {
    if (!node) return true;
    if (node.val <= lo || node.val >= hi) return false;
    // Left subtree caps hi at node.val; right subtree raises lo to node.val.
    return check(node.left, lo, node.val) && check(node.right, node.val, hi);
  }
  // Root has no bounds — start with ±Infinity sentinels.
  return check(root, -Infinity, Infinity);
}
// Time O(n), Space O(h) recursion stack
  • Bounds approach beats in-order-and-compare: handles duplicates cleanly and never allocates the traversal array.
  • Start with lo=-Infinity, hi=Infinity — the root has no constraint; tighten ONE side per recursion.
  • Use strict <= and >= — a BST disallows equal values (unless the problem says otherwise).

Alternate approaches

Iterative in-order traversal O(n) / O(h)

Reach for this when the interviewer asks for an iterative solution, or when you want to avoid the -Infinity/+Infinity sentinel ceremony. In-order of a valid BST is strictly increasing — a single non-increase means invalid. Also useful when you need to return the offending node rather than just true/false.

function isValidBST(root) {
  const stack = [];
  let prev = -Infinity;
  let node = root;
  while (node || stack.length) {
    // Descend to the leftmost node.
    while (node) {
      stack.push(node);
      node = node.left;
    }
    node = stack.pop();
    // In-order visit: must be strictly greater than previous.
    if (node.val <= prev) return false;
    prev = node.val;
    node = node.right;
  }
  return true;
}
const good = { val: 2, left: { val: 1, left: null, right: null }, right: { val: 3, left: null, right: null } };
const bad  = { val: 5, left: { val: 1, left: null, right: null }, right: { val: 4, left: { val: 3, left: null, right: null }, right: { val: 6, left: null, right: null } } };
console.log(isValidBST(good));
console.log(isValidBST(bad));
  • Push lefts until null, pop, compare with prev, then move to the right child — the standard iterative in-order template.
  • prev starts at -Infinity so the leftmost node always passes; any non-increasing step means invalid.
  • Space is O(h) for the explicit stack — same as the recursive bounds approach but no call-stack risk on very deep trees.

Q1 What bounds does the left child of a node with value v inherit from a parent (lo, hi)?

  1. A (lo, v) correct
  2. B (v, hi)
  3. C (lo, hi)
  4. D (-Infinity, Infinity)

Why: Going left tightens the UPPER bound to v; lo is unchanged.

Q2 Why is the bounds approach preferred over in-order-traversal-and-compare?

  1. A Bounds short-circuit on the first violation, while in-order must complete the full traversal before comparing
  2. B Handles duplicates cleanly and avoids allocating the traversal list correct
  3. C In-order traversal can't distinguish between a valid BST and its mirror image
  4. D Bounds-passing tightens monotonically, so it correctly handles trees where values exceed safe-integer range

Why: The strict <= lo / >= hi checks reject a duplicate on the spot, and nothing is allocated beyond the O(h) call stack. Early exit isn't the distinguishing win — traversal-and-compare bails on the first non-increase just as fast; materializing the values into an array is the O(n) cost bounds-passing skips.

Q3 Initial call uses which bounds?

  1. A (Number.MIN_SAFE_INTEGER, Number.MAX_SAFE_INTEGER)
  2. B (-Infinity, Infinity) correct
  3. C (root.val - 1, root.val + 1)
  4. D (null, null) — checked with lo == null short-circuits

Why: The root is unconstrained, and ±Infinity are real JS numbers that lose every comparison against a finite value, so no real node value can fail the first check. MAX_SAFE_INTEGER as hi would wrongly reject a legitimate node holding exactly that value, since the test is >=.

Q4 Time and space complexity?

  1. A O(n log n) time, O(1) space
  2. B O(n) time, O(h) recursion stack correct
  3. C O(n^2) time, O(n) space
  4. D O(log n) time, O(log n) space

Why: Each node is checked once with two O(1) comparisons, and the bounds ride along as arguments — the only extra space is one call frame per level of the current path.

Q5 A candidate validates a BST by only checking node.left.val < node.val < node.right.val at every node. Why is this WRONG?

  1. A It allows duplicates because non-strict <= is implicit when comparing object properties
  2. B It only enforces the local parent constraint; a node deep in a subtree can satisfy its parent yet still violate a distant ancestor's bound correct
  3. C It compares child values rather than subtree min/max, so it misses internal violations within a subtree
  4. D It returns false on valid trees whose left subtree happens to be deeper than the right

Why: The BST property is global: every node in a left subtree must be less than the ANCESTOR, not just the direct parent — the local-only check passes invalid trees like [10,5,15,null,null,6,20].

Q6 In the tree [10,5,15,null,null,6,20], the node 6 is the left child of 15. Why is this tree invalid?

  1. A 6 is greater than its parent 15
  2. B 6 sits in the right subtree of 10, so it must be greater than 10, but 6 < 10 correct
  3. C 15 has no left structure
  4. D 20 is greater than 15

Why: 6 is locally fine (6 < 15) but globally invalid: it descends from the right of 10 so it inherits lo=10, and 6 <= 10 fails the bound.

Q7 What is the alternative validation technique using in-order traversal?

  1. A The traversal must be strictly increasing correct
  2. B The traversal must be non-decreasing
  3. C The traversal must be sorted descending
  4. D Any traversal order works as long as no duplicates exist

Why: An in-order traversal of a valid BST yields values in strictly increasing order; a single non-increase (including an equal pair) means it is not a valid BST.

Q8 Why does the check use strict <= lo and >= hi rather than < and >?

  1. A Non-strict bounds would let a node equal its ancestor's value but still treat its subtree's bounds as strict, causing inconsistent rejection
  2. B To reject duplicate values — a standard BST disallows equal keys correct
  3. C The recursion tightens bounds by +/- 1 on each call, so strict comparison is needed to prevent off-by-one drift
  4. D Strict comparison is required because lo/hi start at +/-Infinity, where non-strict comparisons are undefined in JS

Why: Strict bounds reject equality, so duplicates like [2,2] correctly return false; if the problem allowed duplicates on one side you would relax one comparison.
