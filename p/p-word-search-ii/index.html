Word Search II (Trie + Backtrack)

Build a trie of the dictionary, DFS each cell stepping into the trie — early-exit when the next char has no trie edge. Far faster than running Word Search I per word.

Problem

Implement findWords(board, words) using a trie + DFS. Run on the standard 4x4 board with words ["oath","pea","eat","rain"] and log the sorted result as a JSON array.

Expected output: ["eat","oath"]

Canonical solution

Trie-guided grid DFS with mark-and-restore backtracking · O(R·C·4^L) / O(W·L) (time / space)

function findWords(board, words) {
  const root = {};
  for (const w of words) {
    let n = root;
    for (const ch of w) n = n[ch] = n[ch] || {};
    n.word = w;            // stash the full word at the terminal
  }
  const found = [];
  const R = board.length, C = board[0].length;
  const dfs = (r, c, node) => {
    const ch = board[r][c];
    const next = node[ch];
    if (!next) return;     // PRUNE: no trie edge for this character
    if (next.word) { found.push(next.word); next.word = null; } // dedupe
    board[r][c] = "#";     // mark visited in place
    for (const [dr, dc] of [[1,0],[-1,0],[0,1],[0,-1]]) {
      const nr = r + dr, nc = c + dc;
      if (nr >= 0 && nr < R && nc >= 0 && nc < C && board[nr][nc] !== "#") dfs(nr, nc, next);
    }
    board[r][c] = ch;      // restore
  };
  for (let r = 0; r < R; r++) for (let c = 0; c < C; c++) dfs(r, c, root);
  return found;
}
// Time O(R*C * 4^L) worst case, but trie pruning collapses huge subtrees in practice
  • Storing the full word at the terminal node avoids reconstructing it from the DFS path.
  • Set next.word = null after collection — same word reachable from multiple cells would otherwise appear twice.
  • Mark-and-restore on the board itself is the standard trick to avoid a separate visited set.
  • Time O(R·C · 4^L) worst case (L = longest word); trie pruning makes actual runtime far lower.

Alternate approaches

Naive DFS per word (Word Search I × W) O(W·R·C·4^L) / O(L)

Only viable for a tiny dictionary (≤5 words). Shows why the trie matters: for W=5000 words, this runs W independent DFS passes over the entire board, repeating all shared-prefix work per word. Use this framing to motivate the trie in an interview — explain this, then say 'the trie folds all W passes into one.'

function findWords(board, words) {
  const R = board.length, C = board[0].length;
  function exists(word) {
    function dfs(r, c, i) {
      if (i === word.length) return true;
      if (r < 0 || r >= R || c < 0 || c >= C) return false;
      if (board[r][c] !== word[i]) return false;
      const ch = board[r][c];
      board[r][c] = "#";
      const found = dfs(r+1,c,i+1)||dfs(r-1,c,i+1)||dfs(r,c+1,i+1)||dfs(r,c-1,i+1);
      board[r][c] = ch;
      return found;
    }
    for (let r = 0; r < R; r++) for (let c = 0; c < C; c++) if (dfs(r, c, 0)) return true;
    return false;
  }
  return words.filter(w => exists(w));
}
const board = [
  ["o","a","a","n"],
  ["e","t","a","e"],
  ["i","h","k","r"],
  ["i","f","l","v"]
];
const words = ["oath","pea","eat","rain"];
console.log(JSON.stringify(findWords(board, words).sort()));
  • Each exists call re-walks the board independently — words sharing prefix 'ca' ('cat', 'car') both traverse c→a from scratch, duplicating work.
  • The W factor vanishes in the trie version: all dictionary words are in the trie simultaneously, so one grid DFS tests all of them at once.
  • Acceptable to present as 'the obvious baseline' before proposing the trie — it makes the complexity improvement concrete and earned.

Q1 Why is Trie + DFS better than running Word Search I per word?

  1. A Trie lookup is O(1) per character while Word Search I uses O(L) string comparison
  2. B The trie lets a single DFS test all dictionary prefixes at once and prune dead branches early correct
  3. C Building a trie reorders the words so the longest are checked first, reducing wasted DFS depth
  4. D Per-word Word Search I needs a fresh visited matrix each call; the trie version shares it

Why: One grid DFS descends the trie in parallel, so words sharing a prefix walk it once instead of once each, and if (!next) return kills an entire subtree the moment no dictionary word continues. The W factor drops out of the bound entirely.

Q2 Why store the FULL word at the terminal node?

  1. A So the trie can re-verify each match against the original dictionary before reporting it
  2. B Avoids rebuilding the word from the DFS path correct
  3. C Without it, multiple words sharing a terminal node would collide on the same flag
  4. D It encodes the word length so the DFS knows when to stop descending

Why: found.push(next.word) reads the finished string straight off the terminal node, so the DFS never has to carry the path characters down the recursion or re-join them on a hit.

Q3 Why set next.word = null after pushing it to results?

  1. A Prunes the entire subtree rooted at this terminal, so the DFS won't explore further suffixes
  2. B Dedupes — the same word may be reachable from multiple start cells correct
  3. C Required to terminate DFS
  4. D Releases the trie node's child pointers so they can be garbage-collected mid-search

Why: The same terminal is reachable from more than one start cell, and nulling the field makes if (next.word) false on every later hit. It does NOT prune the subtree — the node's children survive, so a longer word below it is still found.

Q4 Why mark board[r][c] = "#" during recursion?

  1. A Marks visited cells without a separate visited set; restored on backtrack correct
  2. B Signals to the trie that this cell's character has been consumed for the current word
  3. C Forces neighbor DFS calls to skip this cell because '#' is not a valid trie key
  4. D Caches the cell's original character at a sentinel so backtracking can restore from a single global

Why: The neighbor guard board[nr][nc] !== "#" is what stops a cell being reused inside one word, so the sentinel replaces a separate visited matrix. board[r][c] = ch on the way out frees the cell again for other paths — drop that line and the board stays permanently marked.
