Problem

Write bfsOrder(graph, start) that returns an array of node ids in BFS visit order. Use a queue + a seen set. Log JSON.stringify(bfsOrder({A:["B","C"], B:["D"], C:["D"], D:[]}, "A")).

Expected output: ["A","B","C","D"]

Canonical solution

Queue + seen-set BFS (visit-all + level-order variants) · O(V + E) / O(V) (time / space)

// ---------- Variant A: visit-all-reachable BFS ----------
// Use when you just need to walk every node reachable from start.
function bfs(start, graph) {
  const q = [start];
  const seen = new Set([start]);
  const order = [];
  while (q.length) {
    const cur = q.shift();              // dequeue front (FIFO)
    order.push(cur);
    for (const n of graph[cur] || []) {
      if (!seen.has(n)) {               // gate enqueue on seen
        seen.add(n);                    // mark BEFORE enqueue — not when you pop
        q.push(n);
      }
    }
  }
  return order;
}

// ---------- Variant B: level-order BFS ----------
// Use when you need per-level groups, shortest path in unweighted graphs, etc.
function bfsLevels(start, graph) {
  const q = [start];
  const seen = new Set([start]);
  const levels = [];
  while (q.length) {
    const n = q.length;                 // SNAPSHOT — children pushed below are next level
    const level = [];
    for (let i = 0; i < n; i++) {
      const cur = q.shift();
      level.push(cur);
      for (const nb of graph[cur] || []) {
        if (!seen.has(nb)) { seen.add(nb); q.push(nb); }
      }
    }
    levels.push(level);
  }
  return levels;
}
  • Mark seen BEFORE enqueue, not after dequeue — otherwise a node can be enqueued multiple times before its first visit.
  • Array.shift is O(n); fine for interview-scale, but for huge queues use a head pointer or a real deque.
  • Level-order needs const n = q.length snapshotted BEFORE the inner loop — children pushed inside belong to the NEXT level.
  • Queue gives FIFO ⇒ BFS. Swap shift→pop and you've accidentally written DFS.

Alternate approaches

Multi-source BFS O(V + E) / O(V)

Reach for this when the problem has MULTIPLE simultaneous starting points and asks for the minimum distance (or time) to reach every other node — Rotting Oranges, Walls and Gates, 01-Matrix. The trick: seed the queue with ALL sources at once, marked seen up-front. They expand in lock-step, so the first time any source reaches a node IS the shortest distance from the NEAREST source. Running single-source BFS from each start separately would be O(S·(V+E)); the multi-source version is one pass at O(V+E) regardless of how many sources you have.

function multiSourceBFS(starts, graph) {
  // Seed the queue with EVERY start at distance 0, all marked seen.
  const q = starts.map(s => [s, 0]);
  const seen = new Set(starts);
  const dist = {};
  for (const s of starts) dist[s] = 0;
  while (q.length) {
    const [cur, d] = q.shift();
    for (const n of graph[cur] || []) {
      if (!seen.has(n)) {
        seen.add(n);                    // mark BEFORE enqueue — same rule as single-source
        dist[n] = d + 1;                // first arrival = shortest distance from the NEAREST source
        q.push([n, d + 1]);
      }
    }
  }
  return dist;
}
// Smoke test: diamond with A as the only source — same visit set as Variant A.
const order = Object.keys(multiSourceBFS(["A"], { A: ["B", "C"], B: ["D"], C: ["D"], D: [] }));

function bfsOrder(graph, start) {
  const q = [start];
  const seen = new Set([start]);
  const order = [];
  while (q.length) {
    const cur = q.shift();
    order.push(cur);
    for (const n of graph[cur] || []) {
      if (!seen.has(n)) { seen.add(n); q.push(n); }
    }
  }
  return order;
}
  • Seeding ALL sources at distance 0 up-front is the whole trick — they expand in lock-step, so the first arrival at any node comes from the NEAREST source. Running BFS from each source separately would be S× more work.
  • Same mark-before-enqueue discipline applies — without it a node mid-way between two sources gets enqueued twice and the distances may overwrite each other.
  • Returning a dist map gives you the shortest-distance-from-nearest-source for free in the same pass — no separate level-counting needed.

Q1 What ordering does a BFS queue produce, and what data-structure operation gives it?

  1. A LIFO — push + pop
  2. B FIFO — push + shift correct
  3. C Sorted — push + sort
  4. D Random — push + splice

Why: BFS visits nodes in arrival order: enqueue at the back (push), dequeue from the front (shift).

Q2 Why mark a node in seen BEFORE enqueueing it (instead of when you dequeue)?

  1. A So the BFS depth-counter increments only on the dequeue side, keeping levels aligned
  2. B Otherwise multiple neighbors can each enqueue the same node before any of them gets visited correct
  3. C It's faster to call seen.add during enqueue than during dequeue on V8
  4. D Otherwise the seen set grows past the graph's node count and breaks O(V) space

Why: If you wait until pop to mark seen, a high-degree node can be pushed many times — blowing up the queue and re-doing work.

Q3 In the level-order BFS, why snapshot const n = q.length BEFORE the inner for-loop?

  1. A So seen.size matches q.length at the level boundary
  2. B Because children pushed during the inner loop belong to the NEXT level, not the current one correct
  3. C To handle the case where q.shift() returns undefined on an empty queue
  4. D Because reading .length inside the loop creates a new iterator and breaks for...of

Why: Reading q.length live would grow as you push children, mixing the current level with the next.

Q4 What's the actual cost of queue.shift() on a JS array of length n, and why is it acceptable here?

  1. A O(1) — same as pop
  2. B O(log n) — the array is a tree internally
  3. C O(n) — every remaining element re-indexes; fine for interview-scale, swap to a head pointer if huge correct
  4. D O(n^2) — both shift and rebuild are linear

Why: shift re-indexes every remaining element. At interview scale (≤10^4) it's fine; at production scale, use a head index or deque.

Q5 You change q.shift() to q.pop() but leave everything else. What traversal do you get?

  1. A BFS but with each level visited right-to-left
  2. B DFS — popping the back makes the queue a LIFO stack correct
  3. C Reverse-BFS — the same node set in reverse arrival order
  4. D Topological order, since pop drains the most-recently-discovered branch first

Why: pop() takes the most-recently-pushed node (LIFO), which dives deep before broad — that's depth-first search, not breadth-first.

Q6 For finding the shortest path in an UNWEIGHTED graph, why is BFS the right tool over DFS?

  1. A DFS can revisit ancestors via recursion, inflating the path length
  2. B BFS reaches nodes in non-decreasing distance order, so the first time you reach the target is via a shortest path correct
  3. C DFS finds A path but never the shortest because its recursion stack drops backtracking info
  4. D BFS sorts neighbors by distance before visiting, which DFS skips

Why: BFS expands by levels (distance from start), so a node's first discovery is along a minimum-edge path; DFS may find the target via a long path first.

Q7 You drop the seen set entirely from BFS on a graph with cycles. What happens?

  1. A Each node is still visited once because the FIFO queue can't hold duplicates
  2. B Nodes get enqueued repeatedly, causing redundant work or an effectively infinite/exploding queue on cyclic graphs correct
  3. C The traversal silently terminates early when a back-edge is reached, missing nodes
  4. D Output order stays correct but time complexity degrades from O(V+E) to O(V·E)

Why: Without a visited check, every path back to a node re-enqueues it; on a cycle the queue never drains and work blows up. The seen set is what makes graph BFS terminate.
