Recognition checklist — read the bound off the loop/recursion shape

// ────────────────────────────────────────────────────────────
// 1. O(1) — CONSTANT TIME
// ────────────────────────────────────────────────────────────
//
//   The tell: no loop. No recursion. Direct lookups, arithmetic,
//   hash-table read/write — work that doesn't depend on input size.
//
const first = arr => arr[0];                  // bracket access
const last  = arr => arr[arr.length - 1];     // .length is O(1) too
const has   = (set, key) => set.has(key);     // Map/Set ops O(1) avg
//
//   n=10 → 1 step.  n=10,000,000 → 1 step.  Input size doesn't matter.


// ────────────────────────────────────────────────────────────
// 2. O(log n) — LOGARITHMIC: HALVE EACH STEP
// ────────────────────────────────────────────────────────────
//
//   The tell: each iteration discards HALF the remaining problem.
//   Binary search, balanced-tree descent, heap sift, repeated halving.
//
function binarySearch(arr, target) {
  let l = 0, r = arr.length - 1;
  while (l <= r) {
    const m = (l + r) >> 1;
    if (arr[m] === target) return m;
    if (arr[m] < target) l = m + 1;          // discard LEFT half
    else                 r = m - 1;          // discard RIGHT half
  }
  return -1;
}
//
//   Why "log"?  After k halvings the size is n / 2^k.
//   Loop ends when size ≤ 1, i.e. 2^k ≥ n, i.e. k ≥ log₂(n).
//
//   n=1,024            → ~10 steps
//   n=1,000,000        → ~20 steps
//   n=1,000,000,000    → ~30 steps
//
//   Logs grow GLACIALLY. Doubling n adds ONE step, not double the steps.
//   This is why binary search feels like cheating: 10 billion elements
//   take ~33 comparisons.


// ────────────────────────────────────────────────────────────
// 3. O(n) — LINEAR: ONE PASS
// ────────────────────────────────────────────────────────────
//
//   The tell: one loop over the input doing O(1) work per element.
//   Sum, count, max, single-pass two-pointer, hash-map first pass.
//
function maxOf(arr) {
  let best = -Infinity;
  for (const x of arr) {                     // ← one pass
    if (x > best) best = x;                  // ← O(1) per element
  }
  return best;
}
//
//   Doubling n doubles the time. Often optimal — you can't beat O(n)
//   for anything that has to LOOK AT every input element.


// ────────────────────────────────────────────────────────────
// 4. O(n log n) — LINEAR × LOG: SORT, MERGE, DIVIDE-AND-CONQUER
// ────────────────────────────────────────────────────────────
//
//   The tell: a sort step, or recursion that halves the input AND
//   does O(n) work at each level. Merge sort, heap sort, JS .sort().
//
function distinctCount(arr) {
  arr.sort((a, b) => a - b);                 // ← O(n log n) — dominates
  let runs = 1;
  for (let i = 1; i < arr.length; i++) {     // ← O(n) — dominated
    if (arr[i] !== arr[i - 1]) runs++;
  }
  return runs;
}
//
//   Big-O addition rule: O(n log n) + O(n) = O(n log n).
//   Keep the biggest term, drop the rest.
//
//   This is the floor for any comparison-based sort.


// ────────────────────────────────────────────────────────────
// 5. O(n²) — QUADRATIC: NESTED LOOPS OVER THE SAME INPUT
// ────────────────────────────────────────────────────────────
//
//   The tell: two nested loops, BOTH bounded by input size.
//   Pair brute force, naive substring search, distance matrix build.
//
function hasPairSum(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    for (let j = i + 1; j < arr.length; j++) {   // ← inner ALSO ∝ n
      if (arr[i] + arr[j] === target) return true;
    }
  }
  return false;
}
//
//   Even though the inner only runs n-i times, the SUM
//   1 + 2 + ... + (n-1) = n(n-1)/2 ≈ n²/2 — still O(n²).
//
//   Doubling n QUADRUPLES the time.
//   The canonical interview move is replacing an O(n²) brute force
//   with an O(n) single pass + hash map. Two Sum is the textbook case.


// ────────────────────────────────────────────────────────────
// THE RECOGNITION CHECKLIST
// ────────────────────────────────────────────────────────────
//
//   No loop at all? ............................. O(1)
//   Single loop, halving each step? ............. O(log n)
//   Single loop, one pass over n? ............... O(n)
//   Sort + single pass? ......................... O(n log n)
//   Two nested loops over the same input? ....... O(n²)
  • Halving each step → log. After k halvings, size is n / 2^k; loop ends when 2^k ≥ n, so k ≈ log₂(n). Doubling n adds ONE step, not double the steps — that's the logarithmic signature.
  • Drop constants and lower-order terms when reporting Big-O: O(2n + 3) = O(n), O(n log n + n) = O(n log n). The largest term dominates as n grows.
  • Nested loops aren't always O(n²) IF the inner bound is independent of n — but if the inner bound shrinks predictably (j = i+1…n), the sum is still ~n²/2 → still O(n²). What matters is whether the inner work is proportional to n.
  • Hash-map operations (Map.get, Map.set, Set.has) are O(1) AVERAGE — assume O(1) for interview analysis. The pathological O(n) only happens on adversarial inputs designed to collide.

Q1 A loop runs while n > 0 and does n = Math.floor(n / 2) each iteration. What's the complexity in terms of input n?

  1. A O(1)
  2. B O(log n) correct
  3. C O(n)
  4. D O(n log n)

Why: Halving each step → log. After k halvings, size is n/2^k; loop ends when 2^k ≥ n, so iterations ≈ log₂(n).

Q2 An algorithm runs in 100 steps when n=1,000 and 200 steps when n=2,000. Most likely complexity?

  1. A O(log n)
  2. B O(n) correct
  3. C O(n log n)
  4. D O(n²)

Why: Doubling n doubled the step count — linear's signature. O(log n) would add ~1 step; O(n²) would quadruple to ~400.

Q3 An algorithm runs in 100 steps when n=1,000 and ~110 steps when n=2,000. Most likely complexity?

  1. A O(1)
  2. B O(log n) correct
  3. C O(n)
  4. D O(n log n)

Why: Doubling n added only ~1 step — the unmistakable logarithmic signature. Each doubling of n bumps log₂(n) by exactly 1.

Q4 Outer for i in 0..n, inner for j in i+1..n, constant work in the body. What's the complexity?

  1. A O(n)
  2. B O(n log n)
  3. C O(n²) correct
  4. D O(2ⁿ)

Why: Inner runs n-i times per outer i. Sum is (n-1) + (n-2) + … + 1 = n(n-1)/2 ≈ n²/2 — still O(n²) after dropping constants.

Q5 arr.sort() followed by one linear scan of arr. Total complexity?

  1. A O(n)
  2. B O(n log n) correct
  3. C O(n²)
  4. D O(log n)

Why: Sort is O(n log n), scan is O(n). Sum is O(n log n) + O(n) = O(n log n) by the largest-term rule — the sort dominates.

Q6 Two loops one after another (not nested): first for i in 0..n, THEN a separate for j in 0..n. Total time?

  1. A O(n²) — there are two loops over n
  2. B O(n) — sequential loops add (2n), and constants drop correct
  3. C O(n log n)
  4. D O(2ⁿ)

Why: Sequential (not nested) loops ADD: n + n = 2n = O(n). Nesting multiplies; sequencing adds. Only nested-over-the-same-input loops give O(n²).

Q7 An algorithm builds an n×n distance matrix it must keep around. Its SPACE complexity is:

  1. A O(1)
  2. B O(n)
  3. C O(n²) correct
  4. D O(log n)

Why: Time and space are tracked separately — storing n² values means O(n²) extra space regardless of how fast the time is.

Q8 Pushing n items onto a dynamic array is O(n) total even though an occasional push triggers an O(n) resize. What is this called?

  1. A Probabilistic O(1) — assumes uniform hash distribution across capacity
  2. B Amortized O(1) per push — rare costly resizes spread out over many cheap pushes correct
  3. C Asymptotic O(log n) — the resize threshold doubles each time, so resizes are log n total
  4. D Aggregate O(n²) — n pushes can each trigger O(n) work, so the total is O(n²)

Why: Doubling-on-resize makes the expensive operations rare enough that the AVERAGE cost per push is O(1) — that averaged-over-a-sequence cost is the amortized cost.

L3 — Write it from memory

One position, the code's third segment.

Write countHalvings(n) that returns how many times the loop body runs in while (n > 0) { n = Math.floor(n / 2); }. Log countHalvings(64).

Hints
  • Initialize a counter at 0 and increment after each halving.
  • On n=64 you'll see 7 — that's ⌈log₂(64)⌉ + 1 = 6 + 1, because the final halving takes 1 down to 0.
  • This is the empirical proof of why binary search is O(log n): the step count grows by exactly 1 each time you double n.
function countHalvings(n) {
  let steps = 0;
  while (n > 0) {
    n = Math.floor(n / 2);
    steps++;
  }
  return steps;
}
console.log(countHalvings(64));
