Promises

Promises represent eventual values — chain with .then, handle errors with .catch, run cleanup in .finally.

Results carried by this link

Problem

Write doubleAsync(x) returning Promise.resolve(x * 2). Call doubleAsync(5) and log the resolved value with .then.

Expected output: 10

Canonical solution

// 1) Construct from scratch — executor gets resolve/reject
const p = new Promise((resolve, reject) => {
  if (Math.random() > 0.5) resolve(42);
  else reject(new Error("bad luck"));
});

// 2) Shortcut factories
Promise.resolve(7);              // already-fulfilled with 7
Promise.reject(new Error("x"));  // already-rejected

// 3) Chain .then — return values flow forward
Promise.resolve(5)
  .then(v => v * 2)              // 10
  .then(v => console.log(v));    // logs 10

// 4) .catch handles any rejection in the chain
Promise.reject(new Error("nope"))
  .then(v => console.log("never"))
  .catch(e => console.log("caught", e.message));

// 5) .finally runs after settle, no value passed
Promise.resolve(1).finally(() => console.log("done"));
  • Returning from .then becomes the next promise value; throwing inside .then becomes a rejection.
  • Without a .catch, an unhandled rejection just disappears (and warns in modern runtimes). Always terminate chains with .catch.
  • .finally is for cleanup — it does not receive the value or affect the resolved value.

L1 — Concept questions 4

Positions 1–4 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 What does Promise.resolve(7) return?

  1. A 7
  2. B A pending Promise
  3. C A Promise already fulfilled with 7 correct
  4. D undefined

Why: It wraps the value rather than handing it back — you still need .then (or await) to read the 7 out, which is exactly what doubleAsync relies on in L3.

Q2 A rejected Promise is handled by:

  1. A .then (rejections fall through to its single callback)
  2. B .catch correct
  3. C .finally (since it always runs, it can branch on rejection)
  4. D try/catch wrapped around the .then chain

Why: .catch(fn) is just .then(undefined, fn) — a rejection skips every fulfillment handler until it finds one. A surrounding try/catch never sees it, because the chain settles long after that block has exited.

Q3 What does throwing inside a .then callback do?

  1. A Propagates synchronously to the surrounding try/catch around the .then call
  2. B Becomes a rejected Promise the next .catch handles correct
  3. C Resolves the chain with the Error as the fulfilled value
  4. D Skips the rest of the chain and triggers unhandledrejection immediately

Why: The handler already runs in a microtask, so its throw can only settle the promise that .then returned — as rejected — and the next .catch downstream picks it up.

Q4 When does .finally run?

  1. A Only on success
  2. B Only on failure
  3. C After the Promise settles, either way correct
  4. D Before .then

Why: It fires on fulfill and reject alike, receives no argument, and passes the original settlement through untouched — a rejection stays rejected after .finally.
