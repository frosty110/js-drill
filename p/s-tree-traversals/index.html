Pre/in/post-order traversal

Three recursive tree-traversal shapes side-by-side — only the position of visit(n) moves between them.

patterns Algorithms 7 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Given the BST { val:2, left:{val:1,...}, right:{val:3,...} }, log its values in inorder — one console.log per value. Expected: 1, then 2, then 3 on separate lines.

Expected output: 1 2 3

Canonical solution

Recursive DFS — the position of visit(n) selects pre/in/post · O(n) / O(h) (time / space)

// Three recursive traversal shapes — only visit(n) moves

function preorder(n) {
  if (!n) return;
  visit(n);                 // root FIRST
  preorder(n.left);
  preorder(n.right);
}

function inorder(n) {
  if (!n) return;
  inorder(n.left);
  visit(n);                 // root MIDDLE
  inorder(n.right);
}

function postorder(n) {
  if (!n) return;
  postorder(n.left);
  postorder(n.right);
  visit(n);                 // root LAST
}

// Classic uses:
//   preorder  -> serialize a tree, clone, print structure top-down
//   inorder   -> BST scan in SORTED order
//   postorder -> bottom-up aggregation (subtree sum, height, safe delete)
  • Inorder on a BST yields values in sorted ascending order — that is the one-line BST invariant.
  • Preorder visits root before children — natural for serialize/clone (you have the root before recursing).
  • Postorder visits children before root — natural for bottom-up aggregation (subtree sum, height, safe delete).
  • All three are O(n) time and O(h) recursion-stack space — only the visit position differs.

Alternate approaches

Iterative inorder (explicit stack) O(n) / O(h)

Reach for this when the interviewer asks for the iterative formulation, or when the tree could be deep enough (≥10k nodes) to blow JS's recursion stack. Same O(n) time, O(h) stack space — but the 'stack' is explicit and controlled rather than the call stack.

function inorder(n) {
  const stack = [];
  let curr = n;
  while (curr || stack.length) {
    while (curr) {
      stack.push(curr);
      curr = curr.left;
    }
    curr = stack.pop();
    console.log(curr.val);
    curr = curr.right;
  }
}
const root = { val: 2, left: { val: 1, left: null, right: null }, right: { val: 3, left: null, right: null } };
inorder(root);
  • Walk all the way down the left chain first (inner while), then pop-and-visit, then pivot right.
  • The outer while (curr || stack.length) handles both 'not yet exhausted left chain' and 'stack still has ancestors waiting'.
  • Preorder iterative is simpler (just push right then left after visiting); postorder needs a second stack or a reverse trick.

Q1 Which traversal yields a BST's values in sorted ascending order?

  1. A preorder
  2. B inorder correct
  3. C postorder
  4. D level-order (BFS)

Why: BST invariant: left < node < right. Visiting in left -> node -> right order emits sorted output.

Q2 In preorder traversal, when is the current node visited relative to its children?

  1. A After both children
  2. B Between the two children
  3. C Before either child correct
  4. D After the left child but before the right child

Why: In preorder, visit(n) sits above BOTH recursive calls, so the parent is emitted before either subtree. "Between the two children" is inorder; "after both" is postorder.

Q3 Postorder traversal is the natural choice for which task?

  1. A Serializing a tree top-down
  2. B Scanning a BST in sorted order
  3. C Bottom-up aggregation like subtree sum or safe delete correct
  4. D Finding the shortest path between two nodes

Why: Postorder finishes both children before the parent, so you have child results ready when you visit the parent.

Q4 Across all three traversals, what changes between them?

  1. A The recursion order (left-then-right vs right-then-left)
  2. B Whether the function returns a value or accumulates into an output array
  3. C Only the position of visit(n) correct
  4. D The base case — postorder returns at internal nodes, preorder returns at leaves

Why: Left-then-right order is identical; only where visit(n) sits relative to the two recursive calls changes.

Q5 Which traversal is the natural choice for serializing a tree so it can be rebuilt by reading nodes in order?

  1. A preorder — you emit the root before its subtrees, so deserialization knows the parent before its children correct
  2. B inorder — sorted output rebuilds the tree
  3. C postorder — children-first is easiest to rebuild
  4. D Any of them work identically for serialization

Why: Preorder emits root-first, so a recursive deserializer reads the parent, then reconstructs left then right subtrees — inorder alone is ambiguous for reconstruction.

Q6 What is the time and recursion-stack space cost of any of these traversals on a tree of n nodes with height h?

  1. A O(n log n) time, O(n) space
  2. B O(n) time, O(h) space correct
  3. C O(h) time, O(n) space
  4. D O(n) time, O(n) space always

Why: Every node is visited once → O(n) time; the call stack only holds the current root-to-node path → O(h), which is O(log n) for balanced and O(n) for a degenerate (linked-list) tree.

Q7 To write an ITERATIVE traversal that mimics the recursion, which auxiliary structure replaces the call stack?

  1. A A queue (FIFO)
  2. B An explicit stack (LIFO) correct
  3. C A min-heap
  4. D A hash set

Why: Recursion uses the call stack (LIFO), so an iterative version pushes/pops an explicit stack; using a queue instead would give level-order (BFS), not a depth-first traversal.
