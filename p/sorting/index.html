Sort with comparator

`.sort()` MUTATES and defaults to STRING comparison. Always pass a comparator for numbers.

patterns Algorithms 7 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write sortByAge(arr) returning the array sorted by .age ascending. Log JSON.stringify(sortByAge([{name:"A",age:30},{name:"B",age:25}])).

Expected output: [{"name":"B","age":25},{"name":"A","age":30}]

Canonical solution

Comparator sort in place (project onto a numeric key) · O(n log n) / O(log n) (time / space)

// Numbers ascending
arr.sort((a, b) => a - b);

// Numbers descending
arr.sort((a, b) => b - a);

// Strings (locale-aware)
arr.sort((a, b) => a.localeCompare(b));

// Objects by key
arr.sort((a, b) => a.age - b.age);

// Non-mutating copy
const sorted = [...arr].sort((a, b) => a - b);
  • .sort MUTATES the original array. Use [...arr].sort() if you need a copy.
  • Default sort converts to string, so [10, 2, 1].sort() gives [1, 10, 2].
  • Comparator returns negative → a first, positive → b first, 0 → equal (order preserved on stable sorts).
  • Time O(n log n) / Space O(log n) auxiliary (TimSort's run stack).

Alternate approaches

.toSorted() — non-mutating (ES2023) O(n log n) / O(n)

Reach for this when the caller must not observe a changed array, or when you're in a functional pipeline where mutation is a bug. Same O(n log n) / O(n) cost as [...arr].sort() but cleaner to read.

function sortByAge(arr) {
  return arr.toSorted((a, b) => a.age - b.age);
}
console.log(JSON.stringify(sortByAge([{name:'A',age:30},{name:'B',age:25}])));
  • Returns a NEW sorted array; the input is untouched — unlike .sort() which mutates in place.
  • Available in Node 20+ and all modern browsers (ES2023); polyfill with [...arr].sort(...) for older targets.
  • The comparator syntax is identical to .sort() — the only change is the method name.

Q1 What does [10, 2, 1].sort() produce?

  1. A [1, 2, 10]
  2. B [10, 2, 1]
  3. C [1, 10, 2] correct
  4. D TypeError

Why: Default sort compares as strings: "1" < "10" < "2".

Q2 Does .sort() mutate?

  1. A Yes correct
  2. B No — returns a new sorted array, like .map
  3. C Only when the comparator returns 0 for some pair (otherwise it sorts a copy)
  4. D Mutates only if the array has more than 10 elements (V8 picks insertion-sort-on-copy below that threshold)

Why: .sort() reorders in place and returns the SAME array reference — which is why the canonical return arr.sort((a, b) => a.age - b.age) hands back the caller's own array, reordered. .map returns a new array; .sort does not.

Q3 To sort numbers descending, pass:

  1. A (a, b) => a - b
  2. B (a, b) => b - a correct
  3. C (a, b) => a > b
  4. D (a, b) => -1

Why: Flipping the operands flips the order: when a is the larger value, b - a is negative, so a is placed first. (a, b) => a > b returns a boolean that coerces to 1/0 — never negative — so it can't order anything.

Q4 A comparator returning a negative number means:

  1. A Skip this pair — the sort tries again with a different pivot
  2. B a comes before b correct
  3. C b comes before a
  4. D Sorts in descending order, regardless of which arg is bigger

Why: The comparator contract is negative → a first, positive → b first, 0 → equal. That's exactly why a - b sorts ascending: whenever a < b the difference is negative and a lands ahead.

Q5 You need the sorted result but must NOT change the original array. Which is correct?

  1. A arr.sort((a, b) => a - b)
  2. B [...arr].sort((a, b) => a - b) correct
  3. C arr.sorted((a, b) => a - b)
  4. D Array.sort(arr)

Why: .sort() mutates in place, so copy first with [...arr] (or arr.slice()); there is no non-mutating .sorted() on arrays.

Q6 You write (a, b) => a > b as a numeric comparator. What's the bug?

  1. A It works fine for numbers
  2. B It returns a boolean (true/false), which coerces to 1/0 — it never returns a negative, so the sort order is unreliable correct
  3. C It throws a TypeError
  4. D It only sorts descending

Why: A comparator must return negative/zero/positive; a > b yields true/false → 1/0, never negative, so equal-or-less cases are indistinguishable and ordering is broken.

Q7 Two objects compare equal under your comparator. A 'stable' sort guarantees what about them?

  1. A They are coalesced — only the first instance is kept, the rest are dropped
  2. B Their relative order from the input is preserved correct
  3. C They are grouped together but their internal order depends on the sort algorithm chosen at runtime
  4. D Stability only applies when sorting primitives; objects always sort in unspecified order

Why: Stability means equal elements keep their original relative order — modern V8 .sort() is stable, which matters when sorting by a secondary key after a primary one.
