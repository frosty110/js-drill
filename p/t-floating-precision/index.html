Floating-point precision (0.1 + 0.2)

JS numbers are IEEE 754 doubles, so 0.1 + 0.2 !== 0.3 and most decimal fractions can't be represented exactly in binary — compare with an epsilon, round with toFixed, or scale to integers for money math.

Problem

Write nearlyEqual(a, b, eps) that returns true when |a - b| <= eps. Then log: the raw value of 0.1 + 0.2, whether 0.1 + 0.2 === 0.3, whether nearlyEqual(0.1 + 0.2, 0.3, 1e-9), and whether nearlyEqual(0.1 + 0.2, 0.4, 1e-9) — one result per line.

Expected output: 0.30000000000000004 false true false

Canonical solution

// The classic surprise — 0.1 + 0.2 is NOT 0.3 in binary floating point.
console.log(0.1 + 0.2);            // 0.30000000000000004
console.log(0.1 + 0.2 === 0.3);    // false

// Why: 0.1 and 0.2 are infinite repeating fractions in binary,
// just like 1/3 is 0.333... in decimal. Doubles get 52 bits of
// mantissa, so the stored value is the nearest representable double.

// Fix 1 — epsilon comparison. Number.EPSILON ~ 2.22e-16 is the
// smallest gap near 1.0; for friendlier real-world tolerance use 1e-9.
const a = 0.1 + 0.2;
const b = 0.3;
console.log(Math.abs(a - b) < Number.EPSILON); // true (diff is ~5.5e-17)
console.log(Math.abs(a - b) < 1e-9);           // true (friendlier threshold)

// Fix 2 — toFixed then string-compare. toFixed RETURNS A STRING.
console.log(a.toFixed(2));                     // "0.30"
console.log(a.toFixed(2) === b.toFixed(2));    // true

// Fix 3 — scale to integers. Best for money: store cents, not dollars.
// Naive  0.1 * 100 + 0.2 * 100  can STILL be 30.000000000000004,
// so wrap each scaled term in Math.round before adding.
const cents = Math.round(0.1 * 100) + Math.round(0.2 * 100);
console.log(cents / 100);                      // 0.3

// Money example — summing a receipt without losing pennies.
const prices = [0.1, 0.2, 0.3];
let totalCents = 0;
for (const p of prices) totalCents += Math.round(p * 100);
console.log(totalCents / 100);                 // 0.6
  • Why it happens: 0.1 and 0.2 are infinite repeating fractions in binary, so the stored IEEE 754 double is the nearest representable value — the rounding error surfaces on add.
  • Number.EPSILON (~2.22e-16) is the gap between 1 and the next representable double; for values away from 1 you usually want a friendlier tolerance like 1e-9.
  • === between two floats is almost always wrong unless one side is an integer literal you control end-to-end.
  • toFixed(n) returns a STRING, not a number. Useful for display or string-compare, never for further arithmetic without re-parsing.
  • For money, store integer cents (or use a library like decimal.js / big.js). Round each scaled term — 0.1 * 100 can already be 10.000000000000002.
  • The trap appears in many languages — it's not a JS bug, it's IEEE 754. Python's 0.1 + 0.2 prints 0.30000000000000004 too.

Q1 What does console.log(0.1 + 0.2) print?

  1. A 0.3
  2. B 0.30000000000000004 correct
  3. C 0.30000000000000001
  4. D NaN

Why: IEEE 754 can't represent 0.1 or 0.2 exactly in binary — the sum lands at the nearest representable double, which prints with the trailing ...004.

Q2 What is 0.1 + 0.2 === 0.3?

  1. A true
  2. B false correct
  3. C throws TypeError
  4. D NaN

Why: The left side is 0.30000000000000004, not 0.3 — strict equality on floats almost always loses to rounding error.

Q3 Which is the safest way to check that two floats are 'equal' within tolerance?

  1. A a === b
  2. B a == b
  3. C Math.abs(a - b) < 1e-9 correct
  4. D Object.is(a, b)

Why: Compare the absolute difference against an epsilon. Object.is is even stricter than === for numbers and doesn't help with rounding error.

Q4 What type does (0.1 + 0.2).toFixed(2) return?

  1. A number
  2. B string correct
  3. C boolean
  4. D BigInt

Why: toFixed returns a string. Useful for display or string-compare, but you'll need Number(...) or +... to do further math.

Q5 Why store money as integer cents instead of dollar floats?

  1. A Integers are faster on modern CPUs
  2. B Floats can lose pennies because 0.1, 0.2, etc. aren't exactly representable correct
  3. C JavaScript numbers don't support decimals
  4. D JSON can't serialize float values

Why: Summing 0.1 + 0.2 + 0.3 as floats can drift away from 0.6. Scaling to integer cents (and rounding each scaled term) sidesteps the rounding error entirely.

One position, the code's third segment.

Write nearlyEqual(a, b, eps) that returns true when |a - b| <= eps. Then log: the raw value of 0.1 + 0.2, whether 0.1 + 0.2 === 0.3, whether nearlyEqual(0.1 + 0.2, 0.3, 1e-9), and whether nearlyEqual(0.1 + 0.2, 0.4, 1e-9) — one result per line.

Hints
  • Math.abs(a - b) collapses both signs of the gap into one nonnegative number.
  • <= (not <) is the conventional comparison so exact-equal values also pass.
  • 1e-9 is a friendlier tolerance than Number.EPSILON (~2.22e-16) when the values aren't right at 1.0.
function nearlyEqual(a, b, eps) {
  return Math.abs(a - b) <= eps;
}
