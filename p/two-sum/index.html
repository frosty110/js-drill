Two Sum (hash map)

Find indices of two values that sum to target. The canonical hash-map pattern. O(n).

patterns Arrays & Hashing 8 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write twoSum(nums, target) returning the indices of two numbers that add to target, or [] if no pair exists. O(n). Log JSON.stringify(twoSum([2, 7, 11, 15], 9)).

Expected output: [0,1]

Canonical solution

Hash map (one-pass complement lookup) · O(n) / O(n) (time / space)

function twoSum(nums, target) {
  const seen = new Map();          // value → index
  for (let i = 0; i < nums.length; i++) {
    // Complement: the partner value we'd need to hit target.
    const need = target - nums[i];
    // Check BEFORE set — prevents matching the current element with itself.
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
}
// Time O(n), Space O(n)
  • Check BEFORE you set — that prevents matching an element with itself.
  • Map stores VALUE → INDEX (not the other way around).
  • Return immediately on first match. The problem promises exactly one answer exists.

L1 — Concept questions 8

Positions 1–8 of the code's first segment. The correct option is marked; in the app the options are shuffled, but the lettering here is the authored order the code refers to.

Q1 Why check seen.has(need) BEFORE seen.set?

  1. A So seen.get(need) returns the smaller of the two paired indices
  2. B To avoid matching the current element with itself correct
  3. C To preserve the Map's insertion order during iteration
  4. D To skip storing duplicate values, keeping the Map small

Why: When target is 2 * nums[i], need equals nums[i] itself; checking first means the current element isn't in the map yet, so it can't pair with its own index. On [3,3] target 6 the second 3 still matches the first — the guard blocks self-matching, not duplicates.

Q2 Time complexity?

  1. A O(n²)
  2. B O(n log n)
  3. C O(n) correct
  4. D O(1)

Why: One pass over nums doing an O(1) seen.has and seen.set per element — no inner scan and no sort, so n × O(1) is O(n).

Q3 Space complexity?

  1. A O(1)
  2. B O(log n)
  3. C O(n) correct
  4. D O(n²)

Why: The Map gains one entry per element visited before the match and nothing is ever removed, so a match on the last element leaves n−1 entries stored.

Q4 The Map stores:

  1. A index → value
  2. B value → index correct
  3. C value → count
  4. D index → complement

Why: seen.set(nums[i], i) keys by value so seen.has(need) can look up a complement VALUE, and seen.get(need) then hands back the partner's index for the returned pair. Keying by index would leave you scanning for the value again.

Q5 Why store value → index rather than just value → true (a Set)?

  1. A A Set would be slower to query than a Map
  2. B The problem asks for the INDICES of the pair, so we need the partner's index to return it correct
  3. C A Set can't tell you whether the same value appears twice in the array
  4. D Sets are limited to ~32 entries before degrading to a list

Why: We must return [i, j] indices; a Set only tells you a value was seen, not where, so it cannot reconstruct the answer.

Q6 Why is the hash-map approach O(n) while brute force is O(n²)?

  1. A The map approach only scans half the array because it returns early
  2. B The map turns each complement search into an O(1) lookup instead of an O(n) inner scan correct
  3. C Hashing pre-sorts the array, dropping the inner loop to O(log n)
  4. D Map iteration is faster than array iteration on modern engines

Why: Brute force scans the rest of the array (O(n)) for each element; the map makes that lookup O(1), so n elements times O(1) is O(n).

Q7 On input nums=[3,3], target=6, what does the canonical return?

  1. A [0,0]
  2. B [0,1] correct
  3. C [] (no pair)
  4. D It throws

Why: i=0 stores 3→0; i=1 sees need=3 already in the map and returns [0,1] — the check-before-set order pairs the two distinct 3s without reusing an index.

Q8 Why prefer the hash map over sorting the array then using two pointers?

  1. A Two pointers is asymptotically slower at O(n log n) than the map's O(n)
  2. B Sorting destroys the original indices, which this problem must return correct
  3. C Sorting in place uses more memory than a map of size n
  4. D Two pointers can't find pairs when the target is larger than the array's max value

Why: Sorting reorders elements so you lose the original positions; since the answer is indices, you'd need extra bookkeeping — the map preserves index info directly.

function twoSum(nums, target) {
  // Map of value → index so we can return the partner's index.
  const seen = new Map();
  for (let i = 0; i < nums.length; i++) {
    // Complement: the partner value we'd need to hit target.
    const need = target - nums[i];
    // Check BEFORE set — prevents matching the current element with itself.
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
  return [];                                       // explicit miss case
}
