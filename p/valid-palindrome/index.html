Valid Palindrome

Two-pointer convergence: left and right walk inward comparing characters. O(n) time, O(1) extra.

patterns Two Pointers 8 concept · 2 fill-in · 1 drill

Results carried by this link

Problem

Write isPalindrome(s) ignoring case and non-alphanumeric. Log isPalindrome("A man, a plan, a canal: Panama").

Expected output: true

Canonical solution

function isPalindrome(s) {
  // Normalize: lowercase + strip non-alphanumeric ([^...] = negated class, /g = all).
  const clean = s.toLowerCase().replace(/[^a-z0-9]/g, '');
  let l = 0, r = clean.length - 1;
  // l < r (not <=) — the middle char in odd-length strings trivially matches itself.
  while (l < r) {
    if (clean[l] !== clean[r]) return false;
    l++;
    r--;
  }
  return true;
}
// Time O(n), Space O(n) for clean; O(1) if you skip in-place
  • Always lowercase + strip non-alphanumeric for "ignore case/spaces" palindromes.
  • Loop condition is l < r (not <=) — the middle char trivially matches itself.
  • /[^a-z0-9]/g: ^ inside [] negates the class; /g makes replace replace all.

Alternate approaches

In-place O(1) space (skip non-alnum on original) O(n) / O(1)

Reach for this when the interviewer asks for O(1) extra space — no cleaned string is allocated. The tradeoff is fiddlier logic: each pointer must skip non-alphanumeric characters before comparing.

function isPalindrome(s) {
  const isAlnum = c => (c >= 'a' && c <= 'z') || (c >= '0' && c <= '9');
  let l = 0, r = s.length - 1;
  while (l < r) {
    while (l < r && !isAlnum(s[l].toLowerCase())) l++;
    while (l < r && !isAlnum(s[r].toLowerCase())) r--;
    if (l < r) {
      if (s[l].toLowerCase() !== s[r].toLowerCase()) return false;
      l++;
      r--;
    }
  }
  return true;
}
console.log(isPalindrome('A man, a plan, a canal: Panama'));
  • Two inner while-loops skip non-alphanumeric chars before each comparison — the l < r guard prevents over-running on punctuation-only inputs.
  • The outer if (l < r) after the skip loops protects against comparing past the midpoint when both skip-loops exhaust the window simultaneously.
  • O(1) extra space vs. the cleaned-string approach's O(n); the same O(n) time since each character is visited at most once by l or r.

Reverse-and-compare O(n) / O(n)

The simplest first-pass: clean the string, reverse it, compare with ===. Correct but allocates an extra O(n) reversed string — use only when code clarity matters more than the second allocation.

function isPalindrome(s) {
  const clean = s.toLowerCase().replace(/[^a-z0-9]/g, '');
  const reversed = clean.split('').reverse().join('');
  return clean === reversed;
}
console.log(isPalindrome('A man, a plan, a canal: Panama'));
  • Three array operations (split, reverse, join) each traverse the cleaned string once — still O(n), just with higher constant.
  • Does not short-circuit on a mismatch — must fully build the reversed string even if the first and last chars differ.
  • Both clean and reversed are O(n) allocations; the two-pointer approach halves this by allocating only clean.

Q1 Why l < r rather than l <= r?

  1. A l <= r would read clean[r] one past the end on even-length strings, returning undefined
  2. B The middle character trivially equals itself correct
  3. C l <= r causes l and r to swap roles after they meet, reverse-walking the same pairs
  4. D l <= r is fine; the convention is < only to mirror C-style array bounds

Q2 What does the regex /[^a-z0-9]/g match?

  1. A Any letter or digit
  2. B Anything that is NOT a lowercase letter or digit correct
  3. C Whitespace only
  4. D Punctuation only

Why: ^ inside a character class negates it; /g replaces every match.

Q3 Time complexity?

  1. A O(log n)
  2. B O(n) correct
  3. C O(n log n)
  4. D O(n²)

Q4 The canonical two-pointer convergence pattern is:

  1. A Both start at 0, walk forward at different speeds (fast/slow)
  2. B One at 0 and one at end, walking inward correct
  3. C Both at the end, walking leftward in lockstep
  4. D Both at the midpoint, walking outward to the ends

Q5 On input ".," (only punctuation), the cleaned string is empty, so r = -1. Why does the function still correctly return true?

  1. A An explicit if (clean.length === 0) return true short-circuits the loop on empty input
  2. B The loop condition l < r is 0 < -1, which is false, so the loop never runs and it falls through to return true correct
  3. C clean[0] !== clean[-1] is both undefined, so undefined === undefined keeps the loop running until l > r terminates it
  4. D r = -1 is coerced to clean.length - 1 = 0 at the comparison, so l < r becomes 0 < 0 and the loop exits cleanly

Why: With clean = "", r = -1, so 0 < -1 is false; the loop is skipped and the empty/punctuation-only string is treated as a palindrome by convention.

Q6 Why must the normalize step (lowercase + strip non-alphanumeric) run BEFORE setting up the pointers, not inside the loop?

  1. A Because String.prototype.replace mutates the underlying string and would invalidate l and r mid-loop
  2. B Because the pointers index into the cleaned string, and r = clean.length - 1 needs the final cleaned length correct
  3. C Because toLowerCase invalidates the regex engine's compiled pattern, so it can only be called once per scope
  4. D Because the global /g flag preserves state between calls — running it in the loop would advance the regex past characters we still need to inspect

Why: l and r index the cleaned string; r is initialized from clean.length - 1, so the cleaning must already be done before the pointers are positioned.

Q7 What is the extra space complexity of this implementation, and could it be reduced?

  1. A O(1) always — no extra allocation happens
  2. B O(n) for the cleaned string; it could be O(1) by walking two pointers on the original string and skipping non-alphanumeric chars in place correct
  3. C O(n) and it cannot be reduced below O(n)
  4. D O(log n) due to the regex engine

Why: Building clean allocates O(n); an in-place variant skips non-alphanumeric chars while comparing s directly, achieving O(1) extra space at the cost of fiddlier skip logic.

Q8 If a mismatch is found at the second pair, two pointers returns immediately. How does this compare to a reverse-and-compare approach on the same non-palindrome input?

  1. A Reverse-and-compare is faster because it uses built-ins
  2. B Two pointers short-circuits on the first mismatch, while reverse-and-compare must build the full reversed string before comparing correct
  3. C They do exactly the same amount of work
  4. D Reverse-and-compare also short-circuits automatically

Why: Both are O(n) worst case, but two pointers bails out at the first mismatch; reverse-and-compare materializes the whole reversed string first regardless of where the mismatch is.
