Planning

Turn a goal into a sequence of steps before or while acting. Planning ranges from an explicit plan artifact produced up front and then executed, to interleaved plan-act-observe loops that decide the next step from what the last one returned. The explicit plan buys inspectability, validation, parallelization, and human review; the interleaved loop buys adaptability. Both need replanning, step budgets, and a definition of done.

Key ideas

  • Planning separates deciding what to do from doing it, which is what makes an agent's behaviour reviewable before anything irreversible happens.
  • Plan-then-execute produces an artifact you can validate, show to a human, parallelize, cache, and resume; interleaved planning (act, observe, decide) adapts to what it finds but is harder to inspect ahead of time.
  • A plan is a hypothesis, not a contract: the world changes and steps fail, so replanning on failure or on new information is part of the pattern rather than an error path.
  • Plans should reference only tools and resources that exist — validating a plan against the real tool catalog before execution catches hallucinated steps cheaply.
  • Every plan needs a success criterion per step and for the goal overall, or the agent cannot tell progress from motion.
  • Planning is overhead: for simple, single-step requests it adds latency and cost for nothing, so it should be applied when the task genuinely has multiple interdependent steps.
  • Hierarchical planning — a high-level plan whose steps expand into sub-plans — keeps long tasks tractable without one enormous flat step list.

Q1 multiple choice

What is the main advantage of producing an explicit plan artifact before execution?

  1. A It reduces the number of model calls to one
  2. B It makes the intended actions inspectable and validatable before anything is executed — enabling human review, tool validation, parallelization, and resumption correct
  3. C It guarantees the plan will succeed
  4. D It removes the need for error handling

Why: The artifact is the point. You can check that every step references a real tool, spot destructive actions before they happen, run independent steps concurrently, show it to a user for approval, and resume from step four after a crash.

Q2 multiple choice

How does interleaved planning (plan, act, observe, replan) differ in its tradeoffs?

  1. A It is always cheaper than plan-then-execute
  2. B It cannot use tools
  3. C It adapts to what each step reveals, which suits uncertain environments, but the trajectory is not knowable in advance so it is harder to review, bound, and predict correct
  4. D It only works with a single tool

Why: When you cannot know the next step until you see the last result — searching, debugging, browsing — interleaving is the right shape. The cost is that you cannot approve the whole plan up front, so bounds and per-step permission checks carry the safety load.

Q3 multiple choice

Why is replanning a first-class part of the pattern rather than an exception?

  1. A Because models cannot produce correct plans
  2. B Because steps fail and the world changes — a plan built on assumptions that turn out false must be revised, not blindly retried correct
  3. C Because providers require it
  4. D Because plans expire after a fixed time

Why: A plan is a hypothesis about how to reach the goal. When a step returns something unexpected — the record does not exist, the API changed, the file is empty — the correct response is to revise the plan with that new information, which is why plans should be revisable state rather than a fixed script.

Q4 multiple choice

What cheap validation should run on a generated plan before execution begins?

  1. A A grammar check on the plan text
  2. B Re-generating the plan five times and comparing
  3. C Checking that every referenced tool, resource, and parameter actually exists and is permitted, and flagging destructive or costly steps correct
  4. D Translating the plan into another language and back

Why: Planners hallucinate tools and resources that would be convenient. A schema-level check against the real catalog catches that before the first call, and surfacing the destructive steps lets policy decide whether a human should approve them.

Q5 multiple choice

Why does each step need a success criterion?

  1. A To satisfy logging requirements
  2. B Because without one the agent cannot distinguish progress from motion — it may loop, repeat a step, or declare success on partial results correct
  3. C Because criteria reduce token usage
  4. D Because criteria are needed to parallelize

Why: 'Did this step accomplish what it was for?' is the signal that drives advancing, retrying, or replanning. Without it, the loop is running on vibes and the classic failure — repeating the same action and calling it progress — becomes invisible.

Q6 multiple choice

When is planning the wrong pattern?

  1. A When the request is simple and single-step — the planning overhead adds latency and cost while producing a one-item plan correct
  2. B When the task requires more than one tool
  3. C When a human must approve the outcome
  4. D When the environment is uncertain

Why: Planning earns its keep on multi-step, interdependent tasks. Applying it to every request means paying an extra call and a second of latency to be told that the answer is one search away — which is why many systems route simple requests around the planner entirely.

Q7 multiple choice

What does hierarchical planning add for long tasks?

  1. A It removes the need for tools at the leaf level
  2. B It guarantees parallel execution
  3. C It keeps the top-level plan short and comprehensible while letting each step expand into its own sub-plan when executed — avoiding one enormous flat list that drifts correct
  4. D It caches the plan across users

Why: Long flat plans degrade: later steps are guesses made without the information earlier steps produce. Expanding a step into a sub-plan at execution time means the detail is decided when the relevant context exists.

Q8 explain & apply

Design the planning layer for an agent that handles multi-step operational tasks (for example: 'investigate why the nightly job failed and open a ticket with the cause'). Cover plan generation, validation, execution, and failure.

Points a strong answer hits:

  • Generate a structured plan — ordered steps with the tool, arguments, expected outcome, and dependencies — rather than prose.
  • Validate the plan before executing: tools exist, permissions allow them, arguments type-check, and destructive steps are flagged.
  • Classify steps by risk: read-only investigation runs automatically, write actions (ticket creation, restarts) need approval or stricter checks.
  • Execute with per-step success criteria, running independent steps in parallel where dependencies allow.
  • Feed observations back and replan when a step fails or reveals something the plan did not anticipate, rather than continuing on stale assumptions.
  • Bound everything: step count, wall-clock, and cost, with a clear escalation to a human when a bound is hit.
  • Keep the plan and its revisions as inspectable state, with a full trace of steps, arguments, and outcomes.
  • Define done: the goal's success criterion is the ticket existing with a cause supported by evidence, not merely the steps having run.
Model answer: I would have the planner emit a structured artifact rather than prose: an ordered list of steps, each naming the tool, its arguments, the expected outcome, and which earlier steps it depends on. That structure is what everything else keys off. Before anything runs, the plan is validated mechanically — every tool exists, the current principal is allowed to call it, arguments type-check, and any step that writes or restarts something is flagged. That single pass catches the hallucinated tool and the accidentally destructive step at zero risk. Then I classify by risk: read-only investigation — fetching logs, checking job history, querying metrics — runs automatically, while write actions like opening the ticket or restarting a service require either approval or, for low-stakes writes, an idempotency guarantee and a preview. Execution walks the dependency graph, running independent steps concurrently, with a success criterion per step so the loop can tell whether to advance, retry, or stop. Observations feed back into the plan, and when a step fails or turns up something unexpected — the job did not fail, it never started — the agent replans rather than pushing on through a plan whose premise is now false. I bound the whole thing three ways: maximum steps, wall-clock, and cost, with any breach escalating to a human with the trace attached rather than silently continuing. The plan and all its revisions stay as inspectable state, alongside a full trace of calls and outcomes, because for operational work the reasoning is as valuable as the result. And I define done at the goal level: the task is complete when a ticket exists whose stated cause is supported by evidence the trace contains — not when the last step returned without error.

Q9 explain & apply

Compare plan-then-execute with a ReAct-style interleaved loop. When would you choose each, and can they be combined?

Points a strong answer hits:

  • Plan-then-execute suits tasks whose steps can be known up front: predictable workflows, batch processing, anything needing pre-approval.
  • It enables review, validation, parallel execution of independent steps, caching, and resumption from a known point.
  • Interleaved loops suit exploration and uncertainty — searching, debugging, browsing — where each observation determines the next action.
  • Interleaving is harder to bound and audit ahead of time, so safety shifts to per-step permission checks, step budgets, and loop detection.
  • Cost/latency differ: an up-front plan is one extra call but enables parallelism; interleaving is sequential by nature and multiplies round trips.
  • Hybrid: plan at a high level, execute steps that themselves run interleaved sub-loops, replanning when a step's outcome invalidates the plan.
  • The choice should follow the environment's predictability and the risk of the actions, not stylistic preference.
Model answer: The deciding question is whether the next step is knowable before the previous one runs. If it is — a defined workflow, a batch of documents, an onboarding sequence — plan-then-execute is clearly better. You get an artifact you can validate against the tool catalog, show to a human for approval, execute with independent steps in parallel, cache, and resume from step four after a crash. All of that is impossible when the trajectory only exists in hindsight. If the next step genuinely depends on what the last one returned — investigating a failure, searching until you find the answer, debugging — then an interleaved loop is the honest model, and forcing a plan up front just produces a fiction that is wrong by step two. The price is that you cannot approve the trajectory in advance, so the safety burden moves to per-step permission checks, tight step and cost budgets, and loop detection so the agent does not repeat the same query forever. It is also inherently sequential: every step is a round trip, so latency grows linearly. In practice I combine them, and I think the hybrid is the default in serious systems. Plan at a coarse level — investigate, then diagnose, then act — validate that plan and get approval for the acting phase, then let each step run its own bounded interleaved sub-loop that adapts to what it finds. When a step's outcome invalidates the premise of the plan, replan at the coarse level rather than thrashing inside a step. That gives you the reviewability of an explicit plan where the risk is, and the adaptability of ReAct where the uncertainty is.
