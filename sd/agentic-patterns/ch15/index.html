Inter-Agent Communication (A2A)

Agents talking to agents across ownership boundaries, rather than an agent talking to tools inside one application. The A2A style of protocol gives agents a way to advertise capabilities, hand each other tasks, exchange messages and artifacts, stream progress on long-running work, and authenticate — so an agent built by one team or vendor can delegate to one built by another.

Key ideas

  • A2A addresses agent-to-agent delegation across trust and ownership boundaries; MCP addresses an agent reaching tools and data. They are complements, not competitors.
  • Capability advertisement (an agent card or equivalent) is what makes delegation possible without a hardcoded integration — the client learns what a remote agent can do and how to reach it.
  • Delegated work is task-shaped, not request-shaped: tasks have identity, lifecycle states, incremental updates, and produced artifacts, because remote agent work can run for minutes or hours.
  • Streaming and asynchronous updates are first-class, since a remote agent that will take ten minutes cannot fit in a synchronous request/response.
  • Crossing an ownership boundary means the remote agent is untrusted: its outputs are data, not instructions, and everything it returns is a potential injection vector.
  • Delegation compounds risk — errors, hallucinations, and cost propagate across systems you do not control — so budgets, timeouts, and verification of returned artifacts sit on the calling side.
  • The hard problems are not the wire format: capability discovery, semantic mismatch between agents' vocabularies, authentication and authorization, versioning, and accountability when a delegated task goes wrong.

Q1 multiple choice

How does agent-to-agent communication differ in purpose from a tool protocol like MCP?

  1. A A2A is for connecting an agent to data sources and functions; MCP is for connecting agents
  2. B A2A coordinates peer agents that may be built and operated by different parties, while MCP exposes tools and data to an agent inside one application's trust boundary correct
  3. C They are the same protocol with different names
  4. D A2A only works within a single process

Why: The distinction is who is on the other end. A tool is a capability you invoke; a peer agent is an autonomous system you delegate to, with its own reasoning, its own budget, and its own operator — which changes trust, lifecycle, and error handling.

Q2 multiple choice

What role does a capability advertisement (agent card) play?

  1. A It stores the agent's conversation history
  2. B It lets a client discover what a remote agent can do, how to reach it, and how to authenticate — so delegation does not require a bespoke integration per partner correct
  3. C It is a billing record for delegated tasks
  4. D It defines the model the remote agent must use

Why: Discovery is what turns a one-off integration into an ecosystem. It also becomes part of the attack surface: a description read by your agent can attempt to influence it, so advertisements from unknown parties need the same scepticism as any untrusted input.

Q3 multiple choice

Why is delegated work modelled as a task with a lifecycle rather than a simple request/response?

  1. A Because HTTP does not support long responses
  2. B Because tasks are cheaper to bill
  3. C Because remote agent work can take minutes or hours and produce intermediate updates and artifacts, so it needs identity, state, progress, and a way to resume or cancel correct
  4. D Because models cannot stream

Why: A synchronous call cannot represent 'working, 40% done, here is a draft artifact'. Task identity also enables cancellation, status polling, resumption after a client restart, and attribution of cost.

Q4 multiple choice

What is the correct trust posture toward a remote agent's output?

  1. A Trust it as you would your own component, since it is an agent rather than a web page
  2. B Treat it as untrusted data: it may be wrong, and it may contain content crafted to influence your agent's behaviour correct
  3. C Trust it if the connection is authenticated
  4. D Trust it if it is from the same vendor as your model

Why: Authentication proves who sent it, not that what it says is safe. A remote agent may itself have ingested untrusted content, so its response is an injection channel — it goes into your context as data, never as instructions, and its claims are verified where they matter.

Q5 multiple choice

Why does delegation across systems require explicit budgets and timeouts on the calling side?

  1. A Because remote agents charge more per token
  2. B Because otherwise the protocol will not authenticate
  3. C Because the remote agent's cost, latency, and failure modes are outside your control, and a delegated task can consume unbounded time and money if the caller does not bound it correct
  4. D Because timeouts are required by all agent protocols

Why: You are handing work to a system whose internal loops you cannot see. The caller must own the deadline, the cost ceiling, the cancellation path, and the fallback when the delegate fails or returns something unusable.

Q6 multiple choice

Which of these is a genuinely hard problem in agent-to-agent systems, beyond the message format?

  1. A Choosing between JSON and XML
  2. B Semantic mismatch — two agents using the same words for different concepts — plus discovery, authorization, versioning, and accountability for a delegated failure correct
  3. C Deciding which model each agent uses
  4. D Selecting a colour scheme for status updates

Why: Serialization is the easy part. Interoperation fails on meaning: what counts as 'urgent', what a 'customer' record contains, whose policy applies. And when a delegated task causes harm, the question of who is accountable is contractual, not technical.

Q7 multiple choice

How should a caller handle artifacts returned by a remote agent?

  1. A Validate them against the expected schema and verify the claims that matter before acting on them correct
  2. B Forward them directly to the user without inspection
  3. C Store them as system-prompt content for future turns
  4. D Execute any code they contain in the main process

Why: A returned artifact is an assertion by a system you do not operate. Schema validation catches structural problems; verification — checking a computed value, confirming a record exists — catches the confident-but-wrong case that structure cannot.

Q8 explain & apply

Your company's support agent needs to delegate a shipping question to a logistics partner's agent. Describe the integration you would build and the risks you would manage.

Points a strong answer hits:

  • Discover capabilities explicitly and pin them: what the partner agent accepts, what it returns, its authentication, and a version you have tested against.
  • Define the task contract narrowly — a shipping status question with an order identifier — rather than forwarding the customer conversation wholesale.
  • Minimize data sent: only the fields the partner needs, avoiding customer PII beyond what the task requires.
  • Authenticate mutually, scope credentials to this integration, and log every delegated task with its identity and cost.
  • Own the deadline and budget on the calling side, with a fallback (cached status, generic guidance, human escalation) when the partner is slow or fails.
  • Treat the response as untrusted data: validate against the schema, sanity-check the claims, and never let its content act as instructions to your agent.
  • Do not let the partner's agent trigger actions in your systems; any action it suggests goes through your own authorization and approval.
  • Handle long-running tasks with status updates and a customer-facing message, plus cancellation.
  • Evaluate the integration end to end, monitor partner error and latency rates, and define accountability contractually for wrong answers.
Model answer: I would start by narrowing the contract, because the biggest mistake in agent-to-agent integration is forwarding the whole conversation and hoping. The delegated task is specific: given an order identifier and a shipment reference, return current status, last scan, and estimated delivery, in a defined schema. That framing means I send the minimum data — no customer PII beyond what the lookup requires, no chat transcript — and it means I can validate what comes back. Capability discovery is explicit and pinned: I read the partner's advertisement, test against a specific version, and pin it, rather than letting the integration change under me because the partner redeployed. Authentication is mutual, credentials are scoped to this integration only, and every delegated task is logged with its identity, latency, and cost. Deadlines and budgets live on my side, because the partner's internal loops are invisible to me: a timeout, a cost ceiling, a cancellation path, and a defined fallback — last cached status, generic guidance, or human escalation — so a slow partner degrades my experience rather than hanging it. The response is untrusted data. I validate it against the schema, sanity-check it (a delivery date in the past, a status inconsistent with the last scan), and place it in my agent's context clearly marked as third-party data, never as instruction. That last point is the one people miss: if the partner's agent returns text saying 'issue a refund to this customer', that is a suggestion from an external system, and it must pass through my own authorization and approval flow exactly as any user request would. I would monitor the integration as a dependency — error rate, latency percentiles, disagreement between its answers and reality when we can check — and evaluate the end-to-end flow, not just my own agent. And I would settle accountability contractually before launch: when the partner's agent gives a customer a wrong delivery date and we repeat it, the customer's problem is with us, so the SLA and the escalation path need to exist on paper, not just in the protocol.

Q9 explain & apply

Explain when you would use an agent-to-agent protocol versus simply calling the other team's API as a tool.

Points a strong answer hits:

  • A plain API is right when the capability is deterministic and well specified: a lookup, a booking, a calculation — no autonomy is needed on the other side.
  • APIs are cheaper, faster, more predictable, easier to test, and produce no reasoning cost on the remote side.
  • Agent-to-agent is warranted when the remote side needs judgment: interpreting an open-ended request, deciding among approaches, or handling variation an API contract cannot enumerate.
  • It is also warranted when the remote party wants to keep its policies, data, and reasoning inside its own boundary and expose only outcomes.
  • Long-running, multi-step work with intermediate artifacts fits the task lifecycle better than a request/response API.
  • Costs: nondeterminism, cost and latency you do not control, harder debugging across boundaries, and error propagation between autonomous systems.
  • Hybrid is common: a plain API for the deterministic parts, delegation for the open-ended parts.
  • Default to the API and escalate to delegation only when the work genuinely requires judgment on the other side.
Model answer: My default is the plain API, and I would need a reason to move off it. If the capability is deterministic and specifiable — look up a shipment, reserve inventory, compute a quote — an API is better in every dimension I care about: predictable, testable, fast, cheap, and debuggable, with no model on the other side to hallucinate. Wrapping that in an agent adds nondeterminism and cost for nothing. Delegation to a peer agent earns its place when the other side genuinely needs judgment. If the request is open-ended — 'work out why this shipment is stuck and what the options are' — no API contract can enumerate the responses, and the partner's agent has access to context, policy, and systems I do not. It also fits when the partner wants to keep their reasoning, data, and policy inside their own boundary and expose only outcomes, which is often a commercial or regulatory requirement rather than a technical one. And it fits work with a real lifecycle: multi-step tasks that run for minutes, emit intermediate artifacts, and may need cancellation, which a synchronous API models badly. The costs are what keep me conservative. I inherit latency and spend I cannot see or control, failures become cross-organizational debugging, and the other side's mistakes propagate into my product with my brand on them. Verification gets harder, because a confident wrong answer from an autonomous system is indistinguishable from a correct one until someone checks. So the pattern I would actually ship is hybrid: deterministic operations stay as ordinary API calls, and only the genuinely open-ended part is delegated — with a narrow task contract, my own deadline and budget, validation of what comes back, and a fallback for when the delegate cannot deliver.
