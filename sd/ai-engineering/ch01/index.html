Introduction to Building AI Applications with Foundation Models

Why a new engineering discipline appeared: self-supervision removed the labeled-data bottleneck, scale turned language models into general-purpose foundation models, and readily available models flipped the workflow from data-first to product-first. Covers the use-case landscape, how to evaluate and plan an AI application, the three-layer AI stack, and how AI engineering differs from ML engineering and full-stack engineering.

Key ideas

  • Self-supervision is the unlock: training signal is inferred from the data itself (predict the next token), so models could scale past the human labeling bottleneck that capped supervised ML.
  • A language model becomes a foundation model when scale plus multimodality make one model a general-purpose base that many applications adapt, instead of one model per task.
  • AI engineering is building applications on top of models you did not train — the differentiator moves from model training to model adaptation, context construction, and evaluation.
  • The workflow is reversed versus classic ML: AI engineering starts with the product and works backwards to data, while ML engineering started with data and worked forward to a product.
  • The AI stack has three layers — application development, model development, and infrastructure — and AI engineers spend most of their time in the top layer.
  • Planning an application means evaluating the use case (including the cost of a wrong answer and whether AI is needed at all), setting measurable expectations, planning milestones for the last-mile gap between demo and production, and budgeting for maintenance as models change underneath you.

Q1 multiple choice

What does Huyen identify as the key reason language models could scale far beyond earlier NLP models?

  1. A Transformers removed the need for GPUs, so training became cheap
  2. B Self-supervision infers training labels from the data itself, escaping the human-labeling bottleneck that limited supervised learning correct
  3. C Reinforcement learning replaced gradient descent as the training objective
  4. D Tokenization compressed text enough that models could memorize the entire web

Why: Supervised learning needs labeled data, and labeling is slow and expensive — that ceiling capped model and dataset size. Self-supervision derives the label from the input sequence itself (the next token is the answer), so any text becomes training data. Transformers and accelerators mattered, but the data bottleneck is the one Huyen calls out as the unlock.

Q2 multiple choice

In the book's terms, what is a token and why do models work with tokens rather than words or characters?

  1. A A token is always one word; models use words because they map cleanly to meaning
  2. B A token is a fixed 4-byte unit; models use it because GPUs address memory in 4-byte words
  3. C A token is the model's basic unit of text — often a word piece — a compromise that keeps the vocabulary small while letting the model compose unseen words from known pieces correct
  4. D A token is a compressed embedding vector produced after the first transformer layer

Why: Tokens are usually subword units. Characters give a tiny vocabulary but very long sequences; whole words give short sequences but an unbounded vocabulary that breaks on anything unseen. Word pieces sit in between: a bounded vocabulary that can still spell out novel or misspelled words.

Q3 multiple choice

What distinguishes a masked language model from an autoregressive language model?

  1. A Masked models predict a missing token using context on both sides; autoregressive models predict the next token using only preceding tokens correct
  2. B Masked models are trained on private data; autoregressive models are trained on public data
  3. C Masked models can only classify; autoregressive models can only embed
  4. D Masked models use self-supervision; autoregressive models require human labels

Why: A masked model fills in a blank with bidirectional context (useful for sentiment analysis, classification, and code debugging). An autoregressive model predicts the next token from what came before, which is what makes continuous text generation possible — and why generative applications are built on autoregressive models.

Q4 multiple choice

What makes a model a foundation model rather than just a large language model?

  1. A It has more than one trillion parameters
  2. B It is trained exclusively on curated, licensed data
  3. C It is open-weights so anyone can build on it
  4. D It is a general-purpose base that many downstream applications adapt, typically extending beyond text to other modalities correct

Why: Foundation names the role, not the size or license: one model that many applications build on. The term also signals the move beyond text — images, audio, video — since the same self-supervised recipe works on other data types.

Q5 multiple choice

Huyen splits model adaptation techniques into two families. What is the dividing line?

  1. A Whether the technique updates the model's weights — prompt-based techniques do not, finetuning does correct
  2. B Whether the technique runs on GPU or CPU
  3. C Whether the technique is open source or proprietary
  4. D Whether the technique uses embeddings or raw text

Why: Prompt-based adaptation (prompt engineering, context, retrieval) changes what the model sees but leaves the weights alone — cheap, fast, easy to iterate. Finetuning changes the weights, needs data and compute, and carries maintenance cost. The distinction drives nearly every build decision later in the book.

Q6 multiple choice

How does the AI engineering workflow differ in ORDER from the classic ML engineering workflow?

  1. A AI engineering skips evaluation until after launch; ML engineering evaluates first
  2. B AI engineering starts with a product idea and works backwards to data; ML engineering started with data and worked forward to a model and then a product correct
  3. C AI engineering trains a model first and finds a use case later
  4. D There is no difference in order; only the tooling changed

Why: Because a capable model is available on day one, you can build a product first and only then discover what data and adaptation it needs. In classic ML you needed data to get a model at all, so data collection and training came first and product came last.

Q7 multiple choice

Which are the three layers of the AI stack as the book describes them?

  1. A Prompting, finetuning, and pretraining
  2. B Frontend, backend, and database
  3. C Application development, model development, and infrastructure correct
  4. D Data collection, training, and serving

Why: Infrastructure is compute, serving, and data management. Model development is training, finetuning, dataset engineering, and inference optimization. Application development is evaluation, prompt/context construction, and the interface — where AI engineers spend most of their time because the model layer is increasingly bought rather than built.

Q8 multiple choice

When evaluating whether to build an AI use case, which question does Huyen put front and center alongside what does success look like?

  1. A Which cloud provider offers the cheapest GPUs
  2. B Whether the team can publish a paper about it
  3. C Whether the model can be trained from scratch in under a week
  4. D What the cost of a wrong answer is — and therefore whether the application can tolerate mistakes or needs a human in the loop correct

Why: Foundation models are probabilistic, so failures are certain over enough requests. The use case is viable when the cost of a bad output is bounded — internal tools, drafts, and suggestions tolerate errors; irreversible or high-stakes actions need review, constraints, or a different approach entirely.

Q9 multiple choice

What does the book mean by the last-mile problem in AI applications?

  1. A Network latency between the model host and the user's device
  2. B Getting an impressive demo is fast, but closing the gap to a reliable production system takes far longer than the demo suggests correct
  3. C The final training epoch consumes most of the compute budget
  4. D Users abandon the product on the last screen of onboarding

Why: A prototype that works on a handful of hand-picked inputs is easy because foundation models are strong on average. Production demands consistency across the long tail, plus evaluation, guardrails, latency, and cost work. Milestone planning should budget for that gap rather than treating the demo as 80% done.

Q10 multiple choice

Why does the book insist that maintenance is a first-class cost of an AI application, unlike much traditional software?

  1. A Prompt files grow linearly with the user base and must be sharded
  2. B GPU drivers must be recompiled for each new customer
  3. C The underlying model can change or be deprecated under you — new versions shift behavior, so evaluations and prompts must be re-run and re-tuned correct
  4. D Token prices are fixed by contract and never change

Why: You are building on a dependency you do not control. Providers deprecate models, silently update them, and change pricing; open models get superseded. Anything tuned to one model's quirks — prompts especially — is a maintenance liability, which is why a durable evaluation pipeline is the asset that makes migration survivable.

Q11 explain & apply crux

A colleague says: AI engineering is just ML engineering with a different library. Argue the case that it is a distinct discipline, naming at least three concrete differences in what the engineer actually does day to day.

Points a strong answer hits:

  • Model development vs adaptation: ML engineering builds and trains a model from data; AI engineering starts from an existing model and adapts it via prompting, context, retrieval, or finetuning.
  • The workflow order is reversed — product first, then data — because a capable model exists on day one, so time shifts to product iteration and away from training infrastructure.
  • Evaluation is harder and more central: open-ended outputs have no single ground truth, so building an evaluation pipeline (criteria, guidelines, judges, data) is a core deliverable rather than an accuracy number.
  • New surfaces appear that ML engineering barely had: prompt and context construction, token cost and latency budgets, inference optimization, guardrails against prompt injection, and dependency management for a model you do not control.
  • Data work changes shape: rather than collecting labeled training sets, the work is dataset engineering for finetuning and evaluation, plus retrieval corpora and user-feedback capture.
Model answer: The libraries are the least of it — the leverage points move. In ML engineering, the model is the artifact you produce: you collect labeled data, train, tune, and ship weights, and your headline metric is task accuracy on a test set. In AI engineering, the model is a dependency you consume. The artifacts you produce are the prompt/context pipeline, the evaluation harness, the retrieval corpus, and the guardrails — and your leverage is in adaptation, not training. The workflow order flips: you can build the product first and let it tell you what data you need, which is impossible when the data must exist before the model does. Evaluation gets harder rather than easier, because open-ended outputs have no single correct answer, so you invest in criteria, annotation guidelines, and AI judges instead of reading an accuracy score. Finally, you inherit a set of concerns ML engineering barely had: per-token cost and latency budgets, inference optimization, prompt injection and other adversarial input, and the fact that your core dependency can be deprecated or silently updated underneath you. Same math background, different job.

Q12 explain & apply

You are asked to add an AI feature to an existing product. Walk through how you would evaluate the use case and plan the work before writing any code.

Points a strong answer hits:

  • Ask whether AI is needed at all, and what the product does today — if a deterministic rule or existing search already solves it, the probabilistic option adds risk without adding value.
  • Assess the cost of a wrong answer, which decides whether the feature can be autonomous, must be a suggestion the user accepts, or needs an explicit human reviewer.
  • Weigh doing it versus not doing it: importance to the product, whether competitors will ship it regardless, and whether the value survives when the underlying model becomes commodity.
  • Set measurable expectations up front — the quality bar, latency and cost per request, and what the fallback is when the model is wrong or unavailable.
  • Plan milestones that budget for the last mile: demo, evaluation pipeline, guardrails, staged rollout with feedback capture — plus ongoing maintenance as the model changes.
  • Decide the first adaptation to try, defaulting to the cheapest (prompting and context) and reserving finetuning for when evaluation shows prompting cannot close the gap.
Model answer: First, interrogate the use case itself. What is the user actually trying to do, does the product already solve it some other way, and does the feature need a probabilistic system at all? Then price failure: I want to know what happens on a wrong output, because that single question decides the interaction design — autonomous action, a suggestion the user must accept, or a draft that a human reviews. Low-stakes and internal-facing use cases are where I want to start; irreversible actions need constraints or a human in the loop. Next, weigh building against not building: how central is this to the product, does it defend anything durable, and what happens if a competitor ships it first or if the capability becomes a commodity feature of the model in six months. Before code, I set expectations in numbers — the quality bar we would ship at, an acceptable p95 latency, a cost-per-request ceiling, and the fallback path when the model is wrong or the API is down. Then I plan milestones that respect the last mile: a demo proves feasibility, but the real work is the evaluation pipeline, the guardrails, and a staged rollout that captures user feedback. I explicitly budget maintenance, because the model underneath will change. Implementation-wise I start with the cheapest adaptation — prompting plus context, retrieval if the task needs private data — and only reach for finetuning when evaluation shows prompting has plateaued below the bar.
