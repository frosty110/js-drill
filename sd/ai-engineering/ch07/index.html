Finetuning

When changing the weights is the right move and when it is a trap: the reasons to finetune (and the stronger reasons not to), how finetuning relates to RAG, the memory math that decides what you can train on what hardware, numerical representations and quantization, and the parameter-efficient techniques — LoRA and friends, soft prompts, partial finetuning — plus model merging and practical finetuning tactics.

Key ideas

  • Finetuning changes behavior, format, and style far more reliably than it adds knowledge — if the problem is 'the model does not know our data', retrieval is usually the correct tool, not finetuning.
  • Try prompting first and exhaust it: finetuning costs data, compute, evaluation, and permanent maintenance, and it locks you to a base model that will be superseded.
  • Training memory is dominated by more than the weights — gradients, optimizer states, and activations mean full finetuning can need several times the model's inference footprint.
  • Numerical format is a lever: FP32 to FP16/BF16 halves memory, and quantization to INT8/INT4 shrinks it further; quantization is standard for inference and increasingly viable in training (QLoRA).
  • LoRA freezes the base weights and trains small low-rank matrices, cutting trainable parameters by orders of magnitude, allowing many swappable adapters over one base model, and merging back at inference for no added latency.
  • Model merging combines finetuned models without further training and can serve multi-task needs or on-device constraints — an alternative to one model per task.
  • Finetuning tactics are mostly about discipline: pick the right base model, start with a small high-quality dataset, tune few hyperparameters (learning rate, batch size, epochs), and measure against the prompting baseline you are trying to beat.

Q1 multiple choice

What is the single most common reason teams finetune when they should not?

  1. A They want to reduce inference latency
  2. B They want the model to know their private data — a knowledge problem that retrieval solves better, more cheaply, and with fresher data correct
  3. C They want structured output
  4. D They want to reduce prompt length

Why: Finetuning teaches behavior, tone, and format; it is a poor and expensive way to install facts, which then go stale and cannot be cited or updated. Retrieval keeps knowledge outside the weights where it can be edited, attributed, and access-controlled.

Q2 multiple choice

Which of these is a legitimate reason to finetune?

  1. A The documentation changes weekly and answers must stay current
  2. B The team wants to avoid paying per token
  3. C A cheaper, smaller model must reliably match a larger model's behavior on one narrow task, or the task needs an output style/format that prompting cannot make consistent correct
  4. D The prompt is longer than 500 tokens

Why: Distilling a big model's behavior into a small one for a narrow, high-volume task is the classic win: quality held, cost and latency cut. So is enforcing a domain-specific style or structure prompting keeps missing. Frequently-changing facts are the counter-case.

Q3 multiple choice

Why does the book insist finetuning should come after prompting has been exhausted?

  1. A Because finetuning APIs are not generally available
  2. B Because prompting always produces better quality
  3. C Because prompt iteration takes minutes while finetuning adds data collection, training, evaluation, hosting, and permanent maintenance — and without a prompting baseline you cannot even tell if the finetune helped correct
  4. D Because finetuning is only legal on open-weight models

Why: The prompting baseline is both the cheaper option and the yardstick. It also generates the data: a working prompted system's outputs and corrections become the finetuning set later, if you still need one.

Q4 multiple choice

Why does full finetuning require several times more memory than running the same model for inference?

  1. A Because training uses a larger context window by default
  2. B Because gradients, optimizer states (two per parameter for Adam-style optimizers), and cached activations must be held alongside the weights correct
  3. C Because the tokenizer is duplicated per GPU
  4. D Because training requires FP64 precision

Why: Inference needs weights plus a KV cache. Training adds a gradient per parameter, optimizer state per parameter, and activations for backpropagation — which is exactly the arithmetic that makes parameter-efficient methods attractive.

Q5 multiple choice

What is the difference between FP16 and BF16, and why does BF16 dominate training?

  1. A BF16 has more mantissa bits, giving higher precision at the same size
  2. B BF16 is an integer format; FP16 is floating point
  3. C BF16 trades mantissa bits for exponent range, matching FP32's dynamic range, which makes training far less prone to overflow/underflow than FP16 correct
  4. D They are identical; the names are vendor branding

Why: Both are 16-bit, but the split differs. FP16's narrow exponent range causes gradient overflow and underflow (hence loss scaling); BF16 keeps FP32's range with less precision, which training tolerates well.

Q6 multiple choice

What does quantization do, and where is it most commonly applied?

  1. A It reduces numerical precision (for example FP16 to INT8 or INT4) to cut memory and speed up compute, most commonly applied to inference — though methods like QLoRA bring it into training correct
  2. B It removes redundant layers from the network
  3. C It compresses the training dataset before tokenization
  4. D It converts a dense model into a mixture of experts

Why: Lower precision means smaller weights and faster memory-bound inference, at some quality cost that depends on the method. Post-training quantization is the default; quantization-aware approaches recover more quality when the drop matters.

Q7 multiple choice

How does LoRA work at a mechanical level?

  1. A It removes attention heads that contribute least to the loss
  2. B It trains a separate small model that post-edits the base model's output
  3. C It freezes the base weights and learns a low-rank update — two small matrices whose product is added to a weight matrix — so only a tiny fraction of parameters are trained correct
  4. D It rewrites the prompt automatically using gradient descent

Why: If a weight update matrix is approximately low rank, you can represent it as A×B with a small rank r. Training only A and B slashes trainable parameters and optimizer memory, and the product can be merged into the base weights at inference so there is no extra latency.

Q8 multiple choice

What operational advantage does LoRA give beyond cheaper training?

  1. A It guarantees better quality than full finetuning
  2. B It removes the need for evaluation
  3. C It eliminates the need to host the base model
  4. D Adapters are small and swappable, so one base model in memory can serve many task-specific or customer-specific variants correct

Why: A full finetune produces another whole model to store and serve. LoRA adapters are megabytes, can be hot-swapped or served in a batched multi-adapter setup, and can be merged when a variant becomes the default — a serving-economics win as much as a training one.

Q9 multiple choice

What is a soft prompt (prefix/prompt tuning), and how does it differ from prompt engineering?

  1. A It is a shorter prompt automatically generated by a helper model
  2. B It is a set of trainable embedding vectors prepended to the input — learned continuous 'tokens' that do not correspond to any words, unlike a human-written text prompt correct
  3. C It is a system prompt stored on the provider's side
  4. D It is a prompt compressed by removing stop words

Why: Soft prompts optimize in embedding space rather than word space, so they can encode instructions no phrasing captures — but they are unreadable, tied to the model, and generally less effective than adapter methods like LoRA.

Q10 multiple choice

What is model merging, and when is it useful?

  1. A Running two models in sequence and concatenating their outputs
  2. B Combining the parameters of multiple finetuned models (by interpolation, task arithmetic, or layer stacking) into one model without further training — useful for multi-task capability or on-device deployment where you can ship only one model correct
  3. C Sharding a model across multiple GPUs
  4. D Ensembling by majority vote at inference time

Why: Merging operates on weights, not outputs, so unlike ensembling it costs nothing extra at inference. It is a cheap way to combine separately trained capabilities, with the caveat that results are empirical and can degrade any single task.

Q11 explain & apply crux

A team says their support bot 'needs finetuning because it does not know our products'. Explain when they are right and when they are wrong, and what you would do instead or in addition.

Points a strong answer hits:

  • Distinguish knowledge from behavior: not knowing facts is a retrieval problem; not behaving correctly (tone, format, refusal policy, domain jargon usage) is a candidate for finetuning.
  • Facts that change — prices, inventory, policy — must live outside the weights so they can be updated, cited, and access-controlled.
  • Start with retrieval plus prompting, and measure; that also produces the dataset a finetune would need later.
  • Legitimate finetuning cases here: consistent house style and format, reliable adherence to the escalation policy, better handling of domain vocabulary, or distilling a large model into a cheap one for high volume.
  • Costs to state explicitly: data collection and cleaning, training and evaluation, hosting, re-doing the work when the base model is superseded, and the loss of citation/attribution.
  • A hybrid is usually right: retrieval for knowledge, plus a small LoRA for behavior if evaluation shows prompting has plateaued.
  • Whatever the choice, the prompting baseline and an evaluation set must exist first, or improvement is unmeasurable.
Model answer: They are wrong about the mechanism and possibly right about the symptom. 'Does not know our products' is a knowledge gap, and knowledge is the thing finetuning is worst at installing: it takes a lot of data to move facts into weights, the facts go stale the moment a price changes, the model cannot cite them, and you cannot revoke a document's access after it has been trained in. That work belongs in retrieval, where the corpus is updatable, attributable, and permission-checked. So step one is a RAG baseline with a decent prompt, and an evaluation set built from real tickets, so we can say precisely what fails. What that evaluation usually reveals is a second, different problem: the bot's tone is off, it does not follow the escalation policy, it ignores the required format, it misuses domain vocabulary. Those are behavior problems, and behavior is exactly what finetuning is good at. A small LoRA on a few thousand curated examples — ideally real conversations that were corrected by human agents — will move those reliably when prompting has plateaued. The other legitimate case is economics: if the prompted system works on a large model and volume is high, distilling that behavior into a small model can hold quality while cutting cost and latency substantially. I would put the costs on the table before anyone starts: dataset curation is the real work, evaluation has to exist either way, you now host and version a model, and when the next base model lands you may repeat all of it. The recommendation that usually survives that conversation is a hybrid — retrieval for what we know, a light finetune for how we behave — and never a finetune as the first move.

Q12 explain & apply

Explain why parameter-efficient finetuning exists by walking through the memory cost of full finetuning, and describe how LoRA changes each term.

Points a strong answer hits:

  • Full finetuning must hold the weights, a gradient per trainable parameter, optimizer states (typically two per parameter for Adam-style optimizers), and activations for backpropagation.
  • In practice this is several times the memory of inference for the same model, which puts large models out of reach of accessible hardware.
  • Precision choices scale every term: FP32 to BF16 halves weight/gradient memory; quantizing the frozen base (QLoRA) shrinks the largest term further.
  • LoRA freezes base weights, so no gradients or optimizer states are needed for them — the dominant terms collapse to the tiny adapter.
  • Only the low-rank matrices are trained, cutting trainable parameters by orders of magnitude; rank r trades capacity for cost.
  • Activation memory still scales with batch size and sequence length, so it does not disappear — gradient checkpointing and batch size are the levers there.
  • At inference the adapter can be merged into the base weights, so there is no added latency, and unmerged adapters allow many variants over one hosted base.
Model answer: Full finetuning is expensive because the weights are the smallest part of the bill. You hold the parameters, then a gradient for every one of them, then optimizer state — Adam-style optimizers keep roughly two moments per parameter — and on top of that the activations cached during the forward pass so backpropagation can use them. Add it up and training needs several times the memory that serving the same model needs, which is why a model you can happily run inference on may be untrainable on the same hardware. Precision multiplies through every term, so moving from FP32 to BF16 halves most of it, and that is the first thing anyone does. LoRA attacks the dominant terms directly by freezing the base model: if the base weights are not trained, they need no gradients and no optimizer state at all. What remains trainable is a pair of low-rank matrices per targeted weight matrix, often well under one percent of the parameters, so gradient and optimizer memory become negligible. QLoRA pushes further by keeping the frozen base in 4-bit, shrinking the one large remaining term. What LoRA does not remove is activation memory, which scales with batch size and sequence length — that is handled with gradient checkpointing and smaller batches, and it is the term that bites on long-context training. The payoff at serving time is the part people underrate: because the learned update is a product of two small matrices, you can merge it into the base weights and pay zero extra latency, or keep it separate and swap adapters per customer or per task over a single hosted base model. Rank is the tuning knob — higher rank means more capacity and more cost — and for most behavioral finetunes a small rank is enough.
