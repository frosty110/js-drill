Traffic & Routing

How a request finds a healthy server. 5 building blocks drilled by recall: the signal that says reach for one, what it costs, how it breaks, which sibling rules it out, and what it is doing across the canonical problems.

Key ideas

  • Load Balancer — A single address in front of many interchangeable servers, spreading requests and routing around dead ones.
  • Reverse Proxy — A server-side intermediary that terminates the client connection and speaks to backends on its behalf, so cross-cutting work happens once at the edge.
  • API Gateway — The single front door for external callers: authenticates, applies quota, routes to the right service, and normalises the response.
  • Service Discovery — A registry that answers 'where is service X right now', so callers reach live instances without hardcoded addresses.
  • DNS & Anycast Routing — Steering users to a region or PoP before a connection is ever made, using DNS answers or a single IP announced from many locations.

Q2 explain & apply

You put Load Balancer in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • The backends are NOT interchangeable — a request must reach one specific shard owner, which is routing, not balancing
  • You reach for it to solve a database bottleneck; balancing the tier in front of the bottleneck moves nothing
  • One more hop of latency and one more thing that can be misconfigured
  • It becomes the failure domain — an LB outage is a total outage, so it needs its own redundancy
  • Health-check tuning is a real tradeoff: aggressive checks eject healthy nodes, lax ones send traffic into a black hole
Model answer: Don't reach for it when: The backends are NOT interchangeable — a request must reach one specific shard owner, which is routing, not balancing; You reach for it to solve a database bottleneck; balancing the tier in front of the bottleneck moves nothing. And it is never free: One more hop of latency and one more thing that can be misconfigured; It becomes the failure domain — an LB outage is a total outage, so it needs its own redundancy; Health-check tuning is a real tradeoff: aggressive checks eject healthy nodes, lax ones send traffic into a black hole.

Q3 explain & apply

Load Balancer is in your design and load goes up ten times. How does it break?

  • Sticky sessions defeat even distribution and turn one hot client into one hot server
  • A slow-but-alive backend passes health checks while poisoning latency for everyone routed to it
  • Cascading ejection: checks eject nodes under load, concentrating load on the survivors, which then fail checks too
Model answer: Sticky sessions defeat even distribution and turn one hot client into one hot server A slow-but-alive backend passes health checks while poisoning latency for everyone routed to it Cascading ejection: checks eject nodes under load, concentrating load on the survivors, which then fail checks too

Q4 explain & apply

Load Balancer vs DNS & Anycast Routing vs Service Discovery — what decides between them?

Points a strong answer hits:

  • DNS & Anycast Routing — DNS steers between REGIONS; an LB steers between servers. Different blast radius, different failover speed.
  • Service Discovery — Discovery lets the caller pick a backend itself, removing the middle hop — normal for internal service-to-service.
  • Load Balancer — A single address in front of many interchangeable servers, spreading requests and routing around dead ones.
Model answer: DNS & Anycast Routing: DNS steers between REGIONS; an LB steers between servers. Different blast radius, different failover speed. Service Discovery: Discovery lets the caller pick a backend itself, removing the middle hop — normal for internal service-to-service.

Q5 explain & apply

Load Balancer appears in 5 of the canonical design problems. Name as many as you can, and say what it is doing in each.

Points a strong answer hits:

  • Design a Chat System — Spreads long-lived socket connections across the chat fleet, where the stateless assumption breaks — a connection pinned for hours is not a request you can rebalance.
  • Design a Ride-Sharing Service — Distributes driver and rider connections across the matching fleet, rebalancing only on reconnect since an open socket cannot be moved.
  • Design a Collaborative Document Editor — Distributes collaborator sockets across the edit fleet, with everyone on one document needing to reach the same session owner.
  • Design a Live Streaming Service — Spreads viewer connections at broadcast start, when a million clients arrive inside the same few seconds rather than arriving smoothly.
  • Design an Authentication & Session Service — Fronts a stateless auth tier, which is what lets any node validate any session — and the reason session state lives in a shared store rather than server memory.
Model answer: Load Balancer carries different work in each: in Design a Chat System, spreads long-lived socket connections across the chat fleet, where the stateless assumption breaks — a connection pinned for hours is not a request you can rebalance. in Design a Ride-Sharing Service, distributes driver and rider connections across the matching fleet, rebalancing only on reconnect since an open socket cannot be moved. in Design a Collaborative Document Editor, distributes collaborator sockets across the edit fleet, with everyone on one document needing to reach the same session owner. in Design a Live Streaming Service, spreads viewer connections at broadcast start, when a million clients arrive inside the same few seconds rather than arriving smoothly. in Design an Authentication & Session Service, fronts a stateless auth tier, which is what lets any node validate any session — and the reason session state lives in a shared store rather than server memory.

Q21 explain & apply

You put DNS & Anycast Routing in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • Fast failover is required — resolver and client TTL caching means DNS changes take minutes to hours to propagate
  • You are steering individual requests; by the time DNS answered, the request already committed to an address
  • TTL is a tradeoff you cannot escape: short TTLs cost query volume, long TTLs cost failover time
  • Clients and resolvers routinely ignore your TTL anyway
  • Anycast requires network-layer control most teams do not have in-house
Model answer: Don't reach for it when: Fast failover is required — resolver and client TTL caching means DNS changes take minutes to hours to propagate; You are steering individual requests; by the time DNS answered, the request already committed to an address. And it is never free: TTL is a tradeoff you cannot escape: short TTLs cost query volume, long TTLs cost failover time; Clients and resolvers routinely ignore your TTL anyway; Anycast requires network-layer control most teams do not have in-house.
