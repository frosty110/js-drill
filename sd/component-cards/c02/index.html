Caching & Delivery

How to stop doing the same expensive work twice. 4 building blocks drilled by recall: the signal that says reach for one, what it costs, how it breaks, which sibling rules it out, and what it is doing across the canonical problems.

Results carried by this link

Key ideas

  • Cache — A fast store holding the answer to work you already did, so the expensive path runs once for many reads.
  • CDN — A globally distributed cache of your static bytes, serving users from a nearby PoP instead of your origin.
  • Hot-Key Mitigation — Techniques for the one key whose traffic exceeds what a single shard or cache node can serve — replicate it, split it, or absorb it locally.
  • Edge Compute — Running small amounts of your logic in the CDN's PoPs, so personalisation, auth or rewriting happens near the user instead of at origin.

Q2 explain & apply

Q3 explain & apply

Cache is in your design and load goes up ten times. How does it break?

Points a strong answer hits:

  • Stampede — a hot key expires and every concurrent request hits the origin at once
  • Hot key — a single entry exceeds one node's throughput no matter how many nodes you add
  • Cold start after a flush or deploy sends full production load at a database sized for cache-miss traffic
  • Silent staleness: an invalidation is missed and wrong data is served indefinitely with no error
Model answer: Stampede — a hot key expires and every concurrent request hits the origin at once Hot key — a single entry exceeds one node's throughput no matter how many nodes you add Cold start after a flush or deploy sends full production load at a database sized for cache-miss traffic Silent staleness: an invalidation is missed and wrong data is served indefinitely with no error

Q4 explain & apply

Cache vs CDN vs Inverted Index / Search — what decides between them?

Points a strong answer hits:

  • CDN — Same idea moved to the network edge. Pick a CDN when the payload is static and the win is geographic distance.
  • Inverted Index / Search — If reads are QUERIES rather than key lookups, a precomputed index beats caching every distinct query.
  • Cache — A fast store holding the answer to work you already did, so the expensive path runs once for many reads.
Model answer: CDN: Same idea moved to the network edge. Pick a CDN when the payload is static and the win is geographic distance. Inverted Index / Search: If reads are QUERIES rather than key lookups, a precomputed index beats caching every distinct query.

Q5 explain & apply

Cache appears in 13 of the canonical design problems. Name as many as you can, and say what it is doing in each.

Points a strong answer hits:

  • Design a URL Shortener — Hot short-code → long-URL lookups. The mapping is immutable once created, so there is no invalidation story to get wrong — only capacity and TTL.
  • Design a News Feed — The per-user timeline of post IDs in Redis, hydrated to full post bodies on read. The cache IS the precomputed feed, not an optimisation over it.
  • Design a Distributed Rate Limiter — The counter state itself. Limiter state is small, extremely hot, and worthless once stale — which is exactly the shape an in-memory store is for.
  • Design a Leaderboard — Top-N slices per leaderboard window, so the overwhelmingly common 'show me the top 100' read never touches the underlying ranking structure.
  • Design a Distributed Cache — The whole problem. Ring placement, replication and eviction all exist to make one cache survive nodes joining and leaving without losing its value.
  • Design a Typeahead / Autocomplete Service — Precomputed top-K completions per prefix, held in memory because the keystroke budget is tens of milliseconds and a rebuild is a batch job.
  • Design a Ticket Booking System (Ticketmaster-style) — Event and seat-map reads, which vastly outnumber bookings. Availability counts are cached loosely on purpose; the actual hold stays transactional.
  • Design an LLM Inference Platform — Prompt-prefix and KV-cache reuse across requests, so a shared system prompt is not recomputed per call — the dominant saving in LLM serving.
  • Design a RAG / Semantic Search System — Embeddings and retrieval results for repeated queries, since embedding a query costs a model call every single time.
  • Design a Proximity Service — Popular geo cells, whose query volume is wildly skewed toward a few dense urban areas. A short TTL absorbs most reads before the index sees them.
  • Design a Feature Store — The online store is a cache by another name: precomputed features in a low-latency store, because inference cannot wait for a batch job to finish.
  • Design an Authentication & Session Service — Session and token-validation state, so every authenticated request is not a database read. Revocation is what makes the TTL choice genuinely hard.
  • Design a Sanctions Screening System — Adjudications are cached rather than raw matches, so a name a human already cleared against the current list version does not re-enter the review queue on every payment.

Q7 explain & apply

Q12 explain & apply

You put Hot-Key Mitigation in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • Key splitting (key#1..key#N) pushes fan-in complexity to every reader
  • Local in-process caches multiply staleness windows by the number of app servers
  • Detection needs per-key telemetry you probably are not collecting yet
Model answer: Don't reach for it when: Load is genuinely uniform; you are solving a problem the workload does not have; The hot entity needs strong consistency — replicating it multiplies the write-coordination cost.
