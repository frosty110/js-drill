Storage & Data Stores

Where bytes live, and which store to name. 8 building blocks drilled by recall: the signal that says reach for one, what it costs, how it breaks, which sibling rules it out, and what it is doing across the canonical problems.

Key ideas

  • Relational Database — Row storage with a fixed schema, joins, secondary indexes and multi-row ACID transactions.
  • Key-Value Store — A hash table with an operations team: get and put by key, partitioned across nodes, no query language.
  • Document Store — Key-value where the value is a structured document the engine can index and query inside.
  • Wide-Column Store — Partition-key-first storage (Cassandra, HBase, DynamoDB) built for enormous write volume and range scans within a partition.
  • Time-Series Store — A store specialised for append-only timestamped measurements, with automatic downsampling, retention and time-range queries.
  • Object / Blob Storage — Cheap, effectively unbounded storage for immutable files addressed by key, with HTTP access and lifecycle tiering.
  • Chunking — Splitting a large payload into independently addressable pieces, so transfer, retry, dedup and parallelism operate per piece.

Q37 explain & apply

Deduplication vs Bloom Filter vs Chunking — what decides between them?

Points a strong answer hits:

  • Bloom Filter — If you only need 'have I seen this before' and can tolerate false positives, a bloom filter is far cheaper.
  • Chunking — Chunk-level dedup catches partial overlap that whole-file dedup misses.
  • Deduplication — Storing identical content once by addressing it with a hash of its bytes, so repeats cost a reference instead of a copy.
Model answer: Bloom Filter: If you only need 'have I seen this before' and can tolerate false positives, a bloom filter is far cheaper. Chunking: Chunk-level dedup catches partial overlap that whole-file dedup misses.
