Data Distribution

Spreading one dataset across many machines. 5 building blocks drilled by recall: the signal that says reach for one, what it costs, how it breaks, which sibling rules it out, and what it is doing across the canonical problems.

Component Flash Cards 24 questions

Results carried by this link

Key ideas

  • Sharding — Splitting one logical dataset across many machines by a partition key, so capacity and throughput scale horizontally.
  • Replication — Keeping copies of the same data on multiple nodes, for read capacity, fault tolerance, or geographic proximity.
  • Consistent Hashing — Placing keys and nodes on a ring so adding or removing a node moves only ~1/N of keys instead of remapping everything.
  • Quorum (N/W/R) — Requiring W acknowledgements to write and R responses to read out of N replicas, tuning consistency against availability.
  • Distributed ID Generation — Producing unique identifiers across many machines without a central allocator — Snowflake-style, UUID, or ranged counters.

Q2 explain & apply

You put Sharding in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • One machine still fits — sharding is a permanent complexity tax paid in advance
  • Queries routinely span all partitions; you have built scatter-gather, not scale
  • No good key exists and every candidate is skewed
  • Cross-shard queries and transactions become application problems
  • Resharding is a migration with a data-movement plan, not a config change
  • Every operational task multiplies by the shard count
Model answer: Don't reach for it when: One machine still fits — sharding is a permanent complexity tax paid in advance; Queries routinely span all partitions; you have built scatter-gather, not scale; No good key exists and every candidate is skewed. And it is never free: Cross-shard queries and transactions become application problems; Resharding is a migration with a data-movement plan, not a config change; Every operational task multiplies by the shard count.

  • Sharding — Splitting one logical dataset across many machines by a partition key, so capacity and throughput scale horizontally.

Q5 explain & apply

Sharding appears in 7 of the canonical design problems. Name as many as you can, and say what it is doing in each.

Points a strong answer hits:

  • Design a URL Shortener — Splits the mapping table by short-code hash once one primary cannot hold the row count. Access is pure key lookup, which shards about as cleanly as anything does.

  • Design a Distributed Key-Value Store — The core mechanic. The keyspace is divided across nodes by ring position, and every other feature in the design is built on top of that division.
  • Design a Proximity Service — Geo cells are the partition key, so nearby entities land on the same node. Locality is the point; population skew is the price you agree to pay.

  • Design an Observability Platform — Telemetry is partitioned by series or tenant, because ingest volume is the defining constraint and no single node absorbs a firehose.

Q9 explain & apply

Replication vs Quorum (N/W/R) vs Sharding — what decides between them?

Points a strong answer hits:

  • Quorum (N/W/R) — Quorum reads/writes let you tune the consistency-availability point instead of accepting the default.
  • Sharding — Replication scales reads; sharding scales writes and capacity. Most real systems need both.
  • Replication — Keeping copies of the same data on multiple nodes, for read capacity, fault tolerance, or geographic proximity.
Model answer: Quorum (N/W/R): Quorum reads/writes let you tune the consistency-availability point instead of accepting the default. Sharding: Replication scales reads; sharding scales writes and capacity. Most real systems need both.

Q10 explain & apply

Replication appears in 6 of the canonical design problems. Name as many as you can, and say what it is doing in each.

Points a strong answer hits:

  • Design a Distributed Cache — Each entry is held on N successive ring nodes, so losing one node degrades the hit rate instead of losing a whole slice of the keyspace.
  • Design a Payment System (Wallet / Ledger) — Synchronous replication of the ledger, because losing an acknowledged financial write is not a degraded mode — it is an unrecoverable defect.
  • Design a Distributed Message Queue — Each partition has a leader and followers; the in-sync replica set is what lets an acknowledged publish survive a broker dying.
  • Design a Distributed Key-Value Store — N replicas per key range with tunable W and R — where this problem's entire consistency-versus-availability conversation actually lives.
  • Design a Search Engine — Index shards are replicated for read throughput and node loss. Query volume, not durability, is what drives the replica count here.
  • Design an Authentication & Session Service — Session state is replicated across regions, so a login in one region is honoured in another without a cross-region read on every request.
Model answer: Replication carries different work in each: in Design a Distributed Cache, each entry is held on N successive ring nodes, so losing one node degrades the hit rate instead of losing a whole slice of the keyspace. in Design a Payment System (Wallet / Ledger), synchronous replication of the ledger, because losing an acknowledged financial write is not a degraded mode — it is an unrecoverable defect. in Design a Distributed Message Queue, each partition has a leader and followers; the in-sync replica set is what lets an acknowledged publish survive a broker dying. in Design a Distributed Key-Value Store, n replicas per key range with tunable W and R — where this problem's entire consistency-versus-availability conversation actually lives. in Design a Search Engine, index shards are replicated for read throughput and node loss. Query volume, not durability, is what drives the replica count here. in Design an Authentication & Session Service, session state is replicated across regions, so a login in one region is honoured in another without a cross-region read on every request.

Q12 explain & apply

You put Consistent Hashing in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • The node set is fixed and rare changes can be handled by a planned migration
  • Load is skewed by demand rather than by key count — the ring cannot fix a viral key
  • Virtual nodes are required for even distribution, which means more ring metadata
  • Every client needs the same ring view, so ring membership becomes shared state
  • Range queries are impossible; the hash destroys ordering by design
Model answer: Don't reach for it when: The node set is fixed and rare changes can be handled by a planned migration; Load is skewed by demand rather than by key count — the ring cannot fix a viral key. And it is never free: Virtual nodes are required for even distribution, which means more ring metadata; Every client needs the same ring view, so ring membership becomes shared state; Range queries are impossible; the hash destroys ordering by design.
