Correctness & Coordination

Getting the right answer when parts fail independently. 6 building blocks drilled by recall: the signal that says reach for one, what it costs, how it breaks, which sibling rules it out, and what it is doing across the canonical problems.

Key ideas

  • Idempotency — Making a repeated operation produce the same result as one execution, usually via a client-supplied key recorded with the effect.
  • Saga — A multi-step workflow across services where each step has a compensating action, because no distributed transaction is available.
  • Reservation / Hold — Temporarily claiming a scarce resource with an expiry, so a user can complete a multi-step flow without it being sold underneath them.
  • Conflict Resolution — Deciding what the truth is when two writers modified the same thing concurrently — last-write-wins, version vectors, OT or CRDTs.
  • Leader Election — Picking exactly one node to perform a role, with an agreed way to notice failure and pick again.
  • Distributed Lock — A lease held in a shared store that grants one holder the right to act on a resource for a bounded time.

Q2 explain & apply

You put Idempotency in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • The key must be recorded atomically with the effect, which constrains your storage choices
  • Clients must generate and reuse keys correctly — a contract you have to document and police

Q3 explain & apply

  • Same key reused for a genuinely different request, silently returning the wrong prior result

Q5 explain & apply

Idempotency appears in 9 of the canonical design problems. Name as many as you can, and say what it is doing in each.

Points a strong answer hits:

  • Design a Notification System — Deduplicates sends, so an at-least-once redelivery does not mean the user's phone buzzes twice for one event.
  • Design a Payment System (Wallet / Ledger) — The client-supplied key on every transfer, recorded in the same transaction as the ledger entry — the difference between a retry and a double charge.
  • Design a Ticket Booking System (Ticketmaster-style) — Booking requests carry a key, so a double-tap or a lost response does not leave one user holding two seats for the same show.
  • Design a Prescription Drug Marketplace — Orders must survive retry without dispensing twice; the key is recorded with the fulfilment record, not before it.
  • Design a Distributed Job Scheduler — A job execution is keyed, so at-least-once dispatch does not run the same scheduled task twice on two different workers.
  • Design a Webhook Delivery System — The delivery id sent with every request, so receivers can recognise a redelivery. Its absence is what makes at-least-once dangerous for them.
  • Design an Authentication & Session Service — Token issuance and refresh are made repeat-safe, so a retried login does not mint a second live session the user cannot see or revoke.
  • Design a Financial Crime Alert Investigation System — A redelivered alert file must not re-investigate what was already decided, so the key is the source alert id and revision rather than anything the pipeline generates.
  • Design a Business Verification Pipeline — A vendor timeout is ambiguous about whether the work happened, so the retry has to record one result and incur one charge no matter how many attempts it took.
Model answer: Idempotency carries different work in each: in Design a Notification System, deduplicates sends, so an at-least-once redelivery does not mean the user's phone buzzes twice for one event. in Design a Payment System (Wallet / Ledger), the client-supplied key on every transfer, recorded in the same transaction as the ledger entry — the difference between a retry and a double charge. in Design a Ticket Booking System (Ticketmaster-style), booking requests carry a key, so a double-tap or a lost response does not leave one user holding two seats for the same show. in Design a Prescription Drug Marketplace, orders must survive retry without dispensing twice; the key is recorded with the fulfilment record, not before it. in Design a Distributed Job Scheduler, a job execution is keyed, so at-least-once dispatch does not run the same scheduled task twice on two different workers. in Design a Webhook Delivery System, the delivery id sent with every request, so receivers can recognise a redelivery. Its absence is what makes at-least-once dangerous for them. in Design an Authentication & Session Service, token issuance and refresh are made repeat-safe, so a retried login does not mint a second live session the user cannot see or revoke. in Design a Financial Crime Alert Investigation System, a redelivered alert file must not re-investigate what was already decided, so the key is the source alert id and revision rather than anything the pipeline generates. in Design a Business Verification Pipeline, a vendor timeout is ambiguous about whether the work happened, so the retry has to record one result and incur one charge no matter how many attempts it took.
