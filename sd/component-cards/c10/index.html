Q2 explain & apply

You put Transcoding Pipeline in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • Media is already in a single known format every client supports
  • Volume is low enough that an off-the-shelf managed service is obviously right
  • CPU or GPU capacity that dwarfs the rest of the system
  • Storage multiplies by the number of renditions you generate
  • Latency between upload and availability is now a product decision
Model answer: Don't reach for it when: Media is already in a single known format every client supports; Volume is low enough that an off-the-shelf managed service is obviously right. And it is never free: CPU or GPU capacity that dwarfs the rest of the system; Storage multiplies by the number of renditions you generate; Latency between upload and availability is now a product decision.

Q3 explain & apply

Transcoding Pipeline is in your design and load goes up ten times. How does it break?

Points a strong answer hits:

  • Queue backing up during an upload spike, so publish latency grows without bound
  • A single enormous file monopolising workers and starving everything behind it
  • Partial ladder published, so some clients get a resolution that does not exist
  • Retrying a half-finished job and paying full cost again with no checkpointing
Model answer: Queue backing up during an upload spike, so publish latency grows without bound A single enormous file monopolising workers and starving everything behind it Partial ladder published, so some clients get a resolution that does not exist Retrying a half-finished job and paying full cost again with no checkpointing

Q4 explain & apply

Transcoding Pipeline vs Chunking vs CDN — what decides between them?

Points a strong answer hits:

  • Chunking — Segmenting first makes transcoding parallel and restartable per segment.
  • CDN — Transcoding makes the renditions; the CDN is what makes serving them affordable.
  • Transcoding Pipeline — Converting uploaded media into the ladder of formats, resolutions and bitrates that clients actually stream.
Model answer: Chunking: Segmenting first makes transcoding parallel and restartable per segment. CDN: Transcoding makes the renditions; the CDN is what makes serving them affordable.

Q7 explain & apply

You put Feature Store / Serving in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • One model with features computable from the request payload alone
  • You have no training/serving skew problem yet and are pre-building for one
  • Two stores to keep consistent — offline history and online serving
  • Point-in-time correctness for training data is genuinely hard to get right
  • Feature definitions become shared contracts with versioning and deprecation
Model answer: Don't reach for it when: One model with features computable from the request payload alone; You have no training/serving skew problem yet and are pre-building for one. And it is never free: Two stores to keep consistent — offline history and online serving; Point-in-time correctness for training data is genuinely hard to get right; Feature definitions become shared contracts with versioning and deprecation.

Q9 explain & apply

Feature Store / Serving vs Cache vs Stream Processing — what decides between them?

Points a strong answer hits:

  • Cache — A plain cache of precomputed features when there is one consumer and no training-parity requirement.
  • Stream Processing — Where real-time features are computed before they are stored and served.
  • Feature Store / Serving — Serving the same computed signals to training and to inference, with an offline store for history and an online store for low-latency reads.
Model answer: Cache: A plain cache of precomputed features when there is one consumer and no training-parity requirement. Stream Processing: Where real-time features are computed before they are stored and served.

Q11 explain & apply

You put Resource Scheduling in a design. Name the signals that should have stopped you — and what it costs even when it is the right call.

Points a strong answer hits:

  • Capacity is cheap and elastic — just autoscale
  • Requests are uniform and a plain queue suffices
  • Batching trades per-request latency for throughput, and that curve must be chosen deliberately
  • Priority classes need admission control or the top class starves everyone else
  • The scheduler becomes a critical, stateful component of its own
Model answer: Don't reach for it when: Capacity is cheap and elastic — just autoscale; Requests are uniform and a plain queue suffices. And it is never free: Batching trades per-request latency for throughput, and that curve must be chosen deliberately; Priority classes need admission control or the top class starves everyone else; The scheduler becomes a critical, stateful component of its own.

Q12 explain & apply

Resource Scheduling is in your design and load goes up ten times. How does it break?

Points a strong answer hits:

  • Head-of-line blocking from one very large request occupying the resource
  • Batch window tuned for throughput, blowing the latency budget for interactive traffic
  • Fragmentation leaving capacity unusable because no waiting request fits it
  • Preemption losing partially completed work with no checkpoint
Model answer: Head-of-line blocking from one very large request occupying the resource Batch window tuned for throughput, blowing the latency budget for interactive traffic Fragmentation leaving capacity unusable because no waiting request fits it Preemption losing partially completed work with no checkpoint

Q13 explain & apply

Resource Scheduling vs Work Queue vs Rate Limiting — what decides between them?

Points a strong answer hits:

  • Work Queue — When requests are uniform and fair FIFO ordering is acceptable.
  • Rate Limiting — Capping demand per caller is simpler than scheduling it, when fairness is the actual goal.
  • Resource Scheduling — Allocating scarce, expensive compute — GPUs, batch slots — across competing requests by priority, batching and queueing.
Model answer: Work Queue: When requests are uniform and fair FIFO ordering is acceptable. Rate Limiting: Capping demand per caller is simpler than scheduling it, when fairness is the actual goal.
