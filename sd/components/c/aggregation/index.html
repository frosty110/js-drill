Pre-Aggregation & Rollups

Maintaining counters and summaries as data arrives, so a read is a lookup instead of a scan.

Reach for it when

  • The prompt asks for counts, totals or top-N over volumes too large to scan per request
  • The same aggregate is read far more often than the underlying events change
  • Dashboards or leaderboards need sub-second reads

Don't reach for it when

  • Query dimensions are unknown or ad-hoc; you cannot pre-aggregate every combination
  • Exact answers over arbitrary time ranges are required and the rollup granularity would not support them

What it costs you

  • Every new dimension multiplies the number of aggregates to maintain
  • Backfilling a new aggregate means reprocessing history
  • Aggregates can drift from the source and need periodic reconciliation

How it breaks

  • Double counting on retry, so the counter is wrong and nothing signals it
  • Hot counter — one popular entity's increments exceed a single partition's write throughput
  • Rollup granularity chosen too coarse to answer a question the product later asks

Instead, consider

  • Stream Processing — When aggregation needs windows, joins or late-data handling, you want a real stream engine.
  • Hot-Key Mitigation — Sharded counters are the standard fix once one aggregate becomes a write hotspot.

Used in 4 design problems

  • Design a Leaderboard — Scores are maintained as running totals rather than recomputed, so a read is a range query on a sorted set instead of a scan.
  • Design an Ad Click Aggregator — The output of the system: click counts per ad per window, maintained incrementally because the raw stream is far too large to scan on demand.
  • Design an Observability Platform — Metrics are pre-rolled into time buckets at ingest, so a dashboard query reads summaries instead of scanning raw telemetry.
  • Design a Feature Store — Windowed feature values — counts and averages over recent activity — computed once and served to every model that needs them.
