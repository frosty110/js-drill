API Gateway

The single front door for external callers: authenticates, applies quota, routes to the right service, and normalises the response.

Reach for it when

  • The prompt has many backend services but one public API surface
  • Auth, rate limiting and request validation must be enforced before traffic reaches any service
  • Clients need one contract while services behind it change shape

Don't reach for it when

  • Internal service-to-service calls — a gateway in the middle of a mesh adds a hop and a bottleneck for no policy benefit
  • It becomes a place to put business logic; that turns the gateway into an undeployable monolith everyone is afraid of

What it costs you

  • A shared choke point: its capacity is the API's capacity, and its deploys are everyone's deploys
  • Latency on every single request, including ones that needed nothing from it
  • Route config becomes a distributed-ownership problem across teams

How it breaks

  • Auth-service dependency makes the gateway fail closed and take the whole API down with it
  • Per-route config drift: a service ships a new endpoint the gateway does not know about
  • Fan-out aggregation inside the gateway turns one client timeout into N abandoned backend calls

Instead, consider

  • Reverse Proxy — If you need TLS and routing but no per-caller policy, a plain reverse proxy is less machinery.
  • Rate Limiting — The gateway is usually WHERE rate limiting lives; the limiter is the mechanism, the gateway is the venue.
