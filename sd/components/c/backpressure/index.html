Backpressure

Letting a saturated consumer slow its producer, so queues stay bounded instead of absorbing an overload until something breaks.

Reach for it when

  • Producer and consumer rates can diverge for sustained periods
  • The prompt has a pipeline where an unbounded buffer would just relocate the failure
  • Memory or queue depth is a real constraint

Don't reach for it when

  • Bursts are short and a buffer genuinely absorbs them
  • The producer physically cannot slow down — a firehose of external events — in which case you must shed instead

What it costs you

  • Slowness propagates upstream by design, so the effect is visible to callers
  • Every stage needs a bounded buffer and a policy for what happens when it is full
  • Harder to reason about: a slow leaf can stall the root

How it breaks

  • Unbounded queue chosen 'temporarily', converting a latency problem into an out-of-memory crash
  • Backpressure propagating all the way to a user-facing request path and timing everyone out
  • Deadlock when two stages apply backpressure to each other in a cycle

Instead, consider

  • Load Shedding — When you cannot slow the producer, drop work deliberately by priority.
  • Work Queue — A durable queue absorbs bursts; pair with backpressure so 'burst' cannot silently become 'forever'.

Used in 5 design problems

  • Design a Web Crawler — Politeness limits and frontier depth bound how fast the crawler pulls, so it neither melts a target site nor outruns its own parsers.
  • Design a Distributed Message Queue — Producers are slowed when partitions cannot absorb writes, because the alternative is unbounded broker storage followed by a hard failure.
  • Design an LLM Inference Platform — Queue depth signals the admission controller to reject or shed, rather than accumulating requests that will time out before a GPU frees up.
  • Design an Observability Platform — Ingest pushes back on agents when the pipeline saturates — dropping telemetry is preferable to the observability platform collapsing under it.
  • Design a Webhook Delivery System — A slow or dead receiver must not consume unbounded delivery capacity; per-endpoint concurrency limits stop one customer starving the rest.
