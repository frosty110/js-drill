Object / Blob Storage

Cheap, effectively unbounded storage for immutable files addressed by key, with HTTP access and lifecycle tiering.

Reach for it when

  • The prompt has large binary payloads — images, video, backups, documents
  • The bytes are written once and read many times
  • Storage cost at scale is a stated concern, or the data must outlive any server

Don't reach for it when

  • You need to update a small part of an object; blob stores replace, they do not patch
  • Access needs to be transactional with your database
  • Latency requirements are single-digit milliseconds

What it costs you

  • Eventually-consistent listing and metadata in many implementations
  • Egress is the line item that surprises people, which is why a CDN sits in front
  • Two systems now hold related state — the object and the row that describes it

How it breaks

  • Orphaned objects when the database row is deleted but the object is not, or vice versa
  • Uploads going through the app tier and saturating it, instead of client-direct with presigned URLs
  • Hot prefixes throttling throughput in stores that partition by key prefix

Instead, consider

  • Chunking — For very large or resumable payloads, chunk before you store — it changes the failure story entirely.
  • CDN — Blob storage holds the bytes; a CDN is how users actually get them without paying origin egress.

Used in 3 design problems

  • Design a Photo-Sharing Service — Holds the original photos and their derived sizes; the database stores only metadata and the object key that points at them.
  • Design a Video Streaming Service — Stores raw uploads and every transcoded rendition, which is why storage cost multiplies by the size of the bitrate ladder.
  • Design a File Sync / Object Storage Service — The backing store for content-addressed chunks, with the file manifest in a database pointing at each one.
