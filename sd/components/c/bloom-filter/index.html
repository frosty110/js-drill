Bloom Filter

A compact probabilistic set that answers 'definitely not present' or 'probably present', trading exactness for tiny memory.

Reach for it when

  • You need to avoid an expensive lookup for keys that are usually absent
  • Memory is the constraint and false positives are cheap to recover from
  • The prompt has dedup or membership checks over a huge keyspace

Don't reach for it when

  • A false positive would be a correctness bug rather than a wasted lookup
  • You need deletion — standard bloom filters cannot remove elements
  • The set is small enough for an exact structure

What it costs you

  • Sizing must be decided up front from expected cardinality and target error rate
  • It degrades as it fills, and the only fix is to rebuild
  • Another structure to keep in sync with the real data

How it breaks

  • Filter saturating past its design cardinality so the false-positive rate silently climbs
  • Treating 'probably present' as 'present' and skipping the confirming lookup
  • Attempting deletion by clearing bits and corrupting other members

Instead, consider

  • Deduplication — When you need certainty, an exact content-address index is the honest answer.
  • Cache — A negative cache stores known-absent keys exactly, at higher memory cost.
