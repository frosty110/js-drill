Bulkhead Isolation

Partitioning resources — thread pools, connections, even fleets — so one dependency or tenant cannot consume everything.

Reach for it when

  • One slow dependency currently exhausts a shared pool and takes down unrelated paths
  • The prompt is multi-tenant and one customer must not be able to starve the others
  • Critical and non-critical work share infrastructure today

Don't reach for it when

  • There is only one dependency and one class of work — partitioning buys nothing
  • Utilisation matters more than isolation; reserved partitions sit idle by design

What it costs you

  • Lower average utilisation, since capacity is reserved rather than pooled
  • More pools to size and monitor, each with its own saturation behaviour
  • Cell-based isolation multiplies deployment and operational surface

How it breaks

  • Pools sized by guesswork, so one saturates constantly while another idles
  • A shared resource one level down (a connection pool, a database) undoing the isolation above it
  • Noisy-neighbour effects surviving because the partition was logical, not physical

Instead, consider

  • Circuit Breaker — Detect and cut off a bad dependency rather than pre-partitioning for it.
  • Rate Limiting — Per-tenant quotas achieve fairness without reserving capacity per tenant.

Used in 3 design problems

  • Design an LLM Inference Platform — Separate GPU pools per priority class, so a batch job cannot consume the capacity interactive requests depend on.
  • Design an Observability Platform — Per-tenant ingest partitions, so one customer instrumenting a hot loop cannot degrade everyone else's dashboards.
  • Design a Webhook Delivery System — Per-endpoint delivery concurrency, so one slow receiver occupies a bounded slice of the worker pool and no more.
