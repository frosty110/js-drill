Cache

A fast store holding the answer to work you already did, so the expensive path runs once for many reads.

Reach for it when

  • The prompt gives a lopsided read:write ratio — 100:1 and up
  • The answer is expensive to compute or fetch and changes far more slowly than it is read
  • A stated staleness tolerance ('feed can be up to a minute old') is an explicit invitation

Don't reach for it when

  • Reads must reflect writes immediately — a cache is a correctness hazard you added on purpose
  • The working set is uniformly random over a huge keyspace; the hit rate will not pay for the machinery
  • Write-heavy workloads where you would spend more invalidating than serving

What it costs you

  • Every cache is a second copy of the truth, and now you own the invalidation problem
  • Memory is expensive, so capacity forces an eviction policy you must justify
  • Debugging gets harder: behaviour now depends on whether something was warm

How it breaks

  • Stampede — a hot key expires and every concurrent request hits the origin at once
  • Hot key — a single entry exceeds one node's throughput no matter how many nodes you add
  • Cold start after a flush or deploy sends full production load at a database sized for cache-miss traffic
  • Silent staleness: an invalidation is missed and wrong data is served indefinitely with no error

Instead, consider

  • CDN — Same idea moved to the network edge. Pick a CDN when the payload is static and the win is geographic distance.
  • Inverted Index / Search — If reads are QUERIES rather than key lookups, a precomputed index beats caching every distinct query.

Used in 11 design problems

  • Design a URL Shortener — Hot short-code → long-URL lookups. The mapping is immutable once created, so there is no invalidation story to get wrong — only capacity and TTL.
  • Design a News Feed — The per-user timeline of post IDs in Redis, hydrated to full post bodies on read. The cache IS the precomputed feed, not an optimisation over it.
  • Design a Distributed Rate Limiter — The counter state itself. Limiter state is small, extremely hot, and worthless once stale — which is exactly the shape an in-memory store is for.
  • Design a Leaderboard — Top-N slices per leaderboard window, so the overwhelmingly common 'show me the top 100' read never touches the underlying ranking structure.
  • Design a Distributed Cache — The whole problem. Ring placement, replication and eviction all exist to make one cache survive nodes joining and leaving without losing its value.
  • Design a Typeahead / Autocomplete Service — Precomputed top-K completions per prefix, held in memory because the keystroke budget is tens of milliseconds and a rebuild is a batch job.
  • Design a Ticket Booking System (Ticketmaster-style) — Event and seat-map reads, which vastly outnumber bookings. Availability counts are cached loosely on purpose; the actual hold stays transactional.
  • Design an LLM Inference Platform — Prompt-prefix and KV-cache reuse across requests, so a shared system prompt is not recomputed per call — the dominant saving in LLM serving.
  • Design a Proximity Service — Popular geo cells, whose query volume is wildly skewed toward a few dense urban areas. A short TTL absorbs most reads before the index sees them.
  • Design a Feature Store — The online store is a cache by another name: precomputed features in a low-latency store, because inference cannot wait for a batch job to finish.
  • Design an Authentication & Session Service — Session and token-validation state, so every authenticated request is not a database read. Revocation is what makes the TTL choice genuinely hard.
