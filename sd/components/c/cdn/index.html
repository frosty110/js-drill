CDN

A globally distributed cache of your static bytes, serving users from a nearby PoP instead of your origin.

Reach for it when

  • The payload is large, static and read by many people — images, video segments, JS bundles
  • The prompt names a global user base and latency is a stated requirement
  • Origin egress bandwidth is the thing that will not scale

Don't reach for it when

  • Responses are personalised per user — you are caching a thing with an audience of one
  • Content must be revoked instantly; purge propagation is not immediate
  • The bottleneck is compute, not distance or bandwidth

What it costs you

  • You now have cache state in hundreds of places you cannot inspect
  • Purge is eventually consistent and often billed per request
  • Cache-key design becomes a real engineering problem the moment headers or query strings vary

How it breaks

  • Stale asset served long after deploy because the URL did not change
  • Cache fragmentation: a varying header splits one hot object into thousands of cold ones
  • Origin shielding absent, so a cold global cache means every PoP independently stampedes the origin

Instead, consider

  • Cache — An origin-side cache when the win is compute, not distance.
  • Edge Compute — When the response must be assembled per request but you still want it done near the user.

Used in 4 design problems

  • Design a Photo-Sharing Service — Serves the image bytes themselves, so origin egress does not scale with viewer count and users fetch from a nearby PoP.
  • Design a Video Streaming Service — Distributes video segments — the economics of the whole design, since origin bandwidth for video is the cost that dominates everything else.
  • Design a Live Streaming Service — Delivers HLS/DASH segments to viewers, which is what makes a million-concurrent-viewer broadcast affordable at all.
  • Design a Short-Form Video Feed — Prefetches and serves the next videos in the feed, because perceived instant playback is the product's core interaction.
