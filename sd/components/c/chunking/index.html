Chunking

Splitting a large payload into independently addressable pieces, so transfer, retry, dedup and parallelism operate per piece.

Storage & Data Stores signature mechanism 2 problems

Reach for it when

  • Files are large enough that a failed transfer must not restart from zero
  • Only part of a file typically changes between versions
  • You want parallel upload or download, or per-piece deduplication

Don't reach for it when

  • Payloads are small; per-chunk metadata will exceed the data
  • The consumer needs the whole object anyway and cannot start early

What it costs you

  • A manifest per object, and now the manifest is a consistency problem of its own
  • Chunk-size choice is a real tradeoff: small chunks dedup better, large chunks cost less metadata
  • Reassembly and ordering logic on the read path

How it breaks

  • Partial uploads leaving orphan chunks nobody garbage collects
  • Manifest written before all chunks are durable, producing an object that reads as corrupt
  • Fixed-size chunking defeating dedup because one inserted byte shifts every boundary

Instead, consider

  • Object / Blob Storage — Multipart upload gives you most of the retry benefit without you owning a manifest.
  • Deduplication — Chunking is usually the enabler for dedup rather than an end in itself.

Used in 2 design problems

  • Design a File Sync / Object Storage Service — Files are split so only changed blocks transfer on edit, which is what makes syncing a large file after a small change cheap.
  • Design a RAG / Semantic Search System — Documents are split into passages small enough to embed meaningfully and to fit a context window, with overlap so meaning survives the cut.
