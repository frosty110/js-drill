Conflict Resolution

Deciding what the truth is when two writers modified the same thing concurrently — last-write-wins, version vectors, OT or CRDTs.

Reach for it when

  • Writes can happen in multiple places at once — offline clients, multi-region, collaborative editing
  • The prompt says users edit the same document or record simultaneously
  • You chose availability over coordination and now must handle the consequence

Don't reach for it when

  • A single leader orders all writes — you do not have conflicts to resolve
  • Silent data loss is unacceptable and you are reaching for last-write-wins because it is easy

What it costs you

  • Version metadata per item, which can rival the data in size
  • CRDTs constrain the operations you may offer; OT requires a central sequencer
  • Some conflicts are genuinely a product decision and must be surfaced to a human

How it breaks

  • Last-write-wins discarding a concurrent update with no trace it existed
  • Clock skew making 'last' the wrong write entirely
  • Tombstone and version metadata growing without bound
  • Merge semantics that are technically correct but produce nonsense the user did not intend

Instead, consider

  • Message Ordering — Route all writes for one key through one partition and the conflict never arises.
  • Distributed Lock — Prevent concurrent modification instead of reconciling it — at the cost of availability.

Used in 3 design problems

  • Design a Collaborative Document Editor — Concurrent edits to the same region are merged rather than rejected — the decision that makes collaborative editing feel live instead of contested.
  • Design a File Sync / Object Storage Service — Two devices editing the same file offline produce divergent versions, and the design must choose between merging and conflicted copies.
  • Design a Distributed Key-Value Store — Concurrent writes accepted by different replicas are reconciled with version vectors, since a quorum permits them by construction.
