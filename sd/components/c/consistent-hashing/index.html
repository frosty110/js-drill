Consistent Hashing

Placing keys and nodes on a ring so adding or removing a node moves only ~1/N of keys instead of remapping everything.

Reach for it when

  • Membership changes routinely — autoscaling caches, nodes failing and returning
  • A remap would invalidate a cache wholesale and stampede the origin
  • You need a placement rule every client can compute without asking a coordinator

Don't reach for it when

  • The node set is fixed and rare changes can be handled by a planned migration
  • Load is skewed by demand rather than by key count — the ring cannot fix a viral key

What it costs you

  • Virtual nodes are required for even distribution, which means more ring metadata
  • Every client needs the same ring view, so ring membership becomes shared state
  • Range queries are impossible; the hash destroys ordering by design

How it breaks

  • Too few virtual nodes producing badly uneven load
  • Clients disagreeing about ring membership and writing the same key to different nodes
  • Cascading failure as a dead node's share lands entirely on its ring successor

Instead, consider

  • Sharding — Range-based sharding when you need ordered scans and can accept manual rebalancing.
  • Hot-Key Mitigation — The ring balances key COUNT, never key DEMAND — pair it with hot-key handling.

Used in 3 design problems

  • Design a Distributed Rate Limiter — Routes each client key to the node holding its counter, so limiter state is not remapped every time a gateway is added or removed.
  • Design a Distributed Cache — Places keys on the ring so adding a node moves ~1/N of them, instead of invalidating the whole cache and stampeding the origin.
  • Design a Distributed Key-Value Store — Assigns key ranges to nodes and defines the replica set as the next N nodes clockwise from the key's ring position.
