CQRS / Read-Model Projection

Serving reads from a second model derived from the write model, so the shape that accepts and validates a change is not the shape that answers a query.

Async & Messaging supporting 8 problems

Reach for it when

  • The write shape and the read shape genuinely disagree — writes are single-entity and validated, reads are wide joins or fan-ins across many entities
  • Reads outnumber writes by orders of magnitude and the read query is the expensive one
  • The same underlying facts must be answered in several different shapes, and one schema cannot be optimal for all of them
  • The write side must stay append-only or auditable, so current state has to be a derived view rather than the record

Don't reach for it when

  • One normalized model already serves both sides — the split buys a second store and a pipeline and nothing else
  • The read must reflect the write immediately; a projection is eventually consistent by construction
  • Read volume is low enough that an index, a cache or a read replica closes the gap

What it costs you

  • Two models to keep correct, and a pipeline between them that is now on the critical path for freshness
  • Every new read shape is another projection to build, backfill and operate
  • Replay tooling is not optional — a projection you cannot rebuild is a second source of truth you did not mean to create

How it breaks

  • Projection lag surfacing as a user writing something and not seeing it, with no error anywhere
  • A projection bug silently corrupting the read model while the write log stays correct — invisible until someone reconciles
  • Read-your-writes broken for the author of a change, because the UI reads the projection it just raced
  • The two models drifting after a partial replay, so which one is right becomes an operational question

Instead, consider

  • Replication — A read replica scales read VOLUME against the same schema; CQRS is for when the read SHAPE is the problem.
  • Cache — A cache stores the answer to a query you already run; a projection maintains a model no query would produce cheaply.
  • Pre-Aggregation & Rollups — Rollups are the narrow case — a projection whose read model is counters. Reach for the general form only when the view is richer than that.
  • Transactional Outbox / CDC — This is how the projection is fed: the write commits its change event in the same transaction, and the read model follows the log.

Used in 8 design problems

  • Design a News Feed — Fan-out on write IS the split: a post is one row on the write side, and every follower's timeline is a separate materialized list maintained for it.
  • Design a Collaborative Document Editor — The edit log is the record and the rendered document is a projection of it, which is what lets a client that fell behind rebuild by replaying rather than by asking.
  • Design a Leaderboard — Scores are written as events and read from a sorted set that exists only to answer top-K and my-rank — a read structure no write path would choose.
  • Design a Payment System (Wallet / Ledger) — The double-entry ledger is append-only, so a wallet balance is a derived view; making the balance the record would mean losing the audit trail that proves it.
  • Design an Ad Click Aggregator — Raw clicks land immutably and the billable counts are a separate rolled-up model, so a counting bug is fixed by reprocessing rather than by admitting the number is lost.
  • Design an Observability Platform — Raw telemetry is written once and queried through pre-built time-series and index models, because the shape that ingests a million points a second cannot also serve a dashboard.
  • Design a Feature Store — The offline and online stores are two projections of the same feature definitions — the whole point being that one definition feeds both so they cannot disagree.
  • Design a Financial Crime Alert Investigation System — The event log is the source of truth and the case row is a projection of it, so the regulator-facing trace is authoritative and the read model can be rebuilt.
