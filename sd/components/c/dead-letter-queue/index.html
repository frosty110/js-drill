Dead-Letter Queue

A side channel for messages that have failed processing too many times, so one bad item cannot block the pipeline forever.

Reach for it when

  • Any at-least-once pipeline — this is the companion, not an optional extra
  • Failures may be permanent (malformed input) as well as transient
  • You need to inspect and replay failures after fixing a bug

Don't reach for it when

  • Nothing — but it is misused when it becomes a place messages go to be forgotten

What it costs you

  • Another queue to monitor, and an alerting policy for it
  • A replay tool, or the DLQ is just a landfill
  • Ordering guarantees are broken for anything that detours through it

How it breaks

  • Nobody watches it, so silent data loss looks exactly like success
  • Replaying without fixing the cause, so items round-trip forever
  • Filling up because the retry threshold was tuned for a transient failure mode that turned permanent

Instead, consider

  • At-Least-Once Delivery — The delivery guarantee that makes a DLQ necessary in the first place.
  • Retry with Backoff & Jitter — Retry policy decides how long something struggles before it is dead-lettered.
