Document Store

Key-value where the value is a structured document the engine can index and query inside.

Storage & Data Stores supporting 3 problems

Reach for it when

  • Entities are self-contained and read as a whole — a product, a profile, an order with its lines
  • The schema varies per record or evolves quickly
  • You want secondary indexes without committing to a rigid schema

Don't reach for it when

  • Data is highly relational and the same fact would be duplicated across many documents
  • You need multi-document transactions as the normal case, not the exception
  • Aggregations across the entire collection are the primary workload

What it costs you

  • Denormalisation means one fact lives in many documents and updates fan out
  • Unbounded arrays inside a document become an anti-pattern that is painful to undo
  • Schema flexibility becomes schema drift without discipline in the application layer

How it breaks

  • Documents grow past the engine's size limit and writes start failing
  • Index bloat from indexing fields inside large nested structures
  • Application-level joins doing N+1 fetches that a relational engine would have planned

Instead, consider

  • Relational Database — When the same entity is read in many different shapes, normalise and join instead of duplicating.
  • Inverted Index / Search — For full-text or faceted query over documents, a search engine is the right tool.

Used in 3 design problems

  • Design a Photo-Sharing Service — Holds photo metadata — a self-contained record read as a whole, with fields that vary by capture source.
  • Design a Collaborative Document Editor — Holds the document snapshot plus its recent operation log, read together whenever a client joins or reconnects.
  • Design a File Sync / Object Storage Service — Holds the file manifest: chunk list, versions and sharing state for one file, all read together on every sync.
