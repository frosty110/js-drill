Edge Compute

Running small amounts of your logic in the CDN's PoPs, so personalisation, auth or rewriting happens near the user instead of at origin.

Reach for it when

  • Responses need small per-user variation but the bulk is cacheable
  • A redirect, A/B assignment or token check should not cost a round trip to origin
  • You want to cache aggressively but the cache key depends on a computed value

Don't reach for it when

  • The logic needs your primary database — you have moved the compute but not the data
  • Anything requiring long execution, large memory, or strong consistency

What it costs you

  • A constrained runtime with tight CPU and memory limits and a restricted API surface
  • Deploys now target a fleet you do not operate, with its own rollout semantics
  • Debugging and observability at the edge is markedly worse than at origin

How it breaks

  • Edge logic diverges from origin logic and the two disagree about the same request
  • A bad edge deploy has global blast radius and no gradual rollout
  • Cold starts add latency to exactly the requests you moved to the edge to speed up

Instead, consider

  • CDN — If the variation can be pushed into the URL, plain CDN caching is simpler and faster.
  • API Gateway — Central policy at origin when consistency of the rule matters more than the round trip.

Used in 2 design problems

  • Design a Video Streaming Service — Validates signed playback tokens at the PoP, so authorisation does not cost a round trip to origin on every segment request.
  • Design a Short-Form Video Feed — Assembles and prefetches the next few videos near the user, because playback starting instantly is the product's core interaction.
