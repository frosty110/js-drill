Feature Store / Serving

Serving the same computed signals to training and to inference, with an offline store for history and an online store for low-latency reads.

Media & ML Serving signature mechanism 2 problems

Reach for it when

  • Models need per-entity features at request time within a few milliseconds
  • The same feature definition must be used in training and serving
  • Several models or teams share features and are currently recomputing them separately

Don't reach for it when

  • One model with features computable from the request payload alone
  • You have no training/serving skew problem yet and are pre-building for one

What it costs you

  • Two stores to keep consistent — offline history and online serving
  • Point-in-time correctness for training data is genuinely hard to get right
  • Feature definitions become shared contracts with versioning and deprecation

How it breaks

  • Training/serving skew from the same feature computed two different ways
  • Label leakage from features that encode information unavailable at prediction time
  • Stale online features silently degrading model quality with no error anywhere
  • Backfill of a new feature being far more expensive than anyone estimated

Instead, consider

  • Cache — A plain cache of precomputed features when there is one consumer and no training-parity requirement.
  • Stream Processing — Where real-time features are computed before they are stored and served.

Used in 2 design problems

  • Design a Short-Form Video Feed — User and video features are fetched at request time to score the candidate set inside the feed's latency budget.
  • Design a Feature Store — The problem itself — the online/offline split and point-in-time correctness are the entire design.
