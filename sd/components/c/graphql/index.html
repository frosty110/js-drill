GraphQL

A single endpoint where the client declares exactly which fields of a graph it wants, in one round trip.

APIs & Realtime supporting 2 problems

Reach for it when

  • Many client types need very different subsets of the same data
  • Mobile round trips are the bottleneck and over-fetching is measurable
  • The data is genuinely a graph and clients traverse it differently

Don't reach for it when

  • One client with stable needs — you have added a query planner for nothing
  • HTTP caching is important; a POSTed query defeats it
  • You cannot control or budget what clients ask for

What it costs you

  • N+1 resolution unless you build dataloader-style batching
  • Query cost analysis is required or a single query can take down the backend
  • Caching moves from HTTP into your application

How it breaks

  • Deeply nested query exhausting the server, effectively a self-inflicted denial of service
  • N+1 database calls hidden behind innocuous-looking field resolvers
  • Schema growing into a shared dumping ground nobody can deprecate anything from
  • Errors returned with HTTP 200, so infrastructure-level monitoring reports everything as fine

Instead, consider

  • REST — Fewer moving parts, real HTTP caching, and usually enough.
  • gRPC — When the callers are services rather than varied UI clients.

Used in 2 design problems

  • Design a News Feed — Lets the client fetch posts, authors and engagement counts in one round trip instead of three, which matters most on mobile.
  • Design a Photo-Sharing Service — Serves web, iOS and Android clients that each need a different slice of the same photo and profile graph.
