gRPC

Binary RPC over HTTP/2 with an IDL-defined contract, code generation, streaming and multiplexing.

Reach for it when

  • Internal service-to-service calls at high volume
  • You want a generated, type-checked contract across several languages
  • Bidirectional or server streaming is needed without hand-rolling it

Don't reach for it when

  • Browsers are first-class clients — it needs a proxy layer to work there
  • Third-party developers must integrate quickly with curl and a doc page
  • Human-debuggable payloads matter more than efficiency

What it costs you

  • Toolchain and codegen in every language you ship
  • Binary payloads are hard to inspect on the wire
  • Load balancing HTTP/2 needs L7 awareness; naive L4 pins all calls to one connection

How it breaks

  • Long-lived HTTP/2 connections defeating L4 balancing and hot-spotting one backend
  • Proto field reuse or renumbering silently corrupting decoded messages
  • Deadline not propagated, so a cancelled call keeps running downstream
  • Streaming RPCs leaking when neither side closes

Instead, consider

  • REST — External consumers, browser clients, or when 'works with curl' is a requirement.
  • Pub/Sub — If the caller does not need a response, an event is looser coupling than an RPC.
