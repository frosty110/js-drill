Distributed ID Generation

Producing unique identifiers across many machines without a central allocator — Snowflake-style, UUID, or ranged counters.

Data Distribution signature mechanism 1 problem

Reach for it when

  • Many nodes must mint ids concurrently without coordinating on every one
  • Ids need to be roughly time-ordered for index locality or pagination
  • The prompt needs short, opaque or non-guessable public identifiers

Don't reach for it when

  • One database's auto-increment still keeps up — it is simpler and monotonic
  • Ids must be strictly gapless or sequential, which distributed generation cannot promise

What it costs you

  • Snowflake-style ids need a machine-id assignment scheme and clock discipline
  • Random UUIDs destroy index locality and inflate B-tree page splits
  • Encoding choices leak information — a sequential id tells competitors your volume

How it breaks

  • Clock skew or NTP step-back producing duplicate or out-of-order ids
  • Machine-id collision after a scaling event reuses an identifier
  • Range allocator becoming a single point of failure everyone forgot was in the path

Instead, consider

  • Relational Database — A single auto-increment column is correct and boring until you actually outgrow one primary.
  • Consistent Hashing — If the id only needs to route, hashing an existing natural key may remove the problem.

Used in 1 design problem

  • Design a URL Shortener — Produces the short code itself. Counter-encoding versus random-with-collision-check versus hashing is the heart of this problem.
