Idempotency

Making a repeated operation produce the same result as one execution, usually via a client-supplied key recorded with the effect.

Reach for it when

  • Any retry path exists — and in a distributed system one always does
  • The prompt involves payments, orders, or anything a user could double-submit
  • Network timeouts leave the caller genuinely unable to tell whether the write happened

Don't reach for it when

  • The operation is naturally idempotent already (a PUT of a full resource); adding keys is ceremony
  • There is nowhere durable to record the key at the moment of the effect

What it costs you

  • A key store with a retention window, and that window is a real correctness parameter
  • The key must be recorded atomically with the effect, which constrains your storage choices
  • Clients must generate and reuse keys correctly — a contract you have to document and police

How it breaks

  • Key recorded after the effect, so a crash between them admits a duplicate
  • Retention expiring before the last legitimate retry arrives
  • Client regenerating a new key per retry, which defeats the entire mechanism
  • Same key reused for a genuinely different request, silently returning the wrong prior result

Instead, consider

  • Exactly-Once (Effectively-Once) — The pipeline-level version of the same goal; idempotency is the per-operation building block.
  • Reservation / Hold — When the operation must hold a scarce resource rather than just be safe to repeat.

Used in 7 design problems

  • Design a Notification System — Deduplicates sends, so an at-least-once redelivery does not mean the user's phone buzzes twice for one event.
  • Design a Payment System (Wallet / Ledger) — The client-supplied key on every transfer, recorded in the same transaction as the ledger entry — the difference between a retry and a double charge.
  • Design a Ticket Booking System (Ticketmaster-style) — Booking requests carry a key, so a double-tap or a lost response does not leave one user holding two seats for the same show.
  • Design a Prescription Drug Marketplace — Orders must survive retry without dispensing twice; the key is recorded with the fulfilment record, not before it.
  • Design a Distributed Job Scheduler — A job execution is keyed, so at-least-once dispatch does not run the same scheduled task twice on two different workers.
  • Design a Webhook Delivery System — The delivery id sent with every request, so receivers can recognise a redelivery. Its absence is what makes at-least-once dangerous for them.
  • Design an Authentication & Session Service — Token issuance and refresh are made repeat-safe, so a retried login does not mint a second live session the user cannot see or revoke.
