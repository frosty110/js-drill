Key-Value Store

A hash table with an operations team: get and put by key, partitioned across nodes, no query language.

Reach for it when

  • Every access in the prompt is 'look this up by its id'
  • You need very high throughput and predictable single-digit-millisecond latency
  • The value is opaque to the store — a session, a blob of JSON, a serialized object

Don't reach for it when

  • You will need to query by anything other than the key; you would be building indexes by hand
  • Cross-key transactions or invariants
  • Analytical scans over the whole dataset

What it costs you

  • Access patterns are frozen into the key design, and changing them means a migration
  • Secondary indexes, if the store has them, are usually eventually consistent
  • You own denormalisation and therefore the consistency between copies

How it breaks

  • Hot partition from a key design that concentrates traffic
  • Unbounded value growth turning one key into a multi-megabyte read
  • Eventual consistency surfacing as a read that does not contain the write you just made

Instead, consider

  • Relational Database — The moment two rows must change together, you want transactions more than you want throughput.
  • Document Store — Same key-based access but with queryable structure inside the value.

Used in 3 design problems

  • Design a URL Shortener — Holds the short-code → URL mapping. Every access is a lookup by key, which is the shape a KV store scales furthest on.
  • Design a Distributed Job Scheduler — Stores per-job execution state keyed by job id, written and read far more often than it is queried.
  • Design an Authentication & Session Service — Holds sessions and refresh tokens keyed by id, with TTL doing the expiry work the application would otherwise schedule itself.
