Leader Election

Picking exactly one node to perform a role, with an agreed way to notice failure and pick again.

Reach for it when

  • Exactly one process must do a job — a scheduler, a compactor, a partition owner
  • The prompt needs automatic failover without an operator
  • Multiple nodes doing the work concurrently would be incorrect, not just wasteful

Don't reach for it when

  • The work is safely parallel — election adds a coordination dependency for nothing
  • You would be implementing consensus yourself; use etcd, ZooKeeper or Raft

What it costs you

  • A consensus system in your dependency graph, with its own availability story
  • Failover is not instant; there is a detection window where nobody is leader
  • Leases and fencing tokens must be honoured by the work itself, not just the election

How it breaks

  • Split brain — a paused leader wakes up still believing it holds the role
  • Election storms flapping the role between nodes under load
  • Work performed after the lease expired because the worker never checked
  • The leader becoming a throughput bottleneck nobody planned for

Instead, consider

  • Distributed Lock — A lock with a lease is election for one task rather than for a standing role.
  • Consistent Hashing — Partition ownership by hash gives every node a role without a single leader.

Used in 2 design problems

  • Design a Distributed Message Queue — Each partition has exactly one leader accepting writes, and electing a new one on failure is what lets the broker survive node loss.
  • Design a Distributed Job Scheduler — Exactly one scheduler instance may decide which jobs are due, or every due job fires once per running instance.
