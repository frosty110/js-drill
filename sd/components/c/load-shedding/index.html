Load Shedding

Deliberately dropping or degrading lower-priority work under overload so the system serves its most important traffic instead of failing at everything.

Reach for it when

  • Demand can exceed capacity and you cannot slow the source
  • Some traffic is genuinely more important than the rest — checkout over recommendations
  • The prompt asks what happens at 10× expected load

Don't reach for it when

  • All traffic is equally critical, so there is nothing to shed that does not hurt equally
  • Capacity is the actual answer and shedding is being used to avoid provisioning

What it costs you

  • You need a priority classification for traffic, which is a product decision
  • Shed requests are visible failures, so the client experience must be designed
  • Detecting overload accurately is harder than it looks — queue depth beats CPU

How it breaks

  • Shedding triggered too late, once queues are already deep and latency is unrecoverable
  • Shedding cheap requests while expensive ones sail through, so it does not reduce load
  • Clients retrying shed requests immediately, converting a shed into an amplification

Instead, consider

  • Rate Limiting — Per-caller fairness before overload; shedding is the emergency response after.
  • Backpressure — If the producer CAN be slowed, do that instead — no work is lost.
