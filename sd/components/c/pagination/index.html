Cursor Pagination

Returning a page plus an opaque cursor pointing at the last item, so the next page seeks rather than counting from the start.

APIs & Realtime supporting 4 problems

Reach for it when

  • Result sets are large and clients page through them
  • New items arrive while a client is paging — a feed, a log, a timeline
  • Deep pages must stay as fast as shallow ones

Don't reach for it when

  • Users must jump to an arbitrary page number, which cursors cannot express
  • The result set is small and bounded
  • There is no stable, unique sort key to build a cursor from

What it costs you

  • Requires a stable total ordering, usually a compound key including a tiebreaker
  • No total count without a separate query
  • Cursor encoding becomes a compatibility surface once clients persist them

How it breaks

  • OFFSET used instead, so page 500 scans and discards 10,000 rows
  • Items skipped or repeated when new rows arrive between requests
  • Non-unique sort key causing rows at a boundary to be dropped
  • Cursor format changed and previously issued cursors stop decoding

Instead, consider

  • Inverted Index / Search — For ranked or faceted results, the engine's own paging semantics apply and deep paging is its own problem.
  • Server-Sent Events — If the client wants everything new as it happens, push beats repeated paging.

Used in 4 design problems

  • Design a News Feed — Cursor-based feed paging, so posts arriving mid-scroll do not shift the window and duplicate what the user just read.
  • Design a Chat System — Scrollback through message history, keyed on message id so a long thread pages backwards at constant cost.
  • Design a Proximity Service — Results page outward by distance band, so 'more places near me' does not rescan the whole radius.
  • Design a Search Engine — Result paging, where deep pages are expensive by construction because every shard must produce the full prefix.
