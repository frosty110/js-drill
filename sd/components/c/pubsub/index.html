Pub/Sub

One published event delivered to every interested subscriber, so producers never learn who consumes them.

Async & Messaging supporting 4 problems

Reach for it when

  • Several unrelated systems must react to the same event
  • You want to add a new consumer later without touching the producer
  • The prompt describes an event that fans out to notifications, analytics and search indexing at once

Don't reach for it when

  • Exactly one worker should handle each item — that is a work queue
  • The producer needs to know the work completed

What it costs you

  • No single place shows what happens when an event fires; tracing gets harder
  • Every subscriber is a new failure mode for the same event
  • Schema evolution must satisfy consumers you may not know about

How it breaks

  • A slow subscriber applying backpressure to the whole topic, or being silently dropped
  • Event-schema change breaking a consumer nobody remembered existed
  • Redelivery producing duplicate side effects in every subscriber at once

Instead, consider

  • Work Queue — When the work must happen once, not N times.
  • Transactional Outbox / CDC — If the event must be exactly as durable as the database write that caused it.

Used in 4 design problems

  • Design a Notification System — One triggering event delivered to the email, push and SMS pipelines independently, so adding a channel never touches the producer.
  • Design a Collaborative Document Editor — Edit events fan out to every collaborator's session, decoupled from whichever client produced the change.
  • Design an Observability Platform — Telemetry is published once and consumed by alerting, storage and dashboards separately, each at its own pace.
  • Design a Content Moderation Pipeline — An upload event reaches the scoring models, the audit log and the review queue without the uploader knowing any of them exist.
