Quorum (N/W/R)

Requiring W acknowledgements to write and R responses to read out of N replicas, tuning consistency against availability.

Reach for it when

  • The prompt asks you to reason explicitly about the consistency-availability tradeoff
  • You want strong reads sometimes and fast reads other times, from the same store
  • Replicas span regions and you must survive losing one

Don't reach for it when

  • A single-leader store already gives you what you need with less to explain
  • The application cannot handle the conflict resolution that concurrent writes require

What it costs you

  • Latency is governed by the slowest replica in the quorum
  • W+R>N gives overlap, not linearizability — concurrent writes still need conflict resolution
  • Operational reasoning gets harder; correctness now depends on numbers in a config

How it breaks

  • Sloppy quorum accepting writes on nodes outside the intended set, so a later read misses them
  • Read repair storms after a partition heals
  • Choosing W+R≤N for latency and quietly accepting stale reads nobody documented

Instead, consider

  • Replication — Plain leader-follower replication when you do not need per-request tuning.
  • Conflict Resolution — Quorums make concurrent writes possible; something still has to decide who wins.

Used in 2 design problems

  • Design a Payment System (Wallet / Ledger) — W and R are set so an acknowledged ledger write survives losing a replica; latency is spent deliberately to buy that guarantee.
  • Design a Distributed Key-Value Store — Tunable N/W/R is the interface through which this design exposes the consistency-availability tradeoff to its callers.
