Relational Database

Row storage with a fixed schema, joins, secondary indexes and multi-row ACID transactions.

Storage & Data Stores supporting 4 problems

Reach for it when

  • The prompt says money, inventory, bookings, or anything where a partial write is a bug with a lawyer attached
  • Entities are related and access patterns are not known up front — joins buy you flexibility
  • You need read-your-writes and cross-row invariants enforced by the store

Don't reach for it when

  • Write volume that exceeds one primary and the data has no clean partition key
  • Schemaless, high-churn documents where every row would be half null
  • Append-only telemetry at millions of events per second

What it costs you

  • Vertical scaling has a ceiling and horizontal scaling means sharding you implement yourself
  • Schema migrations on large tables are an operational event, not a deploy
  • Joins that were free at 1M rows are a capacity plan at 1B

How it breaks

  • Lock contention on a hot row serialises the whole workload
  • Connection exhaustion from an app tier that scaled out faster than the pool
  • An unindexed query pattern discovered in production as a full table scan

Instead, consider

  • Key-Value Store — If every access is by primary key and you need no transactions, a KV store scales further for less.
  • Wide-Column Store — When write volume and partition-key access dominate and you can give up joins.

Used in 4 design problems

  • Design a Payment System (Wallet / Ledger) — Holds the ledger, where a partial write is not a degraded mode but a lost or duplicated payment — the case ACID exists for.
  • Design a Ticket Booking System (Ticketmaster-style) — Enforces seat uniqueness transactionally; overselling is the specific failure this store is chosen to make impossible.
  • Design a Prescription Drug Marketplace — Holds orders, authorisations and the dispensing audit trail, where regulatory correctness outranks throughput.
  • Design an Authentication & Session Service — The user and credential store — modest volume, strong consistency, and the place a password change must take effect immediately.
