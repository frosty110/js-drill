Replication

Keeping copies of the same data on multiple nodes, for read capacity, fault tolerance, or geographic proximity.

Reach for it when

  • Durability or availability is a stated requirement — losing one node must not lose data
  • Read volume dwarfs write volume and the dataset fits on one machine
  • Users are geographically spread and reads should be served locally

Don't reach for it when

  • Writes are the bottleneck — replication multiplies write work rather than reducing it
  • The application cannot tolerate reading a value that is momentarily behind

What it costs you

  • Replication lag is now a semantic your application must handle explicitly
  • Synchronous replication trades latency and availability for consistency; asynchronous trades the reverse
  • N× storage and N× write amplification

How it breaks

  • Read-your-writes violated because a read landed on a lagging replica
  • Split brain during a partition, with two nodes both accepting writes
  • Failover promoting a replica that had not caught up, silently losing acknowledged writes

Instead, consider

  • Quorum (N/W/R) — Quorum reads/writes let you tune the consistency-availability point instead of accepting the default.
  • Sharding — Replication scales reads; sharding scales writes and capacity. Most real systems need both.

Used in 6 design problems

  • Design a Distributed Cache — Each entry is held on N successive ring nodes, so losing one node degrades the hit rate instead of losing a whole slice of the keyspace.
  • Design a Payment System (Wallet / Ledger) — Synchronous replication of the ledger, because losing an acknowledged financial write is not a degraded mode — it is an unrecoverable defect.
  • Design a Distributed Message Queue — Each partition has a leader and followers; the in-sync replica set is what lets an acknowledged publish survive a broker dying.
  • Design a Distributed Key-Value Store — N replicas per key range with tunable W and R — where this problem's entire consistency-versus-availability conversation actually lives.
  • Design a Search Engine — Index shards are replicated for read throughput and node loss. Query volume, not durability, is what drives the replica count here.
  • Design an Authentication & Session Service — Session state is replicated across regions, so a login in one region is honoured in another without a cross-region read on every request.
