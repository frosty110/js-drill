Resource Scheduling

Allocating scarce, expensive compute — GPUs, batch slots — across competing requests by priority, batching and queueing.

Media & ML Serving signature mechanism 1 problem

Reach for it when

  • The bottleneck resource is expensive enough that utilisation is the design goal
  • Requests vary in priority or in cost and cannot be treated identically
  • Batching several requests together materially improves throughput

Don't reach for it when

  • Capacity is cheap and elastic — just autoscale
  • Requests are uniform and a plain queue suffices

What it costs you

  • Batching trades per-request latency for throughput, and that curve must be chosen deliberately
  • Priority classes need admission control or the top class starves everyone else
  • The scheduler becomes a critical, stateful component of its own

How it breaks

  • Head-of-line blocking from one very large request occupying the resource
  • Batch window tuned for throughput, blowing the latency budget for interactive traffic
  • Fragmentation leaving capacity unusable because no waiting request fits it
  • Preemption losing partially completed work with no checkpoint

Instead, consider

  • Work Queue — When requests are uniform and fair FIFO ordering is acceptable.
  • Rate Limiting — Capping demand per caller is simpler than scheduling it, when fairness is the actual goal.

Used in 1 design problem

  • Design an LLM Inference Platform — GPU allocation across requests, where continuous batching and priority classes decide whether very expensive hardware sits idle.
