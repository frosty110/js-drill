REST

Resource-oriented HTTP with standard verbs, status codes and cacheable GETs — the default public API shape.

Reach for it when

  • A public API consumed by clients you do not control
  • You want HTTP caching, proxies and tooling to work without special support
  • Broad accessibility matters more than payload efficiency

Don't reach for it when

  • Chatty internal service-to-service calls where serialisation overhead dominates
  • Clients need wildly different subsets of the same data and you are drowning in endpoint variants

What it costs you

  • Over- and under-fetching, which drives clients to make several round trips
  • Versioning is a real design burden once you have external consumers
  • No schema enforcement unless you add one

How it breaks

  • Non-idempotent POST retried after a timeout, creating a duplicate resource
  • Offset pagination degrading and skipping rows as the underlying data shifts
  • Breaking changes shipped without a version, discovered by customers
  • Endpoint proliferation as each client gets its own bespoke variant

Instead, consider

  • gRPC — Internal, high-volume, strongly-typed service calls where efficiency and contracts matter.
  • GraphQL — When clients need very different shapes of the same graph and round trips are the pain.
