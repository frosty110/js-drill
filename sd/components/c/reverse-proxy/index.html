Reverse Proxy

A server-side intermediary that terminates the client connection and speaks to backends on its behalf, so cross-cutting work happens once at the edge.

Reach for it when

  • TLS termination, compression, or request buffering should happen in one place, not in every service
  • You want to serve static assets and proxy dynamic paths from the same hostname
  • Slow clients must not tie up application threads

Don't reach for it when

  • The only need is spreading load — that is a load balancer, and calling it a proxy adds vocabulary without adding a decision
  • Per-caller policy, auth and quotas are the real requirement — that is an API gateway

What it costs you

  • Another network hop and another config surface
  • Buffering large uploads costs memory at the edge
  • It sees plaintext after TLS termination, so it becomes a security-relevant component

How it breaks

  • Header and body size limits silently truncate or reject at the edge, producing errors the backend never sees
  • Connection-pool exhaustion to backends throttles everything behind it
  • Timeout mismatches between proxy and backend produce duplicated work: the proxy retries a request still running

Instead, consider

  • API Gateway — A gateway is a reverse proxy that also owns auth, rate limits and per-route policy. Pick it when policy is the point.
  • Load Balancer — If nothing cross-cutting happens at the hop, you only needed balancing.

Used in 2 design problems

  • Design a Video Streaming Service — Terminates TLS and buffers large uploads at the edge, so a slow uploader on a phone does not hold an application thread for the length of the transfer.
  • Design a File Sync / Object Storage Service — Absorbs slow client uploads and TLS at the edge, while the chunks themselves go direct to object storage rather than through the application tier.
