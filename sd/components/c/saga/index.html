Saga

A multi-step workflow across services where each step has a compensating action, because no distributed transaction is available.

Correctness & Coordination signature mechanism 2 problems

Reach for it when

  • A business operation spans several services that each own their own data
  • The prompt needs all-or-nothing semantics across boundaries where 2PC is not viable
  • Steps involve external parties — payment processors, shipping, third-party APIs

Don't reach for it when

  • All the state lives in one database — use a transaction and stop inventing
  • Steps genuinely cannot be compensated (an email is sent, a drug is dispensed) and the design pretends they can

What it costs you

  • Every forward step needs a compensating step, roughly doubling the logic
  • Intermediate states are visible to users, so the product must define what they see
  • Orchestration state has to be durable and recoverable, which is another service

How it breaks

  • Compensation itself failing, leaving the workflow stuck in a half-applied state
  • Non-compensatable side effect performed before a step that can still fail
  • Orchestrator crash mid-saga with no durable record of how far it got
  • Concurrent sagas on the same entity interleaving into a state neither expected

Instead, consider

  • Reservation / Hold — A two-phase reserve-then-confirm is a lighter pattern when the risk is only about holding scarce stock.
  • Transactional Outbox / CDC — The reliable way for each saga step to announce completion without a dual-write.

Used in 2 design problems

  • Design a Payment System (Wallet / Ledger) — A transfer spanning accounts or external processors proceeds as compensable steps, because no distributed transaction spans them.
  • Design a Prescription Drug Marketplace — Order → payment → pharmacy fulfilment crosses systems, and each step needs a compensation because some of them cannot be rolled back at all.
