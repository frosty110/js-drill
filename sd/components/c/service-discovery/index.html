Service Discovery

A registry that answers 'where is service X right now', so callers reach live instances without hardcoded addresses.

Reach for it when

  • Instances come and go constantly — autoscaling, rolling deploys, container schedulers
  • Internal callers should route directly to backends rather than through a shared LB
  • The prompt mentions a service mesh or sidecar proxies

Don't reach for it when

  • A fixed, small set of long-lived hosts — a config file is honest and has no failure mode
  • You need routing decisions based on request CONTENT; discovery answers 'where', not 'which one for this request'

What it costs you

  • A strongly-consistent registry is itself a distributed system to run and to keep available
  • Client-side libraries must be kept in step across every language you deploy
  • Registration lag means the registry is always slightly behind reality

How it breaks

  • Stale entries route traffic to instances that are already gone
  • Registry outage is a total outage unless callers cache last-known-good and fail static
  • Thundering herd of re-registration after a network partition heals

Instead, consider

  • Load Balancer — A load balancer centralises the same decision; discovery distributes it to callers. One hop vs. one library everywhere.
  • DNS & Anycast Routing — DNS is discovery with weak TTL semantics — fine for coarse-grained, wrong for second-by-second membership.
