Sharding

Splitting one logical dataset across many machines by a partition key, so capacity and throughput scale horizontally.

Reach for it when

  • The dataset or its write volume exceeds what one machine can hold or serve
  • The prompt gives numbers that clearly exceed one primary
  • There is a natural partition key with high cardinality and even distribution

Don't reach for it when

  • One machine still fits — sharding is a permanent complexity tax paid in advance
  • Queries routinely span all partitions; you have built scatter-gather, not scale
  • No good key exists and every candidate is skewed

What it costs you

  • Cross-shard queries and transactions become application problems
  • Resharding is a migration with a data-movement plan, not a config change
  • Every operational task multiplies by the shard count

How it breaks

  • Skew: one partition holds the celebrity and saturates while others idle
  • Scatter-gather latency governed by the slowest shard, so p99 degrades as shards are added
  • A key chosen for even distribution that forces every read to fan out

Instead, consider

  • Consistent Hashing — The placement scheme that makes adding and removing shards cheap; sharding is the what, this is the how.
  • Replication — If reads are the bottleneck and the data fits, replicas scale reads without splitting anything.

Used in 7 design problems

  • Design a URL Shortener — Splits the mapping table by short-code hash once one primary cannot hold the row count. Access is pure key lookup, which shards about as cleanly as anything does.
  • Design a Leaderboard — Partitions scores by leaderboard and time window; one global sorted set would concentrate every write in the system on a single node.
  • Design a Typeahead / Autocomplete Service — The trie is partitioned by prefix — the textbook uneven partition, since 'a' and 'th' carry orders of magnitude more traffic than 'zq'.
  • Design a Distributed Key-Value Store — The core mechanic. The keyspace is divided across nodes by ring position, and every other feature in the design is built on top of that division.
  • Design a Proximity Service — Geo cells are the partition key, so nearby entities land on the same node. Locality is the point; population skew is the price you agree to pay.
  • Design a Search Engine — The index is split document-wise so each shard holds a slice of the corpus; a query scatters to every shard and gathers the top-K.
  • Design an Observability Platform — Telemetry is partitioned by series or tenant, because ingest volume is the defining constraint and no single node absorbs a firehose.
