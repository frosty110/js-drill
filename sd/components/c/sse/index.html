Server-Sent Events

A one-way stream of events over a normal HTTP response, with browser-native reconnect and event ids for resumption.

Reach for it when

  • Updates flow server-to-client only — notifications, progress, token streaming
  • You want push without owning reconnect logic
  • Corporate proxies and infrastructure that dislike WebSocket upgrades are in play

Don't reach for it when

  • The client needs to send frequently on the same channel — that is WebSockets
  • You need binary frames
  • Very high per-client message rates where framing overhead matters

What it costs you

  • Still one held connection per client, with the same fan-out and capacity implications
  • Text-only, so binary payloads must be encoded
  • Older HTTP/1.1 clients hit per-domain connection limits

How it breaks

  • Buffering proxies holding events until the buffer fills, destroying the latency benefit
  • Missing Last-Event-ID handling, so a reconnect silently loses everything sent while away
  • No heartbeat, so a dead connection looks identical to an idle one

Instead, consider

  • WebSockets / Persistent Connections — When the client must talk back on the same channel at the same cadence.
  • Cursor Pagination — For infrequent updates, polling a cursor endpoint is simpler than any push channel.

Used in 2 design problems

  • Design a Notification System — Streams notifications to a web client one way, with browser-native reconnect doing work a raw socket would make you build.
  • Design an LLM Inference Platform — Streams generated tokens back as they are produced, which is what makes a slow model feel responsive.
