Tenant Isolation

Keeping one customer's data and load away from another's, enforced below application code so a forgotten predicate cannot leak.

Governance & Accountability signature mechanism 6 problems

Reach for it when

  • One deployment serves customers who must never see each other's data, and that is a contractual promise
  • A single tenant can generate enough load to degrade everyone else, so fairness needs enforcing rather than assuming
  • An auditor will ask how isolation is guaranteed, and 'every query filters correctly' will not survive

Don't reach for it when

  • A single-tenant deployment per customer, where the isolation is the deployment and adding a second mechanism adds only cost
  • Data that is genuinely global — a catalogue, a public price list — where scoping it invents a boundary that does not exist

What it costs you

  • Enforcement in the database means every policy predicate needs an index, and a missing one degrades quietly
  • Per-tenant queues and quotas multiply the things you operate and the things that can be misconfigured
  • The largest customers often demand physical separation anyway, so you end up operating both models

How it breaks

  • Isolation enforced only in application code, where one query written without the filter is a breach and nothing catches it
  • Background jobs and admin paths on elevated credentials that bypass enforcement: the likeliest leak
  • A shared cache keyed without the tenant, so the boundary holds in the database and fails one layer above it
  • Fairness measured in requests when the expensive thing is work per request, so a quota that looks fair is not
  • No test that actually attempts a cross-tenant read, leaving isolation a claim rather than a verified control

Instead, consider

  • Bulkhead Isolation — Isolates load between workload classes; tenancy adds a data boundary that a bulkhead says nothing about.
  • Rate Limiting — Caps a tenant's request rate, which is the load half of isolation and none of the data half.
  • Sharding — Splitting by tenant makes isolation physical, at the cost of per-tenant operations and rebalancing.

Used in 6 design problems

  • Design a Distributed Job Scheduler — One tenant flooding the scheduler with jobs must not starve another's, so admission and worker capacity are partitioned rather than shared first-come-first-served.
  • Design an LLM Inference Platform — Per-tenant GPU pools and quotas, so one customer's batch job cannot consume the capacity another customer's interactive traffic depends on.
  • Design an Observability Platform — Per-tenant ingest partitions and query limits, so one customer instrumenting a hot loop cannot degrade everyone else's dashboards.
  • Design a Financial Crime Alert Investigation System — Each bank's policy, data and model configuration stay separate, because the same agents run against institutions that must never see each other's alerts.
  • Design a Human Review Queue — Reviewer pools and queues are scoped per tenant, since someone cleared to see one institution's data usually is not cleared for another's.
  • Design a Business Verification Pipeline — Per-institution verification policy and vendor credentials, so 'sufficient evidence' can mean two different things in the same pipeline.
