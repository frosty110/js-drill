Trie / Autocomplete

A prefix tree with top-K completions precomputed at each node, so a keystroke returns suggestions in a single traversal.

Indexes & Search supporting 2 problems

Reach for it when

  • The prompt is typeahead, search suggestions or command completion
  • Latency budget is tens of milliseconds because it fires on every keystroke
  • The suggestion set changes far more slowly than it is queried

Don't reach for it when

  • Matching should be fuzzy or semantic rather than prefix-based
  • The suggestion set is tiny — a filter over an array is simpler
  • Suggestions must be personalised per user at full precision

What it costs you

  • Memory grows with the vocabulary, and storing top-K at every node multiplies it
  • Rebuilds are batch jobs, so new terms appear on a delay
  • Sharding a trie by prefix creates uneven partitions by construction

How it breaks

  • Popular prefixes ('a', 'th') becoming hot shards that serve most of the traffic
  • Stale top-K after a spike in popularity for a term the last rebuild missed
  • Memory blowup from storing full strings at every node instead of references
  • No typo tolerance, so a single mistyped character returns nothing

Instead, consider

  • Inverted Index / Search — A general search engine with an edge-ngram analyser, when you want fuzziness and are willing to pay for it.
  • Cache — Popular prefixes dominate the distribution; caching their results absorbs most requests before the trie.

Used in 2 design problems

  • Design a Typeahead / Autocomplete Service — The structure the whole design rests on: prefix nodes carrying precomputed top-K completions.
  • Design a Search Engine — Powers query suggestions alongside the main index, which is a prefix problem rather than a relevance one.
