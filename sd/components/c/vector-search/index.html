Vector Search

Approximate nearest-neighbour lookup over embeddings, retrieving by semantic similarity instead of by keyword.

Indexes & Search signature mechanism 1 problem

Reach for it when

  • The prompt needs 'find things like this' where the match is meaning, not spelling
  • Retrieval feeds an LLM (RAG) or a recommender
  • Users phrase queries differently from the source documents

Don't reach for it when

  • Exact matching and filtering are what users need — keyword search is cheaper and explainable
  • The corpus changes constantly and index rebuilds cannot keep up
  • You cannot explain why a result was returned and the product requires that

What it costs you

  • Embeddings must be generated and regenerated whenever the model changes
  • ANN indexes are memory-hungry and trade recall for latency by construction
  • Hybrid ranking with keyword search is usually necessary, so you run both

How it breaks

  • Model version drift making old and new embeddings incomparable in the same index
  • Recall silently degrading as index parameters are tuned for latency
  • Chunking strategy destroying the context that made a passage meaningful
  • No metadata filtering, so results are semantically close but structurally invalid

Instead, consider

  • Inverted Index / Search — Lexical search when exactness, filters and explainability matter more than semantics.
  • Ranking — Retrieval gets candidates; ranking decides the order. Vector search is the first stage, not the whole answer.

Used in 1 design problem

  • Design a RAG / Semantic Search System — Retrieves passages by embedding similarity, which is what lets a question phrased differently from the source document still find it.
