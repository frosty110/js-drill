Webhooks

Pushing events to a URL the customer registered, so their server learns about changes without polling yours.

Reach for it when

  • External systems must react to your events promptly
  • Polling would be wasteful at your customer count
  • The prompt describes integrations, payment events or third-party notifications

Don't reach for it when

  • The receiver cannot host a public endpoint
  • Ordering across events is required — delivery order cannot be guaranteed
  • Sub-second latency matters; delivery is best-effort with retries

What it costs you

  • You now own delivery: retries, backoff, dead-lettering and a replay tool
  • Receiver endpoints are unreliable and slow, and that becomes your operational problem
  • Signing, secret rotation and replay protection are required, not optional

How it breaks

  • A dead endpoint accumulating an unbounded retry backlog that starves healthy deliveries
  • Retry storms hammering a receiver that is already struggling
  • Duplicate delivery corrupting receiver state because no idempotency key was sent
  • SSRF via customer-supplied URLs pointed at internal addresses

Instead, consider

  • Cursor Pagination — A polled cursor feed is far less machinery when near-real-time is not required.
  • At-Least-Once Delivery — The delivery guarantee webhooks provide — receivers must be idempotent.

Used in 3 design problems

  • Design a Payment System (Wallet / Ledger) — How the payment processor reports that an asynchronous authorisation settled — the event the ledger is waiting on.
  • Design a Prescription Drug Marketplace — Carries fulfilment and authorisation callbacks from pharmacy and payment partners you do not control.
  • Design a Webhook Delivery System — The problem itself: everything here is about delivering one to a receiver you neither control nor trust to be up.
