Wide-Column Store

Partition-key-first storage (Cassandra, HBase, DynamoDB) built for enormous write volume and range scans within a partition.

Reach for it when

  • Write throughput is the headline requirement and writes are spread across many partition keys
  • Access is always 'give me a range within one partition' — a user's messages, a device's readings
  • The prompt needs multi-region writes with tunable consistency

Don't reach for it when

  • Query patterns are unknown or will change — the partition key is close to irreversible
  • You need joins, or transactions spanning partitions
  • The dataset is small enough that one relational primary would do

What it costs you

  • You design tables per query, so a new access pattern means a new table and a backfill
  • Tombstones and compaction are operational concerns that leak into latency
  • Eventual consistency by default; strong reads cost latency and availability

How it breaks

  • Unbounded partition growth turning one partition into a hotspot and then a timeout
  • Tombstone accumulation making range scans progressively slower until compaction catches up
  • Last-write-wins silently discarding a concurrent update

Instead, consider

  • Time-Series Store — If every row is a timestamped measurement, a purpose-built TSDB gives you retention and rollups for free.
  • Key-Value Store — When you never need range scans within a partition, plain KV is simpler.
