Caching

Where to put a cache, how reads and writes flow through it (cache-aside, read-through, write-through, write-back, write-around), how entries are evicted and invalidated, and how to survive the stampede when a hot key expires.

Key ideas

  • Cache-aside (lazy loading): the app checks the cache, and on a miss loads from the DB and populates the cache itself; the cache never talks to the DB.
  • Read-through and write-through push that logic into the cache layer; write-through writes cache and DB synchronously (fresh but slower writes).
  • Write-back (write-behind) writes to cache and flushes to the DB asynchronously — fastest writes but risks data loss if the node dies before flush; write-around writes straight to the DB and skips the cache.
  • Eviction policies (LRU, LFU, FIFO, TTL/random) decide who leaves when the cache is full; cache invalidation is famously one of the two hard problems.
  • A cache stampede/thundering herd happens when a hot key expires and many requests hit the origin at once; mitigate with per-key locking, request coalescing, jittered TTLs, early recomputation, or stale-while-revalidate.
  • Redis is single-threaded with rich data structures and optional persistence; Memcached is multi-threaded, string-only, and purely in-memory.
  • Caches live at many layers — browser, CDN, in-process/application, distributed cache, and the DB buffer pool — and hit ratio measures their effectiveness.

Q1 multiple choice

In the cache-aside (lazy loading) pattern, who is responsible for loading data from the database on a cache miss?

  1. A A background job pre-warms every possible key
  2. B The cache automatically fetches from the DB and returns it
  3. C The application code reads from the DB and then writes the value into the cache correct
  4. D The database pushes the row into the cache when it changes

Why: With cache-aside the application owns the logic: on a miss it queries the DB, returns the value, and populates the cache itself — the cache is a dumb store that never contacts the DB. When the cache does the load for you, that is read-through, a different pattern.

Q2 multiple choice

How does write-through caching behave on a write?

  1. A Writes are dropped unless the key is already cached
  2. B Writes go to the cache only and are flushed to the DB later asynchronously
  3. C Writes go straight to the DB and bypass the cache entirely
  4. D Writes update the cache and the database synchronously as one operation correct

Why: Write-through updates both the cache and the DB synchronously, so the cache is always consistent with the database at the cost of slower writes. Writing to cache and flushing later is write-back; going straight to the DB and skipping the cache is write-around.

Q3 multiple choice

What is the defining risk of a write-back (write-behind) cache?

  1. A Data can be lost if the cache node fails after acking the write but before flushing it to the database correct
  2. B Every write must also invalidate the CDN
  3. C Writes are slower than write-through because of the extra hop
  4. D Reads are always stale because the DB is never updated

Why: Write-back acknowledges the write once it hits the cache and flushes to the DB asynchronously, so a crash before the flush loses those buffered writes — the durability tradeoff for very fast writes. It is actually faster than write-through, which is its whole appeal.

Q4 multiple choice

When is write-around caching (write to the DB, skip the cache) the right choice?

  1. A For data that is written once and read many times immediately after
  2. B For write-heavy data that is rarely re-read soon, so you avoid polluting the cache with entries that will just be evicted correct
  3. C When you need the cache and DB to stay perfectly consistent on every write
  4. D When you want the fastest possible write latency

Why: Write-around sends writes straight to the DB and only caches on a later read, which avoids filling the cache with write-once data that would otherwise evict hotter entries. The tradeoff is that a read right after a write is a guaranteed miss.

Q5 multiple choice

Which pattern combined with write-around causes a recently written item to be a cache miss on the next read?

  1. A Write-through, because it invalidates on write
  2. B Read-through, because it never repopulates
  3. C Cache-aside read, because the write skipped the cache so the value must be loaded from the DB on first read correct
  4. D Write-back, because the flush blocks the read

Why: Write-around does not populate the cache on write, so the first read afterward misses and a cache-aside/read-through load pulls it from the DB. Write-through would have kept the cache fresh, avoiding that miss.

Q6 multiple choice

What does an LRU eviction policy do when the cache is full?

  1. A Evicts a randomly chosen entry
  2. B Evicts the entry that has been accessed the fewest times overall
  3. C Evicts the entry that was inserted earliest, regardless of use
  4. D Evicts the entry that has gone the longest without being accessed correct

Why: LRU (least-recently-used) evicts whichever entry has been idle the longest, betting that recently touched items will be touched again. Evicting by lowest access count is LFU, and evicting the oldest-inserted is FIFO.

Q7 multiple choice

How does LFU differ from LRU?

  1. A LFU evicts by lowest access frequency/count; LRU evicts by longest time since last access correct
  2. B LFU and LRU are identical for read-heavy workloads
  3. C LFU evicts the newest entries first; LRU evicts the oldest
  4. D LFU uses TTL while LRU never expires entries

Why: LFU tracks how often each key is used and drops the least-frequently-used, which can retain a long-popular item that was briefly idle; LRU only looks at recency of last access. A pitfall of LFU is that once-popular-now-cold keys can stick around unless the counts decay.

Q8 multiple choice

A cache stampede (thundering herd) occurs when...

  1. A The cache runs out of memory and evicts everything at once
  2. B A popular key expires and many concurrent requests all miss and hit the origin database simultaneously correct
  3. C Two nodes write the same key with different values
  4. D The TTL is set too long, so entries never refresh

Why: When a hot key expires, every in-flight request misses at once and stampedes the origin to recompute the same value, which can overwhelm the DB. The classic fixes coordinate that recomputation so only one request does the work.

Q9 multiple choice

Which technique lets only one request recompute an expired hot key while the others wait for or reuse its result?

  1. A Disabling TTLs so keys never expire
  2. B Increasing the LRU cache size
  3. C Per-key locking / request coalescing (single-flight) correct
  4. D Switching from Redis to Memcached

Why: A per-key lock (single-flight / request coalescing) ensures the first request rebuilds the value while the rest block briefly and then read the freshly cached result, collapsing N origin hits into one. Bigger caches or a different engine do not address the concurrent-miss problem.

Q10 multiple choice

Why add jitter (randomization) to cache TTLs?

  1. A To guarantee strong consistency with the database
  2. B To reduce the memory footprint of each entry
  3. C To make each key use a different eviction policy
  4. D To spread expirations over time so many keys don't expire at the same instant and cause a synchronized stampede correct

Why: If many entries are written together with an identical TTL, they all expire simultaneously and stampede the origin; adding random jitter to each TTL staggers the expirations. It is a cheap complement to locking and early-recompute strategies.

Q11 multiple choice

What does the stale-while-revalidate strategy do?

  1. A Serves the existing (slightly stale) cached value immediately while asynchronously refreshing it in the background correct
  2. B Deletes the key the moment it becomes stale
  3. C Writes through to the DB on every read
  4. D Blocks all readers until a fresh value is computed

Why: Stale-while-revalidate returns the stale entry right away to keep latency low and kicks off an async refresh so the next reader gets fresh data, avoiding both the miss latency and the stampede. The cost is briefly serving slightly outdated data.

Q12 multiple choice

Which statement correctly contrasts Redis and Memcached?

  1. A Redis is multi-threaded and string-only; Memcached is single-threaded with rich data structures
  2. B Redis is single-threaded (per shard) with rich data structures and optional persistence; Memcached is multi-threaded, stores plain strings, and is purely in-memory correct
  3. C Both persist to disk by default and support the same data types
  4. D Memcached supports replication and pub/sub while Redis does not

Why: Redis offers data structures (lists, sets, sorted sets, hashes), optional persistence (RDB/AOF), and replication, running its command loop single-threaded; Memcached is a simpler multi-threaded string cache with no persistence. Pick Memcached for a pure, multi-core string cache and Redis when you need structures, durability, or pub/sub.

Q13 multiple choice

Which is an example of an in-process (application-layer) cache rather than a distributed cache?

  1. A The database's buffer pool
  2. B A Redis cluster shared by all app servers
  3. C A local in-memory map inside a single application server's heap correct
  4. D A CDN edge PoP caching static assets

Why: An in-process cache lives inside one application instance's memory (fastest access, but not shared and lost on restart); a Redis cluster is a distributed cache shared across servers. CDN and DB buffer pool are separate cache layers entirely.

Q14 multiple choice

A single 'hot key' is receiving so much traffic that its one cache node is saturated. Which mitigation directly addresses this?

  1. A Switch the eviction policy from LRU to FIFO
  2. B Reduce the cache size to force earlier eviction
  3. C Raise the global TTL so the key never expires
  4. D Replicate the hot key across multiple nodes (or add a small local in-process cache) so reads fan out instead of hammering one node correct

Why: A hot key overloads whichever shard owns it, so the fix is to spread its reads — replicate the key to several nodes or front it with a per-app-server local cache. Eviction policy and TTL tuning don't relieve a single overloaded node.

Q15 explain & apply

Explain the difference between write-through and write-back caching, and when you'd accept the durability risk of write-back.

Points a strong answer hits:

  • Write-through writes cache and DB synchronously — always consistent, slower writes, no data-loss window.
  • Write-back writes to cache and flushes to DB asynchronously — much faster writes, but a crash before flush loses buffered writes.
  • Choose write-back when write throughput/latency matters more than never losing a recent write (e.g. metrics, counters, view counts, ephemeral state).
  • Mitigate the risk with replication of the cache, batching flushes, or accepting bounded loss for that data class.
Model answer: Write-through updates the cache and the database in the same synchronous operation, so the DB is always current but every write pays for two writes. Write-back only writes the cache and flushes to the DB asynchronously, which is far faster but opens a window where a node crash loses unflushed writes. I'd accept write-back for high-volume, loss-tolerant data like counters or metrics — ideally with cache replication or bounded batching to cap how much I could lose — and stick with write-through for anything I can't afford to drop.
