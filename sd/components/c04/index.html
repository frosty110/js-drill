Messaging & Queues

Asynchronous messaging decouples producers from consumers so systems can buffer bursts, absorb load spikes, and let components fail and recover independently. This section contrasts the two core delivery shapes (point-to-point queues vs pub/sub fan-out) and the dominant brokers (Kafka's partitioned log vs RabbitMQ's exchange/queue model vs managed SQS), plus the delivery-semantics tradeoffs that force idempotent consumers.

Key ideas

  • A point-to-point queue delivers each message to exactly one consumer; pub/sub fans a copy out to every subscriber.
  • Async messaging buys decoupling, buffering, and load smoothing — producers keep going even when consumers are slow or down.
  • Kafka is a distributed append-only log: partitions are the unit of parallelism, ordering is guaranteed only WITHIN a partition, consumers pull and track offsets, and retention lets them replay.
  • RabbitMQ is a smart broker: producers publish to exchanges (direct/topic/fanout) that route via bindings into queues; it pushes to consumers, waits for acks, then deletes the message.
  • At-least-once is the common default and requires idempotent consumers; exactly-once is hard/costly and is usually approximated as effectively-once via idempotency + dedup.
  • Dead-letter queues capture poison messages that exceed max retries so one bad message can't block the queue.
  • Backpressure and consumer groups let the system match consumption rate to production rate and scale out horizontally.

Q1 multiple choice

What is the defining difference between a point-to-point message queue and a pub/sub topic?

  1. A A queue delivers each message to exactly one consumer; a pub/sub topic delivers a copy of each message to every subscriber correct
  2. B A queue guarantees ordering while pub/sub never preserves order
  3. C A queue is always in-memory while pub/sub is always durable on disk
  4. D A queue supports multiple producers while pub/sub allows only one publisher

Why: In point-to-point, competing consumers share a queue and each message is handled by exactly one of them (load balancing work). In pub/sub, every subscriber to the topic receives its own copy (fan-out). Ordering and durability are separate, broker-specific concerns, not what distinguishes the two shapes.

Q2 multiple choice

Which benefit is the PRIMARY reason to put an async message queue between a producer and consumer?

  1. A It guarantees the message is processed with lower latency than a direct call
  2. B It removes the need for the consumer to be idempotent
  3. C It provides exactly-once delivery for free
  4. D It decouples the two: the producer can keep accepting work and the queue buffers/smooths load even when the consumer is slow or temporarily down correct

Why: Async messaging's core value is decoupling plus buffering — a traffic spike or a slow/failed consumer no longer blocks the producer, because the queue absorbs the backlog. Async typically adds latency (not reduces it), and it makes idempotency MORE important, not less.

Q3 multiple choice

In Kafka, ordering of messages is guaranteed under which condition?

  1. A Across the entire topic, regardless of how many partitions it has
  2. B Only within a single partition; there is no total ordering across partitions of a topic correct
  3. C Only when there is exactly one consumer group
  4. D Only for messages published within the same one-second window

Why: Kafka guarantees order only within a partition — messages with the same key hash to the same partition and stay ordered there. Across partitions there is no global order, which is precisely why partitioning is the unit of parallelism: you trade total ordering for throughput.

Q4 multiple choice

What role does a partition play in Kafka?

  1. A It is a backup copy of the topic kept for disaster recovery
  2. B It is a temporary in-memory buffer flushed to the log every few seconds
  3. C It is the unit of parallelism and ordering: a topic is split into partitions, each an ordered append-only log consumed independently correct
  4. D It is the access-control boundary that restricts which producers may write

Why: A Kafka topic is divided into partitions, each an ordered, append-only log. Parallelism scales with partition count because consumers in a group split partitions among themselves, and ordering is maintained per partition. Replicas (not partitions) provide the backup/DR copies.

Q5 multiple choice

How do consumer groups divide work across the partitions of a Kafka topic?

  1. A Each partition is assigned to at most one consumer within a group, so adding consumers beyond the partition count leaves some idle correct
  2. B Every consumer in the group reads every partition, and duplicates are filtered later
  3. C The broker pushes each message to whichever consumer is least busy at that instant
  4. D Consumers round-robin individual messages regardless of partition

Why: Within a consumer group, each partition is consumed by exactly one member, which preserves per-partition order and spreads load. The direct consequence: you can't have more actively-consuming members than partitions — extras sit idle. Different groups, however, each get the full stream independently.

Q6 multiple choice

What is a Kafka consumer offset, and what does it enable?

  1. A A byte-alignment padding value that keeps records page-aligned on disk
  2. B A countdown that deletes a message once every consumer has acknowledged it
  3. C A priority weight the broker uses to reorder messages before delivery
  4. D The consumer's position (a monotonically increasing index) in a partition's log, which — combined with retention — lets it re-read or replay past messages correct

Why: An offset is a consumer's committed position within a partition. Because Kafka retains messages for a configured period regardless of consumption, a consumer can rewind its offset to reprocess history or catch up after downtime — the replay capability that distinguishes a log from a delete-on-ack queue.

Q7 multiple choice

Which statement best contrasts Kafka's delivery model with RabbitMQ's?

  1. A Kafka pushes messages and deletes them after ack; RabbitMQ is a pull-based log with retention
  2. B Both are pull-based logs with identical retention semantics
  3. C Kafka is a pull-based retained log (consumers poll and track offsets); RabbitMQ is a push-based broker that delivers to consumers and removes messages after ack correct
  4. D Both push messages and delete them immediately on delivery

Why: Kafka consumers pull from a retained log and manage their own offsets, so messages persist for replay. RabbitMQ pushes messages to consumers and, once acknowledged, removes them from the queue — the classic smart-broker/dumb-consumer model versus Kafka's dumb-broker/smart-consumer log.

Q8 multiple choice

In RabbitMQ, how does a published message reach the right queue?

  1. A The producer publishes to an exchange, which uses bindings and a routing type (direct, topic, or fanout) to route the message into one or more queues correct
  2. B The producer names the destination queue directly and the broker appends to it
  3. C Consumers subscribe to a partition and the broker hashes the key to pick one
  4. D A central offset table maps each message id to its queue

Why: RabbitMQ producers publish to an exchange, never directly to a queue. The exchange type plus bindings decide routing: direct matches an exact routing key, topic matches wildcard patterns, and fanout broadcasts to every bound queue. This indirection is what lets one publish fan out or route selectively.

Q9 multiple choice

A RabbitMQ fanout exchange behaves most like which messaging pattern?

  1. A A priority queue that serves high-priority messages first
  2. B Point-to-point work distribution among competing consumers
  3. C Pub/sub, because it copies each message to every queue bound to it regardless of routing key correct
  4. D A dead-letter queue for messages that failed processing

Why: A fanout exchange ignores the routing key and delivers a copy to every bound queue — the fan-out semantics of pub/sub. Direct and topic exchanges, by contrast, route selectively by key, and a single queue with competing consumers gives point-to-point work distribution.

Q10 multiple choice

What does an at-least-once delivery guarantee imply for consumer design?

  1. A Consumers may safely assume each message arrives exactly one time
  2. B Messages may be silently dropped, so consumers must poll a backup store
  3. C The broker deduplicates automatically, so consumers need no special handling
  4. D Consumers can receive a message more than once (e.g. after a redelivery on missing ack), so processing must be idempotent to avoid double effects correct

Why: At-least-once is the common default: if an ack is lost or a consumer crashes mid-processing, the broker redelivers, so the same message can be seen twice. The consumer must therefore be idempotent (or dedup by message id). At-most-once trades duplicates for possible loss; neither the broker nor at-least-once dedups for you.

Q11 multiple choice

Why is true exactly-once delivery considered hard, and how is it usually achieved in practice?

  1. A It requires atomic coordination between broker and consumer side-effects across failures; in practice systems approximate it as effectively-once via at-least-once delivery plus idempotency/deduplication correct
  2. B It is trivial; every modern broker provides it by default with no cost
  3. C It is achieved by disabling acknowledgements so no redelivery can occur
  4. D It only works if there is a single producer and a single consumer with no retries

Why: Exactly-once end-to-end demands that message delivery and the consumer's side effects commit atomically despite crashes and retries, which is expensive and often impossible across external systems. The pragmatic answer is effectively-once: deliver at-least-once and make the consumer idempotent or dedup on a message key so reprocessing is harmless.

Q12 multiple choice

In Amazon SQS, what does the visibility timeout do?

  1. A It deletes a message automatically after that many seconds whether or not it was processed
  2. B It hides an in-flight message from other consumers for a period after one consumer receives it; if that consumer doesn't delete it in time, the message becomes visible again for redelivery correct
  3. C It sets how long the queue waits before creating a message
  4. D It caps the total number of messages the queue can hold

Why: When a consumer receives an SQS message it isn't deleted — it's hidden for the visibility timeout. The consumer must explicitly delete it after successful processing; if it fails or is too slow, the timeout expires and the message reappears for another consumer. This redelivery is exactly why standard SQS is at-least-once.

Q13 multiple choice

How does an SQS FIFO queue differ from a standard SQS queue?

  1. A FIFO queues drop messages under load while standard queues never do
  2. B Standard queues guarantee ordering; FIFO queues explicitly randomize order
  3. C FIFO queues preserve strict ordering and provide exactly-once processing within a dedup window, whereas standard queues offer best-effort ordering and at-least-once delivery at higher throughput correct
  4. D FIFO queues are push-based while standard queues are pull-based

Why: Standard SQS maximizes throughput with best-effort ordering and at-least-once delivery (duplicates possible). FIFO queues trade some throughput for strict first-in-first-out order and exactly-once processing within a 5-minute deduplication window, using message group ids to order related messages.

Q14 multiple choice

What problem does a dead-letter queue (DLQ) solve?

  1. A It speeds up delivery by pre-fetching messages before consumers ask
  2. B It stores acknowledged messages so producers can confirm receipt
  3. C It compresses old messages to reclaim disk space
  4. D It captures 'poison' messages that repeatedly fail processing (exceeding a max-retry count) so they stop blocking the main queue and can be inspected later correct

Why: A single message that always throws can be redelivered forever, stalling the queue and wasting retries. A DLQ moves a message aside once it exceeds the max-retry threshold, isolating the poison message for later debugging while normal processing continues.

Q15 multiple choice

Which scenario most justifies a SYNCHRONOUS request/response call instead of async messaging?

  1. A A background email that can be sent minutes later without the user waiting
  2. B The caller needs the result immediately to continue — e.g. a checkout must know the payment authorization outcome before showing a confirmation correct
  3. C A firehose of analytics events that should be buffered and processed in batches
  4. D Fanning one order event out to inventory, shipping, and billing services independently

Why: Synchronous calls fit request/response flows where the caller must have the answer now to proceed and can tolerate blocking on the dependency. Fire-and-forget work, high-volume event streams, and multi-consumer fan-out are the textbook cases for async messaging, which decouples timing at the cost of an immediate reply.

Q16 explain & apply

An interviewer says your order-processing consumer reads from an at-least-once queue. Explain what can go wrong and how you'd design the consumer to be safe.

Points a strong answer hits:

  • At-least-once means the same message can be delivered more than once (redelivery after a lost ack or a crash mid-processing), so naive processing double-charges or double-ships.
  • Make the consumer idempotent: key the effect on a stable message/order id so reprocessing the same id is a no-op.
  • Deduplicate by recording processed message ids (e.g. an idempotency key row / unique constraint) and skipping ones already seen.
  • Only ack/commit the offset AFTER the side effect has durably committed, so a crash before commit safely redelivers.
  • Route repeat-failing (poison) messages to a dead-letter queue after N retries so one bad message can't block the queue.
Model answer: At-least-once delivery guarantees no loss but allows duplicates — a lost ack or a crash between doing the work and acknowledging causes redelivery. So I make the consumer idempotent: I derive a stable key from the order id and either use a unique constraint / idempotency table to detect and skip already-processed messages, or design the operation so applying it twice is harmless. I commit the offset only after the side effect is durably persisted, and I send messages that fail repeatedly to a dead-letter queue after a max-retry count so a poison message doesn't stall the pipeline. That gives me effectively-once behavior without paying for true exactly-once coordination.
