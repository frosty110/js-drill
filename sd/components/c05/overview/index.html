Where rate limiting lives

System map study sheet

What this sheet shows

The edge authenticates enough of the request to select a key such as user, API key, tenant, or IP. A limiter applies versioned policy and performs an atomic state update before the request reaches scarce downstream capacity.

Identify the enforcement point, policy source, counter state, response contract, and protected downstream service.

Trace the flow

  1. Identify — Derive the limit key and endpoint or resource class after trusted authentication.
  2. Load policy — Resolve capacity, refill rate, request cost, exemptions, and policy version.
  3. Spend atomically — Update token or counter state without a read-modify-write race.
  4. Allow or reject — Forward allowed work; otherwise return 429 with Retry-After and rate-limit headers.
  5. Observe — Record decisions, saturation, hot keys, store latency, and fail-open or fail-closed events.

What this belongs to

Rate limiting protects a service from overload and abuse by capping how many requests a client may make in a window. This section covers the four canonical algorithms (token bucket, leaky bucket, fixed-window counter, and the two sliding-window variants), where in the stack to enforce limits, how to do it accurately across a distributed fleet, and how the server signals a throttled client.
