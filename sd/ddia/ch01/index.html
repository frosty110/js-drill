Reliable, Scalable, and Maintainable Applications

Introduces the three concerns that shape every data system — reliability, scalability, and maintainability — and the vocabulary (faults vs failures, load parameters, response-time percentiles, operability/simplicity/evolvability) for reasoning about them.

Designing Data-Intensive Applications 17 questions

Results carried by this link

Key ideas

  • Data-intensive applications are built by composing standard building blocks — databases, caches, search indexes, stream processing, batch processing — each solving a different need.
  • Reliability means continuing to work correctly even when things go wrong; a fault is one component deviating from spec, a failure is the whole system stopping service, and fault-tolerance means preventing faults from becoming failures.
  • Hardware faults are largely random and independent (mitigated by redundancy), while software errors are systematic and correlated across nodes; human error causes most outages.
  • Scalability is describing load with load parameters and asking what happens to performance as load grows, and what resources you must add to hold performance steady.
  • Response time should be described with percentiles (p50/p95/p99/p999 tail latencies), not the mean, because tail latency reflects the worst user experiences.
  • Maintainability rests on operability (easy for ops), simplicity (managing complexity via good abstractions), and evolvability (making change easy).

Q1 multiple choice

In DDIA's terms, what distinguishes a fault from a failure?

  1. A A fault is a bug in application code; a failure is a hardware defect
  2. B A fault is recoverable; a failure is permanent and unrecoverable by definition
  3. C A fault affects a single user's request; a failure affects all users simultaneously
  4. D A fault is one component deviating from its spec; a failure is the system as a whole stopping to provide the required service to users correct

Why: DDIA defines a fault as one component deviating from spec, and a failure as the whole system stopping service to users. Fault-tolerance is about preventing faults from cascading into failures — the distinction is component-level vs system-level, not hardware-vs-software or recoverable-vs-permanent.

Q2 multiple choice

Why does DDIA describe hardware faults as easier to reason about than software errors?

  1. A Hardware faults never cause outages because redundancy always masks them
  2. B Hardware faults tend to be random and independent across machines, whereas software errors are systematic and often correlated across many nodes at once correct
  3. C Hardware faults are always detected instantly, while software errors are silent
  4. D Software errors can be fixed by rebooting, but hardware faults cannot

Why: Hardware faults (disk crash, RAM fault, power loss) are mostly random and independent, so redundancy like RAID and dual power supplies helps. Software errors are systematic bugs correlated across nodes — a bad input or leap-second bug can take down every replica at once, which redundancy does not protect against.

Q3 multiple choice

According to DDIA, what is the leading cause of outages, and which mitigation matches it?

  1. A Disk failures — mitigated by RAID and off-site backups
  2. B Network partitions — mitigated by multi-region deployment
  3. C Human errors (operator/config mistakes) — mitigated by good abstractions, sandboxes, thorough testing, quick rollback, and telemetry correct
  4. D Memory leaks — mitigated by automatic garbage collection

Why: DDIA cites studies finding humans (configuration errors by operators) as the leading cause of outages. Mitigations target the human loop: well-designed abstractions and APIs, sandbox environments, comprehensive testing, fast rollback of config changes, and detailed telemetry to catch problems early.

Q4 multiple choice

What is the purpose of deliberately inducing faults in production, as with Netflix's Chaos Monkey?

  1. A To continuously exercise and validate the fault-tolerance machinery so that it works when a real fault occurs, rather than staying untested correct
  2. B To reduce cloud costs by shutting down idle machines
  3. C To measure raw throughput under peak load
  4. D To force developers to write more unit tests

Why: Fault-tolerance code that is never triggered may be broken when you finally need it. Deliberately injecting faults (killing random processes) keeps the recovery paths continuously exercised, increasing confidence that the system tolerates real faults. It is not a cost or throughput optimization.

Q5 multiple choice

In DDIA, scalability is best described as…

  1. A The maximum number of servers a system can run on
  2. B A property a system either has or lacks, determined by its programming language
  3. C A system's ability to cope with increased load, discussed by defining load parameters and asking how performance changes as load grows correct
  4. D The guarantee that response time stays constant no matter how much data is stored

Why: Scalability is not a one-dimensional label ('X is scalable'); it is the ability to cope with increased load, reasoned about by first choosing load parameters, then asking what happens to performance when load grows and what resources are needed to hold performance steady.

Q6 multiple choice

In the Twitter home-timeline example, what is the fan-out on write approach and its main tradeoff?

  1. A Timelines are computed by querying all followees' tweets at read time, making writes cheap but reads expensive
  2. B Tweets are stored only once and never copied, minimizing both read and write cost
  3. C Followers poll a central queue on a fixed schedule, decoupling read and write entirely
  4. D Each new tweet is inserted into a precomputed cache for every follower at post time, making reads fast but writes costly — especially for users with millions of followers correct

Why: Fan-out on write pushes each tweet into a cache for every follower when it is posted, so reads are cheap lookups but writes are expensive and amplified by follower count. The read-time alternative (fan-out on read) is cheap to write but expensive to read; Twitter uses a hybrid, fanning out most users on write while handling celebrity accounts on read.

Q7 multiple choice

DDIA distinguishes response time from latency. Which statement is correct?

  1. A They are synonyms and can be used interchangeably
  2. B Response time is the duration a request waits before being handled; latency is the total time the client observes
  3. C Response time is what the client sees (service time plus network delays plus queueing); latency is the duration a request waits to be serviced correct
  4. D Latency is measured on the server; response time is measured only on the client's CPU

Why: DDIA defines response time as what the client sees — service time plus network and queueing delays — while latency is the duration a request spends waiting to be serviced. The two are related but not identical; conflating them obscures where time is actually spent.

Q8 multiple choice

Why does DDIA recommend percentiles (e.g. p95, p99) over the arithmetic mean for reporting response times?

  1. A The mean is harder to compute than percentiles
  2. B Percentiles are always smaller than the mean, making the numbers look better
  3. C The mean cannot be computed for skewed distributions
  4. D The mean does not reveal how many users experience slow responses; percentiles (especially tail latencies) show the worst-case experiences that the mean hides correct

Why: The mean tells you nothing about how many users hit slow responses and is easily skewed by outliers in both directions. Percentiles — p50 as the typical case, p95/p99/p999 as tail latencies — directly express the experience of the slowest requests, which often correspond to your most valuable, data-heavy customers.

Q9 multiple choice

What is tail latency amplification?

  1. A A caching technique that reduces the p99 by precomputing results
  2. B When a single user request fans out to many backend calls and must wait for the slowest one, so the end-to-end request is slow if any backend call is slow correct
  3. C The tendency of median latency to grow faster than mean latency under load
  4. D A monitoring artifact where percentiles are overcounted at high throughput

Why: When one front-end request depends on multiple backend calls, it completes only when the slowest backend responds. As the number of backend calls grows, the chance that at least one is slow rises, so a larger fraction of end-user requests are slow — the tail is amplified. It is a real problem, not a monitoring artifact.

Q10 multiple choice

What does DDIA mean by head-of-line blocking in the context of response-time measurement?

  1. A A few slow requests hold up a server's limited processing slots, delaying subsequent (even cheap) requests queued behind them correct
  2. B The first request in a batch always gets priority scheduling
  3. C Network packets are reordered so the head of the queue arrives last
  4. D The database blocks writes while a read is in progress

Why: With limited parallelism, a small number of slow requests can occupy all processing slots and delay every request queued behind them, even quick ones — so client-observed response time rises. This is why load should be measured client-side, since server-side timing misses queueing delay.

Q11 multiple choice

DDIA contrasts scaling up and scaling out. Which description is accurate?

  1. A Scaling up adds more machines; scaling out buys a bigger machine
  2. B Scaling up increases network bandwidth; scaling out increases disk capacity
  3. C They are the same technique described with different vocabulary
  4. D Scaling up (vertical) means a more powerful single machine; scaling out (horizontal) means distributing load across many smaller machines, often a shared-nothing architecture correct

Why: Scaling up is vertical — a single, more powerful machine. Scaling out is horizontal — spreading load over many commodity machines, commonly shared-nothing. Good architectures usually mix both; DDIA stresses there is no one-size-fits-all 'magic scaling sauce.'

Q12 multiple choice

What does DDIA mean by an elastic system?

  1. A A system that automatically adds computing resources when it detects a load increase, rather than being scaled manually correct
  2. B A system whose data model can change shape without downtime
  3. C A system that compresses data to fit more into memory
  4. D A system that guarantees constant latency regardless of load

Why: An elastic system automatically provisions more resources as load rises (and releases them when it falls). The alternative is manual scaling, where a human analyzes capacity and adds machines. Elasticity is about automatic resource adjustment, not data-model flexibility or latency guarantees.

Q13 multiple choice

DDIA breaks maintainability into three design principles. Which set is correct?

  1. A Availability, consistency, partition-tolerance
  2. B Durability, isolation, atomicity
  3. C Operability, simplicity, and evolvability correct
  4. D Throughput, latency, and capacity

Why: DDIA names operability (make it easy for operations teams to keep the system running), simplicity (manage complexity so new engineers can understand the system), and evolvability (make it easy to change the system for future requirements). The other options describe CAP, ACID, and performance metrics — not maintainability.

Q14 multiple choice

What is accidental complexity as DDIA (drawing on Moseley and Marks) uses the term?

  1. A Complexity inherent in the problem the software solves, which cannot be removed
  2. B Complexity that arises only from the implementation, not from the problem itself, and can be removed with better abstractions correct
  3. C Complexity introduced by hardware faults occurring at random times
  4. D The unavoidable overhead of running in a distributed environment

Why: Accidental complexity is not inherent to the problem but stems from the implementation — tangled dependencies, inconsistent naming, hacks. It can be removed with good abstractions, unlike essential complexity, which is intrinsic to what the software must do. Managing complexity is the core of the simplicity principle.

Q15 explain & apply

Your API's p50 is 30 ms but p99 is 900 ms and product wants a '200 ms for 99% of requests' SLO. How do you reason about where that tail comes from and how to attack it?

Points a strong answer hits:

  • Optimize the tail (p99/p999) specifically, not the mean/p50 — the mean hides the slow requests the SLO targets.
  • Measure response time client-side to capture queueing/head-of-line blocking that server-side timing misses.
  • Name likely tail causes: head-of-line blocking under limited parallelism, GC pauses, cold caches, contention on the slowest backend.
  • Watch for tail-latency amplification — if one user request fans out to many backend calls, the request is only as fast as the slowest call.
  • The heaviest/most-valuable customers (most data) often live in the tail, so the p99 matters commercially, not just cosmetically.
Model answer: First I'd stop looking at the mean and drive off the p99/p999 directly, measured client-side so I capture queueing and head-of-line blocking, not just server service time. Then I'd decompose the tail: is one request fanning out to many backends so it inherits the slowest one (tail-latency amplification), or is it GC pauses, cold caches, and head-of-line blocking where a few slow requests hog limited slots? I'd attack whichever dominates — cap fan-out, add parallel hedged requests, or fix contention — because the tail is where our heaviest, most valuable users actually live.

Q16 explain & apply

A service is hitting its capacity ceiling. Walk me through how you'd decide between scaling up (a bigger machine) and scaling out (more machines), and what makes the decision.

Points a strong answer hits:

  • First define the load parameters that are growing (requests/sec, data volume, fan-out) — scalability is relative to a specific load, not an absolute label.
  • Scaling up (vertical) is simpler operationally but has a hard ceiling and cost/failure-blast-radius grows nonlinearly.
  • Scaling out (horizontal, shared-nothing) has no single ceiling and improves fault tolerance but adds distributed-systems complexity (coordination, partitioning, consistency).
  • Stateless request-serving scales out easily; stateful data scaling out forces partitioning/replication decisions.
  • Real architectures mix both — there is no one-size-fits-all 'magic scaling sauce'; the right split depends on the workload's specific shape.
Model answer: I'd start by naming which load parameter is actually growing, because scalability is always relative to a specific load, not a badge a system has. If the workload is stateful and heading past what one box can hold, or I need fault tolerance, I lean toward scaling out shared-nothing — but that buys distributed-systems complexity like partitioning and coordination. If a bigger machine buys me runway cheaply and keeps the system simple, I scale up first, since vertical is operationally simpler until it hits its ceiling. In practice it's a mix tuned to the workload; there's no universal scaling recipe.

Q17 explain & apply

You're designing a social feed. Contrast fan-out-on-write versus fan-out-on-read, and tell me which you'd default to and how you'd handle a user with 30 million followers.

Points a strong answer hits:

  • Fan-out-on-write precomputes each follower's timeline at post time: cheap reads, expensive/amplified writes proportional to follower count.
  • Fan-out-on-read assembles the timeline by querying followees at read time: cheap writes, expensive reads.
  • The right default depends on the read:write ratio — feeds are read-heavy, so fan-out-on-write usually wins for the average user.
  • A celebrity with millions of followers makes write fan-out explode, so handle those accounts on read (hybrid).
  • The hybrid (fan-out-on-write for normal users, fan-out-on-read for celebrities) is the pragmatic answer Twitter actually adopted.
Model answer: Fan-out-on-write pushes each new post into every follower's precomputed timeline, so reads are cheap lookups but writes are amplified by follower count; fan-out-on-read does the opposite, querying followees at read time. Since feeds are overwhelmingly read-heavy, I'd default to fan-out-on-write for the typical user. But a 30-million-follower account would make a single post trigger 30 million writes, so I'd special-case celebrities and merge their posts in at read time — the hybrid Twitter converged on.
