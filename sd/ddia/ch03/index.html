Storage and Retrieval

How databases physically store data and retrieve it again: the two dominant storage-engine families (log-structured LSM-trees vs page-oriented B-trees), how indexes are built on top, and how storage differs for transaction processing (OLTP) versus analytics (OLAP).

Key ideas

  • Two storage-engine families dominate: log-structured (LSM-tree) and page-oriented (B-tree).
  • LSM-trees turn random writes into sequential appends via a memtable flushed to sorted SSTable segments, then compacted.
  • B-trees update pages in place, use a fixed-size page/block structure, and rely on a write-ahead log for crash recovery.
  • LSM-trees generally offer higher write throughput and less write amplification; B-trees offer more predictable reads and keep each key in exactly one place.
  • Secondary, clustered, covering, multi-column, spatial (R-tree), and full-text indexes address different query shapes.
  • OLTP (row/document, LSM or B-tree) and OLAP (column-oriented, compressed, warehouse) are optimized for opposite access patterns.
  • Column-oriented storage stores each column together to enable heavy compression and vectorized scans over few columns of many rows.

Q1 multiple choice

In Bitcask (the simplest log + hash index), where does the index that maps each key to its value live?

  1. A In an in-memory hash map from key to the byte offset of the latest value in the log file correct
  2. B In a sorted on-disk B-tree keyed by the primary key
  3. C In a sparse in-memory index pointing to sorted on-disk segments
  4. D In a bloom filter that stores the value alongside each key

Why: Bitcask keeps a complete in-memory hash map of key to byte offset, so a read is one hash lookup plus one disk seek. Its main limitation follows directly: all keys must fit in RAM, and range queries are inefficient because keys are not stored in sorted order.

Q2 multiple choice

Why does an append-only log-structured store need compaction and segment merging?

  1. A To keep the in-memory index sorted so range queries stay fast
  2. B To rebalance the tree so it stays at O(log n) height
  3. C To flush the write-ahead log to the main data file after a checkpoint
  4. D To reclaim space by discarding superseded/deleted values, since updates only append new records rather than overwriting correct

Why: Because writes only append, an updated or deleted key leaves stale copies behind; compaction throws away all but the latest value per key and merges segments so disk usage does not grow unbounded. Rebalancing to keep O(log n) height is a B-tree concern, not a log-structured one.

Q3 multiple choice

What is a memtable in an LSM-tree-based storage engine?

  1. A A fixed-size on-disk page that is updated in place
  2. B A bloom filter kept in memory to skip absent keys
  3. C An in-memory balanced tree holding recent writes in sorted order before it is flushed to a sorted segment correct
  4. D The sparse index that maps keys to byte offsets within an SSTable

Why: Writes first go to an in-memory balanced tree (the memtable, e.g. a red-black tree or skip list) kept sorted by key; when it grows large enough it is written out as a new sorted SSTable segment. Because it is already sorted, the flush and later merges are sequential, like the merge step of mergesort.

Q4 multiple choice

In an LSM-tree, what is the primary purpose of a bloom filter?

  1. A To compress each column so it uses fewer bits on disk
  2. B To approximate set membership so lookups can skip reading segments that definitely do not contain a key correct
  3. C To keep multiple sort orders of the same data on different replicas
  4. D To guarantee that a deleted key is physically removed during compaction

Why: A bloom filter is a memory-efficient probabilistic structure for set membership; it may report false positives but never false negatives, so it lets the engine avoid unnecessary disk reads for keys that are absent. Deletes are instead handled by writing a tombstone marker.

Q5 multiple choice

How does an LSM-tree represent a deleted key?

  1. A By immediately overwriting the value's page in place
  2. B By removing the key from the in-memory hash map only
  3. C By writing a special tombstone record that marks the key deleted until compaction drops it correct
  4. D By decrementing a reference count stored in the sparse index

Why: Since segments are immutable and append-only, a delete is recorded as a tombstone; the key's older values are discarded and the tombstone itself is removed during a later compaction/merge. There is no in-place overwrite in a log-structured engine.

Q6 multiple choice

Which statement correctly describes how a B-tree handles writes?

  1. A It appends the new value to a log and later compacts old copies away
  2. B It overwrites the fixed-size page in place, using a write-ahead (redo) log so a crash mid-write can be recovered correct
  3. C It buffers writes in a memtable and flushes them to immutable sorted segments
  4. D It writes each column separately and relies on run-length encoding

Why: B-trees break the database into fixed-size pages and update them in place; because a single logical write may touch several pages, a write-ahead log (redo log) is appended first so an interrupted update can be restored on recovery. Memtables and immutable segments are the LSM approach, not the B-tree approach.

Q7 multiple choice

Per DDIA, which is a genuine advantage of LSM-trees over B-trees?

  1. A Reads are faster because each key exists in exactly one place
  2. B They make range queries impossible, which simplifies the index
  3. C Higher sustained write throughput and lower write amplification, with better compression and less fragmentation on disk correct
  4. D They provide stronger transaction isolation because a key can be locked in one location

Why: Sequential appends and periodic compaction give LSM-trees high write throughput, typically lower write amplification, and denser on-disk layout (better compression, less fragmentation). Faster reads and locking a key in one place are B-tree advantages, since a B-tree keeps each key in exactly one location.

Q8 multiple choice

What is the main downside of LSM-trees that DDIA highlights?

  1. A They cannot support secondary indexes
  2. B They require all keys to fit in memory at once
  3. C They lose data on crash because they have no durable log
  4. D Compaction can compete with reads and writes for disk resources, and at high write load compaction throughput can become a bottleneck correct

Why: Compaction runs in the background but shares finite disk bandwidth; at high write volume it can interfere with concurrent reads/writes and even fall behind, letting unmerged segments pile up. Needing all keys in memory is the limitation of the simple Bitcask hash index, not of LSM-trees in general.

Q9 multiple choice

In a clustered index (e.g. MySQL/InnoDB primary key), what is stored in the index leaf?

  1. A A reference (pointer) to the row stored elsewhere in a heap file
  2. B The full row itself, stored directly within the index correct
  3. C Only the indexed columns, so the query can be answered without touching the row
  4. D A bloom filter summarizing which rows contain the key

Why: A clustered index stores the actual row data inside the index, avoiding an extra hop. That contrasts with a nonclustered index, which stores only a reference to the row, and a covering index, which stores just enough columns to answer certain queries without reading the full row.

Q10 multiple choice

Why do in-memory databases (e.g. Redis, VoltDB) gain performance, according to DDIA?

  1. A Because reading from memory is inherently faster than any disk read, which is their only advantage
  2. B Because they eliminate the need for durability entirely
  3. C Because they avoid the overhead of encoding in-memory data structures into a form that can be written to disk correct
  4. D Because they store each column separately for better compression

Why: DDIA argues the main win is not avoiding disk reads (the OS cache already keeps hot data in RAM) but avoiding the CPU overhead of encoding data structures for durable on-disk storage. In-memory databases can still be durable via an append-only log and periodic snapshots.

Q11 multiple choice

Which pair correctly contrasts OLTP with OLAP?

  1. A OLTP scans huge numbers of rows for aggregates; OLAP looks up small numbers of records by key
  2. B OLTP handles many small, low-latency reads/writes by key; OLAP scans large numbers of rows over few columns to compute aggregates correct
  3. C OLTP uses column-oriented storage; OLAP uses row-oriented storage
  4. D OLTP is served by data warehouses; OLAP is served by the live application database

Why: OLTP (online transaction processing) serves the application with many small key-based reads and writes at low latency; OLAP (online analytic processing) runs fewer, larger aggregate queries scanning many rows over a few columns, typically in a separate data warehouse loaded via ETL.

Q12 multiple choice

In a star schema, what is the fact table?

  1. A A wide table describing an entity such as products, customers, or dates
  2. B The central table holding one row per event, with foreign-key references out to dimension tables correct
  3. C A normalized breakdown of dimensions into sub-dimensions
  4. D A materialized aggregate precomputed from the raw data

Why: The fact table sits at the center of a star schema with one row per event/transaction and foreign keys pointing out to dimension tables (the who/what/where/when). A snowflake schema further normalizes those dimensions into sub-dimensions.

Q13 multiple choice

What is the defining idea of column-oriented storage?

  1. A Store all values of each column together, rather than storing all fields of a row together correct
  2. B Store each row as a self-describing document with its schema inline
  3. C Keep the newest column values in a memtable and flush them to B-tree pages
  4. D Replicate every column to a separate node to spread read load

Why: Column storage lays out each column's values contiguously, so an analytic query that touches only a few columns reads only those columns. This layout also enables strong compression (e.g. bitmap and run-length encoding) and vectorized processing over long runs of same-column values.

Q14 multiple choice

Why is writing to column-oriented storage harder, and how is it typically addressed?

  1. A In-place updates would require rewriting every compressed, sorted column, so writes use an LSM-style approach: buffer in memory, then merge into the column files correct
  2. B Columns cannot be indexed, so every write must scan the whole table first
  3. C Each write must update a write-ahead log per column, doubling write amplification
  4. D Column stores forbid updates entirely, so data must be reloaded from scratch

Why: Because columns are sorted and compressed, an in-place update would mean rewriting large compressed segments, so column stores buffer writes in an in-memory row store and periodically merge them into the column files, exactly the LSM-tree strategy. Sort order can even differ across replicas to speed different queries.

Q15 explain & apply

Explain why an LSM-tree sustains higher write throughput than a B-tree, what it costs you on reads, and the mitigations that make those reads acceptable.

Points a strong answer hits:

  • LSM turns random writes into sequential appends (memtable → immutable sorted SSTables), and sequential I/O is far faster than the random in-place page writes a B-tree does.
  • Lower write amplification and denser on-disk layout (better compression, less fragmentation) than a B-tree that rewrites whole pages plus a WAL.
  • Read cost: a key may live in the memtable or any of several SSTable segments, so a lookup (especially for a missing key) may check multiple places.
  • Mitigation 1: bloom filters let a read skip segments that definitely don't contain the key, avoiding wasted disk reads for absent keys.
  • Mitigation 2: background compaction merges segments to bound the number that must be checked and reclaim space from superseded/tombstoned keys.
  • Caveat: compaction competes for disk bandwidth and can fall behind at very high write load — the real LSM downside.
Model answer: An LSM-tree batches writes in an in-memory memtable and flushes them as sequential, immutable sorted segments, so it converts random writes into sequential I/O and avoids the in-place page rewrites and WAL churn a B-tree pays — that's the write-throughput and write-amplification win. The cost is reads: a key can be in the memtable or scattered across several segments, so a lookup, especially for a missing key, may probe many places. Bloom filters fix most of that by skipping segments that can't hold the key, and background compaction keeps the segment count and dead data bounded. The one thing I'd flag is that compaction shares disk bandwidth and can fall behind under heavy write load.

Q16 explain & apply

You're choosing a storage engine for a write-heavy time-series ingestion service versus a read-latency-sensitive OLTP service with lots of point lookups and updates. Which engine for each, and why?

Points a strong answer hits:

  • Write-heavy ingest → LSM-tree: high sustained write throughput, sequential appends, good compression for append-mostly data.
  • Read-latency-sensitive OLTP with updates → B-tree: predictable read latency and each key in exactly one place.
  • B-tree keeps every key in one location, which also makes locking for transaction isolation cleaner.
  • LSM read latency is less predictable (multiple segments + compaction interference), a liability under tight read SLOs.
  • Frame it as matching the engine to the read/write ratio and latency-predictability needs, not a universal 'LSM is better' claim.
Model answer: For write-heavy time-series ingest I'd pick an LSM-tree: it turns the firehose of writes into sequential appends, sustains high write throughput, and compresses append-mostly data well. For the read-latency-sensitive OLTP service I'd lean B-tree, because it keeps each key in exactly one place, giving predictable read latency and cleaner locking for transaction isolation — whereas an LSM's reads can jump across segments and get disturbed by compaction. The choice is really about matching the engine to the read/write ratio and how tight the read-latency SLO is, not declaring one universally better.

Q17 explain & apply

An analyst runs 'SELECT AVG(price) over 4 of our 200 columns across a billion rows'. Explain why a column-oriented store crushes a row store here, and why you wouldn't just run these queries on the OLTP database.

Points a strong answer hits:

  • Column storage lays each column's values contiguously, so a query touching 4 columns reads only those 4 columns' data, not all 200 per row.
  • Contiguous same-type values compress hard (run-length, bitmap encoding) and enable vectorized/SIMD scans over long runs.
  • A row store must read whole rows (all 200 columns) to get 4 fields, wasting I/O and cache — the opposite access pattern.
  • OLTP databases are tuned for many small low-latency key-based reads/writes; big scan-aggregates would contend with and starve production traffic.
  • So analytics runs in a separate column-oriented warehouse loaded via ETL, isolating OLAP scans from the live OLTP workload.
Model answer: Because a column store keeps each column's values together, that aggregate reads only the 4 relevant columns instead of dragging every 200-column row off disk, and those contiguous same-type values compress heavily and scan in vectorized batches — that's an order-of-magnitude I/O and CPU win over a row store for wide scans. I wouldn't run it on the OLTP database because that engine is tuned for many small low-latency key lookups and writes, and a billion-row scan would contend for resources and hurt production latency. So analytics lives in a separate column-oriented warehouse fed by ETL, keeping OLAP scans off the live OLTP path.
