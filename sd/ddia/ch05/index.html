Replication

How to keep copies of the same data on multiple machines connected by a network — for lower latency, higher availability, and read scalability — and the consistency problems that arise when those copies diverge.

Designing Data-Intensive Applications 17 questions

Results carried by this link

Key ideas

  • Replication buys lower latency (data close to users), fault-tolerant availability, and read-throughput scale-out; the hard part is handling changes.
  • Single-leader replication routes all writes through one leader that streams a replication log to followers; reads can hit any replica.
  • Synchronous replication guarantees an up-to-date follower but can block on a slow node; async is fast but can lose writes if the leader fails.
  • Replication lag breaks read-after-write, monotonic reads, and consistent prefix reads — each has a specific technique to restore its guarantee.
  • Multi-leader and leaderless replication accept concurrent writes, so they must detect and resolve conflicts (LWW, version vectors, CRDTs).
  • Leaderless (Dynamo-style) systems use quorums w + r > n plus read repair and anti-entropy, but quorums still permit stale reads in edge cases.

Q1 multiple choice

In DDIA's terms, what is the defining characteristic of single-leader (master–slave) replication?

  1. A All writes go to one designated leader, which propagates a change log to followers; reads can be served by any replica correct
  2. B Every replica accepts writes and they are merged asynchronously in the background
  3. C A quorum of replicas must acknowledge each write before it is considered committed
  4. D Writes are partitioned across leaders by key range so each key has its own leader

Why: Single-leader means exactly one node accepts writes and ships a replication log to read-only followers. Accepting writes on every replica is multi-leader/leaderless; quorum acknowledgement describes leaderless replication.

Q2 multiple choice

What is the primary risk of fully asynchronous replication in a single-leader system?

  1. A Followers can never catch up to the leader once they fall behind
  2. B Reads always return stale data because followers are never updated
  3. C The leader cannot process writes until every follower has acknowledged
  4. D If the leader fails before its writes reach any follower, those recently confirmed writes are lost correct

Why: Async replication confirms a write to the client before followers have it, so a leader crash can durably lose those writes. Blocking on follower acknowledgement is the synchronous case, which async specifically avoids.

Q3 multiple choice

When setting up a brand-new follower without downtime, what is the standard procedure?

  1. A Lock the leader for writes, copy its files, then unlock — accepting the write outage
  2. B Take a consistent snapshot of the leader, copy it to the follower, then have the follower request all changes since the snapshot's log position correct
  3. C Replay the entire write-ahead log from the beginning of time onto the new follower
  4. D Have the new follower serve reads immediately and lazily fetch missing rows on cache miss

Why: You snapshot the leader (ideally without a full lock), load it, then the follower connects and catches up from the snapshot's exact log position. Locking the leader for writes defeats the point of zero-downtime setup.

Q4 multiple choice

Which of these is a genuine danger during automatic leader failover?

  1. A The new leader immediately reformats all follower disks
  2. B Followers permanently stop accepting reads until the old leader returns
  3. C Split brain, where two nodes both believe they are leader and accept conflicting writes correct
  4. D The replication log is rewritten in reverse chronological order

Why: Failover can produce split brain (two leaders) plus lost async writes and mis-tuned timeouts that trigger unnecessary failovers. The other options are not real failover failure modes DDIA describes.

Q5 multiple choice

Why is statement-based replication (shipping each SQL statement) problematic?

  1. A Nondeterministic constructs like NOW(), RAND(), or triggers can execute differently on each replica, causing divergence correct
  2. B It produces logs far larger than the actual data changes
  3. C It cannot replicate DELETE statements, only INSERTs and UPDATEs
  4. D It requires all replicas to run identical storage-engine versions

Why: Replaying a statement like NOW() or RAND() yields different results per replica, and side-effecting triggers/stored procs compound this. Storage-engine version coupling is a downside of WAL shipping, not statement-based replication.

Q6 multiple choice

What is the main drawback of write-ahead-log (WAL) shipping as the replication method?

  1. A It cannot capture updates, only inserts
  2. B It is nondeterministic and diverges across replicas
  3. C It only works for in-memory databases
  4. D The log is tied to the storage engine's low-level format, so leader and followers usually can't run different database versions — preventing zero-downtime upgrades correct

Why: WAL describes changes at the byte/disk-page level, coupling replicas to the exact storage format and blocking mixed-version rolling upgrades. Nondeterminism is the statement-based problem; logical (row-based) logs decouple from the storage engine to solve this.

Q7 multiple choice

A user posts a comment, reloads the page, and doesn't see their own comment because the read hit a lagging follower. Which guarantee restores correct behavior?

  1. A Monotonic reads
  2. B Read-your-writes (read-after-write) consistency correct
  3. C Consistent prefix reads
  4. D Linearizability across all replicas

Why: Read-your-writes ensures a user always sees data they themselves submitted — e.g., by reading their own recently-modified data from the leader. Monotonic reads prevents going backward in time across reads; consistent prefix concerns causal ordering of different users' writes.

Q8 multiple choice

What anomaly does the 'monotonic reads' guarantee prevent?

  1. A Two users writing conflicting values to the same key
  2. B A read that observes an effect before its cause
  3. C Seeing data move backward in time — a later read returning older data than an earlier read did correct
  4. D Not seeing your own writes after submitting them

Why: Monotonic reads means once you've seen a value, subsequent reads never return an older state — typically achieved by routing a user's reads to the same replica. Cause-before-effect ordering is consistent prefix reads; the own-writes case is read-your-writes.

Q9 multiple choice

Consistent prefix reads is primarily concerned with which anomaly?

  1. A A follower falling permanently behind the leader
  2. B A user failing to read data they just wrote
  3. C Two leaders accepting conflicting writes simultaneously
  4. D An observer seeing writes in an order that violates their causal (happens-before) sequence — e.g., an answer appearing before its question correct

Why: Consistent prefix reads guarantees that if a sequence of writes has a causal order, anyone reading them sees them in that order — preventing an answer showing up before its question (common when writes are spread across partitions). The own-writes case is read-your-writes.

Q10 multiple choice

Which is a canonical, appropriate use case for multi-leader replication?

  1. A Maximizing read throughput within a single datacenter
  2. B A database spanning multiple datacenters (or offline-capable clients like a calendar app), where each location accepts writes locally correct
  3. C Guaranteeing linearizable single-object reads
  4. D Eliminating the need to ever resolve write conflicts

Why: Multi-leader shines across datacenters, offline clients, and collaborative editing — each replica takes local writes and syncs async. It does not eliminate conflicts; on the contrary, allowing concurrent writes is exactly what creates conflicts to resolve.

Q11 multiple choice

Why does 'last write wins' (LWW) conflict resolution risk data loss?

  1. A It silently discards all but one of a set of concurrent writes based on a timestamp, dropping the others' data correct
  2. B It merges concurrent writes field by field, corrupting the record
  3. C It requires a synchronous quorum and blocks on slow nodes
  4. D It can only be used with single-leader replication

Why: LWW picks one concurrent write (by timestamp) and throws the rest away, so genuinely concurrent updates are lost. Version vectors and CRDTs instead preserve/merge concurrent writes; LWW's appeal is simplicity, not correctness.

Q12 multiple choice

In leaderless (Dynamo-style) replication with n replicas, what does the quorum condition w + r > n ensure?

  1. A Every write is replicated to all n nodes before being acknowledged
  2. B Reads and writes never touch the same node, distributing load evenly
  3. C The set of nodes written to and the set read from overlap in at least one node, so a read is likely to see the latest write correct
  4. D The system behaves linearizably under all failure conditions

Why: Overlapping read and write quorums guarantee at least one node in a read set has the newest value. It does not require writing to all n, and quorums still permit stale reads in edge cases (sloppy quorums, concurrent writes, failed writes), so it is not true linearizability.

Q13 multiple choice

In leaderless replication, how do 'read repair' and 'anti-entropy' differ?

  1. A Read repair runs in the background; anti-entropy runs only during client reads
  2. B Both run only during leader failover
  3. C Read repair resolves conflicts; anti-entropy prevents them from ever occurring
  4. D Read repair fixes stale replicas opportunistically when a client read detects a divergence; anti-entropy is a background process that continuously compares and syncs replicas correct

Why: Read repair piggybacks on client reads to write back the newest value to lagging replicas, while anti-entropy is a separate background sync that catches data no one reads. Without anti-entropy, rarely-read values could stay stale indefinitely.

Q14 multiple choice

What do 'sloppy quorums' with 'hinted handoff' provide in a leaderless system?

  1. A Stronger consistency by requiring more than n acknowledgements
  2. B Higher write availability during network partitions by accepting writes on other reachable nodes, which later hand the data off to the intended 'home' nodes correct
  3. C A guarantee that reads always see the latest write
  4. D Automatic conflict resolution using version vectors

Why: A sloppy quorum lets writes land on any reachable nodes (not the designated home nodes) to stay available during partitions; hinted handoff later delivers them home. This boosts availability but weakens the read-your-write guarantee, since a later read of the home nodes may miss it.

Q15 explain & apply

Your app scales reads by serving them from asynchronous followers, but users complain that right after they save a change, a reload sometimes shows the old value. Diagnose the guarantee that's broken and give concrete ways to restore it without abandoning follower reads.

Points a strong answer hits:

  • Identify the anomaly: async replication lag means a user's own recent write hasn't reached the follower they read from — a read-your-writes (read-after-write) violation.
  • Technique 1: read anything the user may have modified from the leader (e.g., their own profile), other data from followers.
  • Technique 2: for a short window after a write, route that user's reads to the leader (or track last-write timestamp / log position and only read a replica caught up past it).
  • Technique 3: client remembers the timestamp/version of its last write and the system ensures the serving replica is at least that current.
  • Distinguish it from monotonic reads (going backward across reads) and consistent prefix (causal ordering) — this is specifically the own-writes case.
  • Preserve the read-scaling benefit — apply the stronger routing only to the user's own recently-written data, not all reads.
Model answer: That's a read-your-writes violation: async replication lag means the follower serving the reload hasn't yet received the user's own just-saved write. I'd keep scaling reads on followers but special-case the writer — for data a user may have modified (like their own posts/profile), read from the leader, or for a short window after their write pin their reads to the leader. A cleaner version records the log position/timestamp of the user's last write and only serves them from a replica that has caught up past it. This is specifically the own-writes guarantee, distinct from monotonic reads or consistent-prefix, and I only tighten it for the writer's own data so the rest of the read traffic still fans out to followers.

Q16 explain & apply

You're running a database across three datacenters on different continents and want each region to accept writes locally with low latency. What replication topology fits, what new problem does it force on you, and how do you handle it?

Points a strong answer hits:

  • Multi-leader replication fits multi-datacenter: each DC has a leader that takes local writes and replicates asynchronously to the others, so writes are low-latency and a DC can keep working during inter-DC network problems.
  • The new problem is write conflicts — two regions can concurrently modify the same record, since there's no single serialization point.
  • Conflict resolution options: last-write-wins (simple but silently drops data), version vectors to detect concurrency, CRDTs / application-defined merge to preserve both.
  • Avoid conflicts where possible: route all writes for a given record to one 'home' DC so the same key isn't concurrently edited.
  • Contrast with single-leader (all writes cross an ocean to one leader — high latency) and note multi-leader trades that latency for conflict-handling complexity.
Model answer: Multi-leader replication is the fit: give each datacenter its own leader that accepts local writes at low latency and replicates asynchronously to the other regions, so a cross-continent link hiccup doesn't stop local writes. The price is write conflicts — two regions can edit the same record concurrently with no single serialization point. I'd first try to avoid them by homing each record's writes to one datacenter, and where conflicts are unavoidable resolve them deliberately: version vectors to detect concurrency plus a merge (or a CRDT) rather than last-write-wins, which silently discards data. Single-leader would dodge conflicts but force every write across an ocean, so multi-leader is trading that latency for conflict handling.

Q17 explain & apply

In a leaderless (Dynamo-style) store with n=3, explain how you'd tune w and r for a read-heavy workload that still wants a good chance of fresh reads, and why a quorum here still isn't linearizable.

Points a strong answer hits:

  • The quorum condition is w + r > n so the write set and read set overlap in at least one node, so a read is likely to see the latest write.
  • For read-heavy load, favor a smaller r to keep reads fast/cheap and a larger w — e.g., w=3, r=1 (or w=2, r=2) — as long as w + r > n holds.
  • Note the availability/consistency tradeoff of that choice (large w hurts write availability if a node is down).
  • Read repair and anti-entropy converge stale replicas so rarely-read data doesn't stay stale forever.
  • Still not linearizable: sloppy quorums, concurrent writes, and writes that partially fail mean a fresh read isn't guaranteed — quorums give 'likely' fresh, not a strict recency guarantee.
  • Concurrent writes still need conflict resolution (version vectors), which linearizability would preclude.
Model answer: Quorum reads/writes work because w + r > n forces the read set and write set to overlap on at least one node, so a read usually sees the newest write. For a read-heavy workload I'd bias toward cheap reads — say w=2, r=2 with n=3, or even w=3, r=1 if I can tolerate a write blocking when a node is down — as long as w + r > n. Read repair and background anti-entropy pull lagging replicas forward so unread data doesn't rot. But this still isn't linearizable: sloppy quorums, concurrent writes needing version-vector resolution, and partially-failed writes mean a quorum gives you a high probability of freshness, not a strict recency guarantee.
