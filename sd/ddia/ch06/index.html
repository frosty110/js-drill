Partitioning

How to break a large dataset into partitions (shards) spread across many nodes for scalability, how to choose a partitioning scheme, keep it balanced as the cluster grows, and route requests to the right partition.

Designing Data-Intensive Applications 17 questions

Results carried by this link

Key ideas

  • Partitioning spreads data and query load across nodes for scalability; it is normally combined with replication so each partition has copies.
  • Key-range partitioning keeps keys sorted (enabling range scans) but risks hot spots; hash partitioning spreads load evenly but loses efficient range queries.
  • Even hashing does not fix a single hot key; that needs application-level splitting such as appending a random suffix.
  • Secondary indexes are either document-partitioned (local, scatter/gather reads) or term-partitioned (global, writes fan out but reads hit one partition).
  • Rebalancing should avoid hash-mod-N; fixed-partition-count, dynamic split/merge, and per-node-proportional strategies move data without reshuffling everything.
  • Request routing (node forwarding, a routing tier, or a partition-aware client) needs consensus on partition assignments — often via ZooKeeper or a gossip protocol.

Q1 multiple choice

In DDIA, what is the main goal of partitioning (sharding)?

  1. A To keep multiple copies of the same data for fault tolerance
  2. B To guarantee transactions execute in a serial order
  3. C To spread data and query load across many nodes so the system scales beyond one machine correct
  4. D To compress data by removing duplicate rows

Why: Partitioning splits a large dataset so different nodes hold different subsets, scaling storage and throughput. Keeping copies for fault tolerance is replication — the two are usually combined but are distinct concerns.

Q2 multiple choice

What does it mean for a partitioning scheme to be 'skewed', and why is it bad?

  1. A Partitions are unevenly loaded so some nodes ('hot spots') get disproportionate data or traffic, undermining the scalability partitioning was meant to provide correct
  2. B Data is sorted incorrectly, breaking range queries
  3. C Replicas of a partition disagree on the current value
  4. D The partition key is stored in a different byte order than the sort key

Why: Skew means load isn't spread evenly; hot spots bottleneck on a few nodes while others idle. The goal of a good scheme is even distribution across partitions.

Q3 multiple choice

What is the key tradeoff of partitioning by key range (keys kept sorted within each partition)?

  1. A It distributes load perfectly evenly but makes point lookups slow
  2. B It loses the ability to do point lookups entirely
  3. C It requires rehashing all data whenever a node is added
  4. D It enables efficient range scans, but certain access patterns (e.g., a timestamp key) can create hot spots correct

Why: Sorted key ranges support range queries, but a key like a timestamp funnels all recent writes into one partition, creating a hot spot. Even distribution is the strength of hash partitioning, not key-range.

Q4 multiple choice

What does partitioning by hash of the key gain and lose compared to key-range partitioning?

  1. A Gains efficient range queries, loses even distribution
  2. B Gains even load distribution, loses efficient range queries (adjacent keys scatter across partitions) correct
  3. C Gains both range queries and even distribution with no downside
  4. D Gains stronger consistency, loses availability

Why: Hashing spreads keys uniformly (good for load) but destroys key adjacency, so a range scan must query every partition. Key-range partitioning is the opposite tradeoff.

Q5 multiple choice

How does Cassandra's compound primary key compromise between hash and range partitioning?

  1. A It hashes every column of the key together into one partition ID
  2. B It stores each column in a separate partition
  3. C It hashes the first part of the key to choose a partition, then keeps rows sorted by the remaining columns within that partition correct
  4. D It uses consistent hashing across all key columns

Why: The first column of a Cassandra compound key is hashed to pick the partition (even spread), while the remaining columns sort rows inside the partition (efficient range scans within one partition key). This gives one-partition range queries without global hot spots.

Q6 multiple choice

Why does hash partitioning fail to solve the problem of a single hot key (e.g., a celebrity's user ID getting huge traffic)?

  1. A All requests for one key still hash to the same single partition, so hashing can't split load for an individual key correct
  2. B Hashing makes the hot key even hotter by duplicating it
  3. C Hashing only distributes writes, not reads
  4. D Hash functions are too slow to keep up with a hot key

Why: A hash spreads different keys evenly, but every request for the same key lands on one partition — a single hot key stays on one node. The book's mitigation is application-level: e.g., append a random number to the key to split it across N partitions, at the cost of more complex reads.

Q7 multiple choice

How does a document-partitioned (local) secondary index behave on reads?

  1. A A single partition holds the whole index, so reads hit exactly one partition
  2. B Reads never use the index; they scan primary keys
  3. C The index is stored on the client, so no partition is queried
  4. D Each partition indexes only its own documents, so a query on the secondary index must scatter to all partitions and gather results correct

Why: A local (document-partitioned) index keeps each partition's index alongside its own data, so a secondary-index query fans out to every partition (scatter/gather). Writes stay local — the opposite tradeoff from a global/term-partitioned index.

Q8 multiple choice

What is the tradeoff of a term-partitioned (global) secondary index versus a local one?

  1. A Reads must query all partitions, but writes touch only one
  2. B Reads hit a single partition (fast), but a write may need to update index entries on several partitions correct
  3. C Both reads and writes always touch exactly one partition
  4. D It eliminates the need to store a primary index

Why: A global index is partitioned by the indexed term, so a read on that term hits one partition — but a single document write can affect several terms living on different partitions, making writes fan out (and often asynchronous). This is the mirror image of the local-index tradeoff.

Q9 multiple choice

Why should rebalancing NOT be done with 'hash mod N' (where N is the number of nodes)?

  1. A Modulo is too computationally expensive at scale
  2. B Modulo produces collisions that corrupt keys
  3. C Changing N reassigns most keys to different nodes, forcing an enormous, disruptive data movement correct
  4. D It only works when N is a power of two

Why: With hash mod N, adding or removing a node changes N and remaps almost every key, so nearly all data must move. Rebalancing strategies aim to move as little data as possible.

Q10 multiple choice

How does the 'fixed number of partitions' rebalancing strategy work?

  1. A It creates many more partitions than nodes up front and, when nodes are added, moves whole partitions between nodes without changing how keys map to partitions correct
  2. B It picks the partition count equal to the current node count and re-splits on every change
  3. C It splits a partition in two whenever it exceeds a size threshold
  4. D It uses hash mod N but caches the result

Why: You over-provision partitions (e.g., 1000 for 10 nodes) so rebalancing just reassigns entire partitions to new nodes; the key→partition mapping never changes. Splitting on a size threshold is the separate 'dynamic partitioning' strategy (HBase/B-trees).

Q11 multiple choice

What characterizes 'dynamic partitioning' as used by HBase and range-partitioned stores?

  1. A The number of partitions is fixed forever at cluster creation
  2. B Partitions are reassigned every time a client connects
  3. C Each node always holds exactly one partition
  4. D Partitions are split when they grow too large and merged when they shrink, so partition count adapts to the data volume — analogous to a B-tree correct

Why: Dynamic partitioning splits an overgrown partition and merges under-filled ones, letting the number of partitions track the dataset size (like B-tree node splits/merges). Fixed-count is the alternative where partition count never changes.

Q12 multiple choice

Which three approaches to request routing does DDIA describe?

  1. A Only client-side routing is possible in distributed databases
  2. B A node receives the request and forwards it; a routing tier decides and forwards; or a partition-aware client connects directly to the right node correct
  3. C DNS round-robin, load balancer, and reverse proxy
  4. D Leader forwarding, follower forwarding, and quorum voting

Why: The three models are: any node forwards to the owner, a dedicated routing tier acts as a partition-aware load balancer, or the client itself knows the partition assignment. All three need current knowledge of which partition lives on which node.

Q13 multiple choice

What role does ZooKeeper commonly play in a partitioned system's request routing?

  1. A It stores the actual partitioned data as a backup
  2. B It hashes keys to partitions on behalf of clients
  3. C It maintains authoritative metadata about partition-to-node assignments, and routing components subscribe to it for changes correct
  4. D It executes the parallel query plan across partitions

Why: ZooKeeper acts as the coordination service holding the authoritative mapping of partitions to nodes; routing tiers/clients watch it so they learn about rebalancing. A gossip protocol among the nodes is the decentralized alternative that avoids a separate coordinator.

Q14 multiple choice

What is massively parallel processing (MPP) in the context of partitioning?

  1. A Running the same query on every replica and voting on the result
  2. B A routing scheme that picks the least-loaded node
  3. C A replication topology for multi-datacenter writes
  4. D Breaking a complex analytic query into stages that execute in parallel across many partitions/nodes to speed up throughput-heavy workloads correct

Why: MPP query engines parallelize a single analytic query across the partitions/nodes holding the data, which suits scan-heavy analytics rather than the point queries typical of OLTP. It is about query execution, not replication or routing.

Q15 explain & apply

You're partitioning a large event store keyed by timestamp. Product wants efficient 'give me everything in this time window' scans, but ingestion is all recent-time writes. Explain the tension and design a scheme that gets range scans without a write hot spot.

Points a strong answer hits:

  • Key-range partitioning keeps keys sorted so time-window range scans are efficient — but a pure timestamp key funnels all current writes into the newest partition, a write hot spot.
  • Pure hash partitioning spreads writes evenly but scatters adjacent timestamps, destroying efficient range scans — the opposite failure.
  • The fix is a compound key: prefix with a higher-cardinality field (e.g., sensor/tenant/customer id) so writes spread across partitions, then sort by timestamp within each partition.
  • This mirrors Cassandra's compound primary key: hash the first component for even spread, keep remaining columns sorted for in-partition range scans.
  • Tradeoff: a time-window query now scatters across the id partitions and gathers, but each partition still does an efficient sorted range scan and the write hot spot is gone.
Model answer: The tension is that a raw timestamp key gives me great time-window range scans because keys stay sorted, but it dumps every recent write into the single newest partition — a classic write hot spot; pure hashing would fix the hot spot but scatter adjacent times and kill the range scan. So I'd use a compound key: prefix with a higher-cardinality field like sensor or tenant id to spread writes across partitions, then sort by timestamp within each partition — exactly Cassandra's compound-key trick of hashing the first component and range-sorting the rest. A window query then scatters across those id-partitions and gathers, but each partition still does an efficient sorted scan and no single node is a write bottleneck.

Q16 explain & apply

One key in your hashed-partitioned system is a celebrity account taking massive traffic, and it's pinning a single node even though hashing usually spreads load. Why doesn't hashing help, and what would you actually do?

Points a strong answer hits:

  • Hashing distributes DIFFERENT keys evenly, but every request for the SAME key hashes to one partition — a single hot key stays on one node.
  • So hash partitioning solves skew across keys, not skew concentrated in one key.
  • Application-level mitigation: split the hot key by appending a random suffix (e.g., 1..N), spreading its traffic across N partitions.
  • Cost: reads must now fan out to all N sub-keys and combine results, and you must track which keys are hot.
  • Apply it selectively to the few known hot keys, not every key, to avoid making all reads more expensive.
Model answer: Hashing only spreads load across different keys — every request for the same key hashes to the same partition, so one celebrity key inevitably lands on one node no matter how good the hash is. The book's mitigation is application-level: split that hot key by appending a random suffix, say 1 through N, so its traffic spreads across N partitions. The cost is that reads for that key now have to fan out to all N variants and merge the results, and I have to track which keys are actually hot — so I'd apply this only to the handful of known hot keys, not universally, to avoid taxing every read.

Q17 explain & apply

Your partitioned product catalog needs to serve queries like 'all red cars' by a secondary attribute. Compare a document-partitioned (local) secondary index versus a term-partitioned (global) one for this, and pick based on the read/write pattern.

Points a strong answer hits:

  • Local (document-partitioned) index: each partition indexes only its own docs, so a secondary-index query must scatter to ALL partitions and gather — reads expensive, writes cheap (stay on one partition).
  • Global (term-partitioned) index: partitioned by the indexed term, so a query for 'red' hits one partition — reads cheap — but a single document write may update index entries on several partitions, so writes fan out.
  • Global indexes are often updated asynchronously, so the index can lag the data.
  • Pick local when writes dominate and secondary-index reads are rare/tolerant of scatter-gather; pick global when secondary-index reads are frequent/latency-sensitive and you can absorb heavier, possibly-lagging writes.
  • Frame it as the mirror-image tradeoff: you're choosing which of read or write pays the cross-partition cost.
Model answer: A local (document-partitioned) index stores each partition's index next to its own data, so writes stay on one partition but a 'red cars' query has to scatter to every partition and gather — cheap writes, expensive reads. A global (term-partitioned) index is partitioned by the term itself, so 'red' resolves on a single partition (fast reads), but one product write can touch index entries on several partitions, making writes fan out and often lag asynchronously. So it's the mirror-image tradeoff of which side pays the cross-partition cost: if this attribute query is frequent and latency-sensitive I'd go global and absorb the heavier, eventually-consistent writes; if writes dominate and these lookups are rare, the local index with scatter-gather reads is simpler.
