Transactions

How transactions group reads and writes into an all-or-nothing unit to simplify error handling and concurrency, the weak isolation levels that trade correctness for performance, the race conditions each prevents, and the three routes to true serializability.

Key ideas

  • ACID: Atomicity = abortability (all-or-nothing on failure), Consistency = an app-level invariant (the odd one out, the app's responsibility), Isolation = concurrent transactions don't interfere, Durability = committed data survives.
  • Read committed prevents dirty reads and dirty writes; snapshot isolation (MVCC) additionally prevents read skew by giving each transaction a consistent point-in-time view.
  • Lost updates need atomic ops, explicit locking (SELECT FOR UPDATE), automatic detect-and-abort, or compare-and-set; replication with LWW silently loses updates.
  • Write skew is a generalized race where two transactions read the same objects then update different ones (e.g., on-call doctors); phantoms are writes that change another transaction's search result.
  • Serializability has three implementations: actual serial execution (single-threaded + stored procedures), two-phase locking (2PL), and serializable snapshot isolation (SSI, optimistic).
  • Do not confuse 2PL (a locking concurrency-control method for isolation) with 2PC (two-phase commit, an atomic-commit protocol).

Q1 multiple choice

In ACID, which property is best described as 'abortability' — the ability to discard all of a transaction's writes if anything goes wrong partway through?

  1. A Consistency
  2. B Isolation
  3. C Atomicity correct
  4. D Durability

Why: DDIA frames atomicity as abortability: on failure the transaction is aborted and all its partial writes are thrown away, so it's all-or-nothing. Durability is about committed data surviving crashes; isolation is about concurrency.

Q2 multiple choice

Why does DDIA call the 'C' (Consistency) in ACID the odd one out?

  1. A It refers to application-level invariants the application must maintain, not a guarantee the database provides — unlike A, I, and D correct
  2. B It is the only property that is impossible to implement
  3. C It is a synonym for isolation and thus redundant
  4. D It only applies to replicated databases

Why: Consistency here means the data satisfies application-defined invariants; the database can only help, but it's the application's job to define and preserve them. Atomicity, isolation, and durability are genuinely database-provided.

Q3 multiple choice

What does read-committed isolation guarantee?

  1. A A fully consistent snapshot of the entire database for the transaction's lifetime
  2. B That transactions execute as if one at a time
  3. C That lost updates cannot occur
  4. D No dirty reads and no dirty writes — you only read/overwrite committed data correct

Why: Read committed prevents dirty reads (seeing uncommitted data) and dirty writes (overwriting uncommitted data). A consistent point-in-time snapshot is snapshot isolation, a stronger level; read committed does not prevent lost updates or read skew.

Q4 multiple choice

How is read committed typically implemented for reads and writes?

  1. A A single global lock serializes all transactions
  2. B Row-level locks prevent dirty writes, while for reads the database remembers and returns the old committed value until the new one commits (rather than holding read locks) correct
  3. C Multi-version snapshots keyed to a transaction start timestamp
  4. D Optimistic detection that aborts on conflict

Why: Write locks per object prevent dirty writes; for reads, holding locks would hurt throughput, so the DB serves the last committed value until the writer commits. Full multi-version snapshots per transaction are how snapshot isolation (a stronger level) works.

Q5 multiple choice

What race condition does snapshot isolation specifically prevent that read committed does not?

  1. A Dirty writes
  2. B Write skew
  3. C Read skew (nonrepeatable read) — a transaction seeing different parts of the database at different points in time correct
  4. D Phantom reads in all cases

Why: Snapshot isolation gives the whole transaction one consistent point-in-time view, preventing read skew where, mid-transaction, you'd see some data pre-update and some post-update. It still does not prevent write skew or all phantoms.

Q6 multiple choice

What is the core mechanism behind snapshot isolation, and what property does it give readers vs. writers?

  1. A Two-phase locking; readers and writers both block each other
  2. B A single serial execution thread; no concurrency at all
  3. C Compare-and-set on every read
  4. D Multi-version concurrency control (MVCC); readers never block writers and writers never block readers correct

Why: Snapshot isolation uses MVCC, keeping multiple committed versions so each transaction reads from a consistent snapshot without blocking writers (and vice versa). This makes it ideal for long-running reads like backups and analytics.

Q7 multiple choice

Which of these is NOT a valid technique for preventing lost updates?

  1. A Enabling last-write-wins conflict resolution on a replicated database correct
  2. B Atomic write operations (e.g., a single UPDATE ... SET x = x + 1)
  3. C Explicit locking with SELECT ... FOR UPDATE
  4. D Compare-and-set (only write if the value hasn't changed since you read it)

Why: Atomic ops, explicit locks, and compare-and-set all prevent lost updates; automatic detect-and-abort does too. LWW on replicated systems is explicitly called out as a way lost updates still happen, because it discards concurrent writes.

Q8 multiple choice

Which scenario is the textbook example of write skew?

  1. A Two users both incrementing the same counter and one increment being lost
  2. B Two on-call doctors each checking that at least one other doctor is on call, then both simultaneously booking off — leaving no one on call correct
  3. C A transaction reading uncommitted data from another transaction
  4. D A backup reading rows at different times mid-transaction

Why: Write skew: two transactions read the same set (doctors on call), each sees the invariant satisfied, then each updates a different row, together violating the invariant. The counter case is a classic lost update, not write skew.

Q9 multiple choice

In DDIA's terminology, what is a 'phantom'?

  1. A A committed write that vanishes after a crash
  2. B A replica that reports itself as leader after failover
  3. C A write in one transaction that changes the result of a search query in another transaction correct
  4. D A read that returns uncommitted data

Why: A phantom occurs when one transaction's write alters the set of rows another transaction's WHERE-clause search would match, causing write skew. Snapshot isolation can't lock rows that don't yet exist; 'materializing conflicts' is one workaround.

Q10 multiple choice

What is the key requirement that makes 'actual serial execution' (single-threaded transactions, as in VoltDB/Redis) viable?

  1. A Extremely fast disks so every transaction can be fsynced individually
  2. B A cluster of at least five nodes for quorum
  3. C Predicate locks on every index range
  4. D The active dataset must fit in memory and transactions must be short (often stored procedures), with writes partitionable for throughput correct

Why: Running transactions one at a time on a single thread only works if data is in RAM (no disk-wait stalls) and transactions are small stored procedures; throughput scales by partitioning. Predicate/index-range locks belong to 2PL, a different approach.

Q11 multiple choice

Two-phase locking (2PL) enforces serializability using which locking scheme?

  1. A Shared (read) and exclusive (write) locks, where readers block writers and writers block everyone — plus predicate or index-range locks to prevent phantoms correct
  2. B A single global mutex held for the whole transaction
  3. C Optimistic locks acquired only at commit time
  4. D Compare-and-set on each written row

Why: 2PL uses shared/exclusive locks so reads and writes mutually block, and adds predicate/index-range locks to stop phantoms. Its downsides are poor performance (lots of blocking) and deadlocks; optimistic-at-commit describes SSI, not 2PL.

Q12 multiple choice

How does serializable snapshot isolation (SSI) differ from two-phase locking?

  1. A SSI is pessimistic and locks earlier than 2PL
  2. B SSI is optimistic: transactions run without blocking on a snapshot, and at commit the database checks whether reads were invalidated by concurrent writes, aborting if so correct
  3. C SSI abandons snapshot isolation entirely
  4. D SSI can only run on a single thread

Why: SSI lets transactions proceed optimistically on a consistent snapshot and detects serialization conflicts (stale premises) at commit, aborting the loser. This avoids 2PL's heavy locking and generally scales better, at the cost of wasted work on aborts.

Q13 multiple choice

Why does DDIA warn readers not to confuse 2PL with 2PC?

  1. A They are the same protocol under two names
  2. B 2PC provides isolation and 2PL provides atomicity
  3. C Both are consensus algorithms like Paxos
  4. D 2PL (two-phase locking) is a concurrency-control method for isolation, whereas 2PC (two-phase commit) is an atomic-commit protocol across nodes — different problems entirely correct

Why: The names are similar but unrelated: 2PL is about serializable isolation via locks (this chapter), while 2PC is about committing a distributed transaction atomically across participants (Chapter 9). Conflating them is a common exam trap.

Q14 multiple choice

What is the practical relationship between single-object and multi-object operations regarding transactions?

  1. A Single-object atomicity/isolation is common even in non-transactional stores, but coordinating an invariant across multiple objects is what genuinely requires multi-object transactions correct
  2. B Multi-object transactions are unnecessary because single-object atomicity covers everything
  3. C Single-object operations always require distributed consensus
  4. D Multi-object transactions only matter for read-only workloads

Why: Many datastores provide atomic single-object writes cheaply, but keeping an invariant consistent across several rows/documents (e.g., moving money between accounts, updating denormalized copies) is exactly where multi-object transactions earn their keep.

Q15 explain & apply

A booking app lets two users concurrently book the last remaining seat: each transaction reads seats_left = 1, both see it's available, and both insert a booking. Which isolation level does this need, why won't snapshot isolation save you, and what's the cheapest fix if you must stay on snapshot isolation?

Points a strong answer hits:

  • Name the race: this is write skew — two transactions read the same premise (a seat is free) and each writes a different row (its own booking), together violating the invariant.
  • Snapshot isolation does NOT prevent write skew: each transaction reads from its own consistent snapshot and neither sees the other's not-yet-committed insert.
  • True fix is serializability (SSI, or 2PL with predicate/index-range locks to catch the phantom).
  • Cheap fix on SI: materialize the conflict — take an explicit lock on the seat row (SELECT ... FOR UPDATE) or a lock row for the resource so the reads collide.
  • A plain UPDATE ... SET x = x - 1 atomic decrement also serializes the contended write.
Model answer: This is write skew: both transactions read seats_left = 1, decide it's safe, then insert conflicting bookings. Snapshot isolation can't stop it because each runs against its own snapshot and can't see the other's phantom insert. The correct fix is serializable isolation (SSI or 2PL with predicate locks); if I must stay on SI, I'd materialize the conflict by taking an explicit SELECT ... FOR UPDATE lock on the seat/resource row so the two transactions actually contend on the same object.

Q16 explain & apply

You're on call for a hospital scheduler whose invariant is 'at least one doctor must remain on call at all times.' Explain to a teammate why weaker isolation is genuinely unsafe here and what specifically serializability buys you.

Points a strong answer hits:

  • Describe the failure: two doctors each check that another is on call, both see the invariant satisfied, and both simultaneously book off — leaving zero, a classic write skew.
  • Read committed and snapshot isolation both permit this because the two transactions read overlapping rows but write disjoint rows, so no lock or snapshot conflict fires.
  • The invariant spans multiple rows and depends on a read staying true through commit — exactly what serializability guarantees.
  • Serializability makes the outcome equivalent to some serial order, in which the second doctor to run would see only one left and be rejected.
  • This is worth the performance cost precisely because a violated safety invariant here is a real-world harm, not cosmetic staleness.
Model answer: The invariant couples multiple rows: each transaction reads the set of on-call doctors, confirms one other is present, then writes its own row — classic write skew that read committed and snapshot isolation both allow, since the writes don't overlap. Under those levels both can commit and leave nobody on call. Serializability forces the result to match some serial order, where whoever runs second would observe only one doctor left and be blocked. The isolation cost is justified because violating this invariant is an actual safety harm, not just stale data.

Q17 explain & apply

Two teams debate serializable isolation for a service with mostly short, read-heavy transactions and rare conflicts. When would you pick two-phase locking (2PL) versus serializable snapshot isolation (SSI), and what's the core mechanical tradeoff?

Points a strong answer hits:

  • 2PL is pessimistic: it takes shared/exclusive locks (plus predicate/index-range locks for phantoms) so conflicting transactions block each other up front.
  • SSI is optimistic: transactions run unblocked on a snapshot and the DB checks at commit whether a read premise was invalidated, aborting the loser.
  • For low-contention, read-heavy workloads SSI wins — few aborts, no lock waiting, better throughput and no reader/writer blocking.
  • For high-contention workloads SSI's abort-and-retry rate climbs and wastes work, so 2PL's blocking can be more predictable.
  • 2PL costs come from lock overhead, reduced concurrency, and deadlocks; SSI costs come from wasted work on aborts.
  • Both give the same correctness (equivalent to a serial order); the choice is a performance-profile decision, not a correctness one.
Model answer: For this mostly-read, low-conflict workload I'd pick SSI: transactions run optimistically on a snapshot without blocking, and since conflicts are rare, few will be aborted at commit — you get near snapshot-isolation throughput with serializable correctness. 2PL would make readers and writers block each other and risk deadlocks even though conflicts almost never happen. I'd flip to 2PL only if contention were high, where SSI's abort-and-retry rate would waste too much work; both deliver identical correctness, so it's purely a performance-profile call.
