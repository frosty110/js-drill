The Trouble with Distributed Systems

A tour of everything that can go wrong once data spans multiple machines connected by an unreliable network: dropped and delayed messages, untrustworthy clocks, arbitrary process pauses, and nodes that cannot even trust their own judgment. The chapter builds toward the system models and safety/liveness vocabulary used to reason about these faults.

Key ideas

  • In distributed systems faults are partial and nondeterministic: some parts work while others fail in confusing ways, unlike a single computer that tends to fail totally and deterministically.
  • The network is asynchronous and unreliable; a timeout cannot distinguish a lost request, a crashed node, or a slow-but-alive node.
  • There is no correct timeout value: too long delays failover, too short declares live nodes dead and triggers duplicate actions and cascading failures.
  • Time-of-day clocks can jump (NTP, leap seconds) and must not be trusted for ordering events; use monotonic clocks for durations, and prefer logical clocks for ordering.
  • A process can pause arbitrarily long (GC, VM migration, paging), so a leader holding a lease may keep acting after the lease expired.
  • Truth is defined by the quorum/majority, not by any single node; fencing tokens stop a paused or deposed leader from corrupting shared state.
  • System models are defined by timing assumptions (synchronous / partially synchronous / asynchronous) and failure assumptions (crash-stop / crash-recovery / Byzantine), and correctness is stated as safety and liveness properties.

Q1 multiple choice

How does DDIA characterize faults in a distributed system compared with faults on a single computer?

  1. A Distributed faults are total and deterministic, so they are easier to reproduce than single-machine faults
  2. B Distributed faults are partial and nondeterministic: some components fail unpredictably while others keep working correct
  3. C Distributed systems have no more failure modes than a single machine; they just occur more often
  4. D A single computer fails partially, whereas a distributed system always fails completely

Why: A single computer usually fails cleanly and deterministically (it either works or crashes entirely), which is a deliberate design choice. Distributed systems instead suffer partial failures that are nondeterministic — one node or link misbehaves while the rest run — which is what makes them hard to reason about.

Q2 multiple choice

When a node sends a request over an asynchronous network and gets no reply, what can it actually conclude?

  1. A That the remote node has definitely crashed
  2. B That the request was definitely lost in transit
  3. C Nothing definite; it cannot distinguish a lost request, a dead node, or a slow/queued response — only that no reply arrived yet correct
  4. D That the network has partitioned and will stay partitioned

Why: On an asynchronous packet network the sender cannot tell whether the request was lost, the node died, the response was lost, or everything is merely slow. The only signal available is the absence of a reply within some timeout, which is inherently ambiguous.

Q3 multiple choice

Why does DDIA say there is no universally correct timeout for detecting a failed node?

  1. A Because timeouts should always be set to twice the average round-trip time
  2. B Because TCP already guarantees delivery, so timeouts are only needed for UDP
  3. C Because clocks are unsynchronized, so any timeout measured in wall-clock time is meaningless
  4. D Because a long timeout means slow detection/failover while a short timeout risks declaring a live node dead, causing duplicate actions and cascading load correct

Why: A long timeout makes users wait a long time before failover; a short timeout prematurely declares a healthy-but-slow node dead, which can hand its work to another node (risking double execution) and pile extra load onto an already struggling system, causing cascading failures. Network delay has no upper bound, so no single value is correct.

Q4 multiple choice

What is the key difference between a traditional synchronous (circuit-switched) telephone network and a packet-switched data network?

  1. A A circuit reserves a fixed amount of bandwidth end-to-end giving bounded latency, whereas packet switching dynamically shares links and gives variable, unbounded delay correct
  2. B Packet-switched networks reserve bandwidth per call, so they have lower latency
  3. C Circuit-switched networks use queueing, which is the main cause of bufferbloat
  4. D Packet-switched networks guarantee delivery order, whereas circuits do not

Why: A telephone circuit reserves a fixed slice of bandwidth for the whole call, giving bounded latency with no queueing. Packet-switched networks are optimized for bursty traffic by sharing links dynamically, so packets queue in buffers (bufferbloat) and delay is variable with no guaranteed upper bound — the tradeoff is efficiency for predictability.

Q5 multiple choice

In DDIA's terms, what is a time-of-day clock (wall-clock) and why is it dangerous for ordering events?

  1. A A clock returning the current calendar time that is synchronized via NTP and can jump forwards or backwards, so timestamps can order events incorrectly correct
  2. B A clock that only moves forward and is ideal for ordering events across machines
  3. C A hardware counter measuring elapsed durations that never goes backward
  4. D A logical counter incremented on every message, immune to clock drift

Why: A time-of-day clock reports calendar time and is kept in sync by NTP, so it can jump backward (or forward) when corrected, and different nodes disagree by their sync error. Using such timestamps to order events across machines can silently misorder them; that is why last-write-wins based on wall clocks can drop writes.

Q6 multiple choice

What is a monotonic clock best used for, and what does it guarantee?

  1. A For reading calendar time; it guarantees agreement with other machines' wall clocks
  2. B For ordering events globally; it guarantees a total order consistent with causality
  3. C For timestamping database writes; it guarantees NTP-corrected accuracy
  4. D For measuring elapsed time/durations; it only ever moves forward and never jumps backward, but its absolute value is meaningless across machines correct

Why: A monotonic clock is a counter guaranteed never to go backward, so it is the right tool for measuring a duration (e.g. a timeout or request latency) on one machine. Its absolute value has no meaning and comparing monotonic readings across nodes is nonsensical — it says nothing about calendar time or cross-machine ordering.

Q7 multiple choice

How does last-write-wins (LWW) conflict resolution based on wall-clock timestamps fail?

  1. A It always deadlocks when two writes have the same timestamp
  2. B It requires a global lock, which does not scale
  3. C Because clocks are not perfectly synchronized, a write with an earlier real time but a later timestamp can silently overwrite (drop) a newer write correct
  4. D It corrupts data whenever a leap second is inserted

Why: LWW keeps the write with the highest timestamp, but clock skew means the highest timestamp does not reliably correspond to the write that actually happened last. A node whose clock is ahead can make its stale write win, so a genuinely newer write is silently discarded — data loss with no error.

Q8 multiple choice

What problem does Google Spanner's TrueTime address, and how?

  1. A It eliminates clock drift entirely by using a single global master clock
  2. B It replaces physical clocks with Lamport timestamps to get a total order for free
  3. C It uses GPS to make every server's clock read exactly the same value
  4. D It returns time as a confidence interval [earliest, latest] and waits out the uncertainty so it can safely order transactions despite clock error correct

Why: TrueTime acknowledges clocks are uncertain by exposing time as an interval bounding the true time, using GPS and atomic clocks to keep that interval narrow. Spanner deliberately waits for the interval's uncertainty to pass (commit-wait) before releasing a transaction, guaranteeing non-overlapping intervals reflect real ordering.

Q9 multiple choice

Why is a process pause (e.g. a stop-the-world garbage collection) dangerous for a node that holds a lease as leader?

  1. A The pause corrupts the node's memory, forcing a restart
  2. B The node may be paused past the lease's expiry, so another node becomes leader while the paused node, on resuming, still believes it is leader correct
  3. C GC pauses reset the monotonic clock, breaking duration measurements
  4. D Leases are unaffected by pauses because they are enforced in hardware

Why: A node can be paused for an arbitrarily long time (GC, VM live migration, paging, suspended laptop) with no awareness that time passed. If the pause outlasts the lease, the cluster elects a new leader; when the old node wakes it acts as leader without knowing it was superseded, risking split-brain corruption.

Q10 multiple choice

How do fencing tokens prevent a paused or deposed leader from corrupting shared storage?

  1. A Each write is stamped with a monotonically increasing token, and the storage rejects any write bearing a token lower than one it has already seen correct
  2. B The old leader is guaranteed to be killed before a new one starts, so no conflicting write is possible
  3. C Every request must include a wall-clock timestamp, and the newest timestamp wins
  4. D Clients hold a mutex that the storage releases only after a heartbeat

Why: The lock service hands out a monotonically increasing fencing token with each grant; clients attach it to their writes, and the resource refuses any write carrying a token older than the highest already accepted. So a woken-up former leader, holding a now-stale token, is fenced out even though it still thinks it holds the lock.

Q11 multiple choice

In DDIA's discussion of 'knowledge, truth, and lies', how is the truth about the cluster's state defined?

  1. A By whichever node has the most up-to-date wall clock
  2. B By the current leader, whose word is authoritative
  3. C By the majority/quorum of nodes, because no single node's perception can be trusted correct
  4. D By the node with the lowest ID, chosen deterministically

Why: A single node cannot trust its own view — it may be paused, partitioned, or have a dead network card even though it feels fine. DDIA's principle is that decisions require agreement among a quorum (majority) of nodes, so the majority defines truth and a node declared dead by the quorum must comply even if it disagrees.

Q12 multiple choice

What is a Byzantine fault, and what assumption do most datacenter systems make about it?

  1. A A node that sends arbitrary, possibly malicious or contradictory information ('lies'); most datacenter systems assume nodes are non-Byzantine (trusted) correct
  2. B A node that crashes and never recovers; most systems assume this cannot happen
  3. C A network partition that splits the cluster in two; most systems tolerate it automatically
  4. D A clock that drifts beyond NTP correction; most systems handle it with fencing tokens

Why: A Byzantine fault is when a node behaves arbitrarily — it may lie, send conflicting messages to different peers, or be actively malicious. Byzantine fault-tolerant algorithms exist (and matter in aerospace or blockchains) but are costly, so most systems inside a single trusted datacenter assume non-Byzantine behavior.

Q13 multiple choice

In DDIA's system-model taxonomy, what distinguishes the three timing models — synchronous, partially synchronous, and asynchronous?

  1. A They describe whether nodes crash-stop, crash-recover, or act Byzantine
  2. B They describe whether the algorithm uses locks, leases, or fencing tokens
  3. C They describe assumptions about bounds on network delay and clock drift: bounded always, bounded most of the time, or no timing guarantees at all correct
  4. D They describe whether messages are delivered in FIFO, causal, or total order

Why: The timing models concern assumptions about delays: a synchronous model assumes bounded network delay and clock skew, an asynchronous model assumes no timing guarantees at all (and cannot use timeouts), and the partially synchronous model — the most realistic — assumes the system behaves synchronously most of the time but occasionally exceeds any bound. Crash-stop vs Byzantine is the separate node-failure axis.

Q14 multiple choice

What is the difference between a safety property and a liveness property?

  1. A Safety means the system stays available under partitions; liveness means it stays consistent
  2. B Safety applies to synchronous models and liveness to asynchronous ones
  3. C Safety concerns data durability; liveness concerns network throughput
  4. D A safety property says 'nothing bad ever happens' (a violation is irreversible), while a liveness property says 'something good eventually happens' correct

Why: A safety property requires that nothing bad ever happens — once violated the damage is done and cannot be undone (e.g. two leaders elected). A liveness property requires that something good eventually happens (e.g. a request eventually gets a response); it can be pending for a while without being violated. DDIA usually insists safety always holds while allowing liveness to depend on timing assumptions.

Q15 explain & apply

Your failure detector marks a node dead after a 5-second timeout and reassigns its work. In production this occasionally double-executes jobs. Explain why you fundamentally can't distinguish a slow node from a dead one, and how you'd design around it instead of just tuning the timeout.

Points a strong answer hits:

  • On an asynchronous network a missing reply is ambiguous: lost request, dead node, or slow/queued response are indistinguishable from the outside.
  • There is no correct timeout — too long delays failover, too short declares live-but-slow nodes dead, triggering duplicate work and cascading load.
  • Network delay has no guaranteed upper bound, so no single value eliminates the ambiguity.
  • Design around it: don't rely on timeouts for correctness — make reassigned work idempotent or guard shared state with fencing tokens so a wrongly-declared-dead node can't corrupt anything.
  • Let a quorum, not one observer, decide liveness, and accept the timeout only as a liveness/latency heuristic, never a safety guarantee.
Model answer: The absence of a reply is inherently ambiguous — I can't tell whether the node crashed, the network dropped the packet, or the node is just slow, because packet delay has no upper bound. So any timeout is a guess: shorter ones declare healthy-but-slow nodes dead and cause the double execution I'm seeing. Rather than chase a magic value, I'd stop treating the timeout as truth: make the reassigned work idempotent and protect shared state with fencing tokens, so even if the 'dead' node is actually alive and resumes, it can't corrupt results. Liveness should be a quorum decision and the timeout only a heuristic for when to react.

Q16 explain & apply

A leader acquires a lease on a lock service, then suffers a 30-second stop-the-world GC pause; meanwhile the cluster elects a new leader. When the old leader wakes it writes to shared storage believing it still holds the lock. Walk through how fencing tokens prevent corruption here.

Points a strong answer hits:

  • A process can pause arbitrarily (GC, VM migration, paging) with no awareness that time passed, so a lease can silently expire mid-pause.
  • During the pause the cluster times out the lease and elects a new leader, creating a split-brain window.
  • The lock service hands out a monotonically increasing fencing token with each grant; the new leader gets a higher token than the old one.
  • Clients attach their token to every write to the storage/resource.
  • The storage rejects any write bearing a token lower than the highest it has already accepted, so the woken old leader's stale-token write is refused.
  • Correctness comes from the resource enforcing the token, not from trusting the lock client to behave.
Model answer: The GC pause is invisible to the old leader — it can't know its lease expired while it was frozen, so on waking it still thinks it's leader (split brain). Fencing fixes this at the resource: each lock grant carries a monotonically increasing token, so the new leader holds a higher token than the old one. Every write to shared storage includes its token, and the storage refuses any write whose token is lower than the highest it has seen. The old leader's write, stamped with a now-stale token, is rejected — and crucially the guarantee lives in the resource enforcing the token, not in the paused client behaving correctly.

Q17 explain & apply

A colleague proposes ordering events across servers by their time-of-day (wall-clock) timestamps and resolving conflicts with last-write-wins. What breaks, and what would you use instead for (a) measuring a request's duration and (b) ordering events causally?

Points a strong answer hits:

  • Time-of-day clocks are NTP-synced and can jump forward or backward; nodes disagree by their sync error, so timestamps can misorder events.
  • LWW on wall clocks silently drops data: a write with an earlier real time but a higher timestamp (skewed-ahead clock) wins, discarding a genuinely newer write with no error.
  • For durations use a monotonic clock — it only moves forward and never jumps, though its absolute value is meaningless across machines.
  • For cross-machine event ordering use logical clocks (Lamport timestamps / version vectors), which order by causality, not wall time.
  • If real-time ordering is truly required, something like Spanner's TrueTime (bounded uncertainty interval + commit-wait) is needed, not raw NTP timestamps.
Model answer: Wall-clock ordering breaks because time-of-day clocks are NTP-corrected and can jump backward or disagree between nodes; LWW then keeps the highest timestamp, so a node whose clock runs fast can make a stale write win and silently drop a newer one — data loss with no error. For measuring a request's duration I'd use a monotonic clock, which never goes backward (its absolute value is meaningless, but deltas are reliable). For ordering events across machines I'd use logical clocks like Lamport timestamps or version vectors, which capture causality; only something like TrueTime with bounded uncertainty and commit-wait can safely order by real time.
