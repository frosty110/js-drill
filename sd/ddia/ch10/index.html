Batch Processing

How systems that process a large, bounded input all at once — from Unix pipelines to MapReduce and modern dataflow engines — turn big datasets into derived outputs like search indexes and read-only key-value stores, prioritizing throughput over latency.

Key ideas

  • Three system types: online services (latency-bound), batch processing (throughput-bound, bounded input), and stream processing (near-real-time, unbounded input).
  • The Unix philosophy — small composable tools with a uniform interface (text streams over stdin/stdout) and immutable inputs — is the intellectual ancestor of MapReduce.
  • MapReduce runs mapper → shuffle/sort-by-key → reducer across a distributed filesystem (HDFS), moving computation to the data and materializing intermediate state to disk between jobs.
  • Reduce-side joins (sort-merge) bring both sides together by key; map-side joins (broadcast hash, partitioned hash) avoid the shuffle when a table is small or co-partitioned.
  • Batch outputs are immutable read-only artifacts (search indexes, KV stores) swapped in atomically, making rollback trivial and buggy code safe to rerun.
  • MapReduce tolerates faults by materializing and retrying individual tasks; dataflow engines (Spark, Tez, Flink) model the job as a DAG, keep intermediate data in memory, and recompute lost partitions from lineage.

Q1 multiple choice

DDIA distinguishes three types of systems by their performance goal. How does batch processing differ from an online service?

  1. A Batch processing takes a large bounded input, runs a job to produce derived output, and is measured by throughput rather than per-request latency correct
  2. B Batch processing consumes an unbounded stream of events as they arrive
  3. C Batch processing optimizes for low response-time latency per request, like a service
  4. D Batch processing is a synonym for stream processing with a larger buffer

Why: A batch job crunches a fixed, bounded dataset and is judged on throughput (records processed / total job time), not the response latency an online service cares about. Consuming unbounded events as they arrive is stream processing (Ch 11).

Q2 multiple choice

Which principle is central to the Unix philosophy that DDIA credits as the ancestor of MapReduce?

  1. A Every tool maintains its own persistent mutable database of state
  2. B Each program does one thing well and programs compose via a uniform interface (text streams over stdin/stdout) correct
  3. C Programs communicate only through shared memory for speed
  4. D A single monolithic program should handle the entire pipeline end to end

Why: Unix tools do one thing well and chain through pipes using a uniform interface — a stream of bytes/text — so they compose freely. This uniform interface and immutable-input mindset is exactly what MapReduce generalizes to a distributed filesystem.

Q3 multiple choice

What is the correct sequence of stages in a MapReduce job?

  1. A Reducer extracts key-value pairs, then the mapper aggregates them
  2. B Mapper and reducer run concurrently on the same records with no sort step
  3. C Mapper emits key-value pairs from each record, the framework shuffles and sorts them by key, then the reducer processes all values for each key correct
  4. D A coordinator sorts the input first, then a single mapper produces the final output

Why: The mapper extracts a key-value pair per input record; the framework's shuffle brings all values with the same key to one reducer (sorted by key); the reducer then processes each key's grouped values. There is no separate reducer-extract-then-mapper ordering.

Q4 multiple choice

Why must MapReduce mapper and reducer callbacks be pure and stateless (no external side effects)?

  1. A Because JavaScript closures cannot capture mutable state
  2. B Because HDFS blocks any function that writes to memory
  3. C So the reducer can run before the mapper finishes
  4. D So the framework can freely re-run them on retries and speculative execution without the results depending on prior runs correct

Why: Determinism and freedom from side effects let MapReduce retry failed tasks and run speculative duplicate tasks safely, since re-execution yields the same output. If callbacks mutated external state, retries could corrupt results.

Q5 multiple choice

What does 'putting the computation near the data' mean in MapReduce on HDFS?

  1. A Scheduling each map task to run on (or near) the machine that already stores that input file block, to avoid copying data over the network correct
  2. B Copying the entire dataset to a central compute node before processing
  3. C Storing the code inside the database alongside the rows
  4. D Caching query results in the client so repeated reads are local

Why: The scheduler tries to place a mapper on a machine holding a replica of its input block, so the bulky data stays put and only the (small) code moves. This locality optimization conserves scarce network bandwidth on large jobs.

Q6 multiple choice

How does MapReduce handle intermediate state between chained jobs differently from a Unix pipeline?

  1. A MapReduce streams intermediate records directly between jobs with no persistence
  2. B MapReduce materializes each job's full output to the distributed filesystem before the next job reads it, unlike a Unix pipe's in-memory streaming correct
  3. C Both keep all intermediate state only in RAM
  4. D MapReduce discards intermediate output immediately to save disk

Why: A Unix pipe streams bytes between processes in memory; MapReduce fully materializes each job's output to HDFS, so the next job can only start once the previous one finishes completely. This materialization aids fault tolerance but adds latency and storage cost — a point dataflow engines push back on.

Q7 multiple choice

In a MapReduce sort-merge (reduce-side) join, how are the two sides brought together?

  1. A The smaller table is broadcast into every mapper's memory
  2. B One table is loaded into a database and looked up per record over the network
  3. C Both inputs are mapped so that records with the same join key get the same key; the shuffle sorts them together and the reducer sees all matching records for a key adjacently correct
  4. D The join is computed by a single reducer scanning the whole dataset

Why: A reduce-side (sort-merge) join emits the join key from both datasets in the map phase; the framework's sort brings matching records adjacent at the reducer, which merges them. Broadcasting the small table into every mapper is instead the broadcast-hash (map-side) join.

Q8 multiple choice

When is a broadcast hash join (a map-side join) appropriate?

  1. A When both datasets are enormous and neither fits in memory
  2. B Only when the join key is a monotonically increasing timestamp
  3. C When you need to detect and resolve write conflicts between replicas
  4. D When one of the two datasets is small enough to load entirely into each mapper's memory as a hash table, avoiding the shuffle correct

Why: A broadcast hash join loads the small side fully into the memory of every mapper, which then streams the large side and probes the hash table — no reducer shuffle needed. If both sides are large, you fall back to a partitioned hash join or a sort-merge (reduce-side) join.

Q9 multiple choice

What problem do 'skewed' (also called sharded) joins address in batch processing?

  1. A A few hot keys with disproportionately many records overloading a single reducer, so the join is spread across multiple reducers for those keys correct
  2. B The distributed filesystem running out of replicas
  3. C Nondeterministic mapper functions producing divergent output
  4. D Records arriving in the wrong causal order

Why: When one key has vastly more records than others (hot key), the reducer handling it becomes a straggler; skewed/sharded-join techniques split that key's records across several reducers to rebalance. This is a load-distribution fix, not a determinism or ordering fix.

Q10 multiple choice

How does a MapReduce job typically deliver output such as a search index or key-value store to serving systems?

  1. A It issues individual UPDATE statements against the live production database as it computes
  2. B It writes brand-new immutable files (e.g. Lucene index segments or a read-only KV store) that are then swapped in atomically, so a bad run is easy to roll back correct
  3. C It mutates the previous output in place to save disk space
  4. D It streams each record to clients as it is produced with no intermediate file

Why: Batch jobs build fresh immutable output files and atomically swap the whole dataset into the serving layer; because the old version is untouched, rollback is trivial and buggy code causes no permanent damage. Issuing live per-record UPDATEs would be slow and risk half-applied state.

Q11 multiple choice

How does MapReduce's fault-tolerance strategy contrast with that of a massively parallel processing (MPP) distributed database?

  1. A MapReduce aborts and restarts the entire query on any node failure, like most MPP databases
  2. B MPP databases retry individual tasks while MapReduce restarts everything
  3. C MapReduce materializes intermediate results and retries only the individual failed tasks, letting huge jobs survive frequent failures (e.g. on preemptible resources), whereas MPP databases keep more work in memory and typically restart the whole query correct
  4. D Both keep all intermediate state in memory and never retry

Why: By writing intermediate output to disk, MapReduce can re-run just the tasks that failed, tolerating a high failure rate on large or preemptible clusters. MPP databases favor keeping data in memory for speed but generally must restart a whole query on failure — MapReduce trades performance for resilience.

Q12 multiple choice

What is the core architectural difference of dataflow engines (Spark, Tez, Flink) versus classic MapReduce?

  1. A They forbid joins and grouping entirely
  2. B They require the input to fit in a single machine's memory
  3. C They eliminate the distributed filesystem and store everything in one node
  4. D They model the whole workflow as a DAG of operators, avoid fully materializing every intermediate stage to disk (keeping data in memory / pipelining), and support operators beyond just map and reduce correct

Why: Dataflow engines treat the entire job as a DAG of operators, so they can pipeline and keep intermediate data in memory instead of materializing to HDFS between every map/reduce step, and they offer richer operators. This cuts the redundant sorts and disk round-trips MapReduce incurs when chaining jobs.

Q13 multiple choice

How does Spark recover from a lost partition of intermediate data without re-running the whole job?

  1. A It recomputes the lost partition from its RDD lineage — the recorded sequence of deterministic operations that produced it correct
  2. B It restores the partition from a periodic full backup on tape
  3. C It queries a replica of the partition from another datacenter
  4. D It cannot recover and must restart the entire job from the input

Why: Because Spark tracks each RDD's lineage (the deterministic operations that built it), it can recompute just a lost partition from its ancestors rather than restarting everything. This depends on the transformations being deterministic, so lineage-based replay reproduces the same data.

Q14 multiple choice

What computational model does DDIA describe for iterative graph processing frameworks like Pregel?

  1. A A single reducer walks the entire graph depth-first
  2. B The bulk synchronous parallel (BSP) model, where vertices process incoming messages and send messages to neighbors in a series of synchronized iterations (supersteps) correct
  3. C A stream of events consumed with sliding-window joins
  4. D Two-phase commit across all graph vertices per edge

Why: Pregel uses the bulk synchronous parallel model: in each superstep, a vertex processes messages received in the prior step and emits messages to neighbors, iterating until convergence. This is well suited to graph algorithms that would need many MapReduce jobs otherwise.

Q15 explain & apply

You're joining a huge clickstream against a user table in a batch job, but a handful of celebrity users account for a massive share of the clicks. A plain reduce-side join makes one reducer a straggler. How do you design the join, and which join strategy applies if the user table is small?

Points a strong answer hits:

  • Identify the cause: a hot key sends disproportionately many records to one reducer, which becomes a straggler that stalls the whole job.
  • Use a skewed/sharded join: split the hot key's records across several reducers (e.g. randomize a suffix on the hot key) and replicate the other side of the join to all those reducers.
  • This rebalances load so no single reducer carries the celebrity user alone.
  • If the user table is small enough to fit in memory, skip the shuffle entirely with a broadcast hash join — load the table into every mapper and probe it while streaming the clicks.
  • Broadcast/map-side joins avoid the reducer bottleneck by removing the sort-and-shuffle step altogether; if both sides are large, fall back to partitioned-hash or sort-merge with the skew mitigation.
Model answer: The straggler comes from a hot key — the celebrity users funnel most clicks to one reducer. I'd use a skewed (sharded) join: hash-and-split each hot key's records across several reducers (adding a random suffix to the key) and replicate the matching user rows to all of those reducers, so the load spreads instead of piling on one. If the user table is small enough to fit in memory, I'd sidestep the shuffle entirely with a broadcast hash join — load the whole user table into every mapper and probe it while streaming clicks, which removes the reducer bottleneck. Only if both sides are large do I stay reduce-side, applying the skew mitigation.

Q16 explain & apply

A data scientist runs an iterative machine-learning job (many passes over the same dataset) on classic MapReduce and it's painfully slow. Why is MapReduce a poor fit, and what does a dataflow engine like Spark do differently — including how it still recovers from a failure?

Points a strong answer hits:

  • MapReduce fully materializes each job's output to the distributed filesystem (HDFS) before the next job starts, so every iteration pays a full read/write-to-disk round trip plus re-sort.
  • For iterative jobs that reuse the same data, this repeated materialization dominates runtime.
  • A dataflow engine models the whole job as a DAG of operators, pipelines stages, and keeps intermediate data in memory across iterations instead of writing to HDFS between each step.
  • It also offers richer operators than just map and reduce and avoids redundant sorts.
  • Fault recovery: Spark tracks each partition's lineage (the deterministic ops that built it) and recomputes only a lost partition from its ancestors, rather than checkpointing everything to disk like MapReduce.
  • The tradeoff: MapReduce's disk materialization gives cheap fine-grained retries for very large/failure-prone jobs; the dataflow engine trades some of that for in-memory speed, relying on deterministic recomputation.
Model answer: MapReduce writes every job's full output to HDFS before the next one can read it, so an iterative job pays a disk round-trip and re-sort on every pass — that materialization is what's killing you. A dataflow engine like Spark models the whole workflow as a DAG, pipelines the operators, and keeps intermediate data in memory across iterations instead of materializing to HDFS each step, with richer operators than plain map/reduce. It still survives failures via RDD lineage: it records the deterministic operations that produced each partition and recomputes just a lost partition from its ancestors, rather than re-running everything. The tradeoff is that MapReduce's disk materialization buys cheap task-level retries on huge, failure-prone clusters, while Spark trades that for in-memory speed backed by deterministic recomputation.

Q17 explain & apply

Batch jobs write brand-new immutable output files and swap them into the serving layer atomically, rather than issuing per-record UPDATEs to the live database. Explain why this design makes buggy code and reruns safe.

Points a strong answer hits:

  • Inputs are immutable and the job produces fresh, immutable output files (e.g. Lucene segments, a read-only KV store) rather than mutating existing state.
  • The new dataset is swapped in atomically, so the serving layer only ever sees the old complete version or the new complete version, never a half-applied mix.
  • Because the previous output is untouched, rollback is trivial — just point back at the old files if the new run is bad.
  • A buggy or crashed run causes no permanent damage: you rerun on the same immutable input and get a clean deterministic result (human fault tolerance).
  • Contrast: issuing live per-record UPDATEs risks half-applied state, is hard to roll back, and a bug corrupts the production data in place.
  • This mirrors the Unix philosophy of immutable inputs and safe, repeatable transformations.
Model answer: The job treats inputs as immutable and produces entirely new, immutable output files, then swaps the whole dataset into the serving layer atomically — so consumers only ever see the old complete version or the new complete version, never a half-written mix. Because the previous output is never touched, rollback is just re-pointing at the old files, and a buggy or crashed run does no permanent harm: I rerun over the same immutable input and get a clean, deterministic result. That's a world apart from streaming per-record UPDATEs to the live DB, where a bug leaves half-applied, hard-to-reverse corruption in place. It's the Unix immutable-input philosophy applied to derived data, and it's what makes the pipeline forgiving of human error.
