Windows Watermarks And Late Data

Focused mechanism study sheet

What this sheet shows

Event time reflects reality; processing time reflects arrival. Watermarks bound how long to await late data.

Trace the flow

  1. Event time reflects reality — Event time reflects reality; processing time reflects arrival. Watermarks bound how long to await late data.
  2. Stream time reasoning distinguishes event — Stream time reasoning distinguishes event time from processing time and uses windows (tumbling/hopping/sliding/session) with watermarks; fault tolerance targets exactly-once via checkpointing, idempotence, and atomic.
  3. Tumbling windows are fixed, non-overlapping — Tumbling windows are fixed, non-overlapping intervals; hopping and sliding windows are fixed-length but overlap.
  4. A traditional AMQP/JMS broker deletes — A traditional AMQP/JMS broker deletes each message once acknowledged, so history and replay are gone; it's the right tool when you instead want to load-balance individual tasks with uneven cost across a worker pool,.
  5. Stream processing treats unbounded events — Stream processing treats unbounded events as data, maintaining derived views while handling time, replay, and delivery.

What this belongs to

How to process unbounded, continuously arriving data as a stream of immutable events — the messaging systems and log-based brokers that transport events, the change-capture and event-sourcing patterns that turn databases into streams, and the time-reasoning and fault-tolerance issues stream operators must handle.
