The Future of Data Systems

Kleppmann's synthesis: no single tool fits all needs, so applications should be built by composing specialized systems around dataflows — funneling writes through ordered logs to keep derived data consistent — while aiming for end-to-end correctness, auditing rather than blind trust, and ethical responsibility for the data we collect.

Key ideas

  • No one system does everything, so real applications integrate multiple tools; distinguishing the system of record (source of truth) from derived data is the key to reasoning about it.
  • Funneling all writes through a single ordered log gives derived systems a deterministic order to follow, keeping search indexes, caches, and warehouses consistent.
  • The lambda architecture (batch + speed/stream + serving layers) is criticized for duplicated logic; the trend is to unify by reprocessing streams (Kafka + reprocessing).
  • Unbundling the database means treating indexes and materialized views as stream-maintained components — the 'database inside-out' — and designing applications around dataflow and subscribing to changes.
  • Correctness needs the end-to-end argument: exactly-once/dedup ultimately requires end-to-end identifiers (e.g. request IDs); TCP or a DB transaction alone is not enough.
  • Integrity (no corruption or contradiction) usually matters more than timeliness (recency); trust but verify with auditing, and take ethical responsibility for bias, privacy, consent, and surveillance.

Q1 multiple choice

What is DDIA's central argument about data integration in this chapter?

  1. A Because no single tool satisfies all requirements, applications must combine several specialized systems, and the key discipline is distinguishing the system of record from derived data correct
  2. B One database technology can and should handle every access pattern in an application
  3. C Derived data should always be treated as authoritative alongside the source of truth
  4. D You should avoid derived data entirely and read everything from one store

Why: Kleppmann argues real systems compose multiple tools, and clarity comes from knowing which store is the source of truth (system of record) versus which are derived (reconstructable) from it. Derived data is not authoritative — it can always be rebuilt from the system of record.

Q2 multiple choice

Why does funneling all writes through a single totally-ordered log help keep multiple derived systems consistent?

  1. A It makes writes faster by skipping durability
  2. B It gives every derived consumer the same deterministic order of events to apply, so search indexes, caches, and warehouses converge to the same state instead of diverging from concurrent dual writes correct
  3. C It encrypts the writes end to end
  4. D It removes the need for any derived systems at all

Why: A single ordered log means all derived systems process the same events in the same order, so they stay mutually consistent — the fix for the dual-write divergence problem. The benefit is deterministic ordering, not speed or encryption.

Q3 multiple choice

What is the lambda architecture, and what is DDIA's main criticism of it?

  1. A A single stream layer only; criticized for losing historical data
  2. B A purely batch design; criticized for being too slow to ever use
  3. C A batch layer plus a fast stream (speed) layer feeding a serving layer; criticized because you must implement and maintain the same logic twice in two different frameworks correct
  4. D A leaderless replication scheme; criticized for weak consistency

Why: Lambda runs a batch layer (accurate, high-latency) alongside a stream/speed layer (fast, approximate) and merges them in a serving layer, but this forces maintaining duplicate logic in two systems. The trend Kleppmann favors is unifying them — reprocessing the same event log via a stream processor to get both speed and correctness.

Q4 multiple choice

What does 'unbundling the database' (the 'database inside-out') mean?

  1. A Splitting one database into many shards of the same engine
  2. B Removing all indexes to speed up writes
  3. C Storing the database schema outside the database
  4. D Viewing the whole data system as a set of indexes and materialized views maintained by streams — composing separate specialized tools to do what one monolithic database's internals do, coordinated via logs correct

Why: Unbundling treats a database's internal pieces — the log, indexes, materialized views — as separately composable systems kept in sync by event streams, so you assemble the equivalent of a database from best-of-breed tools. This 'inside-out' view is about synchronizing derived state via logs, not about sharding one engine.

Q5 multiple choice

How does DDIA contrast federation with unbundling as approaches to combining data systems?

  1. A Federation provides a unified read interface over disparate stores (a federated query), while unbundling focuses on a unified write path that keeps the separate systems in sync via logs correct
  2. B Federation unifies writes; unbundling unifies reads
  3. C They are two names for the same technique
  4. D Federation is only for batch and unbundling only for streams

Why: Federation (unified query) presents one read interface over heterogeneous underlying stores; unbundling instead concentrates on the write path, using logs to keep independently-specialized systems consistent. The chapter emphasizes the unbundled write-synchronization model as the harder, more valuable problem.

Q6 multiple choice

What does it mean to 'design applications around dataflow,' per DDIA's spreadsheet analogy?

  1. A Store all application data in a spreadsheet file
  2. B Treat derived state as automatically maintained from its inputs — when a value changes, dependent views (all the way to the UI) recompute and update, like cells recalculating in a spreadsheet correct
  3. C Require users to manually refresh every screen
  4. D Compute all state on the server and never cache anything

Why: Like a spreadsheet where changing one cell cascades updates to dependent cells, dataflow design has derived state (including the UI) subscribe to changes in its inputs and update automatically. This extends the write path end-to-end so clients observe fresh derived data reactively.

Q7 multiple choice

According to the end-to-end argument, why is a database transaction or TCP alone insufficient to guarantee exactly-once processing?

  1. A Because transactions are too slow to be practical
  2. B Because TCP already guarantees exactly-once at the application level
  3. C Because deduplication must happen at each individual layer with its own retry semantics, and only an end-to-end identifier (such as a client-generated request ID carried through the whole path) can suppress duplicates caused by retries above those layers correct
  4. D Because databases cannot detect duplicate rows at all

Why: A retry at a higher layer (e.g. a user resubmitting, or an app retrying after a timeout) produces a duplicate that TCP's or a single transaction's local guarantees can't catch. Only an end-to-end unique identifier threaded through the whole request path lets the system recognize and suppress that duplicate.

Q8 multiple choice

How does DDIA suggest enforcing a uniqueness constraint (e.g. a unique username) in a log-based / partitioned system?

  1. A By locking the entire database on every write
  2. B By relying on eventually-consistent replicas to converge
  3. C By using last-write-wins to pick a winner
  4. D By routing all requests for the constrained value through a single partition of a totally-ordered log (partitioned by that value), so a deterministic consumer can accept the first claim and reject conflicts correct

Why: Partitioning the log by the value that must be unique funnels all competing claims into one ordered stream, where a deterministic processor grants the first and rejects the rest. Eventual convergence or LWW would silently allow or drop conflicting claims rather than enforce uniqueness.

Q9 multiple choice

How does DDIA distinguish 'timeliness' from 'integrity,' and which does it argue usually matters more?

  1. A Timeliness means users see up-to-date (recent, consistent) data; integrity means the data has no corruption, loss, or contradiction — and integrity usually matters more because many apps tolerate temporary staleness but not permanent data loss correct
  2. B Timeliness (recency of data) matters more, since users never tolerate any staleness
  3. C They are the same property under different names
  4. D Integrity means low latency and timeliness means durability

Why: Timeliness is about recency/consistency (seeing current data), while integrity is about the absence of corruption or contradiction; a brief violation of timeliness is usually recoverable, but an integrity violation (lost or corrupted data) may be permanent. ACID conflates the two, but they are separable and integrity generally deserves higher priority.

Q10 multiple choice

What is the 'trust, but verify' stance DDIA advocates for data systems?

  1. A Assume hardware and software are fault-free because modern systems are reliable
  2. B Don't blindly assume the layers beneath you are correct; build auditing and self-validating checks (like end-to-end integrity checks / checksums at the application level) to detect corruption rather than silently trusting it correct
  3. C Encrypt all data so it never needs checking
  4. D Trust only the database and never the application code

Why: Because bugs, hardware faults, and misconfiguration do corrupt data in practice, Kleppmann urges building systems that continuously audit and verify their own integrity end-to-end rather than assuming the lower layers are perfect. This mirrors HDFS block checksums, but applied at the application data level.

Q11 multiple choice

Why does immutability of the event log make auditing easier?

  1. A It compresses the audit trail automatically
  2. B Because immutable logs cannot be read by unauthorized users
  3. C Because the append-only log preserves the full history of what happened, you can reconstruct and independently re-derive any state to check whether the current derived data is correct correct
  4. D Because it removes the need to store derived data

Why: An immutable, append-only event log retains the complete sequence of facts, so an auditor can replay it to verify that derived state was computed correctly and detect discrepancies. Mutable state that overwrites history would erase the very evidence auditing depends on.

Q12 multiple choice

In the chapter's ethics discussion, what is a 'feedback loop' risk in predictive analytics?

  2. B The database replicates predictions to too many followers
  3. C Users can see the model's internal weights
  4. D A biased model's decisions shape future data (e.g. denying opportunities to a group), which then reinforces and amplifies the original bias in later model training — a self-perpetuating cycle of discrimination correct

Q14 explain & apply

For a payments ledger, an interviewer asks whether you'd prioritize integrity or timeliness, and why. Define both, make the call, and explain what it means for your design under a failure.

Points a strong answer hits:

  • Timeliness = users see up-to-date, recent/consistent data; integrity = the data is free of corruption, loss, or contradiction.
  • A timeliness violation (brief staleness) is usually temporary and self-correcting; an integrity violation (lost or corrupted money) can be permanent.
  • For a ledger, prioritize integrity: it's acceptable for a balance to be a few seconds stale, but never acceptable to lose or double-count a transaction.
  • Design implication: build the ledger as an append-only, ordered event log so no committed fact is lost or overwritten, and derive balances from it.
  • Under a failure you favor correctness over immediacy — you'd rather delay showing the newest balance than risk a corrupt one.
  • Note ACID conflates the two, but they're separable, and here integrity clearly deserves the higher priority.
Model answer: Timeliness is about recency — users seeing current, consistent data — while integrity is about the absence of corruption, loss, or contradiction. For a payments ledger I prioritize integrity without hesitation: a balance being a few seconds stale is recoverable, but losing or double-counting a transaction is a permanent harm. Concretely I'd model the ledger as an append-only, totally-ordered event log so no committed fact is ever lost or overwritten, and derive balances from it. Under a failure I'd rather delay showing the very latest balance than ever serve a corrupt one — ACID bundles these two together, but they're separable and integrity wins here.

Q15 explain & apply

A user double-clicks 'Pay' and gets charged twice, even though every layer (TCP, the DB transaction) is 'reliable.' Using the end-to-end argument, explain why per-layer guarantees didn't prevent this and how you'd fix it.

Points a strong answer hits:

  • Per-layer reliability only dedups within that layer: TCP guarantees delivery on one connection, a DB transaction is atomic for one execution — neither sees a retry that originates above them.
  • The double-click / app retry is a new request from a higher layer, so the lower layers legitimately process it as a distinct operation.
  • The end-to-end argument: correctness that spans the whole path (dedup across retries) must be enforced at the endpoints, not delegated to intermediate layers.
  • Fix: attach a client-generated unique request ID to the operation and thread it through the entire path.
  • The system records processed request IDs and suppresses (or makes idempotent) any repeat, so the second click with the same ID is recognized as a duplicate and ignored.
  • This makes the write idempotent end-to-end, which is the only place the duplicate is visible.
Model answer: TCP and the DB transaction each only guarantee correctness within their own layer — TCP dedups packets on one connection, the transaction is atomic for one execution — but the double-click is a brand-new request coming from above them, so both layers correctly treat it as a separate, legitimate operation. The end-to-end argument says a guarantee that spans the whole path, like suppressing duplicate submits, has to live at the endpoints, not in the middle. So I'd have the client generate a unique request ID, carry it through the entire request path, and have the server record processed IDs and make the charge idempotent — the second click arrives with the same ID, is recognized as a duplicate, and is ignored. That end-to-end identifier is the only place the retry is actually visible.

Q16 explain & apply

Explain how you'd enforce a unique-username constraint in an unbundled, log-based data system, and why eventual consistency or last-write-wins would be wrong here.

Points a strong answer hits:

  • Partition a totally-ordered log by the value that must be unique (the username), so all competing claims for a given name land in the same partition.
  • Within that single partition, messages have a definite total order.
  • A deterministic consumer reads the claims in order, grants the first claim for a name, and rejects every later conflicting one.
  • This gives a linearizable compare-and-set on the name — the primitive a uniqueness constraint actually needs.
  • Eventual consistency is wrong: concurrent claims on different replicas would both succeed and only later 'converge,' violating uniqueness in the meantime.
  • Last-write-wins is wrong: it silently picks one and discards the other rather than rejecting the conflict, so a user thinks they registered a name they don't own.
Model answer: I'd partition a totally-ordered log by the username itself, so every competing claim for a given name is routed into the same partition where it has a definite order. A deterministic consumer then reads claims in that order, grants the first one for each name, and rejects the rest — that's effectively a linearizable compare-and-set on the username, which is exactly the primitive a uniqueness constraint requires. Eventual consistency would let two concurrent claims on different replicas both succeed and only 'converge' afterward, breaking uniqueness in the window between. Last-write-wins is just as wrong: it silently keeps one write and discards the other instead of rejecting the conflict, so a user believes they registered a name they actually don't own.

Q17 multiple choice

An immutable, append-only event log is in direct tension with which data-protection requirement?

  1. A Purpose limitation — data collected for one purpose should not be reused for another
  2. B The right to erasure — a user can demand their personal data be deleted, but an append-only log is designed never to lose a committed fact correct
  3. C Data portability — a user can demand an export of their data
  4. D Breach notification — a controller must disclose a breach within a fixed window

Why: The architecture's core virtue — nothing committed is ever lost — is exactly what erasure forbids, which is why systems resort to crypto-shredding or storing personal data outside the log behind a reference. Portability and breach notification are satisfiable by an immutable log without any structural conflict.

Q18 multiple choice

Which technique lets a system keep an append-only log while still honoring a deletion request?

  1. A Rewriting the log to remove the affected events and recomputing all downstream derived state
  2. B Marking the events as deleted with a tombstone so consumers skip them
  3. C Keeping personal data outside the log and storing only a reference, or encrypting per-user and discarding the key so the ciphertext becomes unreadable correct
  4. D Reducing the log's retention period so the events expire naturally

Why: Both approaches make the data unrecoverable without violating the log's append-only guarantee — indirection removes it from the log entirely, crypto-shredding leaves bytes that decode to nothing. A tombstone (the tempting distractor) hides data from well-behaved consumers but does not delete it, which does not satisfy erasure.

Q19 multiple choice

A model denies loan applications at a higher rate for one neighborhood, though the applicant's neighborhood was never an input. What is the mechanism?

  1. A A proxy variable — an included feature correlates with the excluded attribute, so removing the attribute does not remove its influence correct
  2. B Overfitting to the training set, which will resolve with more data
  3. C Label leakage from the target variable into the features

Q20 multiple choice

In DDIA's framing, what makes accountability for an algorithmic decision difficult in practice?

  1. A Models are proprietary, so their internals cannot be disclosed
  2. B The decision emerges from data, code, and thresholds owned by different people, so no one party can explain or is answerable for a specific outcome correct
  3. C Regulations do not yet require any explanation of automated decisions

Q21 multiple choice

What does a durable execution engine (workflow engine) add over retrying a multi-step process from the beginning?

  1. A It guarantees each step is idempotent, so retries are always safe
  2. B It runs the steps in parallel, reducing total latency
  3. C It rolls back completed steps automatically when a later step fails
  4. D It persists progress after each step, so a failure resumes from the last completed step rather than replaying side effects already performed correct

Why: Checkpointing each step is the whole point: a process that already charged a card resumes after that step rather than charging again. It does not make your steps idempotent for you (you still must), and automatic rollback is the saga pattern, which compensates rather than undoes.

Q22 explain & apply

You've built an event-sourced system, and legal informs you that users can now request full deletion of their personal data. Walk through your options and make a recommendation.

Points a strong answer hits:

  • State the conflict precisely: the log's guarantee is that no committed fact is ever lost, and erasure requires exactly that loss — this is structural, not a bug.
  • Reject log rewriting as the default: it invalidates every offset and hash downstream, forces a rebuild of all derived state, and destroys the auditability the log existed to provide.
  • Reject tombstones as insufficient — they hide data from cooperative consumers but the data is still there, so the obligation is not met.
  • Option one — indirection: keep personal data in a mutable store and put only a stable reference in the log. Deletion becomes a normal delete; the log keeps its shape and its history.
  • Option two — crypto-shredding: encrypt personal data per user, store the ciphertext in the log, and discard the key on request so the remaining bytes decode to nothing.
  • Recommend indirection as the default for new design because it is simpler to reason about and to prove, and crypto-shredding where the data must remain inline for replay to work.
  • Note the downstream obligation either way: derived views, caches, search indexes and backups also hold the data, so deletion is a pipeline-wide operation and needs to be designed as one.
  • Close on the design lesson — retention and deletion are architectural requirements to be settled before the log shape is chosen, not policies bolted on afterwards.
Model answer: The conflict is structural, not accidental: the log's guarantee is that nothing committed is lost, and erasure demands exactly that. I'd rule out rewriting the log — it invalidates every downstream offset and forces a full rebuild, and it destroys the auditability we built the log for. Tombstones don't satisfy the obligation either, since the data is still there. That leaves two real options: keep personal data in a mutable store and put only a reference in the log, so deletion is an ordinary delete; or encrypt per user and discard the key so the ciphertext decodes to nothing. I'd default to indirection because it's easier to prove to an auditor, and use crypto-shredding where the data has to stay inline for replay to work. Either way deletion is a pipeline-wide operation — derived views, search indexes and backups hold it too. The real lesson is that retention is an architectural requirement, and it should be settled before you choose the log's shape.
