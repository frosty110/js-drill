System map study sheet

What this sheet shows

The mapping store is authoritative, Redis accelerates the read-heavy redirect path, and click analytics leaves the request path through a durable queue. Creation may coordinate for uniqueness; redirection is optimized for latency and availability.

Place every service, store, cache, and asynchronous boundary before walking either API.

Trace the flow

  1. Create — The authenticated client submits a long URL through the edge to the stateless URL service.
  2. Generate and persist — Allocate a unique ID, encode it in Base62, and durably store code → URL before responding.
  3. Redirect — Resolve GET /{code} from Redis when possible and fall back to a point read from the mapping store.
  4. Measure asynchronously — Publish click events to a queue so analytics workers and the warehouse cannot delay redirects.

What this belongs to

A service (like TinyURL / bit.ly) that maps a long URL to a short unique code and redirects on lookup. The signature challenge is generating short, unique, collision-free codes at write scale while serving an extremely read-heavy redirect workload cheaply.
