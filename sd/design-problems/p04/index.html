Design a Video Streaming Service

A YouTube/Netflix-style platform where creators upload video, the system transcodes it into multiple resolutions/bitrates chunked into short segments, and viewers stream it with adaptive bitrate over a CDN. The signature challenges are the asynchronous transcoding pipeline and pushing the enormous read bandwidth to the edge.

Results carried by this link

Key ideas

  • Upload once, transcode asynchronously via a queue of workers into a ladder of resolutions/bitrates, each chunked into ~2–10s segments (HLS/DASH).
  • Adaptive bitrate (ABR) is client-driven: the player measures throughput/buffer and requests the next segment at the bitrate it can sustain, using a manifest (.m3u8/.mpd) that lists all variants.
  • The CDN is the core scaling lever — 99%+ of egress bytes are served from edge caches, not origin; video is immutable and cache-friendly.
  • Separate the control plane (metadata service, small relational/NoSQL rows) from the data plane (huge immutable segment blobs in object storage + CDN).
  • View counts are aggregated approximately and asynchronously (stream → batch/count-min), never a synchronous row increment per view.
  • Read:write ratio is extreme (millions of reads per upload); design the whole system around cheap, cacheable, geo-distributed reads.

Q1 explain & apply

You're asked to design YouTube. Scope the functional and non-functional requirements out loud before drawing anything — what do you build, and what are the hard non-functional constraints?

Points a strong answer hits:

  • Functional: upload video, transcode/process it, stream playback with adaptive quality, browse/search metadata, view counts, comments/likes (can descope).
  • Explicitly descope recommendations, monetization, live streaming, DRM as v2 (name them so the interviewer knows you know).
  • Non-functional: extremely read-heavy (reads >> writes), high availability for playback, low startup latency + no rebuffering, global low-latency delivery.
  • Durability of the master upload is critical (never lose a creator's source); eventual consistency is fine for view counts/metadata propagation.
  • Scale anchor: hundreds of millions of DAU, huge egress bandwidth is the dominant cost.
Model answer: Core features are upload, asynchronous transcoding, adaptive-bitrate playback, and metadata/browse; I'd descope recommendations, ads, live, and DRM up front. The defining non-functional traits are an extreme read:write ratio, global low-latency playback with fast startup and minimal rebuffering, and high availability on the read path — while the creator's master file must be durably stored. Consistency can be relaxed almost everywhere on reads (view counts and metadata can lag seconds), which is what lets us lean entirely on caching and a CDN.

Q2 explain & apply

Do a back-of-envelope capacity estimate: uploads/day, storage growth per year, and — the number that dominates — egress bandwidth. Use round numbers and show the math.

Points a strong answer hits:

  • Uploads: ~500 hours/min uploaded (YouTube-scale) ≈ 30k hours/hr; or pick simpler: 1M uploads/day, avg 10 min each.
  • Storage: after transcoding, one source fans out to ~5–6 renditions. A 10-min 1080p video ≈ a few hundred MB; times renditions ≈ ~1 GB stored per upload. 1M/day × 1 GB ≈ 1 PB/day of new stored bytes (order of magnitude).
  • Read:write: if each video averages even a few hundred views, reads dwarf writes by 100–1000×.
  • Egress is the crux: peak concurrent streams × avg bitrate. e.g. 10M concurrent viewers × ~5 Mbps ≈ 50 Tbps of egress — this MUST come from the CDN edge, not origin.
  • Conclusion: storage is large but linear; bandwidth is the cost/scaling driver and forces CDN offload.
Model answer: Say ~1M uploads/day at ~10 min each; transcoding into ~5 renditions makes roughly 1 GB stored per upload, so ~1 PB/day of new storage — large but linear, and object storage handles it. The number that actually shapes the design is egress: at, say, 10M concurrent viewers pulling ~5 Mbps each that's ~50 Tbps, which no origin fleet can serve. That single figure is why the entire architecture is built to serve 99%+ of bytes from CDN edge caches, with origin only handling cache-misses and the write path.

Q3 explain & apply

Sketch the core APIs. What are the key endpoints for the upload path and the playback path, and why does upload need more than a single POST?

Points a strong answer hits:

  • Upload: request an upload URL (POST /videos → returns videoId + presigned/resumable upload target), then client uploads bytes directly to object storage (resumable/multipart for large files).
  • Client uploads to blob store directly, not through the app tier — offloads bandwidth and enables resumable chunks.
  • On upload complete, a finalize call (or storage event) enqueues the transcoding job.
  • Playback: GET /videos/{id} → metadata + the manifest URL; player then fetches .m3u8/.mpd manifest and segment URLs (all CDN-fronted).
  • Metadata/browse: GET /videos/{id}, search, and an async POST /videos/{id}/view (fire-and-forget) for counting.
Model answer: Upload is a two-step handshake: POST /videos returns a videoId plus a resumable/presigned upload target, the client streams the raw bytes directly to object storage (multipart so a dropped connection resumes), and a finalize/storage-event enqueues transcoding — you never funnel the raw upload through your app servers. Playback is GET /videos/{id} for metadata and a manifest URL, then the player pulls the .m3u8/.mpd manifest and individual segments straight from the CDN. Views are a separate fire-and-forget POST so counting never blocks playback.

Q4 explain & apply

Draw the high-level architecture and name the data stores. Which components are on the control plane vs. the data plane, and what's the key metadata schema?

Points a strong answer hits:

  • Data plane: object storage for master + transcoded segments (immutable blobs), fronted by a CDN. This is where the bytes and bandwidth live.
  • Control plane: metadata service backed by a DB (relational or NoSQL) holding video rows; a transcoding queue + worker fleet; a view-count aggregation pipeline.
  • Upload → blob store → event → queue → transcoding workers → write segments back to blob store + update metadata status.
  • Metadata schema: videos(id, uploader_id, title, description, status[uploading|processing|ready|failed], duration, created_at, manifest_url) plus a renditions table (resolution, bitrate, segment path).
  • Search/browse index (e.g. Elasticsearch) is a separate derived store fed from metadata.
  • CDN + edge caches sit between viewers and origin object storage.
Model answer: I split control plane from data plane. The data plane is object storage holding the immutable master and all transcoded segments, fronted by a CDN — that's where the petabytes and terabits live. The control plane is a metadata service over a DB with a videos row (id, uploader, title, status, duration, manifest_url) and a renditions table, plus the transcoding queue+workers and the view-count pipeline. Flow: upload lands in the blob store, a storage event enqueues a transcode job, workers write segments back and flip the video's status to ready, and a separate search index is derived from metadata.

Q5 explain & apply

Deep dive #1 — the transcoding pipeline. A creator uploads one 4K master. Walk through how it becomes streamable, and why this is a distributed job rather than one big ffmpeg call.

Points a strong answer hits:

  • Master upload triggers a job on a queue; a pool of stateless transcoding workers pull jobs (decouples burst uploads from fixed worker capacity).
  • Split the source into chunks (by GOP/keyframe boundaries) so chunks transcode in parallel across many workers — critical for throughput and latency on long videos.
  • Each chunk is encoded into the full ladder of renditions (e.g. 240p/360p/480p/720p/1080p/4K at target bitrates), then segmented into ~2–10s HLS/DASH segments.
  • Generate the manifest (.m3u8/.mpd) listing every variant + segment; write segments + manifest to object storage.
  • Mark the video ready (possibly progressively — low res ready first so playback can start before 4K finishes).
  • Idempotency + retries: a failed chunk re-runs without redoing the whole video; workers are stateless and horizontally scalable.
Model answer: The upload drops a job on a queue that a stateless worker pool consumes, which absorbs upload bursts against fixed capacity. A worker splits the master on keyframe boundaries into chunks so a long video fans out across many machines in parallel; each chunk is encoded into the whole bitrate ladder and cut into a few-second HLS/DASH segments. We then emit the manifest listing every rendition and segment, write it all to object storage, and flip status to ready — often progressively, exposing low resolutions first so playback can begin before 4K finishes. Chunking also makes retries cheap: a failed segment re-encodes in isolation instead of redoing the entire file.

Q6 multiple choice crux

Why is video chunked into short (~2–10s) segments with a manifest, rather than streamed as one continuous file per resolution?

  1. A Short segments let the player switch bitrate at each segment boundary based on measured throughput, and each segment is an independently cacheable immutable object at the CDN edge correct
  2. B It lets the database store each segment as a row so queries stay under the 1 MB row limit
  3. C Segments must be short so the transcoding worker can hold the entire segment in a CPU register during encoding
  4. D The TCP protocol cannot transfer files larger than a few megabytes, so video must be split to fit

Why: Segmentation is what makes adaptive bitrate possible: because the manifest lists the same content at multiple bitrates and the timeline is broken into short independent segments, the player can pick a different bitrate for the very next segment when the network changes. As a bonus each segment is a small immutable object, ideal for CDN caching. The other options are fabricated constraints — there is no such TCP limit, and segments aren't DB rows.

Q7 explain & apply crux

Deep dive #2 — adaptive bitrate streaming. Explain exactly how the client decides which quality to fetch, and what signals drive an up-shift or down-shift.

Points a strong answer hits:

  • The player fetches the manifest, which advertises each rendition's bitrate/resolution.
  • For each upcoming segment the player estimates available bandwidth (recent segment download throughput) and monitors its buffer level.
  • Down-shift quickly when throughput drops or buffer drains toward empty (avoid a stall/rebuffer); up-shift cautiously when throughput is comfortably above the next rung and buffer is healthy.
  • Startup: begin at a low bitrate for fast time-to-first-frame, then ramp up (or use buffer-based ABR like BOLA).
  • The decision is entirely client-side; the server/CDN just serves whichever segment URL is requested — keeps the server stateless and cacheable.
  • Tradeoff: aggressive up-shifting risks rebuffering; conservative wastes available quality — ABR algorithms balance startup latency, rebuffer rate, and average bitrate.
Model answer: The player reads the manifest to learn the available bitrate rungs, then for each next segment it estimates recent download throughput and watches its buffer occupancy. If throughput falls or the buffer is draining it drops a rung immediately to avoid a stall; if throughput is comfortably above the next rung and the buffer is healthy it steps up. It starts low for a fast first frame and ramps. Crucially the logic is all client-side — the CDN just serves whatever segment URL is asked for, so the servers stay stateless and every segment stays cacheable. The whole game is trading off startup latency, rebuffer rate, and average quality.

Q8 multiple choice crux

The system must count video views at massive scale. What's the right approach?

  1. A Synchronously UPDATE videos SET views = views + 1 on the primary DB for every playback
  2. B Emit a view event to a stream (e.g. Kafka), aggregate asynchronously/approximately, and periodically write back a count — accepting eventual, slightly-approximate totals correct
  3. C Store one row per individual view and run a COUNT(*) on the reads path each time the count is displayed
  4. D Keep the exact count in a single Redis key incremented on every view, as the sole source of truth with no durable backing

Why: A synchronous per-view DB increment creates a write hotspot on popular videos and couples counting to playback latency — untenable at millions of views. The scalable pattern is to emit view events to a log/stream and aggregate them asynchronously (batch or streaming, often approximate/deduplicated), writing the rolled-up count back periodically. COUNT(*) per display is far too expensive, and a lone un-backed Redis counter risks data loss; a real design might use Redis for a hot approximate count but backed by the stream pipeline.

Q9 explain & apply

Staff-level: what breaks at global scale, and how do you handle hot content, geography, and the storage cost of unpopular videos?

Points a strong answer hits:

  • Hot content (viral video) → CDN handles the fan-out; ensure it's cached at edge; origin only sees cache-fill, not per-viewer load. Pre-warm/push popular content to edges.
  • Geography → multi-region CDN PoPs + regional origins; route viewers to nearest edge; replicate popular content, pull-through cache the long tail.
  • Storage cost of the long tail → tier cold/rarely-watched videos to cheaper storage (e.g. infrequent-access/archive), keep only popular renditions hot; possibly transcode extra renditions lazily on first request.
  • Upload/transcode bursts → queue absorbs spikes; autoscale the worker pool; prioritize (e.g. smaller creators vs. re-encodes).
  • Failure modes: a rendition missing → player falls back to another rung; origin outage → serve from edge cache; partial transcode → keep video in processing.
  • Consistency: metadata/view counts eventually consistent; the master file must be durably replicated (multi-AZ/region) so it's never lost.
Model answer: At global scale the CDN is what absorbs virality — a hot video is served from edge caches so origin only sees cache-fills, and I'd pre-warm known-popular content to PoPs. Geographically I route to the nearest edge with regional origins, replicating popular renditions and pull-through-caching the long tail. The long tail is also a cost problem, so cold videos tier down to archival storage and I'd consider transcoding rare renditions lazily on first request rather than eagerly for everything. Uploads spike, so the queue plus an autoscaled worker pool smooths bursts. Throughout, metadata and view counts are allowed to be eventually consistent, but the creator's master is durably replicated across AZs/regions because that's the one thing we can never regenerate.
