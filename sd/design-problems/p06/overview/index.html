Chat System system map

System map study sheet

What this sheet shows

So two independent forces: the concurrent-connection count sizes the gateway/connection tier — maybe ~500 boxes at 100k sockets each — while message volume and group fan-out drive storage and the delivery design.

Trace the flow

  1. High-level architecture — Long-lived socket gateways route messages through durable conversation storage and online-session metadata.
  2. Route a message to the recipient socket — The session directory identifies the gateway holding a user’s live connection; a broker bridges sender and recipient gateways.
  3. Durable offline delivery — The message is committed before acknowledgement; offline recipients resume from their last delivered sequence.
  4. Shard group fan-out by conversation — A conversation coordinator orders operations, while regional fan-out workers deliver to local gateways without one server owning every member.

What this belongs to

A WhatsApp/Messenger-style messaging service delivering messages in real time over persistent WebSocket connections. The signature challenges are mapping each user to the server holding their live connection, ordering and durably storing messages, delivering to offline users via store-and-forward + push, and fanning out group messages.
