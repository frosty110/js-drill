Design a Leaderboard

A real-time ranking board for a game or app: players submit scores and read the top-K plus their own rank, updated live. The signature challenge is maintaining rank ordering under a high write rate — a Redis sorted set makes score updates and top-K reads O(log N), while cheaply answering a specific user's exact rank at scale is the genuinely hard part.

Components in play 4

  • Cache signature — Top-N slices per leaderboard window, so the overwhelmingly common 'show me the top 100' read never touches the underlying ranking structure.
  • Hot-Key Mitigation signature — One popular leaderboard absorbs most of the reads and writes, so its sorted set has to be split or replicated away from the others.
  • Sharding signature — Partitions scores by leaderboard and time window; one global sorted set would concentrate every write in the system on a single node.
  • Pre-Aggregation & Rollups signature — Scores are maintained as running totals rather than recomputed, so a read is a range query on a sorted set instead of a scan.

The brief

Functional requirements

  • Submit/update a player's score; read top-K; read one user's exact rank plus nearby neighbours; multiple boards (global, per-region, per-mode).
  • Time windows — daily / weekly / monthly / all-time — each queryable independently.
  • Tie-breaking must be specified up front so equal scores have a stable order.

Scale & constraints

  • 20M DAU × ~10 matches → ~200M updates/day, ~2–3K writes/s avg, ~20K peak
  • Reads dominate: ~12K/s average, up to ~100K peak, though top-K is highly cacheable
  • A sorted-set entry is ~100 B with skiplist overhead → a 20M-player board is ~2 GB; a 100M all-time board ~10 GB
  • Rank should reflect a score within seconds; <50ms for top-K and my-rank

Key ideas

  • A Redis sorted set (ZSET) is the core data structure: ZADD/ZINCRBY to update a score, ZREVRANK for a user's rank, ZREVRANGE for top-K — all O(log N) or better, keeping ordering always-sorted instead of sorting on read.
  • A relational 'ORDER BY score' on every read is O(N log N) per query and can't cache well under constant score churn; the ZSET amortizes ordering into each write.
  • Getting one arbitrary user's exact global rank at massive scale is the expensive operation — ZREVRANK is O(log N) on a single node but exact rank across a sharded board requires merging shard ranks.
  • Shard by score range so each shard owns a contiguous band; a user's global rank = (count in higher-scoring shards) + local rank within its shard.
  • Time-windowed boards (daily/weekly/all-time) use bucketed keys like lb:daily:2026-07-10 with TTLs, so windows expire cheaply and are queried independently.
  • Ties are broken deterministically (e.g. encode timestamp into the score's fractional/low bits, or earlier-achiever wins) so rank is stable and reproducible.
  • Redis is the fast serving layer but volatile — a durable store (the game DB / an append log) is the source of truth so the ZSET can be rebuilt after failure.

Q1 explain & apply

Scope a real-time game leaderboard. What are the functional requirements and the non-functional targets that shape the design?

Points a strong answer hits:

  • Functional: submit/update a player's score; read top-K (e.g. top 100); read a specific user's rank and nearby neighbors (the 'players around me' view); support multiple boards (global, per-region, per-mode).
  • Time windows: daily / weekly / monthly / all-time boards, each queryable independently.
  • Non-functional: very high write rate (every match end updates a score), low-latency reads for top-K and my-rank (<50ms), read-heavy but write-significant.
  • Freshness: near-real-time — rank should reflect a score within seconds; brief staleness is acceptable, exact-to-the-millisecond is not required.
  • Scale: state it — e.g. 100M players, tens of millions active/day, millions of score updates/hour at peak.
  • Tie-breaking and determinism must be specified up front (equal scores need a stable order).
Model answer: Functionally: players submit scores, and clients read the top-K, a given user's exact rank, and the neighbors around that user, across multiple boards (global, regional, per-mode) and time windows (daily/weekly/all-time). The system is read-heavy but with a serious write rate since every match end mutates a score, and it needs sub-50ms top-K and my-rank reads with only a few seconds of acceptable staleness. At, say, 100M players and millions of updates an hour, the two hard non-functionals are keeping the board sorted under constant write churn and answering an arbitrary user's exact rank fast — and I'd nail down deterministic tie-breaking early so ranks are stable.

Q2 explain & apply

Do a capacity estimate: from active players and match rate, derive write QPS, read QPS, and the memory footprint of the sorted set.

Points a strong answer hits:

  • Assume 100M registered, 20M DAU; each plays ~10 matches/day → ~200M score updates/day ≈ ~2.3K writes/sec average, ~5-10× at peak ≈ ~20K writes/sec.
  • Reads: players check rank/top-K more than they play — say 5 reads per match → ~1B reads/day ≈ ~12K/sec avg, peak ~50-100K/sec (heavily cacheable for top-K).
  • ZSET memory: each member ≈ key/user-id (~20-40 bytes) + score (8 bytes) + skiplist/dict overhead (~64-100 bytes) ≈ ~100 bytes/entry.
  • 20M active entries × ~100 bytes ≈ ~2 GB per board — fits comfortably in one Redis node's RAM; 100M all-time entries ≈ ~10 GB, approaching a single-node limit → shard.
  • Top-K reads are trivially cacheable (top 100 changes slowly relative to read volume); my-rank reads are the ones that hit the ZSET hard.
  • Multiple boards (global + regions + daily/weekly windows) multiply memory, reinforcing sharding + TTL'd window keys.
Model answer: Take 20M DAU at ~10 matches each: ~200M updates/day, so ~2-3K writes/sec average and maybe 20K at peak. Reads dominate — players check standings more than they play — so on the order of 12K/sec average and up to ~100K at peak, though top-K is highly cacheable. Memory-wise a sorted-set entry is roughly 100 bytes with skiplist overhead, so a 20M-active board is ~2 GB (fine on one node) but a 100M all-time board is ~10 GB and starts pushing single-node limits. That, plus wanting per-region and per-window boards, is what pushes me toward sharding and TTL'd window keys rather than one giant ZSET.

Q3 explain & apply

Define the core API and the Redis operations each endpoint maps to.

Points a strong answer hits:

  • POST /score {board, userId, score} → ZADD board score userId (absolute) or ZINCRBY board delta userId (cumulative) — choose based on whether scores are set or accumulated.
  • GET /leaderboard/{board}/top?k=100 → ZREVRANGE board 0 k-1 WITHSCORES (highest first).
  • GET /leaderboard/{board}/rank/{userId} → ZREVRANK board userId (0-based rank; +1 for human rank) and ZSCORE for the value.
  • GET /leaderboard/{board}/around/{userId}?n=5 → ZREVRANK to find position, then ZREVRANGE pos-n pos+n WITHSCORES for the neighbor window.
  • Board key encodes window + scope: e.g. lb:global:daily:2026-07-10, lb:us-east:alltime.
  • Writes go through a service that also persists to the durable store and applies tie-break encoding before ZADD.
Model answer: Submitting a score is ZADD board score userId when scores are absolute, or ZINCRBY when they accumulate; top-K is a single ZREVRANGE board 0 K-1 WITHSCORES; a user's rank is ZREVRANK board userId (plus ZSCORE for the value); and the 'players around me' view is a ZREVRANK to locate the position followed by a ZREVRANGE of the surrounding window. The board key itself encodes scope and window — lb:global:daily:2026-07-10 or lb:us-east:alltime — and every write flows through a service that also writes the durable store and applies the tie-break encoding before the ZADD.

Q4 multiple choice crux

Why use a Redis sorted set instead of storing scores in SQL and running SELECT ... ORDER BY score DESC LIMIT 100 on each read?

  1. A SQL cannot store integers large enough for game scores
  2. B The sorted set keeps entries continuously ordered so top-K and rank are O(log N), whereas the SQL query re-sorts up to O(N log N) per read and caches poorly under constant score churn correct
  3. C Redis is durable and SQL is not, so Redis never loses the leaderboard
  4. D SQL cannot compute a specific row's rank at all

Why: The sorted set amortizes ordering into each write (an O(log N) skiplist insert), so top-K is an O(log N + K) range read and a user's rank is an O(log N) ZREVRANK — always fresh, no re-sort. The SQL approach re-derives the order per query, which is expensive at scale and hard to cache because scores change constantly, invalidating any cached page. SQL can compute rank (via window functions/counts) and is in fact the more durable store — so those options are wrong; the real reason is the sorted-set's always-sorted structure and read complexity.

Q5 explain & apply crux

The signature deep-dive: getting one arbitrary user's exact global rank is the expensive operation at scale. Why, and how do you shard the board and still answer it?

Points a strong answer hits:

  • On a single node ZREVRANK is O(log N) and cheap — the problem appears once the board is too big for one node and must be sharded.
  • Exact rank is inherently global: your rank = the count of everyone scoring higher, which spans all shards, so no single shard knows it locally.
  • Shard by score range (not by user hash): each shard owns a contiguous score band, so higher-scoring shards are fully 'above' a user by definition.
  • Global rank = sum of ZCARD of all strictly-higher shards + local ZREVRANK within the user's own shard — a bounded fan-out (number of shards), not a full scan.
  • Keep per-shard counts/boundaries cached so the 'count higher shards' step is O(#shards); rebalance bands as the score distribution drifts.
  • If exact rank isn't required, approximate it: histogram/percentile buckets give 'top ~5%' in O(1) and dodge cross-shard fan-out entirely — a common real-world compromise.
Model answer: On one node ZREVRANK is a cheap O(log N), so the pain only starts when the board outgrows a single node and shards. Exact rank is fundamentally global — it's the count of everyone above you — so no single shard can answer it alone. The trick is to shard by score range rather than by user: each shard owns a contiguous band, so a user's global rank is the summed cardinality of all strictly-higher shards plus its local ZREVRANK within its own band, which is a fan-out over the number of shards, not a full scan. I cache each shard's boundaries and counts so the 'count above' step is O(#shards), and rebalance bands as the distribution drifts. When exact rank isn't truly needed, I'd switch to percentile buckets — 'you're in the top 3%' — which is O(1) and sidesteps the cross-shard fan-out entirely.

Q6 explain & apply

How do you implement time-windowed boards (daily/weekly/all-time) and handle ties deterministically?

Points a strong answer hits:

  • Windowed boards = separate keys with the window baked in: lb:daily:2026-07-10, lb:weekly:2026-W28, lb:alltime; a score update writes to all relevant window keys.
  • Set a TTL on window keys (e.g. daily key expires after 48h) so old windows self-clean; all-time has no TTL and is the one to shard.
  • Weekly/monthly can be derived by unioning day keys (ZUNIONSTORE) instead of double-writing, trading read cost for write simplicity — a real tradeoff to name.
  • Ties: sorted sets order equal scores lexicographically by member, which is arbitrary/unfair — instead encode the tiebreak into the score.
  • Common trick: composite score = primary_score in the high bits + inverted timestamp in the low bits (earlier achiever ranks higher on equal score), stored as one 64-bit/float value.
  • This keeps a single ZADD and a single ZREVRANK while making ranks deterministic and reproducible across rebuilds.
Model answer: Each window is just a differently-keyed sorted set — lb:daily:2026-07-10, lb:weekly:2026-W28, lb:alltime — and a score update fans out to the relevant ones. Daily/weekly keys carry a TTL so they self-expire, while all-time is the durable, shard-worthy one; alternatively I can avoid double-writing and derive weekly on read by ZUNIONSTORE-ing the day keys, trading read cost for write simplicity. For ties I don't rely on Redis's lexicographic member ordering because it's unfair — I encode a composite score with the real score in the high bits and an inverted timestamp in the low bits, so an earlier achiever wins an equal score. That keeps everything a single ZADD/ZREVRANK while making ranks deterministic and reproducible if I ever rebuild the board.

Q7 multiple choice crux

You shard the leaderboard across nodes to fit memory. To answer 'top 100 globally' efficiently, which sharding scheme is best?

  1. A Hash the user ID to a shard, then query every shard for its local top 100 and merge
  2. B Put every write on a single shard and replicate it read-only to the others
  3. C Shard by score range so the highest band's shard already holds (most of) the global top-K, minimizing fan-out correct
  4. D Randomly assign each score update to a shard to spread load evenly

Why: Range-sharding by score means the top-K lives in (or starts at) the highest-score shard, so top-100 is answered from essentially one shard instead of scatter-gathering from all of them. Hash-by-user spreads a given score band across every shard, forcing you to query all shards and merge for any top-K or rank query. A single write shard just recreates the single-node bottleneck, and random assignment has the same scatter-gather problem as hashing. Range-sharding aligns the physical layout with the query (ordering), which is the whole point.

Q8 explain & apply

Redis is in-memory and volatile. How do you make the leaderboard durable and recover it after a Redis node failure?

Points a strong answer hits:

  • Treat Redis as the fast serving/index layer, not the source of truth: every score write is also persisted to a durable store (game DB row and/or an append-only score-events log).
  • On Redis loss, rebuild the ZSET by replaying the durable scores — for all-time, from the DB's current-best per user; for windows, from the events log filtered to the window.
  • Use Redis persistence (AOF/RDB) + replicas for fast failover so you rarely do a full rebuild; replicas also serve reads.
  • Make writes idempotent (ZADD with absolute score is naturally idempotent; ZINCRBY needs dedupe keys) so replay/retries don't double-count.
  • Warm caches / accept brief staleness during rebuild; top-K can be served from the DB temporarily.
  • Cross-region: async-replicate the durable store; regional Redis boards are rebuildable locally, keeping the volatile layer disposable.
Model answer: I treat Redis as a rebuildable index, not the truth: every score update also lands in a durable store — the game DB's best-score-per-user for all-time, plus an append-only events log for windowed boards. If a node dies I fail over to a replica (Redis AOF/RDB + replication makes this fast), and worst case I rebuild the ZSET by replaying the durable scores. I keep writes idempotent — absolute ZADD is naturally idempotent, and cumulative ZINCRBY gets a dedupe key — so replays don't double-count, and during a rebuild I can temporarily serve top-K from the DB and accept a few seconds of staleness. Because the durable store is the authority, the whole in-memory layer stays disposable and regionally rebuildable.

Q9 explain & apply

Staff-level: at peak, hot boards get hammered by both writes and my-rank reads. Where does this design strain, and how do you evolve it?

Points a strong answer hits:

  • Write hotspot: a single mega-board's ZSET is one node's write throughput ceiling — range-shard it and/or batch/coalesce rapid updates for the same user before ZADD.
  • Read hotspot on top-K: cache the top-K page (it changes slowly) at the edge/app layer with a short TTL, serving the vast majority of reads without touching Redis.
  • my-rank reads are the un-cacheable tail (unique per user) — this is the load that justifies sharding-by-score and/or serving approximate percentile rank instead of exact.
  • Consistency tradeoff: accept eventual/near-real-time rank; a few seconds of staleness lets you batch writes and cache reads aggressively.
  • Abuse/correctness: validate/authenticate score submissions server-side (anti-cheat), rate-limit, and reconcile Redis against the durable store periodically to catch drift.
  • Global scale: per-region boards with a rolled-up global view (union/merge) avoids one global write bottleneck while still offering a global ranking.
Model answer: The two strain points are the single-board write ceiling and the un-cacheable my-rank read. I relieve writes by range-sharding the board and coalescing rapid same-user updates before the ZADD, and I relieve top-K reads by caching that slowly-changing page at the app/edge with a short TTL so most reads never hit Redis. The genuinely hard load is per-user exact rank, which is unique per request — that's what justifies score-range sharding, and where I'd offer approximate percentile rank when 'top 3%' is good enough. I lean on near-real-time consistency to enable that batching and caching, add server-side score validation and rate limits for anti-cheat, periodically reconcile Redis against the durable store, and go per-region-with-a-global-rollup so no single node is the global write bottleneck.
