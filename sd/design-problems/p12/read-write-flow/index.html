Read Write Flow

Read flow study sheet

What this sheet shows

Write-through updates the cache and the DB together on every write, so a subsequent read hits an already-fresh cache entry — strong read-after-write consistency — but every write pays the cost of two synchronous writes (higher write latency, and it caches data that may never be read).

Trace the flow

  1. Key Hash — Key Hash; then continue to Hash Ring.
  2. Hash Ring — Hash Ring; then continue to Node A Token 1.
  3. Node A Token 1 — Node A Token 1; then continue to Node B Token 1.
  4. Node B Token 1 — Node B Token 1; then continue to Node A Token 2.
  5. Node A Token 2 — Node A Token 2; then continue to Node C Token 1.
  6. Node C Token 1 — Node C Token 1; verify the result and expose the outcome.

What this belongs to

A Redis/Memcached-cluster-style in-memory cache spread across many nodes, sitting in front of a slower datastore. The signature challenge is distributing keys across nodes so that adding or removing a node remaps as few keys as possible — consistent hashing — while handling replication, eviction, the hot-key problem, and cache-DB coherence.
