Payment System (Wallet / Ledger) system map

System map study sheet

What this sheet shows

QPS is modest vs social systems, but every write must be ACID and durable — you can't drop or approximate one.

Trace the flow

  1. High-level architecture — The payment API, immutable double-entry ledger, external processor workflow, and reconciliation loop are separate correctness boundaries.
  2. Idempotent payment command — Reserve the idempotency key and transactionally bind it to one payment result before any retry can repeat the side effect.
  3. Every transfer creates balanced ledger entries — A transaction debits one account and credits another by the same amount, preserving an auditable invariant.
  4. Outbox workflow plus reconciliation — Local ledger state and outbound processor commands commit together; reconciliation later compares both systems and repairs discrepancies.

What this belongs to

A system that moves money correctly — charging cards, crediting wallets, paying out — where integrity beats timeliness. The signature concerns are idempotency (exactly-once charge despite retries), a double-entry ledger for auditable correctness, and orchestrating an external gateway with saga/compensation while staying PCI-compliant.
