Job scheduler system map

System map study sheet

What this sheet shows

Each scales on a different axis, and a saturated worker fleet must never stall scheduling. Submission is durable and immediate; execution is asynchronous.

Show why submission, scheduling, queueing and execution are separate components.

Trace the flow

  1. Accept and persist — The API records the job durably and returns — submission is not execution.
  2. Scan for due work — Schedulers query an index on next-run-time roughly once a second.
  3. Claim exclusively — A conditional update ensures exactly one replica enqueues each job.
  4. Queue by class — Ready work is partitioned so long jobs cannot block short ones.
  5. Lease and execute — Workers hold a renewable lease and report the outcome.

What this belongs to

Run millions of scheduled and on-demand jobs across a worker fleet, on time and without accidental duplicates. The signature challenge is that at-least-once execution is the only guarantee a distributed system can actually offer, so correctness has to come from idempotent jobs rather than from perfect delivery.
