Stopping three schedulers firing one job three times

Mechanism study sheet

What this sheet shows

Every replica sees the same due rows, so without coordination each enqueues the job. A conditional update lets all replicas scan while only one wins.

Show the duplicate-run bug and the two ways to prevent it.

Trace the flow

  1. All replicas scan — Each finds the same rows past their next-run time.
  2. Attempt a conditional claim — Update to claimed only where the state is still pending.
  3. One update succeeds — That replica enqueues the job exactly once.
  4. The others no-op — Zero rows updated means move on without enqueueing.

What this belongs to

Run millions of scheduled and on-demand jobs across a worker fleet, on time and without accidental duplicates. The signature challenge is that at-least-once execution is the only guarantee a distributed system can actually offer, so correctness has to come from idempotent jobs rather than from perfect delivery.
