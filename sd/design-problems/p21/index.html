Design a Distributed Key-Value Store

Build a Dynamo/Cassandra-style durable key-value store: consistent hashing for placement, quorum replication for tunable consistency, and anti-entropy to repair the divergence that leaderless writes inevitably create.

Canonical Design Problems 9 questions

Results carried by this link

Key ideas

  • Consistent hashing with virtual nodes places keys and rebalances only ~1/N of them when membership changes.
  • Leaderless replication means any replica accepts a write — availability comes first, and the cost is that replicas diverge.
  • R + W > N gives read-your-writes overlap; the operator tunes R and W per query instead of the system picking one consistency level.
  • Divergence is repaired on three timescales: read repair (on access), hinted handoff (on brief outage), and Merkle-tree anti-entropy (in the background).
  • Last-write-wins silently loses concurrent updates; version vectors detect concurrency and hand the conflict to the application.
  • The storage engine is an LSM tree — writes append to a memtable and flush to immutable SSTables, so writes are sequential and compaction pays the cost later.
  • Gossip spreads membership without a coordinator, which is what keeps the cluster masterless and avoids a control-plane single point of failure.

Q1 explain & apply crux

Scope a distributed key-value store. What are the functional requirements, and which non-functional choice defines the entire design?

Points a strong answer hits:

  • Functional: get(key), put(key, value), delete(key) over opaque values; no joins, no secondary indexes, no multi-key transactions in the base design.
  • Data must be distributed across many nodes so total capacity and throughput exceed one machine, and the cluster must survive node loss without data loss.
  • The defining choice is the CAP posture: this is an AP store — always writable, tolerating temporary inconsistency — versus a CP store that refuses writes during a partition.
  • Non-functional: single-digit-millisecond p99 for both reads and writes, linear scalability by adding nodes, no single point of failure.
  • Durability target: survive f simultaneous node failures, which sets the replication factor N.
  • Say what's out of scope: range scans over arbitrary keys, strong multi-key transactions, and rich queries all push toward a different design.
Model answer: The interface is deliberately tiny — get, put, delete on opaque values — because everything interesting is in the distribution, not the query model. The choice that defines the whole design is the CAP posture: I'd build this as an AP store that always accepts writes and tolerates temporary divergence, which is what a shopping cart or session store wants. If the requirement were 'never serve a stale read', I'd be designing a consensus-replicated CP store instead and giving up write availability during partitions. Targets: single-digit-ms p99, linear scale-out, no single point of failure, and survive f node failures — which is what sets the replication factor.

Q2 explain & apply

Work the numbers: sizing for 100 TB of logical data at 1M ops/sec.

Points a strong answer hits:

  • With replication factor N=3, 100 TB logical is 300 TB physical before compression and compaction overhead.
  • LSM compaction needs headroom — budget ~1.5x the steady-state footprint, so plan closer to 450 TB of provisioned storage.
  • Per node: with ~4-8 TB usable per node, that's roughly 60-110 nodes. State the assumption rather than a bare number.
  • 1M ops/sec spread over ~100 nodes is ~10K ops/sec per node — comfortable for an LSM engine on SSD, so the cluster is likely storage-bound rather than CPU-bound.
  • Each read at quorum (R=2) contacts 2 replicas, so internal request volume is ~2x client volume; the network fabric must carry the fan-out.
  • Virtual nodes: assign 128-256 vnodes per physical node so ring ownership is smooth and rebuilding a failed node draws from many peers in parallel.
Model answer: At N=3, 100 TB logical is 300 TB physical, and LSM compaction wants headroom, so I'd provision closer to 450 TB. At 4-8 TB usable per node that's roughly 60-110 nodes. Spreading 1M ops/sec over that is only ~10K per node, which an LSM engine on SSD handles easily — so this cluster is storage-bound, not CPU-bound. One thing worth flagging: with quorum reads at R=2 the internal request rate is about double the client rate, so the network fan-out is part of the sizing. And I'd run 128-256 virtual nodes per physical node so ownership is even and a failed node rebuilds from many peers at once rather than from one.

Q3 explain & apply crux

How are keys placed on nodes, and what happens to placement when a node joins or leaves?

Points a strong answer hits:

  • Hash both keys and nodes onto a fixed ring (e.g. 0..2^128). A key belongs to the first node clockwise from its hash — its coordinator.
  • Replicas are the next N-1 distinct physical nodes clockwise, forming the key's preference list.
  • Naive hash(key) % nodes remaps nearly every key when node count changes; the ring remaps only the arc owned by the departing/arriving node — about 1/N of keys.
  • Virtual nodes fix two problems: uneven arc sizes with few nodes, and heterogeneous hardware (a bigger machine simply gets more vnodes).
  • Vnodes also parallelize recovery — a failed node's ranges are spread over many peers, so rebuild pulls from all of them at once instead of stressing one neighbor.
  • The preference list must skip vnodes that map back to the same physical node (and ideally the same rack/AZ), or 'three replicas' can silently mean one machine.
Model answer: Keys and nodes both hash onto a ring, and a key is owned by the first node clockwise, with replicas on the next N-1 distinct physical nodes — that set is the preference list. The point of the ring versus hash % nodes is that membership changes only move the arc that changed hands, roughly 1/N of keys, instead of remapping almost everything. Virtual nodes then smooth the ownership distribution and let heterogeneous hardware take proportional load, and they make recovery parallel because a dead node's ranges are scattered across many peers. The subtlety I'd call out is that the preference list has to skip vnodes landing on the same physical node or rack — otherwise your three replicas can quietly be one machine or one AZ.

Q4 multiple choice crux

With N=3 replicas, why is the quorum rule stated as R + W > N?

  1. A It guarantees every replica has the newest value before a read returns
  2. B It forces the read set and write set to share at least one replica, so a read is guaranteed to see at least one copy of the latest acknowledged write correct
  3. C It minimizes total network round trips for a mixed read/write workload
  4. D It is required for the Merkle-tree anti-entropy protocol to converge

Why: R + W > N is a pigeonhole argument: if writes go to W replicas and reads consult R, and R + W exceeds N, the two sets must intersect in at least one node — so the read sees at least one replica carrying the newest acknowledged write, and versioning picks it. It does not mean all replicas are current (they're not — that's what read repair and anti-entropy are for), it isn't a latency optimization (it costs latency), and anti-entropy converges independently of the quorum setting.

Q5 explain & apply crux

Deep dive: replicas diverge under leaderless writes. Walk through the three mechanisms that bring them back together.

Points a strong answer hits:

  • Read repair — on a quorum read, the coordinator compares replica versions and asynchronously pushes the newest value to the stale ones. Repairs only what is actually read, so cold data stays divergent.
  • Hinted handoff — if a preference-list replica is briefly down, another node accepts the write and holds a hint; when the target returns, the hint is replayed. Covers transient outages without failing writes.
  • Anti-entropy with Merkle trees — replicas exchange a hash tree over their key ranges, descend only into subtrees whose hashes differ, and sync just those keys. That's what repairs cold data and long outages.
  • The Merkle tree is the efficiency argument: comparing two replicas costs O(log n) exchanges to locate differences instead of streaming the whole range.
  • Each mechanism covers a different timescale — access-time, minutes, and background — and none alone is sufficient.
  • Deletes need tombstones: a delete must be a versioned marker that replicates, or an unreachable replica would resurrect the value on repair. Tombstones must outlive the maximum repair window before being garbage collected.
Model answer: Three mechanisms on three timescales. Read repair happens at access time — a quorum read compares versions and pushes the newest value to stale replicas, but it only fixes data someone actually reads. Hinted handoff covers brief outages: if a replica is down, a peer takes the write and holds a hint to replay when it recovers, so writes don't fail. And anti-entropy with Merkle trees handles cold data and long outages — replicas exchange a hash tree, descend only where hashes differ, and sync just those keys, which is O(log n) exchanges rather than streaming everything. The detail people miss is deletes: a delete has to be a replicated tombstone, or an offline replica resurrects the value during repair, and the tombstone has to outlive the longest possible repair window before it's collected.

Q6 multiple choice crux

Two clients concurrently update the same key on different replicas. With last-write-wins conflict resolution, what actually happens?

  1. A Both updates are preserved and returned to the client as siblings
  2. B The update with the higher timestamp survives and the other is silently discarded — including when the two were genuinely concurrent and neither saw the other correct
  3. C The write is rejected and the client must retry with a version number
  4. D The replicas remain permanently divergent until an operator intervenes

Why: Last-write-wins is exactly that: compare timestamps, keep the larger, drop the other — with no way to distinguish 'B happened after A' from 'A and B were concurrent and neither saw the other'. That's a silent lost update, and clock skew between nodes makes 'higher timestamp' not even reliably mean 'later'. Version vectors are the alternative: they detect that two versions are concurrent rather than ordered, and surface both as siblings so the application can merge them (union the shopping cart) instead of guessing.

Q7 explain & apply

Deep dive: describe the storage engine on a single node and why that structure suits this workload.

Points a strong answer hits:

  • LSM tree: writes go to a commit log (durability) and an in-memory memtable (sorted). When the memtable fills it flushes to an immutable, sorted SSTable on disk.
  • Every write is therefore a sequential append plus an in-memory insert — no random disk writes on the hot path, which is why write throughput is high.
  • Reads check the memtable, then SSTables newest-first. A bloom filter per SSTable answers 'definitely not here' cheaply, so most reads touch one or two files rather than all of them.
  • Compaction merges SSTables to reclaim space from overwritten/deleted keys and to bound how many files a read must consult.
  • The tradeoff versus a B-tree: LSM gives better write throughput and space efficiency; B-trees give more predictable read latency. LSM reads are exposed to compaction-induced latency spikes.
  • Write amplification is the operational cost — a byte written may be rewritten several times through compaction levels, consuming disk bandwidth and SSD endurance.
Model answer: Each node runs an LSM tree. A write appends to a commit log for durability and inserts into a sorted in-memory memtable; when that fills, it flushes as an immutable SSTable. So the hot path is a sequential append plus a memory insert — no random writes, which is where the write throughput comes from. Reads check the memtable then SSTables newest-first, with a per-SSTable bloom filter so most lookups skip nearly every file. Compaction merges SSTables in the background to reclaim overwritten space and bound read fan-out. Versus a B-tree, LSM wins on write throughput and space, and loses on read-latency predictability — compaction causes tail-latency spikes, and write amplification consumes real disk bandwidth and SSD endurance.

Q8 explain & apply

How do nodes learn about each other, detect failure, and agree on membership without a coordinator?

Points a strong answer hits:

  • Gossip: each node periodically exchanges state with a few random peers, so membership and heartbeat information spreads epidemically in O(log n) rounds.
  • No central registry means no control-plane single point of failure — the property that makes the cluster masterless.
  • Failure detection is usually a phi-accrual detector: rather than a binary up/down after a fixed timeout, it outputs a suspicion level from the distribution of heartbeat intervals, adapting to network conditions.
  • That matters because a fixed timeout is either too twitchy on a slow network or too slow on a fast one; accrual detection tunes itself.
  • Temporary failure → hinted handoff (no data movement). Permanent removal → explicit decommission that streams ranges to new owners.
  • Distinguishing 'slow' from 'dead' is genuinely undecidable, which is why the design tolerates false positives cheaply instead of trying to be certain.
  • Seed nodes bootstrap gossip for a joining node; they are a convenience, not a coordinator.
Model answer: Gossip — each node periodically swaps state with a few random peers, so membership and liveness propagate epidemically in about log(n) rounds with no central registry, which is exactly what keeps the cluster masterless. For failure detection I'd use a phi-accrual detector rather than a fixed timeout: it models the distribution of heartbeat arrival times and emits a suspicion level, so it adapts instead of being too twitchy on a slow network or too sluggish on a fast one. The important design consequence is that 'slow' and 'dead' are genuinely indistinguishable, so the system is built to make false positives cheap — a suspected node just triggers hinted handoff, not data movement. Only an explicit decommission streams ranges to new owners.

Q9 explain & apply

Staff-level wrap-up: what breaks at scale, and when is this the wrong store to reach for?

Points a strong answer hits:

  • Hot partitions: a single popular key can't be split by adding nodes. Mitigate by salting the key, or by caching in front of the store.
  • Tombstone accumulation on delete-heavy workloads makes reads scan graveyards; a queue-like access pattern on an LSM store is a known anti-pattern.
  • Compaction is the operational hazard — it competes for disk bandwidth with live traffic and drives tail latency. Watch pending-compaction depth.
  • Multi-region: replicate asynchronously per region with local quorums, or every write pays WAN latency. Cross-region strong consistency belongs to a different design.
  • Wrong tool when you need multi-key transactions, joins, ad-hoc queries, or strict read-after-write globally — that's a relational or consensus-replicated store.
  • Wrong tool for large blobs; store those in object storage and keep pointers here.
  • Monitor: p99 read/write latency, pending compactions, hint backlog, dropped mutations, and per-node ownership skew.
Model answer: The failure that adding nodes can't fix is a hot key — one popular key lives on one preference list no matter how big the cluster gets, so it needs salting or a cache in front. Delete-heavy workloads are the other classic trap: tombstones pile up and reads start scanning graveyards, which is why using an LSM key-value store as a queue is a known anti-pattern. Operationally, compaction is what to watch — it competes with live traffic for disk bandwidth and is usually the cause of tail-latency complaints. For multi-region I'd do local quorums with async cross-region replication, because a global quorum puts WAN latency on every write. And I'd argue against this store entirely if the requirements include multi-key transactions, joins, ad-hoc queries, or globally strict read-after-write — those want a different design, not a tuned version of this one.
