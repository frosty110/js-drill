Migrating the embedding model

Lifecycle study sheet

What this sheet shows

Vectors from two models occupy different spaces, so a new query against an old index returns nonsense rather than degraded results. Dual-index and gate the cutover on quality.

Show why an embedding upgrade is a schema migration rather than a config change.

Trace the flow

  1. Stand up index B — Build alongside A rather than in place.
  2. Dual-write on ingest — New documents land in both indexes so B stays current.
  3. Backfill the corpus — Re-embed everything, at a cost estimated up front rather than discovered.
  4. Gate on quality — Compare A and B on a fixed evaluation set before moving traffic.
  5. Cut over, keep A warm — Rollback must stay cheap because regressions surface late.

What this belongs to

Ground an LLM's answers in a private corpus: chunk and embed documents, retrieve the relevant passages at query time, and cite them. The signature challenge is that retrieval quality — not the model — decides the answer, and the embedding model is a schema you cannot migrate cheaply.
