Feature store system map

System map study sheet

What this sheet shows

A feature is declared once and compiled to a batch path and a streaming path, landing in a low-latency online store for inference and a full-history offline store for training.

Establish that one registered definition compiles into both materialization paths.

Trace the flow

  1. Register the definition — Entity, source, transformation, freshness TTL and target stores, all versioned.
  2. Compile to both paths — The same definition drives the batch job and the stream processor.
  3. Materialize online — Current values only, keyed by entity, for single-digit-millisecond reads.
  4. Materialize offline — Full history with timestamps, stored columnar for large temporal joins.
  5. Serve both consumers — Inference reads online by key; training reads offline as of a label time.

What this belongs to

Serve the same features to model training and to online inference without them disagreeing. The signature challenge is training/serving skew — the silent failure where a model scores well offline and badly in production because the numbers it sees at request time were computed differently.
