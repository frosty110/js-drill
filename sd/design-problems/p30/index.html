Design a Feature Store

Serve the same features to model training and to online inference without them disagreeing. The signature challenge is training/serving skew — the silent failure where a model scores well offline and badly in production because the numbers it sees at request time were computed differently.

Canonical Design Problems 9 questions

Results carried by this link

Key ideas

  • The store exists to solve one problem: the same feature definition must produce the same value offline and online, or the model is trained on data it will never see again.
  • Point-in-time correctness is the offline half — a training row must only use feature values that were knowable at that row's timestamp, or the model learns from the future and looks brilliant in backtests.
  • Two stores, one definition: a low-latency online store for single-entity reads and a columnar offline store for large historical joins.
  • Write the definition once and compile it to both paths, rather than maintaining a batch job and a streaming job that drift.
  • Online reads are entity-keyed point lookups at single-digit milliseconds, because they sit inside the request path of the model call.
  • Feature freshness is a per-feature SLO, not a system-wide one — a 30-day average tolerates hours, a session click count tolerates seconds.
  • Serving skew is invisible without monitoring: compare online-served feature distributions against training distributions continuously.

Q1 explain & apply crux

Scope a feature store. What problem does it exist to solve, and what are the functional requirements?

Points a strong answer hits:

  • The core problem: without it, a data scientist computes a feature in a notebook for training, and an engineer reimplements it in the service for inference. The two drift, and the model degrades silently.
  • Functional: register a feature definition once; materialize it to an online store for inference and an offline store for training; retrieve features by entity key online; generate point-in-time-correct training sets offline.
  • Discovery and reuse: a catalog so teams find existing features rather than recomputing them — the secondary but real value.
  • Non-functional online: p99 under ~10ms for a batch of features for one entity, because this sits inside the model request path.
  • Non-functional offline: throughput over latency — building a training set of hundreds of millions of rows is a batch job.
  • Freshness targets differ per feature and must be declared, not assumed.
  • Clarify who the users are — data scientists authoring features and services consuming them — because the API has to serve both.
Model answer: It exists to stop one specific failure: a feature computed one way in a training notebook and reimplemented another way in the serving path, drifting apart until the model quietly degrades. So the requirements are: define a feature once, materialize it to both an online store for inference and an offline store for training, read by entity key online, and generate point-in-time-correct training sets offline. Online is a hard latency target — under ~10ms p99, because it's inside the model request. Offline is a throughput problem. And freshness has to be per-feature: a 30-day spend average and a session click count have nothing in common there.

Q2 explain & apply

Work the numbers: sizing for 50M users, 200 features each, at 10K inference QPS.

Points a strong answer hits:

  • Online store: 50M entities × 200 features × ~50 bytes ≈ 500 GB. Fits a sharded key-value store; not a single node.
  • Read pattern: 10K QPS × 200 features. Fetch them as one row per entity, not 200 gets — that's the difference between one round trip and 200.
  • Latency budget: if the model call must return in 100ms, features get ~10ms of it, which rules out anything but an in-memory or SSD-backed KV store.
  • Offline store: retain history for training. 50M entities × 200 features × daily snapshots × 2 years is enormous, so store as columnar files (Parquet) in object storage partitioned by date, not in a database.
  • Training-set generation is a large point-in-time join — hundreds of millions of label rows against the feature history. This is a Spark-scale job, minutes to hours.
  • Streaming features add write load: session counters update per event, so writes can exceed reads for those features.
  • Note the asymmetry: online is small-and-hot (current values only), offline is huge-and-cold (all history).
Model answer: Online holds only current values: 50M entities × 200 features at ~50 bytes is roughly 500 GB — sharded KV, in-memory or SSD-backed, because the latency budget is about 10ms out of a 100ms model call. The critical access-pattern decision is fetching one row per entity rather than 200 individual gets. Offline is a different animal: full history, so columnar files in object storage partitioned by date, and training-set generation is a Spark-scale point-in-time join over hundreds of millions of rows. The shape to say out loud is the asymmetry — online is small and hot because it only needs current values, offline is huge and cold because it needs all of history.

Q3 explain & apply crux

Design the API and the feature definition. What does a data scientist actually write?

Points a strong answer hits:

  • A feature definition declares: entity (user, merchant), the source (table or stream), the transformation, the freshness/TTL, and the materialization targets.
  • Definitions are versioned and stored in a registry — this is the single source of truth both pipelines compile from.
  • Online read: get_online_features(entities=[user_id], features=[...]) returning current values in one round trip.
  • Offline read: get_historical_features(entity_df_with_timestamps, features=[...]) — the entity dataframe carries the label timestamps, which is what makes point-in-time correctness possible.
  • That timestamp argument is the whole API difference: the offline call is a temporal join, not a lookup.
  • Grouping related features into feature views/services lets a model declare its whole input set as one versioned object, so a model version pins a feature-set version.
  • Support on-demand features computed at request time from request context (e.g. amount ÷ 30-day average) — these can't be precomputed because half the input arrives with the request.
Model answer: A definition declares the entity, the source table or stream, the transformation, a freshness TTL, and which stores to materialize into — versioned in a registry that both pipelines compile from. Online reads are get_online_features(entities, features), a single round trip returning current values. Offline reads are get_historical_features(entity_df, features) where the dataframe carries label timestamps — and that argument is the entire difference, because it makes the offline call a temporal join rather than a lookup. I'd group features into versioned feature services so a model version pins its whole input set, and support on-demand features computed at request time, since something like amount-over-30-day-average has half its input arriving with the request.

Q4 multiple choice crux

A fraud model is trained on a row labelled at 14:00 on March 3. Which value of user_transaction_count_7d must the training row contain?

  1. A The value computed today, since it uses the most complete data available
  2. B The value as it stood at 14:00 on March 3 — using any later value leaks information the model would not have had at prediction time correct
  3. C The average of the values over the 7 days following the label
  4. D Whichever value has the highest data quality score

Why: This is point-in-time correctness, and getting it wrong is the classic silent disaster. If the training row uses today's count, it includes transactions that happened *after* the label — including, for a fraud label, the fraudulent ones themselves. The model learns a feature that will never be available at prediction time, scores superbly in backtests, and collapses in production. The offline store must therefore keep feature history with timestamps and perform an as-of join against each row's label timestamp, not a simple key join.

Q5 explain & apply crux

Deep dive: how is a point-in-time-correct training set actually built?

Points a strong answer hits:

  • Input: an entity dataframe of (entity_id, label_timestamp, label) rows — potentially hundreds of millions.
  • The offline store keeps feature *history*: each feature value with the event timestamp it became valid.
  • The join is an as-of / backward join: for each row, take the latest feature value whose timestamp is <= the label timestamp.
  • Naively this is a per-row lookup; at scale it's done as a sort-merge on (entity_id, timestamp) so both sides stream past each other once.
  • Watch the second timestamp: event time (when it happened) versus processing time (when the pipeline saw it). If a feature only landed in the warehouse an hour later, it was not actually knowable at label time — modelling this needs both timestamps.
  • TTL bounds the join: without a maximum staleness, a row can match a feature value from a year earlier, which is technically valid and practically garbage.
  • The output must be reproducible — same entity dataframe and same feature versions produce the same training set, or experiments cannot be compared.
  • This is the operation that justifies the whole offline store existing; a plain key-value snapshot cannot do it.
Model answer: You start with an entity dataframe of entity id, label timestamp and label. The offline store holds feature history with the timestamp each value became valid, and the join is an as-of backward join: for each row take the latest value whose timestamp is at or before the label timestamp. At scale that's a sort-merge on entity and timestamp rather than per-row lookups. Two subtleties matter. First, event time versus processing time — if a value only landed in the warehouse an hour after the event, it wasn't actually knowable at label time, so you need both timestamps to be honest. Second, a TTL to bound the join, or a row happily matches a value from a year earlier, which is valid and useless. And the whole thing must be reproducible, or you can't compare two experiments.

Q6 multiple choice crux

A batch pipeline computes avg_order_value_30d nightly for training; the serving code computes it live from the last 30 days of orders. Offline accuracy is high, production accuracy is poor. What is the diagnosis?

  1. A The model is overfitting and needs stronger regularization
  2. B Training/serving skew — two independent implementations of one definition produce different values, so production inputs don't match the training distribution correct
  3. C The online store's replication lag is too high
  4. D The 30-day window is too short to be predictive

Why: Two implementations of the same feature is the textbook cause of a model that validates well and fails live. They differ in the ways reimplementations always differ — timezone boundaries, whether cancelled orders count, inclusive or exclusive window edges, null handling — so the model receives a subtly different distribution than it was trained on. The fix is structural, not statistical: one definition, compiled to both paths, so there is no second implementation to drift. Regularization addresses a different failure, and replication lag would show as staleness rather than a distribution shift.

Q7 explain & apply

Deep dive: how do features get into the online store, and how do you handle features with different freshness requirements?

Points a strong answer hits:

  • Batch materialization: a scheduled job computes features from the warehouse and upserts them into the online store. Right for slow-moving aggregates (30-day averages, demographics).
  • Stream materialization: a stream processor consumes events and updates counters in near real time. Required for session-scoped or last-N-minutes features.
  • Both paths must be compiled from the same definition, or you have reintroduced the skew the store exists to prevent.
  • The lambda problem is real here: batch and streaming implementations of one aggregation can disagree, so periodic batch backfill should correct streaming state.
  • Per-feature freshness SLO: declare it, monitor it, and alert on staleness — a stale feature silently degrades predictions with no error anywhere.
  • TTL on online values so a feature that stopped updating expires rather than serving an ancient value forever.
  • Serve a documented default when a feature is missing (cold-start user, pipeline failure) and record that it was defaulted — a silent zero is indistinguishable from a real zero and models treat them very differently.
  • On-demand features are computed at request time from request context and never materialized at all.
Model answer: Two paths. Batch materialization computes from the warehouse on a schedule and upserts — right for slow-moving aggregates. Stream materialization consumes events and updates counters continuously — required for session-scoped features. The rule that matters is that both compile from the same definition, otherwise you've re-created the exact skew the store exists to prevent, just inside the store. I'd declare freshness as a per-feature SLO and alert on staleness, since a stale feature degrades predictions with no error surfacing anywhere. Two details I'd insist on: a TTL so a stopped pipeline expires values instead of serving ancient ones, and an explicit default plus a flag when a feature is missing — a silent zero is indistinguishable from a real zero, and models treat those very differently.

Q8 explain & apply crux

Some features can't be precomputed — they depend on the request itself. How do on-demand features work, and where do they break the model?

Points a strong answer hits:

  • Example: amount / user_avg_order_value_30d for a fraud model. The denominator is precomputed; the numerator arrives with the request.
  • So the feature can only be computed at request time, joining stored features with request context.
  • They must be defined in the same registry and compiled from the same definition as materialized features, or they reintroduce exactly the skew the store exists to prevent — now in the one path nobody is monitoring.
  • For training, on-demand features must be computed by replaying the same transformation over historical request logs, which means request payloads have to be logged with their timestamps.
  • If request context isn't logged, the feature is untrainable — you can serve it but never learn from it, which is a silent and expensive discovery.
  • Latency: this computation is inside the request path, so it must be cheap; heavy on-demand transformations belong in the model itself, not the feature layer.
  • They're also where feature leakage sneaks back in — a transformation that accidentally references a post-outcome field looks fine online and poisons training.
  • Rule of thumb: precompute anything that depends only on stored state; compute on demand only what genuinely requires the request.
Model answer: The canonical case is a ratio like transaction amount over the user's 30-day average — the denominator is precomputed, the numerator arrives with the request, so the feature only exists at request time. The requirement I'd insist on is that it's declared in the same registry and compiled from the same definition as materialized features, because otherwise it reintroduces training/serving skew in the one path nobody is monitoring. The trap is training: to build a training set you have to replay that same transformation over historical requests, which means request payloads and their timestamps must be logged. If they aren't, the feature is servable but untrainable, and that's an expensive thing to discover late. Latency-wise it sits in the request path so it has to be cheap. My rule is: precompute anything that depends only on stored state, and compute on demand only what genuinely needs the request.

Q9 explain & apply

Staff-level wrap-up: what breaks at scale, and how do you detect a problem before the model does?

Points a strong answer hits:

  • Monitor the served distribution against the training distribution per feature — drift in the input is detectable long before accuracy metrics move.
  • Log the exact feature vector served with each prediction. Without it, debugging a bad prediction is guesswork, and it also gives you the ground truth for skew analysis.
  • Skew detection: periodically recompute offline what was served online for the same entity and timestamp, and alert on mismatch. This is the only direct test that the two paths agree.
  • Hot entities: a celebrity or a bot entity can concentrate reads on one shard; cache hot rows in front of the online store.
  • Backfilling a new feature over two years of history is expensive and easy to get wrong — it must respect point-in-time semantics or it poisons every model trained on it.
  • Registry becomes a governance problem at scale: unowned, unused features accumulate; track lineage and usage so deletion is safe.
  • A feature deleted or redefined while a live model depends on it is an outage — version features and pin models to versions.
  • Cost: materializing every registered feature for every entity is wasteful; materialize on demand based on what models actually consume.
Model answer: The detection I'd rely on most is comparing the served feature distribution against the training distribution per feature — input drift shows up well before accuracy metrics move. That requires logging the exact feature vector served with each prediction, which also gives you the ground truth for a direct skew test: periodically recompute offline what was served online for the same entity and timestamp, and alert on mismatch. That's the only test that actually proves the two paths agree. At scale the operational risks are hot entities concentrating reads on one shard, and backfills — adding a feature across two years of history has to respect point-in-time semantics or it poisons every model trained on it. Governance bites too: features get deleted or redefined while a live model depends on them, so features need versions and models need to pin them.
