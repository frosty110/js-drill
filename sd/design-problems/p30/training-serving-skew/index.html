Where training/serving skew comes from

Failure study sheet

What this sheet shows

Two implementations of one definition drift at the edges — timezones, cancellations, null handling — so the model receives a different distribution than it trained on.

Name the silent failure the whole system exists to prevent.

Trace the flow

  1. Feature defined once — A single logical definition, for example a 30-day average order value.
  2. Reimplemented twice — Batch SQL in a notebook, live computation in the serving path.
  3. Edges disagree — Timezone boundaries, cancelled orders, inclusive or exclusive windows, nulls.
  4. Distributions diverge — Serving inputs no longer match what the model learned.
  5. Fix structurally — Compile both paths from one definition so no second implementation exists.

What this belongs to

Serve the same features to model training and to online inference without them disagreeing. The signature challenge is training/serving skew — the silent failure where a model scores well offline and badly in production because the numbers it sees at request time were computed differently.
