Design a Financial Crime Alert Investigation System

A bank's transaction monitoring system emits alerts that are over 95% false positives, and analysts clear them by hand. Automate the investigation with LLM agents that gather evidence, apply the bank's written policy, and dispose of the alert. The signature challenge is that the output is a regulated decision: it must be reconstructable years later, against evidence that the outside world will have overwritten.

Components in play 9

  • Work Queue signature — Alerts arrive as an overnight batch and each investigation runs for minutes, so the queue is what decouples a 4K-alert dump from a fixed pool of concurrent investigations.
  • At-Least-Once Delivery signature — Alert delivery is retried by the bank and by the transport, so the pipeline assumes duplicates by default and makes the investigation step safe to repeat rather than trying to deduplicate at the edge.
  • Idempotency signature — A redelivered alert file must not re-investigate what was already decided, so the key is the source alert id and revision rather than anything the pipeline generates.
  • Backpressure signature — Per-tenant concurrency caps keep one bank's overnight backfill from consuming every worker slot, because the shared ceiling is model and vendor spend rather than CPU.
  • Audit Log & Provenance signature — An examiner can ask years later why one alert was cleared, so the trace pins prompt, model snapshot, policy version and evidence hashes — everything whose change would change the answer.
  • Agent Decision Record signature — Every auto-closed alert carries the reason code it closed under, the agent's confidence, the threshold in force that day, and whether a reviewer later disagreed.
  • Cost Metering signature — An agent choosing its own tools is spending money autonomously, so each case carries a hard budget and cost becomes an input to tool selection rather than a report afterwards.
  • Progressive Rollout — A new agent version is scored against decisions humans already made before it is trusted to dispose of alerts on its own.
  • Tenant Isolation — Each bank's policy, data and model configuration stay separate, because the same agents run against institutions that must never see each other's alerts.

The brief

Functional requirements

  • Ingest alerts from the bank's monitoring system, investigate each one, and return a disposition plus a cited narrative a regulator can read.
  • Gather evidence from internal systems (transactions, KYC records) and external vendors (adverse media, corporate registries, identity data).
  • Apply the bank's own written policy, which is versioned tenant data rather than code.
  • Auto-close the clearly benign band, escalate the rest to a human queue, and preserve the analyst's override.
  • Out of scope: generating the alerts themselves (the bank's monitoring system does that), filing the report with the regulator, and the human review UI.

Scale & constraints

  • A mid-size bank: ~2M customers, ~40M transactions/month, monitoring rules firing on ~0.3% of them = ~120K alerts/month, ~4K/day
  • Arrival is bursty and batch-shaped: most alerts land in an overnight file, so peak is a 4K-alert dump rather than 0.05/s smooth
  • Investigation is slow and expensive by nature: 10-30 external calls and several LLM turns, so 30s-3min of wall clock and $0.20-$2.00 per case
  • That makes the daily bill ~$800-8,000 in model and vendor spend, which is the real capacity constraint, not QPS
  • Retention is 5 years under the Bank Secrecy Act, so every trace and every evidence snapshot outlives the model that produced it

Key ideas

  • Errors are asymmetric. A false negative is a missed crime and a supervisory finding; a false positive is only cost. So you tune for recall against a precision floor, and the auto-close threshold belongs to the bank, not to your F1 score.
  • Every external evidence fetch must be snapshotted at decision time. Vendors mutate their records and will not replay history, so a citation to a vendor is worthless while a citation to a stored artifact is proof.
  • The audit record pins the whole decision tuple: prompt version, model snapshot, policy version, tool versions, evidence artifact ids, code release. 'A GPT-class model' does not survive an examiner.
  • Do not promise deterministic replay of a non-deterministic model. Promise that the inputs, the trace and the evidence are preserved, and that a re-run is a comparison rather than a proof.
  • Incomplete evidence must escalate, never auto-close. A silent decision on partial data is the failure mode that ends in a consent order.
  • Human review is a component, not an error path: leases, SLA timers against the statutory clock, and the analyst's override captured as a first-class event.
  • Autonomy ships as a ratchet — shadow, then suggest, then auto-close on the narrowest risk band with sampled QA — because that is both how banks adopt and how you harvest labels.
  • The scaling ceiling is per-case model and vendor spend, not the database. An agent that picks its own tools is spending money autonomously.

Q1 explain & apply crux

Scope an automated financial-crime alert investigation system. What are the functional requirements, and which non-functional constraint dominates the design?

Points a strong answer hits:

  • Functional: ingest alerts, gather evidence from internal and external sources, apply the bank's written policy, produce a disposition, produce a cited narrative, escalate what the agent should not decide.
  • Explicitly out of scope: generating the alerts (the bank's monitoring system does that), and filing the regulatory report itself.
  • The dominating constraint is not latency or throughput — it is that the output is a regulated decision that must be defensible to an examiner years later.
  • Errors are asymmetric: a false negative is a missed crime and a supervisory finding, a false positive is only cost. That asymmetry sets every threshold.
  • So the auto-close threshold is a policy input owned by the bank, not a number tuned on aggregate accuracy.
  • Retention: Bank Secrecy Act records run 5 years, so the audit trail must outlive the model, the prompt, and possibly the vendor contract.
  • Multi-tenancy is a hard requirement — each bank's data, policy and thresholds are separate, and some will not accept application-level filtering as the isolation story.
  • Latency is generous (minutes per case is fine); the tight constraint is cost per case and correctness, which is unusual and worth saying out loud.
Model answer: Ingest an alert, gather evidence from internal systems and external vendors, test it against the bank's own written policy, then either close it, escalate it, or refer it — always with a cited narrative. Generating the alert and filing the regulatory report are both out of scope. The constraint that dominates is that this is a regulated decision, not a recommendation: an examiner can ask in 2029 why a specific alert was cleared in 2026 and expects a real answer. That drives retention, provenance and versioning into the core of the design rather than bolting them on. And the errors are asymmetric — a missed launderer is a supervisory finding, a false positive is only cost — so I would tune for recall against a precision floor and treat the auto-close threshold as a policy input the bank owns.

Q2 explain & apply crux

Estimate the load and say where the real capacity constraint sits.

Points a strong answer hits:

  • Take a mid-size bank: 2M customers, ~40M transactions/month. Monitoring rules fire on roughly 0.3%, so ~120K alerts/month, about 4K/day.
  • That is only 0.05 alerts/sec averaged — trivially low QPS, which is the first surprise. This is not a throughput problem.
  • But arrival is bursty and batch-shaped: banks deliver alerts in an overnight file, so the real shape is a 4K-alert dump at 02:00, not a smooth stream.
  • Each investigation makes 10-30 external calls and several LLM turns: 30 seconds to 3 minutes of wall clock, mostly waiting on third parties.
  • Cost per case is $0.20-$2.00 in model tokens plus per-query vendor fees. At 4K/day that is $800-8,000 per day, per bank.
  • So the binding constraint is spend and third-party rate limits, not CPU, memory or database throughput.
  • Concurrency: to clear 4K cases in an 8-hour window at 90 seconds each you need ~125 concurrent investigations, which is modest.
  • Storage: the trace and evidence snapshots dominate, maybe 200KB-2MB per case. 120K cases/month at 1MB is ~120GB/month, held 5 years, so single-digit terabytes per bank. Object storage, not a database problem.
Model answer: A 2M-customer bank generates around 120K alerts a month, roughly 4K a day, which averages to 0.05 per second — so throughput is a non-issue and that is worth saying early, because it redirects the whole conversation. The load is bursty rather than smooth: alerts arrive as an overnight batch, so I would size for clearing a 4K dump inside a window rather than for steady QPS, which is about 125 concurrent investigations at 90 seconds each. The real constraint is money. Each case costs twenty cents to two dollars in model and vendor calls, so the daily bill is between eight hundred and eight thousand dollars and the ceiling I would hit first is third-party rate limits and spend, not the database. Storage is a few terabytes per bank over the five-year retention, which is object storage and cheap.

Q3 explain & apply crux

Sketch the high-level architecture and the core data model.

Points a strong answer hits:

  • Ingest tier accepting three shapes, because all three exist in real banks: webhook push, API pull, and an SFTP batch file drop.
  • Land the raw payload immutably before interpreting it, so a parsing change never destroys what was actually received.
  • Idempotency key of (tenant, source_system, alert_id, revision) so a redelivered file cannot double-investigate.
  • A durable workflow engine drives each case: plan, gather, evaluate, decide, narrate. Steps are retryable activities; the workflow survives restarts and can pause for days.
  • An evidence service fronting every external vendor, so adapters own auth, retries, rate limits, and normalization into one envelope.
  • Object storage for raw evidence, content-addressed by hash. Postgres for case state, decisions, and the append-only event log.
  • Core tables: alerts (raw + parsed), cases, evidence_artifacts (hash, source, fetched_at, tenant), decisions (disposition, thresholds, versions), events (append-only trace), policies (versioned per tenant).
  • Case state is a projection of the event log rather than the other way round, so the trace is authoritative and the read model is rebuildable.
Model answer: Ingest accepts webhook, API pull and SFTP batch, because banks genuinely still use the third, and it lands the raw payload immutably before anything parses it. From there a durable workflow engine owns each case as a long-running orchestration: plan, gather evidence, evaluate against policy, decide, narrate. Every external call goes through an evidence service so per-vendor auth, retries and rate limits live in one place and results come back in a common envelope. For storage I would put raw evidence in object storage, content-addressed by hash, and keep case state, decisions and an append-only event log in Postgres. The important modeling choice is that the event log is the source of truth and the case row is a projection of it, so the trace is authoritative and the read model can be rebuilt.

Q4 multiple choice crux

Your agent cleared an alert in March using an adverse-media search that returned nothing. In September a regulator asks you to justify it. What makes that answerable?

  1. A Re-run the same adverse-media query and show it still returns nothing
  2. B A stored, content-addressed snapshot of the vendor's actual March response, cited by the narrative — the vendor's index has since changed and cannot be replayed correct
  3. C The vendor's audit log, requested from them under the data-processing agreement
  4. D The model's reasoning trace, which explains what it concluded from the search

Why: Evidence vendors continuously re-index. The September result is a different answer to a different question, and it is worthless as a defence of a March decision — it may even contradict it, which is worse. Relying on the vendor's own logs makes your audit posture depend on a third party's retention policy and their willingness to produce records under subpoena. The reasoning trace is necessary but not sufficient: it records what the agent concluded, not what it was actually shown, so on its own it is an assertion rather than evidence. The only durable answer is to snapshot the raw response at decision time, address it by hash, and have every claim in the narrative cite that artifact.

Q5 explain & apply crux

Deep dive: design the audit trail. What exactly is written, and what does it have to survive?

Points a strong answer hits:

  • An append-only event log is the source of truth: every agent step emits inputs, the tool called, a reference to the raw response, the model output, and a timestamp.
  • Hash-chain the records so tampering is detectable — an audit log a bank can silently edit is not evidence.
  • Pin the entire decision tuple: prompt version, model identifier AND provider snapshot, policy version, tool versions, evidence artifact ids, code release.
  • Content-address evidence in object storage with an object-lock retention period, so nothing can be deleted inside the 5-year window even by an administrator.
  • Write self-describing, denormalized records. The log outlives your schema, and a log you can only read by joining against a schema you have since migrated is not a log.
  • Every assertion in the generated narrative resolves to a specific artifact and an offset within it, which is what makes the output reviewable rather than merely plausible.
  • Replay means re-running against pinned inputs and diffing the outcome. State plainly that this is reproducibility of inputs, not bit-exact reproduction, because the model is non-deterministic.
  • Design for bulk replay from the start: when a regulator finds a monitoring program deficient, the bank must re-review years of historical alerts, and that lookback is the most expensive event in compliance.
Model answer: The audit trail is an append-only, hash-chained event log that is the source of truth, with case state as a projection of it. Each step records its inputs, the tool called, a hash reference to the raw response, and the model's output. Alongside it I pin the full decision tuple — prompt version, model snapshot, policy version, tool versions, evidence ids, code release — because any one of those changing changes the answer, and 'a GPT-class model' is not something an examiner accepts. Evidence lives in object storage under a hash with object-lock for the retention window. The records have to be self-describing and denormalized, since they outlive the schema that wrote them. On replay I would be explicit that the model is non-deterministic: what I guarantee is that inputs, trace and evidence are preserved exactly, so a re-run is a comparison rather than a proof. Claiming determinism I cannot deliver is worse than naming the limit, because it will eventually be tested.

Q6 multiple choice crux

Mid-investigation, the corporate-registry vendor starts timing out. The agent has gathered eight of its ten planned evidence items. What should the system do?

  1. A Decide on the evidence it has and note the gap in the narrative
  2. B Escalate the case to a human, because the missing source was declared required — deciding on partial evidence is the silent failure this design exists to prevent correct
  3. C Retry indefinitely until the vendor recovers, since the case has no hard deadline
  4. D Auto-close it as a false positive, since nothing found so far was suspicious

Why: Each source is declared required or best-effort at design time, and the difference is the whole point. Missing a best-effort source is fine and gets noted. Missing a required one means the policy could not actually be evaluated, so the only defensible outcome is escalation to a human. Deciding anyway and noting the gap sounds responsible but produces exactly the artefact an examiner will find: a documented decision made on evidence the system itself knew was incomplete. Auto-closing on absence of findings inverts the asymmetry — absence of evidence is not evidence of absence, and this is the direction where the expensive errors live. Retrying forever is a resource leak with a statutory clock running; retry with backoff and a cap, then escalate.

Q7 explain & apply crux

Deep dive: how does the human enter this system, and what happens to what they decide?

Points a strong answer hits:

  • Threshold routing produces three outcomes, not two: auto-close below the band, escalate above it, and route the ambiguous middle to review.
  • Work is claimed with a lease rather than assigned, so two analysts never hold the same case and an abandoned case returns to the queue instead of dying.
  • The queue is priority-ordered by risk and by the statutory clock, not FIFO, with per-tenant fairness so one bank's backlog cannot starve another's.
  • The analyst sees the agent's findings, the evidence behind each claim, the policy clauses tested, and the draft narrative, with every assertion clickable through to its source artifact.
  • The override is the highest-value event in the system: it is simultaneously an audit fact, an evaluation label, and a quality signal, so it gets a schema and a required reason rather than a free-text comment.
  • Four-eyes review for dispositions that policy requires two humans to sign, modeled in the data rather than in a process document.
  • SLA timers run against the regulatory deadline, and breaching one is a reportable operational event rather than a missed ticket.
  • Override rate is the product metric: if analysts override constantly the automation is not working, whatever the accuracy number says.
Model answer: Routing produces three outcomes rather than two — auto-close, escalate, and an ambiguous middle that goes to review — and the human queue is claimed with a lease rather than assigned, so no two analysts hold the same case and an abandoned one returns to the queue. Ordering is by risk and by the statutory clock rather than FIFO, with per-tenant fairness so one bank's backlog cannot starve another's. The screen shows the findings, the evidence behind each claim and the policy clauses tested, with every assertion clickable through to its artifact. The part people under-design is the override: it is an audit fact, a training label and a quality signal at once, so it needs a schema and a mandatory reason, not a comment box. And I would treat override rate as the headline product metric, because if analysts are overriding constantly then the automation is not working no matter what accuracy says.

Q8 explain & apply crux

How do you know the agent is right, and how do you find out when it stops being right?

Points a strong answer hits:

  • A golden set built from human-validated dispositions, stratified by typology (structuring, sanctions nexus, adverse media, unusual counterparty) so accuracy is reported per class rather than as one flattering average.
  • Production traces are sampled by uncertainty and by risk band, labelled by analysts, and promoted into the regression set — the review queue is the label factory.
  • An LLM judge is acceptable at scale only if its agreement with human labels is measured continuously; an unvalidated judge is just a second unvalidated model.
  • A regression gate runs on every change to a prompt, a policy, or a model version, not only on code deploys.
  • Pin provider model snapshots. Providers change models underneath you, and an unpinned upgrade is an unreviewed change to a regulated decision process.
  • Watch input drift too: a bank retuning its monitoring rules changes your alert distribution overnight, which degrades accuracy without anything in your system changing.
  • Be honest about label scarcity — a filed report is not a conviction, so ground truth is mostly unavailable and you are really measuring analyst agreement, a proxy with known bias.
  • A correct disposition reached with a bad rationale has still failed, because what is being audited is whether the decision was defensible on the evidence available at the time.
Model answer: A golden set of human-validated dispositions, stratified by typology so accuracy is reported per class instead of as one average that hides the classes that matter. Production traces get sampled by uncertainty and risk, labelled by the analysts already reviewing them, and promoted into a regression set — the review queue is effectively the label factory. An LLM judge is fine for scale as long as its agreement with human labels is tracked continuously, otherwise it is a second unvalidated model. The gate has to fire on prompt and policy changes, not just code, and provider model versions must be pinned because an unannounced upgrade is an unreviewed change to a regulated decision. The honest caveat is label scarcity: a filed report is not a conviction, so ground truth mostly does not exist and what I am really measuring is analyst agreement, which is a proxy with known bias.

Q9 explain & apply crux

Staff-level wrap-up: what breaks at scale, how do you control cost, and how do you ship autonomy safely?

Points a strong answer hits:

  • The first ceiling is spend and third-party rate limits, not the database. An agent choosing its own tools is spending money autonomously, so cost is an input to tool selection and a hard per-case budget.
  • Instrument cost per disposition against the analyst hour it replaces — that ratio is the business case, and it is the number that decides whether the product survives.
  • Cache evidence with a per-source declared freshness policy: some data is expensive and stable, some must be fresh at decision time, and the audit record captures which snapshot was used.
  • Per-tenant queues and concurrency caps so one bank's overnight dump cannot starve every other tenant.
  • Autonomy ships as a ratchet: shadow mode (runs, decides nothing), then suggest mode (human accepts or rejects), then auto-close on the narrowest risk band with sampled QA, widening as evidence accumulates.
  • Tenant isolation: row-level security in Postgres so a forgotten predicate cannot leak across banks, and the honest caveat that background workers running as a service role bypass it, which is where the real leak would come from.
  • The silent failure to monitor for is quality decay with no error signal — the pipeline is green, throughput is fine, and dispositions have quietly become wrong. Sampled QA is the only detector.
  • A policy change deploys nothing: policy is versioned data, tested against historical cases with an outcome diff, rolled out in stages, and cases in flight stay pinned to the version they started under.
Model answer: The ceiling is cost and third-party rate limits rather than the database, which is the opposite of most systems this shape, so I would put a hard per-case budget in place and make cost a factor in tool selection — an agent choosing its own tools is spending money autonomously. The metric I would instrument first is cost per disposition against the analyst hour it replaces, because that ratio is the entire business case. Operationally: per-tenant queues so one bank's overnight dump cannot starve the rest, evidence caching with a declared freshness policy per source, and row-level security for isolation with the honest note that background workers bypass it and that is where a leak would actually come from. Autonomy ships as a ratchet — shadow, then suggest, then auto-close on the narrowest band with sampled QA. And the failure I would watch hardest is the silent one: the pipeline stays green and throughput stays fine while dispositions quietly go wrong, which nothing but sampled human QA will catch.
