The Framework

The system design interview is not a free-for-all — it follows a repeatable arc that keeps you and the interviewer synchronized. Learn the standard sequence of steps, the ~45-minute time budget, and why you clarify scope before drawing a single box.

The System Design Interview 15 questions

Results carried by this link

Key ideas

  • The standard arc: clarify functional requirements → non-functional requirements → capacity estimation → API/interface → high-level design + data model → deep dive on 1-2 components → bottlenecks/wrap-up.
  • A typical loop is ~45 minutes of design time; budget roughly 5 min requirements, 5 min estimation/API, 10-15 min high-level design, 10-15 min deep dive, 5 min wrap-up.
  • You clarify BEFORE designing because the problem is deliberately under-specified — 'design Twitter' has a hundred valid interpretations and you must pin down which one.
  • Non-functional requirements (scale, latency, consistency) are what actually drive the architecture; functional requirements only define the feature surface.
  • Estimation comes before the deep architecture so the numbers can justify your choices (sharding, caching, replication) rather than being invented after the fact.
  • The interview measures your process and communication as much as the final diagram — a structured, narrated approach beats a lucky guess at the 'right' answer.
  • There is no single correct design; the goal is a defensible design whose tradeoffs you can articulate.

Q1 multiple choice

In the standard system design interview arc, what should you do FIRST after hearing the prompt?

  1. A Clarify the functional requirements and scope the problem correct
  2. B Draw the high-level architecture so the interviewer sees progress quickly
  3. C Estimate QPS and storage so you know how big the system is
  4. D Choose a database and justify SQL vs NoSQL

Why: The prompt is deliberately vague, so you first clarify what the system must do and agree on scope. Jumping straight to architecture or a database choice commits you before you know what you are building.

Q2 multiple choice

Why is capacity estimation typically done BEFORE the detailed component design?

  1. A Interviewers award points for arithmetic regardless of the design
  2. B The numbers justify structural choices like sharding, caching, and replication correct
  3. C It is the only way to determine the functional requirements
  4. D It replaces the need to discuss consistency or availability

Why: Estimates of QPS, storage, and bandwidth tell you whether a single machine suffices or you need partitioning, caches, and replicas — so they should precede and inform the architecture. Estimation does not define features (that is requirements) nor replace the consistency/availability discussion.

Q3 multiple choice

A typical system design loop gives you about how long for the design discussion itself?

  1. A About 15 minutes
  2. B About 45 minutes correct
  3. C About 90 minutes
  4. D About 2 hours

Why: After intros and Q&A, you usually have roughly 45 minutes of actual design time, which is why time budgeting across the steps matters. Trying to cover everything in equal depth will run you out of time before the deep dive.

Q4 multiple choice

Which sequence best reflects the standard interview arc?

  1. A High-level design → requirements → estimation → deep dive → API
  2. B Requirements → estimation → API → high-level design → deep dive → wrap-up correct
  3. C Estimation → API → deep dive → requirements → high-level design
  4. D Deep dive → high-level design → estimation → requirements

Why: You scope requirements, size the system with estimates, define the interface, sketch the high-level architecture and data model, then dive deep on one or two components before wrapping up. The other orderings put design or deep dive before you have scoped or sized the problem.

Q5 multiple choice

The interviewer says only 'Design a URL shortener.' What is the best immediate move?

  1. A Assume the most common feature set and start drawing boxes
  2. B Ask clarifying questions about features, scale, and constraints correct
  3. C State that the problem is too vague to solve
  4. D Begin estimating storage for a trillion URLs

Why: Under-specification is intentional; asking targeted clarifying questions shows you can navigate ambiguity and lets you scope to something you can design well in the time given. Silently assuming, or over-estimating for an unagreed scale, skips the collaboration the interviewer is testing.

Q6 multiple choice

What does 'high-level design' produce in the arc, before the deep dive?

  1. A A line-by-line implementation of the core service
  2. B A finalized capacity plan with exact machine counts
  3. C The complete list of edge cases and failure modes
  4. D A block diagram of major components/services plus the data model and how requests flow correct

Why: High-level design is the box-and-arrow view: the major services, data stores, and request flow, plus a rough data model. Detailed implementation and exhaustive failure analysis belong to the deep dive, not the high-level sketch.

Q7 multiple choice

Which non-functional dimensions most directly shape the architecture you draw?

  1. A The programming language and the team's tooling preferences
  2. B Scale, latency targets, consistency needs, and availability targets correct
  3. C The color of the diagram and the naming of services
  4. D The interviewer's favorite database vendor

Why: Scale, latency SLOs, consistency, and availability are the forces that decide whether you shard, cache, replicate, or relax guarantees. Language and tooling rarely change the high-level shape of an interview design.

Q8 multiple choice

Why does the framework put the API/interface definition before the deep dive?

  1. A Because the API is the only thing interviewers grade
  2. B Because a clear interface pins down inputs/outputs and forces agreement on what the system exposes before internals are refined correct
  3. C Because the API determines the exact number of servers
  4. D Because you cannot estimate storage without the API

Why: Defining the endpoints (their parameters and responses) makes the contract concrete and aligns you with the interviewer on behavior before you refine internals. It is not the sole grading axis, and it does not by itself fix server counts or storage.

Q9 multiple choice

What is the purpose of the deep-dive step?

  1. A To restate the requirements in more detail
  2. B To demonstrate depth by drilling into one or two components' internals, tradeoffs, and failure handling correct
  3. C To re-estimate the capacity with more precision
  4. D To draw every component in the system at equal detail

Why: The deep dive is where you show engineering depth on a chosen component — its data structures, scaling, and failure modes. Trying to detail every box equally dilutes the signal and burns the clock.

Q10 multiple choice

During wrap-up, what is the strongest thing to do with remaining time?

  1. A Add as many new features as possible to look ambitious
  2. B Identify bottlenecks and single points of failure, and note how you would mitigate or evolve the design correct
  3. C Rewrite the whole architecture from scratch
  4. D Recompute the QPS estimate one more time

Why: Naming your design's bottlenecks, SPOFs, and next steps signals maturity and self-awareness. Piling on features or restarting the design late signals poor time judgment.

Q11 multiple choice

Why is 'there is no single correct answer' true for these interviews?

  1. A Because interviewers do not actually evaluate the design
  2. B Because any design passes as long as it has a database and a cache
  3. C Because the goal is a design whose tradeoffs you can justify for the agreed requirements, and several architectures can be defensible correct
  4. D Because the problems are random and unsolvable

Why: Multiple architectures can satisfy the same requirements; you are judged on whether your choices are coherent and well-justified, not on hitting one canonical diagram. The design is still rigorously evaluated — just not against a single key.

Q12 multiple choice

You have spent 30 of your 45 minutes still refining the high-level diagram. What does the framework suggest?

  1. A Keep polishing the diagram until it is perfect
  2. B Time-box it, move to a deep dive on a key component, and leave room to wrap up correct
  3. C Abandon the design and start a different problem
  4. D Skip the deep dive entirely and just estimate again

Why: The arc is a time budget; when a step overruns, you consciously move on so the highest-signal steps (deep dive, wrap-up) still happen. Perfecting the high-level box diagram at the cost of showing depth is a common failure.

Q13 explain & apply

Walk me through your end-to-end approach to a system design interview. What are the steps and roughly how do you budget the ~45 minutes?

Points a strong answer hits:

  • Names the arc in order: clarify functional requirements/scope → non-functional requirements → capacity estimation → API/interface → high-level design + data model → deep dive on 1-2 components → bottlenecks/wrap-up.
  • Assigns a rough time budget (e.g. ~5 min requirements, ~5 min estimation/API, ~10-15 min high-level, ~10-15 min deep dive, ~5 min wrap-up).
  • Explains that clarifying comes first because the prompt is intentionally under-specified.
  • Notes that estimation precedes deep architecture so numbers justify sharding/caching/replication.
  • Mentions driving the conversation and narrating tradeoffs throughout, and time-boxing steps that overrun.
Model answer: I start by clarifying the functional requirements and explicitly scoping what I'll design, then pin down the non-functional requirements — scale, latency, consistency, availability — because those actually drive the architecture. I do quick capacity estimation so my structural choices are numbers-justified, define the API, then sketch a high-level diagram with a data model. With that agreed, I deep-dive one or two components to show depth, and I reserve the last few minutes to call out bottlenecks, SPOFs, and how I'd evolve it. I keep a rough time budget in my head and time-box any step that runs long so the deep dive and wrap-up always happen.

Q14 explain & apply

Why is it a mistake to start drawing the architecture immediately after hearing 'Design Instagram'? What do you do instead?

Points a strong answer hits:

  • The prompt is deliberately vague/under-specified; 'Instagram' has many valid interpretations.
  • Designing before scoping risks solving the wrong problem and wasting limited time.
  • You should clarify features (functional requirements) and agree on an explicit scope first.
  • You should establish non-functional requirements (scale, read/write ratio, latency) that shape the design.
  • It also signals collaboration and ambiguity-navigation, which the interviewer is testing.
Model answer: 'Design Instagram' is intentionally open-ended, so drawing boxes first risks building the wrong system and burning time I can't get back. Instead I clarify the feature surface — is it photo upload and feed, or also stories, DMs, search? — and agree on an explicit scope like 'core photo post + home feed.' Then I establish the non-functional forces: scale, read-heavy vs write-heavy, and latency targets, which are what really shape the architecture. Only once we've agreed on what and how big do I start designing.

Q15 explain & apply

Halfway through, you realize you've spent too long on the high-level diagram and haven't started the deep dive. How do you recover?

Points a strong answer hits:

  • Acknowledge the time budget out loud and consciously move on.
  • Pick one or two high-signal components to deep-dive rather than perfecting the diagram.
  • Prioritize the deep dive because it's where engineering depth is demonstrated.
  • Preserve a few minutes for wrap-up: bottlenecks, SPOFs, next steps.
  • Frame the transition collaboratively ('let me lock this in and dive into X').
Model answer: I'd say out loud that I want to lock in the high-level design and move to a deep dive, since that's where I can show the most depth. I'd pick the component with the most interesting scaling or consistency challenge — say the feed fan-out or the ID generation — and drill into its data structures, scaling, and failure modes. I'd keep an eye on the clock and still leave two or three minutes at the end to name the bottlenecks and how I'd evolve the system, because running out of time before the deep dive is a worse signal than an imperfect diagram.
