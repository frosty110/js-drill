Back-of-Envelope Estimation

Capacity estimation turns 'design Twitter' into concrete numbers that justify your architecture. Master the mental toolkit: powers of two for data sizes, aggressive rounding, the ~86,400 ≈ 10^5 seconds-per-day trick, and deriving peak load and QPS from a daily-active-user count.

Key ideas

  • Data-size powers of two: 2^10 ≈ 10^3 = 1 KB, 2^20 ≈ 10^6 = 1 MB, 2^30 ≈ 10^9 = 1 GB, 2^40 ≈ 10^12 = 1 TB, 2^50 ≈ 10^15 = 1 PB.
  • There are 86,400 seconds in a day; round to ~10^5 so you can divide by it in your head.
  • Round everything: 100M users, 24h → 100k s, character → 2 bytes. Precision is noise at this stage; you want the right order of magnitude.
  • Average QPS ≈ (daily requests) / 86,400 ≈ (daily requests) / 10^5.
  • Peak QPS is not the average — multiply average by ~2-3x (or more for spiky/event-driven traffic) to size for the busy period.
  • Derive load top-down: DAU × actions-per-user-per-day → daily requests → divide by ~10^5 → average QPS → ×2-3 → peak QPS.
  • Reason out loud and write assumptions down; the interviewer cares about your method and whether you can sanity-check, not the exact figure.

Q1 multiple choice

Roughly how many seconds are there in a day, and what approximation makes the math easy?

  1. A 3,600 — approximate as 10^3
  2. B 86,400 — approximate as ~10^5 correct
  3. C 1,440 — approximate as 10^3
  4. D 604,800 — approximate as 10^6

Why: A day is 24 × 3,600 = 86,400 seconds, which you round to ~10^5 so you can divide daily request counts by it in your head. 3,600 is seconds per hour and 604,800 is seconds per week.

Q2 multiple choice

In back-of-envelope sizing, 2^30 bytes is approximately what?

  1. A 1 MB (~10^6)
  2. B 1 GB (~10^9) correct
  3. C 1 TB (~10^12)
  4. D 1 PB (~10^15)

Why: 2^10 ≈ 10^3 (KB), 2^20 ≈ 10^6 (MB), 2^30 ≈ 10^9 (GB), 2^40 ≈ 10^12 (TB), 2^50 ≈ 10^15 (PB). So 2^30 ≈ 1 GB. Memorizing this ladder lets you convert item-count × item-size into a storage figure instantly.

Q3 multiple choice

A service handles 5 billion requests per day. What is the approximate AVERAGE QPS?

  1. A ~500 QPS
  2. B ~5,000 QPS
  3. C ~50,000 QPS correct
  4. D ~500,000 QPS

Why: 5 × 10^9 requests ÷ 10^5 seconds/day ≈ 5 × 10^4 = 50,000 QPS. Dividing by the rounded 10^5 seconds-per-day is the core QPS trick.

Q4 multiple choice

Your average QPS is 20,000. What is a reasonable PEAK QPS estimate to size capacity for?

  1. A About the same, 20,000, since averages already smooth out spikes
  2. B Roughly 40,000-60,000 (a 2-3x peak factor) correct
  3. C Exactly 20,000 / 2 = 10,000, because peaks reduce load
  4. D At least 2,000,000 (a 100x factor by default)

Why: Real traffic concentrates in busy hours, so you multiply the daily average by a peak factor of about 2-3x (higher for spiky, event-driven, or timezone-clustered traffic). Sizing only for the average would leave the system overloaded during peaks; a flat 100x is unjustified without a known spike.

Q5 multiple choice

Why do experienced candidates round 100,000,000 daily active users to '10^8' and one day to '10^5 seconds' before dividing?

  1. A Because rounding changes the answer's order of magnitude to the correct one
  2. B Because only powers of ten are valid inputs to QPS formulas
  3. C Because at this stage you want the right order of magnitude, and rounding makes the arithmetic doable in your head correct
  4. D Because interviewers deduct points for using exact numbers

Why: Estimation targets the order of magnitude; carrying exact digits adds error-prone arithmetic without improving a figure that already has large uncertainty. Rounding to powers of ten keeps the mental math clean. It does not change the order of magnitude — that is the point — and exact numbers are fine, just unnecessary.

Q6 multiple choice

The clean top-down chain for deriving average QPS from users is:

  1. A Peak QPS × 86,400 → daily requests → DAU
  2. B DAU × actions-per-user-per-day → daily requests ÷ ~10^5 → average QPS correct
  3. C Storage per user × DAU → bandwidth → QPS
  4. D DAU ÷ actions-per-user → seconds per day → QPS

Why: Start from daily active users, multiply by how many relevant actions each performs per day to get daily requests, then divide by ~10^5 seconds to get average QPS (and multiply by a peak factor for peak QPS). The other chains mix up the direction or the quantities.

Q7 multiple choice

You assume a tweet is 280 characters. Roughly how many bytes should you budget per tweet's text, and why?

  1. A About 280 bytes, because 1 character is always 1 byte
  2. B About 560 bytes, using ~2 bytes/char to cover Unicode, then rounded correct
  3. C About 28 bytes, since text compresses 10x
  4. D About 2,800 bytes, allowing 10 bytes per character

Why: Assuming ~2 bytes/character (a safe rounding that accounts for multi-byte UTF-8) gives ~560 bytes, which you'd then round for the estimate. Assuming a flat 1 byte/char undercounts non-ASCII text; 10 bytes/char or 10x compression are not defensible defaults.

Q8 multiple choice

Which set of assumptions should you STATE OUT LOUD before estimating, so the interviewer can correct them?

  1. A Only the final QPS number, since assumptions are implied
  2. B DAU, actions per user per day, average item size, read/write ratio, and peak factor correct
  3. C The exact CPU model and memory of each server
  4. D The interviewer's expected answer so you can match it

Why: Sizing depends on inputs like DAU, per-user activity, item size, read/write ratio, and the peak factor — naming them lets the interviewer steer and makes your math auditable. Hardware specifics are premature, and there is no single 'expected answer' to reverse-engineer.

Q9 multiple choice

A photo service stores 10 million new photos/day at ~1 MB each. Approximately how much new storage per day (before replication)?

  1. A ~10 GB/day
  2. B ~100 GB/day
  3. C ~10 TB/day correct
  4. D ~1 TB/day

Why: 10^7 photos × 10^6 bytes = 10^13 bytes ≈ 10 TB per day. Remember 2^40 ≈ 10^12 = 1 TB, so 10^13 is ~10 TB; you would then multiply by a replication factor for real capacity.

Q10 multiple choice

What is the best way to sanity-check an estimate you just produced?

  1. A Compare it against known real-world scales and re-derive it a second way correct
  2. B Assume it is correct because the arithmetic was done carefully
  3. C Add more significant digits until it feels precise
  4. D Pick the number the interviewer seems to want

Why: Cross-checking against a known ballpark (e.g. 'that would be more storage than the whole company has') or re-deriving via a different path catches order-of-magnitude slips. More digits do not add correctness, and steering toward a guessed 'wanted' number defeats the exercise.

Q11 multiple choice

You estimate 5 billion daily reads and 50 million daily writes. What is the approximate read:write ratio, and why does it matter?

  1. A ~1:1 — the system is balanced, so no special optimization is needed
  2. B ~100:1 read-heavy — favor caching and read replicas correct
  3. C ~100:1 write-heavy — favor write-optimized storage and sharding the write path
  4. D ~10:1 write-heavy — favor an LSM-tree write path

Why: 5×10^9 reads ÷ 5×10^7 writes = 100:1, and since reads dominate the system is read-heavy, pushing you toward caches and read replicas. It is read-heavy, not write-heavy — reads are the larger number — so write-optimized framing is the wrong takeaway.

Q12 multiple choice

During estimation, the interviewer hasn't given you a DAU number. What is the best move?

  1. A Refuse to estimate until they provide the exact figure
  2. B State a reasonable assumption like '~100M DAU,' note it's an assumption, and proceed correct
  3. C Use the largest number imaginable to be safe
  4. D Skip estimation entirely and go to the design

Why: Stating a defensible assumption and inviting correction keeps momentum and demonstrates judgment, which is exactly what the interviewer is testing. Refusing stalls, an arbitrarily huge number distorts the design, and skipping estimation removes the justification for your architecture.

Q13 explain & apply

Walk me through how you'd estimate the peak write QPS for a service with 200 million daily active users who each post 2 items per day. Narrate your assumptions and rounding.

Points a strong answer hits:

  • Compute daily writes: 200M × 2 = 400M ≈ 4×10^8 writes/day.
  • Divide by ~10^5 seconds/day (86,400 rounded) to get average QPS ≈ 4,000.
  • Apply a peak factor of ~2-3x → peak write QPS ≈ 8,000-12,000.
  • State assumptions explicitly (DAU, posts/user/day, peak factor) and invite correction.
  • Sanity-check the order of magnitude out loud.
Model answer: I'll assume 200M DAU and 2 posts per user per day, giving 400M writes per day, or about 4×10^8. Dividing by roughly 10^5 seconds in a day gives an average of about 4,000 write QPS. Traffic isn't flat, so I'll apply a peak factor of about 2-3x, landing on roughly 8,000-12,000 peak write QPS. Those are my assumptions — DAU, posts per user, and peak factor — so correct me if any are off, and 10k writes/sec feels like the right order of magnitude for a large social service.

Q14 explain & apply

Why do you round seconds-per-day to 10^5 and data sizes to powers of ten during a design interview? Isn't that sloppy?

Points a strong answer hits:

  • Estimation targets order of magnitude, which already carries large uncertainty.
  • Rounding makes arithmetic doable in your head and keeps the conversation moving.
  • 86,400 ≈ 10^5 and the 2^10/2^20/2^30 ≈ 10^3/10^6/10^9 ladder are close enough to not shift the order of magnitude.
  • The interviewer is evaluating method and sanity-checking, not decimal precision.
  • Exact digits add error-prone work without improving a rough figure.
Model answer: It's not sloppy — it's appropriate precision. The goal is the right order of magnitude to justify a design decision like whether I need one machine or a thousand, and that answer doesn't change whether I use 86,400 or 100,000 seconds. Rounding to powers of ten lets me do the math out loud without arithmetic mistakes, and the 2^10≈10^3 ladder maps bytes to KB/MB/GB/TB cleanly. What the interviewer actually wants to see is that I can reason to a defensible ballpark and sanity-check it, not that I can long-divide.
