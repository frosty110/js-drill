QPS, Storage & Bandwidth Math

The worked-example layer of estimation: turning users and payload sizes into QPS, storage, and bandwidth figures. Practice the standard formulas — QPS from DAU and actions, peak-from-average, storage from item count × size × replication × retention, bandwidth from QPS × payload — plus cache sizing with the 80/20 rule.

Results carried by this link

Key ideas

  • Read/write QPS ≈ (DAU × actions-per-user-per-day) / 86,400; use ~10^5 for the divisor.
  • Peak QPS ≈ average QPS × peak factor (~2-3x, more for spiky traffic).
  • Storage ≈ items × item-size × replication-factor × retention-period; don't forget replication (often 3x) and metadata/indexes.
  • Bandwidth ≈ QPS × average payload size; separate ingress (write) from egress (read) since read-heavy systems push far more egress.
  • Cache sizing via the 80/20 rule: caching the hot ~20% of data often serves ~80% of requests, so you can size the cache to the working set, not the whole dataset.
  • Keep read and write paths separate throughout — a 100:1 read:write ratio means the read side dominates QPS, bandwidth, and cache design.
  • Multiply by replication for storage AND account for it in write bandwidth (each write may fan out to N replicas).

Q1 multiple choice

150 million DAU each make 20 read requests per day. What is the approximate average read QPS?

  1. A ~3,000 QPS
  2. B ~30,000 QPS correct
  3. C ~300,000 QPS
  4. D ~3,000,000 QPS

Why: 150×10^6 × 20 = 3×10^9 reads/day; ÷ 10^5 seconds ≈ 3×10^4 = 30,000 QPS average. You'd then apply a peak factor to size for the busy period.

Q2 multiple choice

A system does 30,000 average QPS. Using a 3x peak factor, what capacity should you plan for?

  1. A ~10,000 QPS
  2. B ~30,000 QPS
  3. C ~90,000 QPS correct
  4. D ~900,000 QPS

Why: Peak QPS = average × peak factor = 30,000 × 3 = 90,000 QPS. Capacity planning targets the peak, not the daily average, or the system tips over during busy hours.

Q3 multiple choice

You store 500 million records at 2 KB each with a replication factor of 3. Approximately how much raw storage?

  1. A ~1 TB
  2. B ~3 TB correct
  3. C ~30 TB
  4. D ~300 GB

Why: 500×10^6 × 2×10^3 bytes = 10^12 bytes = 1 TB of primary data; × replication factor 3 ≈ 3 TB. Forgetting the replication multiplier is a common under-estimate.

Q4 multiple choice

Which formula best captures long-term storage for a system that retains data for a fixed window?

  1. A items-per-day × item-size × replication-factor × retention-in-days correct
  2. B items × item-size, ignoring replication and retention
  3. C QPS × item-size × 86,400
  4. D DAU × replication-factor

Why: New items per day × size per item × replication × how many days you keep them gives the standing storage requirement. Ignoring replication and retention (option 1) undercounts; the QPS/DAU forms conflate throughput or users with stored volume.

Q5 multiple choice

A read-heavy service serves 40,000 QPS with an average response payload of 50 KB. What is the approximate egress bandwidth?

  1. A ~200 MB/s
  2. B ~2 GB/s correct
  3. C ~20 GB/s
  4. D ~200 GB/s

Why: Bandwidth ≈ QPS × payload = 4×10^4 × 5×10^4 bytes = 2×10^9 bytes/s = 2 GB/s of egress. Read-heavy systems are typically egress-dominated, so this is the number that sizes your serving/CDN tier.

Q6 multiple choice

Under the 80/20 rule for cache sizing, what is the practical takeaway?

  1. A You must cache 100% of the data to get any hit-rate benefit
  2. B Only 20% of requests can ever be cached regardless of data
  3. C The cache must be 80% the size of the database
  4. D Caching the hot ~20% of data can serve ~80% of requests, so size the cache to the working set correct

Why: Access is skewed: a small hot subset absorbs most traffic, so a cache sized to that working set captures the bulk of reads cheaply. You don't need to cache the whole dataset, and the hit potential is on the hot 80% of requests, not capped at 20%.

Q7 multiple choice

Daily reads are 8.6 billion. Rounding a day to ~10^5 seconds, the average read QPS is closest to:

  1. A ~8,600
  2. B ~86,000 correct
  3. C ~860,000
  4. D ~8,600,000

Why: 8.6×10^9 ÷ 10^5 ≈ 8.6×10^4 = 86,000 QPS. The rounded 86,400 ≈ 10^5 divisor keeps this a one-step mental calculation.

Q8 multiple choice

You want to cache the hot working set of 1 billion objects averaging 1 KB, assuming ~20% are hot. Roughly how much cache memory?

  1. A ~2 GB
  2. B ~20 GB
  3. C ~200 GB correct
  4. D ~2 TB

Why: 20% of 10^9 objects = 2×10^8 hot objects × 10^3 bytes = 2×10^11 bytes ≈ 200 GB. That figure tells you how many cache nodes (each with tens of GB of RAM) you need for the working set.

Q9 multiple choice

Why should you keep read QPS and write QPS as separate numbers throughout the estimate?

  1. A Because reads and writes always occur at exactly the same rate
  2. B Because they drive different design decisions — reads → caches/replicas, writes → sharding/write path — and are often orders of magnitude apart correct
  3. C Because only write QPS affects storage
  4. D Because the interviewer only grades the write path

Why: A typical read:write ratio like 100:1 means the read path dominates and needs caching/replicas while the write path drives sharding and durability — collapsing them into one number hides the dominant force. Both paths matter, and reads certainly affect serving/bandwidth even if not primary storage.

Q10 multiple choice

A write of 1 KB is replicated to 3 nodes and also written to a message queue consumed by 2 downstream services. Roughly how much write-side traffic does one logical write generate?

  1. A 1 KB — replication and fan-out are free
  2. B ~3 KB — only replication counts
  3. C ~5 KB or more — 3x for replicas plus the queue fan-out to consumers correct
  4. D ~0.5 KB — writes are compressed in half

Why: One logical write amplifies: ~3 KB across replicas plus the queue write and its delivery to 2 consumers, so real write-side bandwidth is several times the payload. Assuming replication or fan-out is free is exactly the under-estimate this question guards against.

Q11 multiple choice

You estimate 10 TB of new data per day with 3x replication, retained for 30 days. Approximate standing storage?

  1. A ~90 TB
  2. B ~300 TB
  3. C ~900 TB correct
  4. D ~30 TB

Why: 10 TB/day × 3 (replication) × 30 (days) = 900 TB ≈ just under 1 PB. This shows how replication and retention together dominate storage sizing, and why you'd then consider tiering older data to cheaper storage.

Q12 multiple choice

Your average QPS estimate comes out to 5 million for a service you know runs on a handful of machines. What should you do?

  1. A Trust the number and design for 5 million QPS
  2. B Re-check your assumptions and arithmetic — the figure likely has an order-of-magnitude error correct
  3. C Multiply by a 3x peak factor and move on
  4. D Round it up to 10 million to be safe

Why: A result that contradicts a known real-world scale is a signal to hunt for a misplaced power of ten in your inputs or division. Sanity-checking against reality is the whole point of estimation; blindly designing for or inflating a suspicious number compounds the error.

Q13 explain & apply

Estimate the storage and daily egress bandwidth for a photo-sharing service: 100M DAU, each uploads 2 photos/day at 1.5 MB, and each photo is viewed 20 times/day on average. Assume 3x replication for storage.

Points a strong answer hits:

  • Uploads/day: 100M × 2 = 200M photos ≈ 2×10^8/day.
  • Raw new storage/day: 2×10^8 × 1.5 MB = 3×10^14 bytes ≈ 300 TB/day; × 3 replication ≈ 900 TB/day (note retention would multiply further).
  • Daily views: 200M photos × 20 = 4×10^9 view-reads/day serving 1.5 MB each.
  • Egress/day ≈ 4×10^9 × 1.5 MB = 6×10^15 bytes ≈ 6 PB/day; or ~70 GB/s average, higher at peak.
  • State replication, note read egress dominates, and suggest a CDN for the egress.
Model answer: Uploads are 100M × 2 = 200M photos/day; at 1.5 MB that's about 300 TB/day of new data, and with 3x replication roughly 900 TB/day before retention. On the read side, 200M photos viewed 20 times is 4 billion view-reads/day at 1.5 MB each, which is about 6 PB/day of egress, or on the order of 70 GB/s averaged and higher at peak. The egress dwarfs everything, so I'd front this with a CDN and object storage rather than serving photos from the origin, and I'd tier or expire cold photos to control the standing storage.

Q14 explain & apply

How do you use the 80/20 rule to size a cache, and what does it save you? Give the reasoning you'd narrate in an interview.

Points a strong answer hits:

  • Access is skewed — a small hot subset of data serves most requests.
  • Caching roughly the hot 20% can satisfy roughly 80% of reads.
  • So you size cache memory to the working set, not the full dataset.
  • Compute cache size = fraction-hot × item-count × item-size.
  • Payoff: high hit rate offloads the database and cuts read latency at a fraction of the memory cost of caching everything.
Model answer: Real access patterns are skewed, so I lean on the 80/20 rule: caching the hot ~20% of objects typically absorbs ~80% of read traffic. That means I size the cache to the working set instead of the whole dataset — for a billion 1 KB objects, ~20% hot is about 200 GB of RAM rather than a terabyte. The payoff is a high hit rate that offloads most reads from the database and cuts tail latency, at a fraction of the memory cost of caching everything, and I'd validate the assumed hotness against real access logs if I had them.
