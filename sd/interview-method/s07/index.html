Numbers Every Engineer Should Know

The classic 'latency numbers every programmer should know,' held at order-of-magnitude precision. Internalize the relative ordering — cache << memory << SSD << datacenter round trip << disk seek << cross-continent round trip — plus rough throughput and single-machine QPS ballparks that let you reason about where time and bottlenecks go.

Key ideas

  • Rough latency ladder: L1 cache ~1 ns, L2 ~10 ns, main memory ~100 ns, SSD random read ~16-150 µs, intra-datacenter round trip ~0.5 ms, disk (HDD) seek ~10 ms, cross-continent round trip ~150 ms.
  • Relative ordering matters more than exact figures: cache << RAM << SSD << same-DC network << spinning disk seek << cross-region network.
  • Each rung is roughly orders of magnitude apart: memory (~100 ns) is ~100-1000x faster than an SSD read (~10-100 µs), which is ~100x faster than a disk seek (~10 ms).
  • Reading 1 MB sequentially: from memory ~microseconds, from SSD ~1 ms, from spinning disk ~tens of ms — sequential is far faster than random, especially on disk.
  • A cross-continent round trip (~150 ms) is dominated by the speed of light, so no amount of server tuning removes it — you place data near users instead.
  • Single-machine ballparks: an in-memory store handles ~100k+ ops/sec; a single relational DB handles low thousands of writes/sec to tens of thousands of reads/sec — order-of-magnitude anchors for when you must shard.
  • Use these numbers to locate the bottleneck: if a request crosses regions or hits disk randomly, that dominates; batching, caching, and locality attack the slow rungs.

Questions 15

Positions 1–15 of the code. Open questions are answered out loud and self-graded, so their characters are Y / p / n rather than option letters.

Q1 multiple choice

Order these from FASTEST to SLOWEST: (a) SSD random read, (b) main memory reference, (c) disk (HDD) seek, (d) L1 cache reference.

  1. A d < b < a < c (L1 < memory < SSD < disk seek) correct
  2. B b < d < a < c (memory < L1 < SSD < disk seek)
  3. C d < a < b < c (L1 < SSD < memory < disk seek)
  4. D a < d < b < c (SSD < L1 < memory < disk seek)

Why: L1 cache (~1 ns) < main memory (~100 ns) < SSD random read (~tens of µs) < HDD seek (~10 ms). Memory is faster than an SSD, and both are far faster than a mechanical disk seek — this ordering is the load-bearing intuition.

Q2 multiple choice

Roughly how long is a main-memory reference, to an order of magnitude?

  1. A ~1 ns
  2. B ~100 ns correct
  3. C ~100 µs
  4. D ~10 ms

Why: Main memory is on the order of 100 nanoseconds — about 100x slower than an L1 cache hit (~1 ns) and about 100-1000x faster than an SSD read. 100 µs is SSD territory and 10 ms is a disk seek.

Q3 multiple choice

A round trip within the same datacenter is closest to which order of magnitude?

  1. A ~0.5 microseconds
  2. B ~0.5 milliseconds correct
  3. C ~50 milliseconds
  4. D ~0.5 seconds

Why: An intra-datacenter round trip is roughly 0.5 ms (~500 µs). That is much slower than a memory reference but far faster than a cross-continent round trip (~150 ms).

Q4 multiple choice

A round trip between continents (e.g. California to Europe and back) is on the order of:

  1. A ~1 ms
  2. B ~15 ms
  3. C ~150 ms correct
  4. D ~1.5 s

Why: Cross-continent round trips are roughly 150 ms, dominated by the speed of light over the distance. Because physics sets this floor, you reduce it by moving data closer to users (CDNs, regional replicas), not by faster servers.

Q5 multiple choice

Approximately how much slower is a spinning-disk seek (~10 ms) than a main-memory reference (~100 ns)?

  1. A About 100x slower
  2. B About 1,000x slower
  3. C About 100,000x slower correct
  4. D About the same

Why: 10 ms / 100 ns = 10^7 ns / 10^2 ns = 10^5, so a disk seek is on the order of 100,000x slower than a memory reference. This enormous gap is why random disk I/O is the classic bottleneck and why caching hot data in RAM pays off so heavily.

Q6 multiple choice

An SSD random read is closest to which order of magnitude?

  1. A ~100 nanoseconds
  2. B ~10-100 microseconds correct
  3. C ~10 milliseconds
  4. D ~1 second

Why: SSD random reads are on the order of tens of microseconds (roughly 16-150 µs), sitting between main memory (~100 ns) and a spinning-disk seek (~10 ms). 100 ns is memory and 10 ms is an HDD seek.

Q7 multiple choice

Why is reading 1 MB sequentially from disk far faster than making many random disk seeks for the same data?

  1. A Sequential reads avoid the ~10 ms mechanical seek per access; the head streams contiguous data correct
  2. B Sequential reads are cached in L1 while random reads are not
  3. C Random reads are always served from the network instead of disk
  4. D Sequential and random disk access actually take the same time

Why: Each random access on a spinning disk pays the ~10 ms seek/rotational cost, whereas a sequential read pays it roughly once and then streams contiguous bytes. This is why algorithms and storage engines favor sequential I/O (e.g. log-structured writes).

Q8 multiple choice

You need a request to complete in under 10 ms, but it makes a cross-continent call. What does the latency ladder tell you?

  1. A Optimize the server code; the network call is negligible
  2. B The ~150 ms cross-region round trip alone blows the budget, so you must serve from a nearby region or cache correct
  3. C Add more CPU cores to absorb the round trip
  4. D Switch from SSD to memory to fix it

Why: A single ~150 ms cross-continent round trip already exceeds a 10 ms budget, and no server-side tuning removes speed-of-light latency. The fix is locality: a regional replica, edge cache, or CDN close to the user.

Q9 multiple choice

Which is the best order-of-magnitude anchor for the write throughput of a single traditional relational database node?

  1. A A few tens of writes/sec
  2. B A few thousand writes/sec (order of magnitude) correct
  3. C A few million writes/sec
  4. D A few billion writes/sec

Why: A single relational DB node handles roughly thousands of writes/sec (and higher tens-of-thousands for reads) as a working ballpark; exact numbers vary with schema and hardware. When your estimated write QPS climbs well past this, it signals you need sharding or a different store — that is the point of knowing the anchor.

Q10 multiple choice

Why do interviewers want you to know these numbers to an ORDER OF MAGNITUDE rather than exactly?

  1. A Exact nanosecond values are required to pass
  2. B The relative gaps between rungs are what drive design decisions like caching, locality, and sharding correct
  3. C The numbers change every day so exactness is impossible
  4. D Only the cross-continent number actually matters

Why: Design decisions hinge on the ~100x-100,000x gaps between memory, SSD, disk, and network — not on whether memory is 90 or 110 ns. Knowing memory << SSD << disk seek << cross-region tells you where the time goes and what to optimize.

Q11 multiple choice

An in-memory key-value store (e.g. Redis) on a single node handles roughly what order of magnitude of simple operations per second?

  1. A ~100 ops/sec
  2. B ~1,000 ops/sec
  3. C ~100,000+ ops/sec correct
  4. D ~1 billion ops/sec

Why: A single in-memory store node handles on the order of 100k+ simple ops/sec, far above a disk-backed relational node, because it avoids disk I/O. This anchor tells you how many cache nodes you need for a given read QPS.

Q12 multiple choice

Reading 1 MB sequentially from memory vs from an SSD differs by roughly which factor?

  1. A They are essentially identical
  2. B SSD is ~10-100x slower than memory for the same sequential 1 MB correct
  3. C Memory is slower than SSD for large blocks
  4. D SSD is ~1,000,000x slower than memory

Why: A sequential 1 MB read from RAM is on the order of microseconds while from an SSD it is closer to ~1 ms, roughly a 10-100x gap. Both are far faster than the tens of milliseconds a spinning disk would take for the same block.

Q13 explain & apply

Recite the latency ladder from fastest to slowest and give the rough order of magnitude for each rung, then say why the relative gaps matter more than the exact numbers.

Points a strong answer hits:

  • L1 cache ~1 ns, L2 ~10 ns, main memory ~100 ns.
  • SSD random read ~tens of µs (16-150 µs).
  • Intra-datacenter round trip ~0.5 ms.
  • Disk (HDD) seek ~10 ms.
  • Cross-continent round trip ~150 ms.
  • Explains that ~100x-100,000x gaps drive caching, locality, sequential-vs-random, and sharding decisions.
Model answer: From fastest to slowest: L1 cache around 1 ns, L2 around 10 ns, main memory around 100 ns, SSD random read in the tens of microseconds, an intra-datacenter round trip around half a millisecond, a spinning-disk seek around 10 ms, and a cross-continent round trip around 150 ms. What matters isn't the exact figure but the gaps — memory is roughly 100,000x faster than a disk seek, and a same-datacenter hop is hundreds of times faster than crossing an ocean. Those gaps are exactly what tell me to cache hot data in RAM, prefer sequential over random I/O, keep chatty calls within a datacenter, and put replicas near users.

Q14 explain & apply

A teammate proposes making a synchronous cross-region database call on the critical path of a request with a 50 ms p99 target. Using the numbers you know, explain why that's a problem and what you'd do.

Points a strong answer hits:

  • A cross-continent round trip is ~150 ms, which alone exceeds the 50 ms budget.
  • Speed-of-light latency can't be tuned away on the server.
  • Options: serve from a same-region replica (~0.5 ms RTT) or an edge cache.
  • Make the cross-region work asynchronous / off the critical path if it must happen.
  • Reason about the budget additively — each hop's latency adds up against the SLO.
Model answer: A cross-region round trip is on the order of 150 ms, so a single synchronous call already blows a 50 ms p99 budget three times over, and that latency is set by the speed of light — no server tuning removes it. I'd keep the critical path within one region by reading from a local replica, where the round trip is under a millisecond, or serving from an edge cache. If the cross-region work is truly necessary, I'd push it off the critical path and do it asynchronously, then reconcile, so the user-facing request stays within budget.

Q15 explain & apply

You estimate a service needs to sustain 50,000 writes/sec. Using single-machine throughput anchors, what does that tell you about the architecture?

Points a strong answer hits:

  • A single relational DB node handles ~thousands of writes/sec (order of magnitude).
  • 50k writes/sec is ~10x+ beyond one node, so a single primary won't suffice.
  • Implies sharding/partitioning the write path across many nodes.
  • Consider write-optimized storage (LSM-based) and batching.
  • Cross-check the anchor and note real numbers vary with schema/hardware.
Model answer: A single traditional relational node tops out around a few thousand writes/sec as a ballpark, so 50,000 writes/sec is more than an order of magnitude past what one primary can take. That tells me I need to shard the write path across many nodes — partition by a key like user or entity ID — and likely reach for write-optimized, LSM-based storage plus batching to raise per-node throughput. The exact per-node number depends on schema and hardware, so I'd validate it, but the anchor is enough to know a single database won't cut it.
