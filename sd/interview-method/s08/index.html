Agentic System Design Tradeoffs

The design questions that only exist once an LLM is making decisions inside your system: how many agents, what goes in the context window, how you know it works, when an agent is the wrong tool entirely, and what you pin, seam off and record so the thing stays explainable as models and prompts move underneath it.

The System Design Interview 19 questions

Results carried by this link

Key ideas

  • Default to one agent with several tools. Splitting buys parallelism and context isolation and costs you information at every handoff, plus a debugging story where no single trace explains the outcome.
  • Context is a budget, not storage. Everything in it competes, so the ordering is stable-first for caching and the discipline is summarizing at the tool boundary rather than appending raw output.
  • Evaluate end-to-end task success against a fixed set. Outcome-based first because it is robust, trajectory checks second for the right-answer-wrong-path case.
  • Cost and latency per task are first-class metrics, not afterthoughts. An agent that is three percent better at four times the cost is usually worse.
  • If you can enumerate the steps, write the code. An agent earns its overhead only when the path cannot be known in advance.
  • Tool descriptions are prompt engineering. The model's failure mode is usually selection rather than execution, so fewer sharply-described tools beat many overlapping ones.
  • Any tool with a side effect needs an idempotency key, because the loop will call it twice eventually.
  • Non-determinism means you cannot promise replay equality. What you can promise is preserved inputs and a comparison.

Q1 multiple choice

You are designing a system to research a topic and write a summary. What is the strongest default architecture?

  1. A One agent per sub-topic, coordinated by a planner agent, so work happens in parallel
  2. B A single agent with a small set of tools, splitting into multiple agents only when sub-tasks need different tools or permissions, or when their contexts would collide correct
  3. C A fixed pipeline with no agent, because agents are unpredictable
  4. D One agent per tool, so each stays simple and specialised

Why: Start with one agent and several tools; it is simpler to build, cheaper to run, and — most importantly — debuggable, because one trace explains the whole outcome. Multi-agent buys genuine parallelism and context isolation, and it costs information at every handoff plus the loss of that single trace. Splitting by tool is the worst version: it multiplies coordination for no isolation benefit, since the tools were never the thing competing for context. A planner-plus-worker split where the planner only ever talks to the worker is really one agent with two prompts, so it pays coordination cost for nothing. And a fixed pipeline is often right — see the last question in this set — but 'agents are unpredictable' is the wrong reason.

Q2 explain & apply

When would you split one agent into several, and what does the split cost you?

Points a strong answer hits:

  • Default is one agent with several tools; splitting is the exception that needs a reason.
  • Good reasons: sub-tasks genuinely need different tools or permissions; contexts would collide; you want independent attempts to compare.
  • Bad reason: splitting along role names or an org chart. A planner that only talks to a worker is one agent with two prompts.
  • The cost is information loss at every handoff — the receiving agent gets a summary, not what the sender actually saw.
  • The other cost is debuggability: no single trace explains the outcome, so failures become archaeology.
  • Every split needs an explicit answer for how results merge, because that is where quality leaks.
Model answer: I default to one agent with several tools and treat splitting as the exception. I split when sub-tasks genuinely need different tools or permissions, when their contexts would otherwise collide, or when I want independent attempts I can compare. What I avoid is splitting along role names, because a planner that only ever talks to a worker is one agent with two prompts paying coordination cost for nothing. The real costs are information loss at every handoff, since the receiver gets a summary rather than what the sender saw, and losing the single trace that explains an outcome. So every split needs an explicit story for how results merge.

Q3 multiple choice

Your agent calls a tool that returns a 40KB JSON document. What do you do with it?

  1. A Append the full response to the message history so nothing is lost
  2. B Truncate it to the first 2KB and continue
  3. C Summarise or extract at the tool boundary, keep a reference to the full payload, and let the agent re-read it on demand correct
  4. D Start a new context window for each tool call

Why: Appending raw payloads is the single most common way a working agent stops working at depth: by turn ten the window is full of JSON nobody will re-read, and attention to any individual fact degrades as the context grows. Summarising at the boundary while keeping the full payload retrievable preserves the information without spending the budget on it. Blind truncation is worse than summarising because it cuts at an arbitrary byte rather than by relevance, and the important field is as likely to be at the end as the start. Starting a fresh context per tool call throws away the task state that made the call meaningful.

Q4 explain & apply

How do you manage context and memory for an agent that runs for many turns?

Points a strong answer hits:

  • Treat context as a budget rather than storage: everything in it competes for attention.
  • Order it stable-first so the reusable prefix caches: system prompt, then task, then retrieved evidence, then working state.
  • Summarise or extract at the tool boundary instead of appending raw output.
  • Externalise long content to a file or store the agent can re-read on demand, keeping only a reference in context.
  • Compact the history into a structured state object — decisions made and questions still open — rather than carrying the transcript.
  • For very long tasks, compaction beats reaching for a bigger window, because a larger window degrades rather than solving the problem.
Model answer: I treat the window as a budget rather than storage, because everything in it competes. I order it stable-first so the prefix caches: system prompt, task, then just-in-time evidence, then working state. The main discipline is summarising at the tool boundary rather than appending raw output, and externalising anything long to a store the agent can re-read on demand. For a long-running task I compact the history into a structured state object — what has been decided, what is still open — instead of carrying the transcript forward. Reaching for a bigger window is usually the wrong instinct, since attention to any single fact degrades as context grows.

Q5 multiple choice

You need to know whether a change to your agent made it better. What is the primary measurement?

  1. A End-to-end task success against a fixed evaluation set, with cost and latency reported alongside correct
  2. B Per-turn quality ratings from whoever is testing it that week
  3. C The number of tool calls per task, since fewer is better
  4. D Whether the model's stated reasoning sounds correct when you read it

Why: The unit that matters is the task, not the turn, because an agent can take a bad path and still land correctly or take a good path and fail at the end. A fixed set makes runs comparable across changes, which per-turn impressions never are. Cost and latency belong in the same report because they are part of the verdict: an agent three percent better at four times the cost is usually worse, and you cannot see that if you only report quality. Tool-call count is a diagnostic, not a goal — fewer calls is sometimes the agent giving up early. And reading the reasoning is useful for debugging but is exactly the signal that sounds most convincing while being least reliable.

Q6 explain & apply

Design the evaluation setup for a production agent. What do you measure, and what do you distrust?

Points a strong answer hits:

  • A fixed evaluation set of representative tasks, so runs are comparable across changes.
  • Outcome-based scoring first because it is robust; trajectory checks second for the right-answer-wrong-path case.
  • Trajectory matters more when the path is part of the product — an audit trail, a regulated decision, a shown rationale.
  • An LLM judge is acceptable at scale only if its agreement with human labels is measured continuously.
  • The regression gate must fire on prompt and tool-description changes, not just code changes.
  • Cost and latency per task reported alongside quality, since a quality gain can be an economic loss.
  • Pin the provider's model version: an unannounced upgrade is an unreviewed change to the system.
  • Build a failure taxonomy — wrong tool, malformed arguments, hallucinated result, gave up early, looped — because 'it failed' is not actionable.
Model answer: A fixed set of representative tasks scored end-to-end, so changes are comparable. Outcome-based first because it is the robust signal, then trajectory checks for the case where it got the right answer down a path I would not accept, which matters most when the path is itself the product. An LLM judge is fine at scale as long as I am tracking its agreement with human labels; otherwise it is a second unvalidated model. The gate has to fire on prompt and tool-description edits, not just code, and I pin the provider's model version because an unannounced upgrade is an unreviewed change. I report cost and latency beside quality, and I keep a failure taxonomy, because 'it failed' does not tell me what to fix.

Q7 multiple choice

A team wants to replace a working rules engine with an agent. The rules are documented, finite, and rarely change. What is the right call?

  1. A Replace it, since the agent will handle edge cases the rules miss
  2. B Run both and take the agent's answer when they disagree
  3. C Replace it, because maintaining rules by hand does not scale
  4. D Keep the rules engine. If the steps can be enumerated, deterministic code is cheaper, faster, testable and debuggable, and an agent adds cost and variance for no capability gain correct

Why: This is the highest-signal question in agentic design, and the answer is usually the unglamorous one. An agent earns its overhead only when the path cannot be known in advance; when it can, you are paying tokens, latency and non-determinism for something an if-statement did correctly and for free. Deterministic code is also testable and debuggable in ways an agent is not. Running both and preferring the agent on disagreement is the worst option: it costs more than either and resolves conflicts in favour of the less predictable component. If edge cases are genuinely being missed, that is an argument for extending the rules or for an LLM step at a specific decision point — a pipeline with model calls in it is not an agent, and is often the right middle answer.

Q8 explain & apply

When is an agent the wrong tool? Give the test you apply.

Points a strong answer hits:

  • The test: can you enumerate the steps in advance? If yes, write the code.
  • An agent earns its overhead only when the path genuinely cannot be known ahead of time.
  • A pipeline with LLM calls at fixed points is not an agent, and is frequently the correct middle answer.
  • Also wrong when the latency budget is tight, since a loop of model calls has an unpredictable tail.
  • Also wrong when you cannot evaluate the outcome, because you will not know whether it is working.
  • Also wrong when a mistaken action is both unrecoverable and unreviewed.
  • The honest framing: agents are expensive and variable, so the burden of proof is on using one.
Model answer: My test is whether I can enumerate the steps. If I can, I write the branch, because deterministic code is cheaper, faster, testable and debuggable, and an agent buys me nothing there. An agent earns its overhead only when the path cannot be known in advance — open-ended research, or an investigation where I do not know what I need until the first result comes back. I would also rule one out when the latency budget is tight, since a loop of model calls has an unpredictable tail; when I cannot evaluate the outcome, because then I will never know if it works; and when a wrong action is both unrecoverable and unreviewed. A pipeline with model calls at fixed points is not an agent and is very often the right middle answer.

Q9 multiple choice

Your agent frequently picks the wrong tool. Where do you look first?

  1. A The model — switch to a larger one
  2. B The tool descriptions and the size of the tool set, since selection is usually the failure and descriptions are the prompt the model selects from correct
  3. C The temperature setting
  4. D The order the tools are registered in

Why: Tool descriptions are prompt engineering and deserve the same care as the system prompt, because they are literally what the model reads when choosing. The common causes are two overlapping tools whose descriptions do not distinguish them, or a set large enough that selection becomes a needle problem. Consolidating or sharpening beats upgrading the model, which is more expensive and often does not fix an ambiguity that a human reader would also trip over. Temperature affects sampling variance rather than a systematic wrong choice, and registration order is not something to design around.

Q10 explain & apply

How do you design the tools an agent calls?

Points a strong answer hits:

  • Fewer, sharply-described tools beat many overlapping ones, because selection is the usual failure mode.
  • Descriptions are prompt engineering: they are what the model reads when choosing, so they get the same care as the system prompt.
  • Validate arguments at the boundary; the model will eventually emit a malformed or hallucinated argument.
  • Return errors the model can act on — name the missing field and its format — rather than a stack trace it can only apologise for.
  • Any tool with a side effect needs an idempotency key, because retries are the default and the loop will call it twice.
  • Scope permissions per tool, so a mistaken call cannot do more damage than the task requires.
Model answer: Fewer tools with sharper descriptions, because the model's failure is usually selection rather than execution, and the description is the prompt it selects from. I validate arguments at the boundary since a malformed or hallucinated argument is inevitable, and I return an error the model can act on — naming the missing field and its format — rather than a stack trace, which it can only apologise for. Anything with a side effect gets an idempotency key, because retries are the default and the loop will eventually call it twice. And I scope permissions per tool so a mistaken call cannot do more damage than the task actually requires.

Q11 multiple choice

An agent in production occasionally loops, calling the same tool with the same arguments until it is killed. What is the most useful fix?

  1. A Lower the temperature so it stops repeating itself
  2. B Remove the tool it loops on
  3. C Add a longer timeout so it has room to work through the task
  4. D Cap iterations and budget, and detect the repeated identical call — then surface the repetition back to the model rather than only erroring correct

Why: You need both the backstop and the diagnosis. A hard iteration cap and a cost budget stop the bleeding, and they should fail loudly rather than silently truncating, so the failure is visible in your metrics. But the useful part is detecting the repeat and telling the model about it, because a loop usually means the agent is not registering that the call already failed — surfacing that gives it a chance to change strategy, where a bare error does not. Lowering temperature does not address a systematic dead end. Removing the tool removes a capability to avoid a bug. A longer timeout makes the same failure more expensive.

Q12 explain & apply

How do you keep an agent's cost under control, and why is cost a design input rather than a report?

Points a strong answer hits:

  • An agent that chooses its own tools is spending money autonomously, so the bound has to exist before the spend, not after.
  • A hard per-task budget in tokens and in paid tool calls, failing loudly when exceeded.
  • Cost as a factor in tool selection where calls have very different prices.
  • Cache expensive lookups with a declared freshness policy per source, since some data is stable and some must be fresh at decision time.
  • Order checks by cost and information gain: run the cheap disqualifying step before the expensive one.
  • The product metric is cost per completed task measured against whatever it replaces, which is what decides if the system is viable.
Model answer: The key idea is that an agent choosing its own tools is spending money autonomously, so the bound has to exist before the spend rather than in a dashboard afterwards. I put a hard per-task budget on tokens and paid tool calls, and make it fail loudly when it trips. Where calls differ a lot in price I make cost a factor in selection, cache expensive lookups with an explicit freshness policy per source, and order checks so the cheap disqualifying one runs before the expensive one. The metric I would actually instrument is cost per completed task against whatever it replaces, because that ratio is what decides whether the system is worth running at all.

Q13 multiple choice

A stakeholder asks you to guarantee that re-running a past agent task will reproduce the same output. What is the honest answer?

  1. A Yes, if you pin the model version and set temperature to zero
  2. B Yes, by caching every response and replaying from the cache
  3. C No. What you can guarantee is that the inputs, the trace and the evidence are preserved exactly, so a re-run is a comparison rather than a proof correct
  4. D No, and therefore reproducibility is not worth designing for

Why: Even pinned and at temperature zero, output is not guaranteed identical: batching, hardware and provider-side changes all introduce variance, and a promise of bit-exact replay is one you will eventually be caught failing. The defensible guarantee is preservation — inputs, the reasoning trace, and the evidence the agent was shown — which makes a re-run a comparison you can reason about. Replaying from a cache reproduces the recording rather than the behaviour, so it proves nothing about the system. And giving up on reproducibility altogether throws out the valuable part: preservation is very much worth designing for, especially anywhere a decision has to be defended later.

Q14 explain & apply

Where does a human belong in an agentic system, and how do you decide the threshold?

Points a strong answer hits:

  • Human review is a designed component, not an error path: it needs a queue, an interface and an SLA.
  • Route by confidence and by stakes, which are different axes — low confidence on a trivial action may need no human, high confidence on an irreversible one may.
  • The threshold is a policy decision owned by whoever carries the risk, not a number tuned on aggregate accuracy.
  • Capture the human's decision as a first-class event with a reason, because it is an audit fact and an evaluation label at once.
  • Feed overrides back into the evaluation set; the review queue is the highest-quality label source you have.
  • Override rate is the product metric: constant overriding means the automation is not working whatever accuracy says.
  • Ship autonomy progressively — shadow, then suggest, then act on the narrowest band — so each widening is earned.
Model answer: I treat human review as a designed component rather than a fallback, so it gets a queue, an interface and an SLA. Routing is by confidence and by stakes, which are separate axes: low confidence on a reversible action might not need anyone, while high confidence on an irreversible one might. The threshold itself is a policy decision owned by whoever carries the risk rather than something I tune on aggregate accuracy. I capture the human's decision with a required reason, because it is simultaneously an audit fact and the best evaluation label I will ever get, and I feed overrides back into the eval set. The metric I watch is override rate: if humans are constantly overriding, the automation is not working whatever the accuracy number says.

Q15 multiple choice

An agent's answer quality degrades noticeably one Tuesday. Nothing was deployed and no code changed. What is the most likely cause, and what would have prevented it?

  1. A The provider moved the alias you point at onto a newer snapshot. Pinning the dated snapshot instead makes that a change you choose rather than one you discover correct
  2. B History accumulated past the point where the important instructions still get attention. Compaction into a structured state object prevents it
  3. C A tool began returning a slightly different response shape. Validating tool output against a schema at the boundary catches it
  4. D Temperature is above zero, so variance day to day is expected. Setting temperature to zero removes it

Why: An alias like a bare model name is a moving pointer, and providers move it. Nothing in your repository changed, which is exactly why this is hard to date afterwards: an unannounced provider upgrade is an unreviewed change to production behavior. Pinning the dated snapshot, and versioning the prompt and tool schema alongside it, converts that into a change you make deliberately. Context rot and a drifting tool response are both real failures, but neither arrives on a day when nothing on your side moved. Temperature zero is the seductive wrong answer: it reduces sampling variance but does not make a model deterministic, and it would not explain a step change on one day.

Q16 multiple choice

You are reading an agent codebase. Feature code imports the provider SDK directly and names the model inline at each call site. What is the strongest argument for putting the model behind an interface?

  1. A SDK imports are heavy, so a single import point reduces cold-start time and bundle size
  2. B It breaks the layering convention the rest of the codebase follows, and consistency makes the code easier to read
  3. C Provider SDKs change their interfaces often, so one import point reduces the work of an upgrade
  4. D Swapping a provider, running two side by side to compare, and stubbing the model in a test all become the same small change instead of three unrelated ones correct

Why: The seam pays for itself in the operations you will actually perform on agent code, and those three are the same operation seen from different angles: substituting the thing behind the interface. Once feature code never names a model and never touches a provider-specific response shape, each is a configuration change. The upgrade-cost argument is true and is the weaker version of the same point, because it only pays on the days you upgrade. Cold start is a real cost but a small one and is not why you would do this. Consistency is the trap: it is an argument from convention, and at a company that says clean code matters less than judgment it answers a question nobody asked. Worth saying the cost out loud too, since an abstraction over a provider you will never swap is speculative generality.

Q17 multiple choice

An agent auto-closes cases. You need to answer both “why did case 4711 close?” and “which reason closed the most cases this month?”. What does the decision row need?

  1. A A free-text rationale, since any structured field will be too coarse to explain one specific case
  2. B A reason code from a closed, versioned enum and a free-text rationale, because one is what you group by and the other is what a person reads correct
  3. C A reason code from a closed, versioned enum, since free text cannot be aggregated and will not be written consistently
  4. D The full model response, since it already contains the rationale and any structured field can be derived from it later

Why: The two questions are different shapes and need different columns. Grouping needs a closed vocabulary, and letting the model emit free-form reason strings produces thousands of near-duplicates and no dimension at all. Explaining one case needs prose, because an enum value cannot say what was specific about this one. Neither substitutes for the other, and saying that is the point. Storing the raw response and deriving the category later is the tempting version and it fails twice: you cannot GROUP BY a paragraph, and re-deriving a category with a second model call adds its own drift on top. One honest limit to state either way: a self-reported rationale is evidence of reasoning rather than proof of it, because the model narrates after the fact.

Q18 multiple choice

Your agent reports a confidence score with every decision and the product acts automatically above 0.85. What has to be true for that threshold to mean anything?

  1. A The score is derived from token probabilities rather than from the model being asked to state a number
  2. B The threshold is set so the share acted on automatically stays inside what the review team can absorb
  3. C Outcomes are sampled and checked, per model and prompt version, so you know whether 0.85 corresponds to being right about eighty-five percent of the time correct
  4. D The score is normalized across agents so that 0.85 carries the same meaning everywhere in the system

Why: A model stating 0.9 is producing a number, not a probability, and the only thing that turns it into one is measuring agreement with outcomes over a sample. It has to be bucketed by model and prompt version, because a prompt change can move calibration without moving anything you would notice. Uncalibrated confidence is worse than none, since people act on it. Token probabilities feel more principled and are still uncalibrated, so they need the same measurement. Sizing the automated share to review capacity is real operational planning and is a different question from whether the number means anything. Normalizing across agents makes uncalibrated scores uniformly meaningless rather than fixing them.

Q19 multiple choice

You are moving an agent from recommending an action to taking it. What should decide when to widen the band it acts on by itself?

  1. A Measured agreement between the agent's recommendation and the reviewer's decision on the same cases, which only exists if you stored both correct
  2. B A schedule agreed with the customer up front, so the rollout has dates everyone can plan around
  3. C The agent's own confidence distribution, widening once a large enough share of decisions clears the threshold
  4. D The size of the queue, widening when the backlog grows past what the reviewers can clear

Why: Autonomy is earned against evidence, and the evidence is disagreement: run the agent alongside the humans, store the recommendation next to the applied action, and widen where they already agree. That column pair is the whole mechanism, and a system that only stores the final outcome cannot compute it at all. Advancing on a schedule is a deploy wearing a rollout's clothes, since the date arrives whether the evidence did or not. Using the agent's own confidence to justify widening is circular unless that confidence has been calibrated against outcomes, which is the thing you are trying to establish. Backlog pressure is the most dangerous of the four: it is a real force and it argues for more autonomy exactly when you have the least evidence for it.
