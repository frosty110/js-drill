Agentic Decision Patterns

The named patterns an LLM system can be built from, arranged as a ladder from one call to a fleet of agents — and the rule for choosing a rung. s08 asks what an agent costs you to operate; this asks which shape you should have reached for in the first place, which is the question an interviewer is actually testing when they say 'how would you architect this'.

The System Design Interview 14 questions

Results carried by this link

Key ideas

  • The patterns form an escalation ladder: single call with tools → prompt chaining → routing → parallelization → reflection → planning/ReAct → multi-agent. Each rung costs more tokens, latency and failure surface than the one below it.
  • The rule is to take the LOWEST rung that solves the problem. Naming a pattern is not the skill; declining to climb is.
  • Workflow versus agent is one question: can you predict the steps? If the path is knowable in advance, encode it. An agent earns its overhead only when the number of steps cannot be known until the work is underway.
  • Parallelization splits two ways for two different reasons — sectioning for independent subtasks (speed), voting for the same task run N times (confidence).
  • Reflection only pays when the criteria are EXTERNALLY verifiable. Self-critique against a subjective goal burns a second model call and returns the model's own taste.
  • Multi-agent has two distinct shapes: a manager that delegates and synthesizes, or decentralized handoff where agents transfer control peer-to-peer. They fail differently — the manager is a bottleneck, handoff loses the thread.
  • Delegation is a specification. A subagent needs an objective, an output format, guidance on which tools and sources to use, and explicit task boundaries, or subagents duplicate each other's work.
  • Multi-agent is a budget decision before it is an architecture decision: agents run roughly 4× the tokens of a chat turn, and multi-agent systems roughly 15×.
  • Decouple plan generation from plan execution. Generate the plan, validate it by heuristic or judge, and only then execute — so a bad plan is caught before anything with a side effect runs.

Questions 14

Positions 1–14 of the code. Open questions are answered out loud and self-graded, so their characters are Y / p / n rather than option letters.

Q1 multiple choice crux

You have seven named agentic patterns available and a task in front of you. What is the selection rule?

  1. A Pick the most capable pattern the task could plausibly need, since headroom costs nothing if unused
  2. B Take the lowest rung on the ladder that actually solves the problem, and climb only when it demonstrably fails correct
  3. C Match the pattern to the one your framework has the best abstraction for
  4. D Start multi-agent and collapse it down once you learn which agents were unnecessary

Why: Each rung adds tokens, latency and failure surface, so unused headroom is not free — it is paid for on every request. Starting high and collapsing down (the tempting distractor) sounds empirical but you pay full cost the whole time you are learning, and a working multi-agent system is rarely torn back down.

Q2 multiple choice crux

In DDIA-style terms, what is the single question that separates a workflow from an agent?

  1. A Whether the system calls external tools or only generates text
  2. B Whether a human reviews the output before it takes effect
  3. C Whether you can predict the required number of steps in advance correct
  4. D Whether the model is allowed to write to a database rather than only read

Why: A workflow is a path you encoded because you knew it; an agent decides its own path because you could not. Tool use (the tempting distractor) does not settle it — a fixed chain can call tools, and that is still a workflow.

Q3 explain & apply

An interviewer describes a support system that must classify a ticket, look up the customer, and draft a reply. Walk the ladder out loud and land on a rung. What would have to change for you to climb higher?

Points a strong answer hits:

  • Name the steps and observe they are knowable in advance — classify, look up, draft — which makes this a workflow, not an agent.
  • Prompt chaining is the natural fit: three steps, each consuming the previous output, with a deterministic order.
  • Add routing if ticket categories need genuinely different downstream handling (a refund path versus a bug report path) — that is classification into specialized handlers, still not an agent.
  • Reject the agent rung explicitly: nothing here has an unknown step count, so the loop buys nothing and costs tokens, latency, and a harder debugging story.
  • The trigger to climb would be a step count that cannot be known until the work starts — e.g. 'investigate until you can explain the charge', which may need one lookup or nine.
  • Note the cheap escape hatch: if the drafted reply must meet a checkable standard (policy compliance, required disclosures), add an evaluator-optimizer loop rather than promoting the whole thing to an agent.
Model answer: The steps are knowable, so this is a workflow — I'd start with prompt chaining: classify, look up, draft, each feeding the next. If different ticket categories need genuinely different handling I'd add routing in front, which is still a workflow. I would not reach for an agent here, because nothing in the task has an unpredictable step count, and the loop would buy me nothing while costing tokens and traceability. What would change my mind is a requirement like 'investigate until the charge is explained' — that has no knowable step count, and that is exactly where an agent earns its overhead.

Q4 multiple choice crux

Parallelization splits into two variants. What distinguishes sectioning from voting?

  1. A Sectioning runs independent subtasks concurrently; voting runs the same task several times and aggregates for confidence correct
  2. B Sectioning splits the prompt by token count; voting splits it by topic
  3. C Sectioning is for read-only tasks; voting is for tasks with side effects
  4. D Sectioning uses one model; voting requires models from different providers

Why: They parallelize for different goods — sectioning buys wall-clock time on decomposable work, voting buys confidence on a single judgement by sampling it repeatedly. Requiring different providers (the plausible-sounding distractor) is an occasional implementation choice, not what defines voting.

Q5 multiple choice

Your team wants to add a reflection loop so a second model call critiques the first. When does this pattern actually pay for itself?

  1. A Whenever output quality matters, since a second opinion is always better than one
  2. B When the criteria are externally verifiable — the critic can check against something outside its own judgement correct
  3. C When the first model is smaller than the critic model
  4. D When latency budget allows it, since the only real cost is the extra round-trip

Why: Reflection works when there is ground truth to check against — tests that run, a schema that validates, a policy that can be cited. Against a subjective goal the critic returns the model's own taste at double the cost, which is why 'quality matters' is the trap: it is true of every task and therefore selects nothing.

Q6 explain & apply

You are asked to justify a multi-agent design to a skeptical staff engineer who thinks one agent with more tools would do. Make the case honestly, including what it costs.

Points a strong answer hits:

  • State the cost first to establish credibility: agents run roughly 4× the tokens of a chat turn, and multi-agent systems roughly 15×.
  • Name the two things the split actually buys — genuine parallelism on independent subtasks, and context isolation so each subagent works in a clean window.
  • Give the qualifying condition: the roles must be genuinely separable and the work must exceed what one context window can hold. If both aren't true, the single agent wins.
  • Concede the losses explicitly — information is dropped at every handoff, and no single trace explains the outcome, which makes debugging materially harder.
  • Point out that token spend correlates strongly with task success, so the 15× is buying something real, not pure waste — but only on tasks whose value justifies it.
  • Land on the decision framing: this is a budget decision before it is an architecture decision, so it should be defended with the task's value, not with elegance.
Model answer: I'd lead with the cost, because it's large: agents run about 4× the tokens of a chat turn and multi-agent systems about 15×. What that buys is real parallelism on independent subtasks and context isolation, so each subagent reasons in a clean window instead of one agent drowning in accumulated tool output. The qualifying test is whether the roles are genuinely separable and the work exceeds a single context — if either fails, his single agent is the better design and I'd say so. The honest cost beyond tokens is that we lose information at every handoff and no single trace explains the outcome. So I'd defend this on the value of the task, not on elegance.

Q7 multiple choice crux

A lead agent spawns subagents that keep duplicating each other's work and returning overlapping findings. What is the most likely defect?

  1. A The subagents share a context window and are reading each other's intermediate output
  2. B Too few subagents were spawned, so each is over-scoped
  3. C The delegation is underspecified — subagents lack objectives, output formats, tool guidance and explicit task boundaries correct
  4. D The lead agent's model is too small to synthesize the results

Why: Delegation is a specification, and a vague one produces subagents that each interpret the task the same broad way. Shared context (the tempting distractor) would cause the opposite symptom — coordination, not duplication — and is not how subagent isolation works.

Q8 multiple choice

Multi-agent systems come in two coordination shapes. Which pair is correct, and how do they fail differently?

  1. A Manager (central orchestrator delegates and synthesizes) versus decentralized handoff (agents transfer control peer-to-peer); the manager becomes a bottleneck, handoff loses the thread correct
  2. B Synchronous versus asynchronous; the first blocks, the second drops messages
  3. C Stateless versus stateful; the first forgets, the second leaks memory across tasks
  4. D Supervised versus unsupervised; the first needs a human, the second does not

Why: Manager centralizes the goal and the synthesis, so it is the throughput ceiling and the single point of misunderstanding; handoff distributes control, so no agent holds the whole objective and intent degrades across transfers. The other pairs are real distinctions in distributed systems but they are not the multi-agent coordination axis.

Q9 explain & apply

Design the step that sits between an agent producing a plan and the agent acting on it. Why is that seam worth building?

Points a strong answer hits:

  • Decouple generation from execution: the agent proposes a plan as a first-class artifact rather than immediately acting.
  • Validate the proposed plan before execution — by heuristic (do the named tools exist, are required parameters present, are constraints satisfied) or by an AI judge.
  • Only execute plans that pass validation; reject or regenerate the rest.
  • The seam is worth building because it catches planning failures — invalid tools, wrong parameters, unmet constraints — BEFORE anything with a side effect runs.
  • It is far cheaper to discard a bad plan than to compensate a bad action, and some actions (payments, emails, deletes) have no compensating transaction at all.
  • It also creates the natural human-in-the-loop insertion point: a human approves the plan, not each individual tool call, which is a far lower review burden.
  • Note the failure taxonomy it addresses — planning failures are distinct from tool failures and from efficiency failures, and only this seam catches the first class.
Model answer: I'd make the plan an artifact rather than a side effect: the agent proposes, a validator checks it, and only an approved plan executes. Validation can be cheap heuristics — do these tools exist, are the parameters well-formed, are the constraints satisfied — or a judge model for the harder cases. The reason the seam is worth building is that planning failures are a distinct class from tool failures, and this is the only place you catch them before something irreversible happens. Discarding a bad plan is cheap; compensating a bad action may be impossible if it was a payment or an email. It also gives you the right human-in-the-loop granularity — a human approves one plan instead of reviewing twenty tool calls.

Q10 multiple choice

You are building a ReAct-style planning loop. Which safeguard is non-optional?

  1. A A second model reviewing every observation before the next action
  2. B An explicit iteration cap on the reason-act-observe cycle correct
  3. C Forcing the model to emit its full remaining plan on every turn
  4. D Running each action twice and comparing the observations

Why: An unbounded loop is the characteristic failure of the pattern — the agent recovers from an error by trying again, forever, burning budget with no termination condition. Re-running every action (the last distractor) doubles cost and is actively unsafe for anything with a side effect.

Q11 explain & apply

An agent runs for fifty turns and its context window is filling with raw tool output. Name the techniques you'd apply and what each one trades away.

Points a strong answer hits:

  • Frame context as a finite attention budget, not storage: recall degrades as the window fills, so everything in it competes.
  • Compaction — summarize the history when it approaches the limit and continue from the summary; trades fidelity for room, and the hard part is choosing what to keep (decisions, constraints, open bugs) versus discard (redundant tool output).
  • Structured note-taking — persist state to an external file the agent re-reads; trades an extra tool round-trip for memory that survives outside the window.
  • Sub-agent isolation — delegate detailed exploration to a subagent with a clean window that returns only a condensed summary; trades information at the handoff for a coordinator that stays legible.
  • Just-in-time retrieval — hold lightweight identifiers and load full content only when needed; trades latency at point of use for a window that isn't pre-loaded with things never read.
  • Tool design as a context lever — tools that return token-efficient results and don't overlap prevent waste at the source, which is cheaper than any cleanup technique.
Model answer: I'd treat the window as an attention budget rather than storage, because recall degrades as it fills. Four techniques, each with a real trade: compaction summarizes history to buy room but loses fidelity, and the skill is keeping decisions and constraints while dropping redundant tool output. Structured note-taking pushes state into an external file the agent re-reads, costing a round-trip. Sub-agent isolation sends detailed exploration to a clean window and returns a summary, which costs information at the handoff. Just-in-time retrieval holds identifiers and loads content only when needed. The cheapest fix is upstream though — tools that return token-efficient results stop the problem at the source.

Q12 multiple choice crux

Which task is the clearest fit for the routing pattern specifically, rather than a chain or an agent?

  1. A Summarizing a long document by splitting it into sections and merging the summaries
  2. B Investigating an incident until the root cause is identified
  3. C Translating a document, then proofreading the translation, then formatting it
  4. D Directing a customer query to refunds, technical support, or account management, each with different tools and prompts correct

Why: Routing classifies an input and dispatches it to one of N specialized handlers, which is exactly the triage shape. The first option is sectioning, the third is prompt chaining, and the second has no knowable step count so it is the agent case.

Q13 multiple choice

A team reports their multi-agent system performs no better than a single agent, despite 15× the token spend. Which explanation best fits the known evidence?

  1. A The task was not decomposable into genuinely independent subtasks, so parallelism bought nothing while handoffs lost information correct
  2. B The subagents used the same model as the single-agent baseline, so no additional capability was introduced
  3. C Multi-agent systems require more turns to converge and needed longer to run
  4. D The lead agent's synthesis step discarded most of the subagent output by design

Why: The split pays only when the work genuinely separates; forced onto a sequential task it adds handoff loss and coordination overhead with no parallelism to show for it. Same-model subagents (the tempting distractor) is not the defect — context isolation is the point, not a smarter model.

Q14 explain & apply

Give the shortest honest answer you can to 'when should we NOT use any of these patterns?' — and defend it against the objection that you're being unambitious.

Points a strong answer hits:

  • The test: if you can enumerate the steps, write the code. Determinism is a feature, not a limitation.
  • A documented, finite, rarely-changing rule set is already a correct program — replacing it with a model trades an auditable artifact for a probabilistic one and gets nothing back.
  • Name what you lose: reproducibility, a readable trace, cheap testing, and a cost that doesn't scale with token prices.
  • Answer the ambition objection directly — the ambitious move is matching the tool to the problem, and shipping a rules engine that is right every time beats an agent that is right most of the time.
  • Give the condition that would flip the call: inputs that are open-ended or unstructured enough that enumeration genuinely fails, or a rule set changing fast enough that maintenance dominates.
  • Note the hybrid that usually wins: deterministic code for the enumerable path, a model only at the specific step that needs judgement.
Model answer: The test is simple: if you can enumerate the steps, write the code. A documented, finite, rarely-changing rule set is already a correct program, and replacing it with a model trades an auditable artifact for a probabilistic one while losing reproducibility, a readable trace, and cheap testing. On the ambition objection — I'd argue matching the tool to the problem is the ambitious move, and a rules engine that's right every time beats an agent that's right most of the time on a path we already understand. What would flip my call is inputs open-ended enough that enumeration genuinely fails, or a rule set churning fast enough that maintenance dominates. Usually the right answer is the hybrid: deterministic code for the enumerable path, a model only at the step that actually needs judgement.
