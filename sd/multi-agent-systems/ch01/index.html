Understanding Multi-Agent Systems

What an agent actually is — a model in a loop with tools, memory, and an environment it can observe and act on — and what changes when there is more than one. Establishes the autonomy spectrum from fixed workflow to fully autonomous, the honest reasons to add a second agent, and the costs that make 'more agents' the wrong default.

Key ideas

  • An agent is a model placed in a loop: it observes, decides, acts through tools, and observes the result — the loop and the environment are what distinguish it from a single model call.
  • Autonomy is a spectrum, not a category: at one end a fixed workflow where code decides the control flow, at the other a system where the model decides what happens next, with most useful systems sitting in between.
  • A multi-agent system is several such agents with distinct roles, contexts, and often distinct tools and permissions, coordinated by some orchestration mechanism.
  • The legitimate reasons to split are specialization, separated context, genuine parallelism, different permission boundaries, and independent evolution of parts — not organizational metaphor.
  • Every added agent costs tokens, latency, coordination failures, and debuggability; a single agent with good tools is the correct default until something specific breaks.
  • Any multi-agent design must answer four questions: who does what, how they communicate, who decides what happens next, and when the system stops.
  • More autonomy means more capability and less predictability — the design choice is how much autonomy the task's risk profile can afford.

Q1 multiple choice

What distinguishes an agent from a single model call?

  1. A The agent uses a larger model
  2. B The agent runs in a loop with an environment — observing, deciding, acting through tools, and observing the results — rather than producing one output from one input correct
  3. C The agent has a longer context window
  4. D The agent is finetuned for its task

Why: The loop and the environment are the defining features. A single call maps input to output; an agent takes actions, sees their consequences, and decides again, which is what makes it capable and what makes it unpredictable.

Q2 multiple choice

What does it mean to say autonomy is a spectrum?

  1. A Models vary in how autonomous they are by default
  2. B Autonomy increases with the number of agents
  3. C Control flow can be owned entirely by code (a fixed workflow), entirely by the model (full autonomy), or shared — and most production systems sit deliberately in between correct
  4. D Autonomy refers to whether the agent can run without a network connection

Why: The useful question is not 'is this an agent' but 'who decides the next step'. Fixed workflows are predictable and testable; autonomous loops adapt to what they find. Real systems usually fix the risky parts and leave the uncertain parts to the model.

Q3 multiple choice

Which is a legitimate reason to introduce a second agent?

  1. A The task has multiple steps
  2. B A distinct role needs different instructions, tools, or permissions, or genuinely parallel work exists — a limitation a single agent cannot resolve correct
  3. C The team wants the architecture to mirror the company's org chart
  4. D The prompt has grown past 500 words

Why: Multi-step work is what chaining and planning are for. The split earns its cost when roles genuinely differ — different context, different tool sets, different trust levels — or when work can proceed concurrently.

Q4 multiple choice

What is the recommended default before adopting a multi-agent architecture?

  1. A A single agent with a well-designed tool set, upgraded only when a concrete limitation appears correct
  2. B Three agents, since fewer cannot cover planning, execution, and review
  3. C A fully autonomous swarm, since it adapts
  4. D One agent per tool

Why: Each additional agent multiplies token cost, latency, and coordination failure modes while making debugging harder. Starting simple keeps those costs unpaid until something specific justifies them.

Q5 multiple choice

Which four questions must any multi-agent design answer?

  1. A Which model, which provider, which framework, which language
  2. B Who does what, how agents communicate, who decides what happens next, and when the system stops correct
  3. C How many agents, how many tools, how many steps, how many retries
  4. D What to log, what to cache, what to monitor, what to alert on

Why: Roles, communication, control, and termination are the load-bearing decisions. A system that has not answered the last one — when it stops — will talk until a budget or a timeout stops it.

Q6 multiple choice

What does context separation buy in a multi-agent system?

  1. A It allows each agent to use a different provider
  2. B It removes the need for memory management
  3. C Each agent sees only what its role requires, so prompts stay focused, context stays small, and irrelevant material cannot distract or mislead it correct
  4. D It guarantees agents cannot disagree

Why: One agent accumulating everything ends up with a bloated, noisy context that costs more and reasons worse. Scoping each agent's view is often the concrete benefit that justifies a split, and it doubles as an information boundary.

Q7 multiple choice

How does increasing autonomy change the engineering burden?

  1. A It reduces it, because the model handles more decisions
  2. B It shifts the burden from specifying control flow to bounding and observing behaviour — budgets, permissions, verification, and tracing become the safeguards correct
  3. C It only changes cost, not risk
  4. D It has no effect if the model is strong enough

Why: You stop writing the steps and start writing the constraints. Because the trajectory is no longer knowable in advance, safety comes from limits on what the system can do and from being able to reconstruct what it did.

Q8 multiple choice

Why is 'the environment' a first-class concept for agents?

  1. A Because it determines the deployment region
  2. B Because it is where the agent's actions have effects and where its observations come from — the environment defines what the agent can perceive, what it can change, and therefore what can go wrong correct
  3. C Because agents must run in containers
  4. D Because environment variables configure the model

Why: Designing an agent means designing its environment: which tools exist, what state they expose, what feedback an action returns. A rich, well-instrumented environment produces a capable agent; a vague one produces a guesser.

Q9 explain & apply crux

A team proposes replacing their working single-agent assistant with a five-agent system. What would you ask them, and what evidence would justify the change?

Points a strong answer hits:

  • Ask what specific limitation the single agent hits — quality on a slice, context pressure, conflicting instructions, or serial latency on parallelizable work.
  • Ask whether the proposed roles differ in tools, permissions, or context, or only in name.
  • Ask what the coordination cost will be: message volume, extra tokens, added latency, and how failure will be debugged.
  • Require a baseline: the current system measured on an evaluation set with quality, cost, and p95 latency.
  • Evidence that justifies the split: a slice where a specialized prompt/tool set demonstrably outperforms, genuinely concurrent work, or a permission boundary that must exist.
  • Suggest incremental steps: better tools, routing, or a single parallel fan-out before a full topology.
  • Insist on the four design questions — roles, communication, control, termination — being answered before implementation.
  • Plan to measure the new system on the same evaluation set and be willing to revert.
Model answer: My first question would be what the single agent is failing at, specifically and measurably. If the answer is a general sense that multi-agent is more sophisticated, that is not a reason — five agents calling the same model with the same tools are five copies of one agent plus a coordination bill. Concrete answers that would persuade me: quality is poor on a slice where a specialized prompt and a narrow tool set would clearly do better; the single prompt has grown so overloaded that instructions conflict; the context is bloated with material only relevant to some requests; the work is genuinely parallel and is currently serialized; or there is a permission boundary that ought to exist, such as the part that reads untrusted content having no business holding write credentials. Second, I would ask whether the proposed roles differ in anything real — tools, permissions, context — or only in their names. Roles that differ only in job title are prompt sections, not agents. Third, I would make the costs explicit: how many inter-agent messages, how many extra tokens, how much added latency, and how anyone will debug a bad outcome across five actors. Before any of it, I want a baseline: the current system scored on an evaluation set with quality, cost, and p95 latency, so the comparison is measurable rather than aesthetic. Then I would push for the smallest change that addresses the named limitation — better tool design, a router, or a single parallel fan-out — rather than a full topology, since those capture most of the benefit at a fraction of the complexity. And whatever we build has to answer the four questions before implementation: who does what, how they talk, who decides the next step, and when it stops. If the new system does not beat the baseline on the same evaluation set, we revert.

Q10 explain & apply

Explain the autonomy spectrum and how you would decide where a given system should sit on it.

Points a strong answer hits:

  • At one end, code owns control flow — fixed workflows that are predictable, testable, and cheap; at the other, the model chooses each next step.
  • Predictability, testability, and auditability decrease as autonomy rises; adaptability to unforeseen inputs increases.
  • Decide by task variability: if the steps can be enumerated, fix them; if the next step depends on what is found, allow autonomy.
  • Decide by risk: irreversible or high-cost actions should sit in the fixed, gated part regardless of the rest.
  • Decide by cost and latency budget: autonomy multiplies round trips and makes spend unpredictable.
  • Hybrid is normal: a fixed skeleton with autonomous steps inside it, or an autonomous planner whose actions pass through fixed permission gates.
  • Autonomy should be earned incrementally as evaluation shows the system handles a class of cases reliably.
  • Whatever the level, bounds and observability are what make it operable — budgets, permissions, tracing.
Model answer: At one end of the spectrum, code decides everything: a workflow with fixed steps where the model is called to do bounded pieces of work. It is predictable, cheap, testable, and auditable, and when it fails it fails in ways you can reproduce. At the other end, the model decides what to do next at every point, which is enormously more flexible and gives up all of those properties. Where a system should sit follows from three things. Task variability first: if I can enumerate the steps in advance, I should, because autonomy buys nothing on a predictable path and costs unpredictability. If the next step genuinely depends on what the last one returned — investigating, searching, debugging — then autonomy is the honest model and forcing a workflow just produces a brittle one. Risk second, and this cuts across the first: irreversible, expensive, or externally visible actions belong in the fixed and gated part of the system no matter how autonomous the rest is. An autonomous investigator that must ask before it acts is a perfectly coherent design. Budget third: every autonomous step is a round trip, so latency and spend become distributions rather than constants, which some products can absorb and others cannot. In practice the answer is almost always hybrid — a fixed skeleton with autonomous work inside individual steps, or an autonomous planner whose proposed actions pass through deterministic permission checks. And I would treat autonomy as something earned: start constrained, measure where the system handles a class of cases reliably, and widen its discretion for that class specifically. Regardless of where it sits, the same two things make it operable — bounds on what it can spend and do, and traces detailed enough to reconstruct what it did.
