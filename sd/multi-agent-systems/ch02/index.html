Multi-Agent Patterns

The coordination vocabulary: deterministic workflows where code owns the control flow, and autonomous topologies where the model does. Sequential, parallel, router, hierarchical manager/worker, group chat, handoff, and shared-state designs each make a different tradeoff between predictability and adaptability, and each fails in its own way.

Key ideas

  • The first fork is whether control flow is decided by code (workflow) or by a model (autonomous) — everything else is a variation on who chooses the next actor.
  • Sequential and parallel workflows are the predictable backbone: testable, cheap, resumable, and the right answer whenever the steps are knowable in advance.
  • A router adds one model-decided branch to an otherwise fixed flow, which is often all the adaptability a system actually needs.
  • Hierarchical manager/worker centralizes decomposition and integration in one coordinator — clear accountability, but the manager is a bottleneck and a single point of misjudgment.
  • Group chat gives every agent visibility into the whole conversation, which surfaces cross-checking and is expensive: context and cost grow with every turn and consensus is not correctness.
  • Handoff (swarm) transfers control to whichever agent is best suited, keeping context focused, at the cost of needing clear handoff criteria and a way to prevent ping-ponging.
  • Shared-state designs let agents coordinate through a common artifact rather than by messaging each other, which decouples them but needs conflict rules.
  • Pattern choice should follow the predictability of the task and the cost of a wrong step, not the elegance of the topology.

Q1 multiple choice

What is the primary distinction between a multi-agent workflow and an autonomous multi-agent system?

  1. A Workflows use one model and autonomous systems use several
  2. B Workflows cannot use tools
  3. C In a workflow, code determines the sequence of agents and steps; in an autonomous system, a model determines what happens next correct
  4. D Autonomous systems require human approval and workflows do not

Why: Ownership of control flow is the dividing line. It determines whether the trajectory can be tested and reviewed in advance, and it is a bigger design decision than which topology or framework you pick.

Q2 multiple choice

When is a sequential workflow the right pattern?

  1. A When the steps are known in advance and each depends on the previous one — it is predictable, cheap, testable, and resumable correct
  2. B Only when a single model is used
  3. C When latency does not matter
  4. D When the task requires exploration

Why: Predictable pipelines should stay pipelines. The reasons to prefer them are practical: you can evaluate each stage, cache stable stages, resume after a failure, and reason about cost before running anything.

Q3 multiple choice

What does a router pattern contribute to an otherwise fixed flow?

  1. A It removes the need for tools
  2. B One model-decided branch point that dispatches to the appropriate specialist — often the only adaptability a system actually needs correct
  3. C It parallelizes all downstream steps
  4. D It guarantees the cheapest model is used

Why: Routing is the minimum viable autonomy: the flow remains predictable while gaining the ability to handle different request types with purpose-built handlers. Its failure mode — silent misrouting — must be measured directly.

Q4 multiple choice

What is the main structural weakness of the hierarchical manager/worker topology?

  1. A Workers cannot use tools
  2. B It cannot run steps in parallel
  3. C The manager is a bottleneck and a single point of misjudgment — bad decomposition or bad integration degrades everything below it correct
  4. D It requires all agents to share one context

Why: Centralizing decomposition and integration gives clear accountability and one place to enforce budgets, but every result passes through the manager's understanding. When the manager misreads the task, competent workers produce competently wrong output.

Q5 multiple choice

What are the costs of a group-chat topology where all agents see all messages?

  1. A It cannot support more than three agents
  2. B Context and token cost grow with every turn, agents influence each other so consensus can be confidently wrong, and termination must be imposed from outside correct
  3. C Agents cannot maintain separate roles
  4. D It requires a shared vector store

Why: Shared visibility is exactly what makes cross-checking possible and what makes it expensive. Cost grows superlinearly, and social dynamics appear — an early confident claim gets adopted, and agreement reads as confirmation.

Q6 multiple choice

How does the handoff (swarm) pattern differ from a manager delegating?

  1. A Handoff requires more agents
  2. B Handoff only works with identical agents
  3. C Handoff transfers control of the task to another agent, which then owns it, rather than a coordinator assigning work and collecting results correct
  4. D Handoff cannot preserve conversation context

Why: Control moves rather than work being farmed out. That keeps each agent's context focused on what it owns, and it introduces two requirements: explicit handoff criteria and protection against agents bouncing a task back and forth.

Q7 multiple choice

What does a shared-state (blackboard) design change about coordination?

  1. A Agents coordinate through a common artifact they read and write rather than by messaging each other, which decouples them but requires conflict and consistency rules correct
  2. B It removes the need for termination conditions
  3. C It requires all agents to run in the same process
  4. D It makes every agent see every message

Why: The artifact — a document, a task board, a structured state object — becomes the coordination medium. Agents need not know about each other, which scales well, but concurrent writes, staleness, and ownership need explicit rules.

Q8 multiple choice

What should drive the choice of pattern?

  1. A The predictability of the task and the cost of a wrong step — deterministic flows where steps are knowable and stakes are high, autonomy where the path genuinely depends on findings correct
  2. B The number of engineers on the team
  3. C Which topology the chosen framework showcases
  4. D The size of the model being used

Why: Topology is a means. Picking one because a framework demonstrates it, or because it mirrors a human team, is how systems acquire coordination cost with no corresponding capability.

Q9 explain & apply crux

For a document-processing product that ingests contracts, extracts terms, checks them against policy, and produces a summary, compare a deterministic workflow with an autonomous topology. Which would you build?

Points a strong answer hits:

  • The steps are knowable in advance, so a deterministic pipeline is the default: extract, classify, check policy, synthesize.
  • A workflow gives per-stage evaluation, caching, resumption, predictable cost, and parallel fan-out across clauses.
  • Autonomy is unnecessary where the flow does not branch on findings; it would add latency, cost, and variance without capability.
  • Where autonomy does help: handling unusual document types, resolving ambiguity, or deciding when to escalate — bounded to specific steps.
  • Hybrid: a fixed skeleton with a router for document type and an autonomous sub-loop for anomalous cases.
  • Parallelize per-clause work; keep synthesis sequential since it needs global context.
  • Define structured handoffs between stages with validation, and evaluate each stage separately.
  • Escalate to a human on low-confidence policy checks rather than letting an autonomous agent decide.
  • Measure before adding autonomy: only introduce it where the deterministic pipeline demonstrably fails.
Model answer: I would build a deterministic workflow, because the steps are knowable before the document arrives: extract clauses, classify them, check each against policy, synthesize the summary. Nothing in that sequence branches on what an earlier step discovers in a way I cannot anticipate, so autonomy would buy variance and latency without buying capability. What the workflow buys instead is everything I need operationally — I can evaluate each stage against its own labelled set, cache the stable stages, resume a failed run from the last completed stage, and predict cost before running. The clause-level work fans out in parallel, since clauses are independent, while synthesis stays sequential because it needs the whole picture. Between stages I define structured handoffs with validation, so a malformed extraction fails loudly rather than silently corrupting the policy check. There are two places autonomy earns its keep. One is a router at the front for document type, since a lease, an NDA, and a master services agreement want different extraction prompts and policy sets — that is a single model-decided branch in an otherwise fixed flow, which is usually all the adaptability a system like this needs. The other is a bounded autonomous sub-loop for anomalous cases: a document that does not match any known type, or a clause the classifier is unsure about, where an agent can look things up and try alternative approaches within a step budget before escalating. Everything else stays deterministic, and low-confidence policy checks escalate to a human rather than being resolved by an agent's judgment, because that is a decision with legal consequences. If the deterministic pipeline turns out to fail on a specific class of documents, that is the evidence that would justify widening autonomy — measured on the evaluation set, for that class, and not further.

Q10 explain & apply

Explain how group chat and handoff topologies differ in their failure modes, and how you would mitigate each.

Points a strong answer hits:

  • Group chat: context and cost grow with each turn as all agents read everything, so long discussions become expensive quickly.
  • Group chat: agents influence one another, so an early confident wrong claim can be adopted by all — consensus is not evidence.
  • Group chat: without an external termination rule, discussion continues until a budget stops it.
  • Mitigations: cap turns, restrict who participates in which exchanges, summarize rather than replaying full transcripts, and designate one agent as the owner of the final answer.
  • Handoff: ping-ponging between agents that each believe the task belongs to the other.
  • Handoff: context loss at the transfer, where the receiving agent lacks what the sender knew.
  • Handoff: no clear ownership of the outcome, so the task can be dropped.
  • Mitigations: explicit handoff criteria, a structured transfer payload, a handoff counter that escalates after N transfers, and a designated fallback owner.
  • Both need tracing that follows the task across agents so failures are attributable.
Model answer: They fail in almost opposite ways. Group chat fails by excess: everyone reads everything, so the context grows with each turn and cost climbs superlinearly while the marginal value of turn seven is usually zero. It also produces social dynamics — one agent states something confidently early, the others build on it, and the group converges on a shared error that now looks like corroboration. And it has no natural end, so without an external rule it keeps going until a budget stops it. My mitigations are structural: cap the number of turns, restrict participation so only the agents with a stake in a particular exchange see it, pass structured summaries rather than replaying whole transcripts, and designate exactly one agent as the owner of the final answer so agreement is not a prerequisite for finishing. Where I want genuine cross-checking rather than consensus, I give the critics different lenses and have them evaluate independently rather than in conversation, so their errors are uncorrelated. Handoff fails by gaps rather than excess. The classic failures are ping-ponging, where two agents each conclude the task belongs to the other; context loss at the transfer, where the receiving agent gets a one-line summary and re-asks the user things it should already know; and dropped ownership, where the task ends up with nobody. The mitigations are equally structural: explicit criteria for when a handoff is appropriate, a structured transfer payload carrying the goal, what has been established, and what remains, a counter that escalates to a human or a default owner after N transfers, and a rule that ownership is always held by exactly one agent at a time. Both topologies need the same instrumentation underneath: a trace keyed to the task that follows it across agents, so when the outcome is wrong I can see which actor introduced the error rather than reading five separate logs.
