UX Design Principles for Multi-Agent Systems

Semi-autonomous systems create interface problems that ordinary software does not have: the user cannot see what the agent is doing, cannot predict what it will do, cannot easily stop it, and has no basis for calibrating how much to trust it. The principles here — observability, steerability, trust calibration, progressive disclosure, and designing for failure — are what turn an impressive demo into something a person can actually work with.

Key ideas

  • Observability is the base requirement: the user must be able to see what the agent is doing now, what it has done, and why — an opaque agent is indistinguishable from a stuck one.
  • Steerability means the user can interrupt, redirect, correct, and constrain mid-task rather than only accepting or rejecting a final result.
  • Trust must be calibrated, not maximized: the interface should help the user trust the system exactly as much as it deserves, using provenance, uncertainty, and visible verification.
  • Progressive disclosure keeps the surface usable — a summary by default, with the trace, sources, and intermediate artifacts available on demand.
  • Latency is a UX problem in agents specifically: streaming, progress indication, and partial results are what make multi-second and multi-minute work tolerable.
  • Design for failure as a normal state: agents will be wrong, so the interface needs cheap correction, clear undo, and a way to escalate rather than a binary success/failure.
  • Multi-agent systems add an attribution problem — the user needs to know which agent did what, or the system reads as one confusing voice.
  • Consent and control over consequential actions belong in the interface: preview exactly what will happen before it happens.

Q1 multiple choice

Why is observability treated as a UX requirement rather than an engineering nicety in agentic systems?

  1. A Because logs are required for compliance
  2. B Because the user cannot otherwise distinguish an agent that is working from one that is stuck or looping — visible activity is what makes a multi-step system usable at all correct
  3. C Because observability reduces token cost
  4. D Because models perform better when observed

Why: In ordinary software, an action completes or fails quickly. An agent may work for a minute across many steps, so without surfaced state the user is left staring at a spinner deciding whether to abandon the task.

Q2 multiple choice

What does steerability mean in this context?

  1. A The ability to choose which model the agent uses
  2. B The ability to accept or reject the final output
  3. C The ability to interrupt, redirect, correct, and constrain the agent while it is working, rather than only judging the finished result correct
  4. D The ability to change the system prompt in settings

Why: A user who can see the agent heading in the wrong direction should be able to say so immediately. Without mid-task control, every misunderstanding costs a full run and the user learns to expect waste.

Q3 multiple choice

Why is 'calibrated trust' the goal rather than maximum trust?

  1. A Because users should be discouraged from relying on AI
  2. B Because over-trust leads users to accept wrong output uncritically while under-trust wastes the system's value — the interface should convey how reliable this particular output is correct
  3. C Because trust cannot be measured
  4. D Because calibration reduces latency

Why: A confident interface around an unreliable answer manufactures over-trust, which is how errors reach production. Showing sources, uncertainty, and what was actually verified lets the user apply the right amount of scrutiny per output.

Q4 multiple choice

What does progressive disclosure solve for agent interfaces?

  1. A It reduces the number of model calls
  2. B It hides the agent's mistakes from users
  3. C It keeps the default view simple while making the trace, sources, and intermediate artifacts available to users who need to verify or debug correct
  4. D It removes the need for streaming

Why: Agents generate far more intermediate material than a user wants by default, and none of it can simply be discarded — a user checking a surprising result needs the reasoning and sources. Layering satisfies both.

Q5 multiple choice

How should long-running agent work be presented?

  1. A With a single spinner until completion, to avoid overwhelming the user
  2. B With streamed output, visible progress through steps, and partial results — so the wait is legible and the user can intervene early correct
  3. C By emailing the result when finished
  4. D By hiding all intermediate steps until the answer is verified

Why: Perceived latency is governed by feedback, not total time. Streaming and step-level progress also serve steerability: the user can catch a wrong direction in the first few seconds rather than after the full run.

Q6 multiple choice

What does 'design for failure' mean for an agent interface?

  1. A Showing an error page whenever the agent is uncertain
  2. B Treating being wrong as a normal state — cheap correction, clear undo, visible escalation paths — rather than a binary success/failure correct
  3. C Retrying automatically until the agent succeeds
  4. D Preventing the agent from acting until it is certain

Why: Probabilistic systems are wrong regularly, so the interface's job is making recovery cheap: edit the result, adjust the instruction and re-run from a step, undo the action, or hand it to a human.

Q7 multiple choice

What extra interface problem does a multi-agent system introduce?

  1. A Attribution — the user needs to know which agent produced which output and which one is currently acting, or the system reads as one incoherent voice correct
  2. B Higher latency, which cannot be mitigated
  3. C The need for a separate application per agent
  4. D The inability to stream output

Why: When several specialists contribute, unattributed output makes the system look inconsistent and makes disagreement impossible to interpret. Labelling who is speaking, and what each one is responsible for, restores a coherent mental model.

Q8 multiple choice

How should consequential actions be presented in the interface?

  1. A As a generic confirm dialog before any tool call
  2. B With a preview of exactly what will happen — recipients, amounts, changes — plus the ability to edit or reject, reserved for actions whose consequences justify the interruption correct
  3. C Silently, with an undo option afterwards in all cases
  4. D Only after the action has been taken, in an activity log

Why: Confirmation is only meaningful when the user can see the specifics. Gating everything produces reflexive clicking, so the interruption should be spent on actions that are irreversible, costly, or externally visible.

Q9 explain & apply crux

Design the interface for a research agent that takes several minutes, browses sources, and produces a report. Apply the UX principles.

Points a strong answer hits:

  • Show a plan or scope up front so the user can correct the interpretation before minutes are spent.
  • Stream progress at a meaningful granularity — which sub-question is being researched, which sources have been found — not raw tokens or opaque spinners.
  • Allow interruption and steering mid-run: narrow the scope, exclude a source, redirect to a different sub-question.
  • Surface partial results as they stabilize so value arrives before the run finishes.
  • Attach provenance to every claim, with links to the sources, and mark claims that could not be verified.
  • Use progressive disclosure: the report by default, expandable to the trace, the queries run, and the rejected sources.
  • Convey uncertainty honestly — a claim from one blog is not a claim from three independent sources.
  • Design failure paths: what happens when a source is inaccessible, when the topic yields nothing, or when the budget runs out — partial delivery with an explanation.
  • Make the output editable and re-runnable from a step rather than only regenerable from scratch.
  • For multi-agent internals, attribute contributions so the user can tell who found what.
Model answer: The first screen after the request should not be a spinner — it should be the agent's interpretation: the sub-questions it plans to research, the sources it intends to use, and the scope it assumed. That costs a few seconds and saves the user from watching three minutes of work aimed at the wrong question, which is the single biggest usability win available in this kind of product. During the run, progress is shown at a granularity that means something: which sub-question is active, which sources have been found and accepted, how many remain. Raw token streams are noise here; step-level progress is legible. Throughout, the user can steer — narrow the scope, exclude a source they distrust, add a sub-question — and partial results appear as sections stabilize so value arrives before the end. On trust, every claim carries its provenance with a link, and claims the agent could not corroborate are marked as such rather than blended into the prose. That is the difference between an interface that manufactures confidence and one that calibrates it: the user should be able to see at a glance which parts are load-bearing evidence and which are the agent's synthesis. Detail is layered — the report reads clean by default, and one interaction away sit the trace, the queries run, the sources considered and rejected, and the reasoning. Failure is a designed state, not an error page: an inaccessible source is reported inline, a topic that yields nothing produces an honest 'not much exists on this, here is what I found', and a budget exhaustion delivers what was completed with a clear note about what was not. Recovery is cheap: the user can edit the report directly, or re-run a single section with an adjusted instruction rather than starting over. And because several agents contribute internally, contributions are attributed, so when two sections disagree the user can see that two different researchers found different things rather than concluding the system is incoherent.

Q10 explain & apply

Explain the over-trust and under-trust failure modes in agent interfaces, with examples of design choices that cause each.

Points a strong answer hits:

  • Over-trust: users accept wrong output without scrutiny, and errors propagate into decisions and downstream systems.
  • Causes of over-trust: confident uniform tone, no uncertainty signalling, no provenance, polished formatting, hidden failures, and automation that acts without preview.
  • Under-trust: users ignore or double-check everything, so the system adds work instead of removing it, and eventually goes unused.
  • Causes of under-trust: opaque process, unexplained answers, visible unnecessary errors, over-refusal, and inconsistency between runs.
  • Calibration tools: provenance and citations, explicit uncertainty, showing what was verified versus inferred, and consistent behaviour.
  • Confidence displays must themselves be calibrated, or they make the problem worse.
  • Different tasks warrant different postures — high-stakes outputs should default to scrutiny, routine ones to flow.
  • Measure it: track correction rates, blind acceptance of seeded errors, and user-reported confidence against actual accuracy.
Model answer: Over-trust is when the interface earns more confidence than the system deserves, and the user stops checking. It is usually caused by presentation: a uniformly confident tone regardless of how well-supported the answer is, polished formatting that reads like a finished document, no citations, no marking of what was inferred versus verified, and automation that acts without showing what it is about to do. Hidden failures make it worse — if a source could not be fetched and the agent silently proceeded, the output looks identical to one built on complete information. The consequence is that a wrong answer flows straight into a decision, and the failure surfaces much later and much more expensively. Under-trust is the mirror image and is just as damaging commercially: the user verifies everything the agent produces, so the system adds a step instead of removing one, and eventually they stop using it. It comes from opacity — an answer with no visible reasoning or sources is hard to accept — from visible sloppiness in low-stakes places, from over-refusal, and from inconsistency, where the same question produces noticeably different answers on different runs. The tools for calibration are the same in both directions: provenance so the user can check the load-bearing claims cheaply, explicit uncertainty where the evidence is thin, a clear distinction between what was verified and what was inferred, and consistent behaviour so a mental model can form. One caution: a numeric confidence display is itself a claim, and an uncalibrated one accelerates over-trust rather than fixing it. Finally, I would measure this rather than assume it. Track how often users edit or correct output, run studies with deliberately seeded errors to see whether they are caught, and compare users' stated confidence against measured accuracy — that gap is the thing the interface is supposed to close.
