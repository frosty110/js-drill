Deploying Multi-Agent Systems

Running agents as real infrastructure. An agent run is long-lived, stateful, expensive, and dependent on third-party services with their own rate limits and outages — which makes deployment closer to job orchestration than to serving a stateless API. Covers execution model, durability, concurrency and rate limits, secrets and isolation, cost controls, observability, and safe rollout.

Key ideas

  • Model agent runs as durable jobs rather than HTTP requests: a queue, workers, persisted state, and status — so a deploy or a crash does not lose work.
  • Statefulness is the defining deployment property; checkpointing after each step is what makes retries safe and resumption possible.
  • Concurrency must be bounded by provider rate limits and by cost, not just by CPU — an agent fleet can exhaust a token quota in minutes.
  • Isolation matters per tenant and per run: credentials scoped to the task, sandboxed execution for code and browsing, and no shared mutable state between runs.
  • Cost controls belong in the platform — per-run, per-user, and global budgets with enforcement, since a runaway loop is a spend incident, not just a bug.
  • Observability means traces first: every step, prompt, tool call, token count, and timing under one run id, retained long enough to debug and audit.
  • Third-party dependencies fail and change: circuit breakers, fallbacks across providers, and pinned model versions where available are basic hygiene.
  • Roll out like a model change, not a code change — shadow traffic, staged exposure, and comparison against the incumbent on live data, with instant rollback.

Q1 multiple choice

Why should agent runs be modelled as durable jobs rather than HTTP requests?

  1. A Because HTTP cannot carry model responses
  2. B Because runs are long-lived and stateful — a queue with workers and persisted state means a deploy, crash, or disconnect does not lose the work correct
  3. C Because queues are cheaper than web servers
  4. D Because providers require asynchronous calls

Why: A request-scoped run dies with its process and cannot be resumed, monitored, or picked up by another worker. Treating it as a job makes restarts, retries, and status queries ordinary rather than exceptional.

Q2 multiple choice

What makes checkpointing essential in production agent deployments?

  1. A It reduces token usage
  2. B It guarantees deterministic outputs
  3. C It lets a run resume from the last completed step so retries and restarts do not repeat work or duplicate side effects correct
  4. D It is required for streaming

Why: Long runs get interrupted by deploys, timeouts, and rate limits. Without step-level state, recovery means starting over — which is expensive and, if earlier steps sent emails or wrote records, actively harmful.

Q3 multiple choice

What should bound concurrency for an agent fleet?

  1. A CPU and memory only
  2. B Provider rate limits and token quotas, plus cost budgets — an agent fleet can exhaust a quota or a budget long before it saturates hardware correct
  3. C The number of available workers
  4. D Network bandwidth

Why: Agents are I/O-bound on external APIs, so the binding constraints are requests per minute, tokens per minute, and money. Concurrency limits and queueing must be expressed in those terms.

Q4 multiple choice

Which isolation properties matter for multi-tenant agent platforms?

  1. A Only network isolation between workers
  2. B Credentials scoped per task and tenant, sandboxed execution for code and browsing, and no shared mutable state or caches between runs of different users correct
  3. C Separate model providers per tenant
  4. D Isolation is unnecessary if authentication is enforced at the API

Why: The classic leak is a shared cache or memory store keyed without the tenant, so one user's retrieved content serves another. Scoped credentials and sandboxes bound what a compromised or misbehaving run can reach.

Q5 multiple choice

Why do cost controls belong in the platform rather than in each application?

  1. A Because providers require centralized billing
  2. B Because a runaway agent is a spend incident that needs enforcement — per-run, per-user, and global budgets with hard stops — not a per-team convention correct
  3. C Because centralized controls are cheaper to implement
  4. D Because applications cannot measure their own cost

Why: Unbounded loops and retry storms are normal failure modes, and their cost is unbounded by default. Enforced budgets with kill behaviour convert an unbounded incident into a capped one.

Q6 multiple choice

What is the primary observability artifact for a deployed agent system?

  1. A Aggregate latency dashboards
  2. B Traces — every step, prompt, tool call with arguments, result, token count, and timing, correlated under one run id correct
  3. C Error logs from failed runs
  4. D The model provider's usage report

Why: Behaviour is emergent and varies per run, so aggregates cannot explain a bad outcome. Only a full trace reconstructs what happened, and it doubles as the audit record for consequential actions.

Q7 multiple choice

Which practices address third-party dependency risk?

  1. A Circuit breakers, fallbacks across providers or models, pinned model versions where available, and monitoring for silent behaviour changes correct
  2. B Increasing retry counts
  3. C Caching all provider responses indefinitely
  4. D Running all agents on a single provider for consistency

Why: Providers have outages, rate limits, deprecations, and silent updates. Failing fast when one is down, having a defined fallback, and detecting behaviour drift are what keep an agent platform operable.

Q8 multiple choice

How should a change to an agent system be rolled out?

  1. A Like a model change — shadow traffic or staged exposure with live comparison against the incumbent, and instant rollback correct
  2. B As a standard code deploy, since the code is what changed
  3. C Only during scheduled maintenance windows
  4. D All at once, to avoid inconsistent behaviour between users

Why: Prompt, tool, and model changes alter behaviour in ways unit tests do not catch. Staged rollout with a live comparison is how quality regressions are caught by measurement rather than by user complaints.

Q9 explain & apply crux

Design the deployment architecture for a platform that runs customer-facing agent tasks lasting up to ten minutes.

Points a strong answer hits:

  • Runs as durable jobs: an API that enqueues, workers that execute, persisted run state and status, and an event log for streaming and replay.
  • Checkpoint after each step; make external writes idempotent so retries and resumptions are safe.
  • Concurrency limited by provider rate and token limits, with queueing, backpressure, and fair scheduling across tenants.
  • Per-run, per-tenant, and global cost budgets enforced in the platform, with hard stops and alerting.
  • Isolation: per-tenant credential scoping, sandboxed execution for code or browsing, and cache keys that include tenant and permission scope.
  • Secrets managed centrally, injected per run, never in prompts or logs.
  • Tracing under a run id, with retention that supports debugging and audit, plus metrics for step counts, tool errors, cost, and latency percentiles.
  • Resilience: circuit breakers per dependency, fallbacks across models or providers, timeouts at every layer, and cancellation propagation.
  • Deploy safely: workers drain rather than kill in-flight runs, state schema versioned, and staged rollout with live comparison and rollback.
  • Human-in-the-loop support: runs that pause for approval must persist and resume, with timeouts and escalation.
Model answer: I would build it as a job platform rather than a request service. An API accepts a task, validates and enqueues it, and returns a run id immediately; workers pull from the queue and execute the agent loop against durable state, appending to a sequenced event log that serves streaming, replay, and tracing. Each step checkpoints, so a worker dying mid-run means another picks it up rather than the customer losing ten minutes of work, and every external write is idempotent because retries and resumptions are routine rather than exceptional. Concurrency is governed by the constraints that actually bind: provider requests and tokens per minute, plus cost. That means a scheduler with queueing, backpressure, and fairness across tenants so one customer's heavy batch cannot starve everyone else. On top of it, budgets are enforced by the platform at three levels — per run, per tenant, and global — with hard stops, because a looping agent is a spend incident and no application-level convention prevents it reliably. Isolation is per tenant and per run: credentials scoped to the specific task and injected at execution rather than living in prompts, sandboxed environments for any code execution or browsing, and every cache keyed by tenant and permission scope so a shared cache cannot leak one customer's data to another. Observability is trace-first: every step, prompt, tool call with arguments, result, token count, and timing under the run id, retained long enough to debug and to serve as an audit record for consequential actions, with metrics on step-count and cost distributions, tool error rates, and latency percentiles. For resilience, each external dependency gets a timeout and a circuit breaker, with defined fallbacks across models or providers, and cancellation propagates from the API through the worker into in-flight model and tool calls. Deploys drain rather than kill workers so in-flight runs finish or checkpoint cleanly, and the run-state schema is versioned so a rollback does not orphan runs. Finally, because these are customer-facing, runs that pause for human approval must persist across that wait with a timeout and escalation policy, and every behaviour change ships staged with live comparison against the incumbent and a one-switch rollback.

Q10 explain & apply

What breaks when a team deploys an agent system the way they would deploy a stateless web service?

Points a strong answer hits:

  • In-flight runs are killed on deploy, losing minutes of work and leaving partial side effects.
  • No resumption: a failure means restarting from scratch, repeating cost and potentially duplicating writes.
  • Autoscaling on CPU misreads the load, since agents are I/O-bound on external APIs and the real limits are rate and token quotas.
  • Provider rate limits are hit under bursty load, producing cascading retries and long tail latency.
  • No cost enforcement, so a runaway loop or a bug generates an unbounded bill.
  • Request-scoped timeouts cut off legitimate long runs.
  • Logs without traces make emergent behaviour impossible to debug.
  • Shared caches and connection reuse leak state between tenants.
  • Standard rollout practice misses behaviour regressions that only measurement against live traffic catches.
Model answer: The mismatch shows up on the first deploy: workers are killed mid-run, and because there is no persisted state, ten minutes of work vanishes — sometimes after the agent has already sent an email or written a record, so the customer is left with a half-completed action and no way to resume. The same fragility appears on any crash, timeout, or rate-limit error: without checkpointing, recovery means starting over, paying the full cost again, and risking duplicate side effects on non-idempotent writes. Scaling misbehaves next. Autoscaling on CPU tells you nothing about agent load, since the workers are almost entirely waiting on external APIs; the real limits are requests and tokens per minute at the provider. So the fleet scales up under a burst, hits the provider's quota, and each worker begins retrying, which converts a capacity problem into a cascading one with terrible tail latency. Cost is the next surprise, because a stateless service has roughly fixed per-request cost and an agent does not. Without platform-enforced per-run and global budgets, one looping bug produces an unbounded bill that nobody notices until the invoice. Meanwhile request-scoped timeouts — a load balancer's sixty seconds, a gateway's thirty — silently cut off legitimate long runs, and the client sees a failure while the work may still be running server-side. Then debugging: with request logs but no run-correlated traces, emergent multi-step behaviour is unreconstructible, so incidents become archaeology. Multi-tenancy leaks appear through the conveniences a stateless service takes for granted — shared caches and reused clients keyed without a tenant, so one user's retrieved content is served to another. And finally rollout: shipping a prompt or model change like a code change skips the measurement that would have caught the behaviour regression, because unit tests pass and the quality drop is only visible against live traffic.
