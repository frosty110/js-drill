Security, Ethics, and Responsible AI

What changes when a probabilistic system can act. Security here is dominated by one structural fact — the model cannot distinguish instructions from data — so defence rests on capability limits, isolation, and approval rather than on instructing the model to behave. Alongside it sit the responsibility questions: disclosure, accountability, fairness, data rights, and who answers for an agent's decision.

Key ideas

  • Prompt injection is the defining security problem: any content an agent reads — a page, a document, a tool result, another agent's message — can carry instructions, and no prompt-level rule reliably prevents it.
  • Defence is capability-shaped: least-privilege tools, scoped credentials, sandboxed execution, restricted destinations, and human approval for consequential actions.
  • Separate the role that ingests untrusted content from the role that can act, so an injection reaching the reader has no dangerous capability to invoke.
  • Data protection spans the whole pipeline — what is sent to providers, what is retained in memory and traces, what is used for training, and whether retrieval respects the user's permissions.
  • Accountability must be assigned to people and processes, not to the system: someone owns the agent's decisions, and there is a path for a person to contest and correct them.
  • Disclosure and honest capability claims are ethical baseline: users should know they are interacting with an AI system and what it can and cannot do reliably.
  • Fairness and harm analysis need slice-level evaluation, because aggregate quality hides systematically worse service for particular groups or languages.
  • Auditability is a requirement, not a nicety: traces of what an agent did, with what inputs and whose authority, are what make investigation and redress possible.

Q1 multiple choice

Why is prompt injection the defining security problem for agents specifically?

  1. A Because agents use larger context windows
  2. B Because agents read untrusted content and can act on it, and the model has no reliable way to distinguish an instruction from data in that content correct
  3. C Because agent frameworks have known vulnerabilities
  4. D Because agents cannot use authentication

Why: A chatbot that follows an injected instruction produces bad text. An agent that does the same sends an email, deletes a record, or exfiltrates data. Capability plus untrusted input is what makes it a security issue rather than a quality issue.

Q2 multiple choice

Which control actually bounds the damage of a successful injection?

  1. A A system-prompt rule instructing the model to ignore instructions in documents
  2. B A larger or better-aligned model
  3. C Least-privilege tools, scoped credentials, sandboxing, and human approval for consequential actions correct
  4. D Filtering the word 'ignore' from inputs

Why: Prompt rules and classifiers lower probability; capability limits cap consequence. If the agent cannot spend money, delete data, or send to arbitrary destinations, a successful injection produces an annoyance rather than an incident.

Q3 multiple choice

How does separating roles help against injection in a multi-agent system?

  1. A It makes each agent's prompt shorter
  2. B The agent that ingests untrusted content holds no write capability, so an injected instruction reaching it has nothing dangerous to invoke correct
  3. C It prevents untrusted content from being retrieved at all
  4. D It encrypts messages between agents

Why: Topology becomes a security boundary: readers read, actors act, and the transfer between them is a structured, validated payload rather than free instruction — so the compromise cannot cross the boundary.

Q4 multiple choice

Which data-protection questions must an agent system answer?

  1. A Only whether data is encrypted in transit
  2. B What is sent to external providers, what is retained in memory and traces, what may be used for training, and whether retrieval enforces the requesting user's permissions correct
  3. C Only whether the vector store is access-controlled
  4. D Only what appears in the user interface

Why: Agents move data through many surfaces: prompts to third parties, long-term memory, trace logs, caches, and retrieved corpora. Each is a place where personal or confidential data can persist or leak, and each needs an explicit policy.

Q5 multiple choice

What does accountability mean in a responsible agent deployment?

  1. A The model provider is responsible for the system's decisions
  2. B The agent explains its reasoning, which constitutes accountability
  3. C A named person or team owns the agent's decisions, and affected people have a path to contest and correct them correct
  4. D Accountability applies only to fully autonomous systems

Why: Systems cannot hold responsibility. Deployment means naming who is answerable, keeping the audit trail that makes review possible, and providing a real route to challenge an outcome — especially where the decision affects someone materially.

Q6 multiple choice

Why is disclosure that a user is interacting with an AI system an ethical baseline?

  1. A Because it improves model accuracy
  2. B Because it lets people calibrate trust, apply appropriate scrutiny, and choose to seek a human — and concealing it is deceptive and in some contexts unlawful correct
  3. C Because providers require it in their terms
  4. D Because disclosure reduces liability entirely

Why: People treat a machine's confident claims differently once they know the source. Disclosure, along with honest statements of what the system can and cannot do, is what makes their reliance informed rather than misled.

Q7 multiple choice

Why must fairness analysis be done at slice level?

  1. A Because slices are cheaper to evaluate
  2. B Because aggregate quality can be strong while the system serves a particular group, language, or dialect systematically worse — the harm is invisible in the average correct
  3. C Because regulators require slicing
  4. D Because slices reduce variance

Why: Failures cluster. A system that performs well overall may fail disproportionately for non-native speakers, uncommon names, or edge-case circumstances — which is exactly the population least able to challenge the outcome.

Q8 multiple choice

Why is auditability treated as a requirement in this chapter?

  1. A Because it reduces cost
  2. B Because traces of what an agent did, with what inputs and under whose authority, are what make investigation, correction, and redress possible after a harmful outcome correct
  3. C Because auditing improves accuracy
  4. D Because auditability is only needed in regulated industries

Why: Without a record, a wrong decision cannot be explained, its scope cannot be determined, and the affected person cannot be made whole. The trace is the prerequisite for every other accountability mechanism.

Q9 explain & apply crux

Perform a threat assessment for an agent with access to a company's email, calendar, and internal documents. What are the risks and the controls?

Points a strong answer hits:

  • Primary threat: indirect prompt injection through email bodies, documents, and calendar invitations — content authored by anyone who can reach the user.
  • Consequences to bound: exfiltration of confidential data, unauthorized sends, deletion or modification of records, and social engineering of the user via the agent.
  • Isolate untrusted content as data, never as instructions, and never in the system prompt.
  • Least privilege: read-only by default, narrow send capability with recipient constraints, no bulk operations, rate limits.
  • Human approval with preview for external sends, deletions, and anything irreversible.
  • Permission-aware retrieval enforced at query time against the requesting user's rights, including derived artifacts, caches, and memory.
  • Separate the reading role from the acting role so injected instructions land where no dangerous capability exists.
  • Output scanning for secrets, credentials, unusual URLs, and encoded blobs before anything leaves.
  • Comprehensive audit logging of every action with arguments, plus anomaly alerts on new external recipients or spikes.
  • Red-team continuously with an adversarial corpus, and have an incident path: revoke, trace scope, notify.
Model answer: The dominant threat is indirect prompt injection, because every input surface here is attacker-writable: anyone can send the user an email, share a document, or add a calendar invitation whose text the agent will read. The consequences worth bounding are exfiltration of confidential material, unauthorized sends in the user's name, destruction or modification of records, and using the agent as a channel to socially engineer the user. Notably, none of those are prevented by telling the model to be careful. The controls are structural. Untrusted content enters the context clearly delimited as data and never as instruction, and never touches the system prompt. Capabilities default to read-only; the send tool is narrow — constrained recipients where possible, no bulk operations, rate limited — and deletions and modifications are separate, sharply restricted capabilities. Anything external or irreversible requires human approval with a preview of exactly what will happen, which is the control that holds even when everything upstream fails. Retrieval is permission-aware and enforced at query time against the requesting user's rights, and that enforcement extends to the surfaces people forget: caches keyed without the user, memories extracted from privileged sessions, and summaries derived from restricted documents. Architecturally, I would split the reading role from the acting role, so the component that ingests email and documents holds no send or delete capability, and the transfer between them is a structured, validated payload rather than free text. Outbound content is scanned for secrets, credentials, unexpected URLs, and encoded blobs. Everything is logged — every tool call with arguments, every recipient, every document read — with alerts on anomalies such as a first-time external recipient or a burst of sends, because detection is the fallback when prevention fails. And I would treat this as ongoing work: an adversarial corpus of injection attempts run against the system regularly, with a defined incident path — revoke credentials, determine scope from the traces, notify affected parties — because the honest position is that some attack will eventually succeed and the question is whether it is contained and visible.

Q10 explain & apply

Beyond security, what responsibility obligations does deploying an agent that acts on people's behalf create?

Points a strong answer hits:

  • Disclosure that the user is dealing with an AI system, and honest description of its limits.
  • Meaningful human oversight proportional to consequence, with a real route to reach a person.
  • Named accountability: someone owns the agent's decisions and is answerable for them.
  • Contestability: an affected person can challenge an outcome, and there is a mechanism to correct and remediate.
  • Fairness: slice-level evaluation across languages, groups, and circumstances, with action when disparities appear.
  • Data rights: consent, minimization, retention limits, visibility into stored memory, correction, and deletion.
  • Auditability: traces sufficient to reconstruct what happened, retained appropriately and access-controlled.
  • Honest capability claims in marketing and interface copy, since over-claiming induces misplaced reliance.
  • Continuous monitoring after launch, since responsibility does not end at release and behaviour drifts.
  • Willingness not to deploy, or to restrict scope, where the consequence of error cannot be adequately bounded.
Model answer: Acting on someone's behalf creates obligations that a text generator does not. The first is disclosure: people should know they are dealing with an AI system, and should be told plainly what it does reliably and what it does not — because over-claiming produces exactly the misplaced reliance that turns a model error into a real harm. The second is proportional human oversight, with a genuine route to a person. Not a buried contact form, but a reachable escalation, especially for anything that materially affects someone. Third, accountability has to sit with named people. A system cannot be responsible, so somebody owns its decisions, and that ownership implies the trace and review capability to actually exercise it. Fourth, contestability: an affected person needs a way to challenge an outcome and have it corrected, and the organization needs a remediation path when the agent got it wrong — that is what distinguishes responsible deployment from an apology policy. Fifth, fairness, measured rather than assumed: slice-level evaluation across languages, dialects, name formats, and circumstances, because failures cluster and the people served worst are typically those least able to push back. Sixth, data rights across the whole pipeline — consent for what is collected, minimization of what is sent to third parties, retention limits, user-visible memory with correction and deletion, and clarity about what is used for training. Seventh, auditability sufficient to reconstruct what happened, retained long enough to investigate and access-controlled because the traces themselves contain personal data. Eighth, monitoring after launch, since the model underneath changes, the input distribution drifts, and a responsibility assessment made at release expires quietly. And finally the obligation people skip: being willing to narrow the scope or not ship at all where the consequence of a wrong action cannot be adequately bounded. Some tasks should stay advisory, with the agent drafting and a person deciding — and choosing that deliberately is part of the job.
